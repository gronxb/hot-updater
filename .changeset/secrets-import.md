`hot-updater secrets import [file]` moves an env file's variables, `.env.hotupdater` by default, into the Console's vault as one `deploy-credentials` secret (`deploy-credentials` unless `--name` names another), then removes them from the file. Only `HOT_UPDATER_CONSOLE_URL` and `HOT_UPDATER_VAULT_TOKEN` stay, with init's `HOT_UPDATER_INIT_BUILD` and `HOT_UPDATER_INIT_PROVIDER`, the client `HOT_UPDATER_API_KEY` that ships in the app, and a `HOT_UPDATER_VAULT_MASTER_KEY`, which never goes into the vault. It asks first (`-y` skips), warns when the new version drops variables the secret set, refuses a variable another secret sets, and writes over only the version it listed: the Console's `PUT /_hot-updater/vault/v1/secrets/:name` takes an optional `expectedVersion` (`0` for no secret) and answers 409 when the secret changed since, which `createVaultClient().put` passes through. While the two connection variables are set, in the environment or `.env.hotupdater`, each command that uses the config's database, storage, or signing (`deploy`, `build:*` with `--register`, `console`, `doctor`, `keys export-public`, `patch`, `promote`, the release and storage commands, `db migrate` and `db generate`, and the in-process `api-key`, `insights`, `remote-config`, and `secrets token` commands, over the config or a server definition passed as their last argument) first sets the variables of the `deploy-credentials` secrets the vault token reaches in `process.env`, a variable set locally winning, so configs that read `process.env` deploy with only those two variables. `hot-updater console` sets them for the console server it starts, except when `HOT_UPDATER_CONSOLE_URL` is that local console, which cannot serve the credentials it starts with. `loadConfig(options, { credentials: true })` and `loadPlatformConfigs(platforms, { channel, credentials: true })` ask for it; any other load reaches no network, so `fingerprint create`, `build:*` without `--register`, `channel set`, and the Expo config plugin work offline. The adapters a config creates check their credentials and create their clients on first use, so a config loads without them: `supabaseStorage`, `supabaseDatabase`, `azureBlobStorage`, `cosmosDatabase`, `vercelBlobStorage`, `firebaseStorage`, `standaloneRepository`, `awsKmsSigning`, `googleCloudKmsSigning`, and `remoteSigning`. A server runtime missing a credential now reports it at its first request instead of at startup. `secrets list`, `put`, and `env` also read the connection from `.env.hotupdater`. The import and these reads parse the file as `process.loadEnvFile` does (`parseLoadedEnv`, `readLoadedHotUpdaterEnv`). `makeEnv` takes `expectedContent` and rewrites only a file that still holds it, which the import uses so a value changed during the vault write stays in the file. In `@hot-updater/cli-tools`, `resolveVaultVariables`, `vaultSecretVariables`, and `loadVaultDeployCredentials` are exported, and `readHotUpdaterEnv` is removed: read `.env.hotupdater` with `readLoadedHotUpdaterEnv(cwd)`, as the config loads it, or `readHotUpdaterInitEnv(cwd).managedEnv`, as init reads it.
