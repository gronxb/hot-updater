# 1.0.0

Release Catalog, manifest artifact protocol v1, and Release Insights infrastructure
generation, including indexed metadata reads. All pre-GA changes are part of the
1.0.0 baseline.

## Compatibility

Generation 0 cannot be upgraded in place. Create a separate generation 1
namespace and endpoint and ship the new endpoint in a new native build.
Preserve the old infrastructure for installed apps. Supabase and Firebase
projects can be reused with the separate namespaces described below.

For an existing generation 1 installation, preserve resource IDs, client API
keys, signing keys and endpoints. An unknown generation or partially incompatible
schema requires investigation before adopting or changing resources.

Version 1.0.0 is not yet generally available. Its initial schemas and first
migrations directly require Bundle manifest metadata and remove archive-specific
Bundle columns. Prerelease schemas and unversioned artifact clients are not a
compatibility target. Inspect and reconcile an existing prerelease namespace
against the current scaffold; do not assume that an already-recorded first
migration has the final shape. Preserve existing resources, secrets and usable
data while applying the explicitly reviewed schema differences.

The SDK uses only `/artifacts/v1/:targetBundleId/from/:currentBundleId`. Each
response requires the target manifest and an original descriptor for every
target file. Optional `bundle.tar.br` integrity and size metadata live in the
signed manifest; no archive database columns or separate archive migration are
needed. Deploy matching server and native SDK builds. Remove `compressStrategy`
from app configuration. Rebuild native apps; no embedded-manifest build hook is
required and old manifestless OTA folders are not launch candidates.

The 1.0 RC baseline includes metadata index projections on AWS and composite
indexes on Firebase. Deploy matching database plugins and servers together. Older
Standalone servers lack `/bundles/:id/patch-children` and must be updated before
using Console child counts. Custom repositories may implement
`bundlePatches.findByBaseBundleIds`; absence fails explicitly instead of scanning
bundle history.

No request path scans metadata to backfill missing indexes or count projections.
Explicit full-list, aggregate and maintenance operations still read their requested
result set without an arbitrary history cap.

## Steps

1. For v0 to v1, record the old endpoint, resource IDs, configuration and
   credential locations, and back up metadata. Keep v0 endpoints and databases
   serving installed v0 binaries throughout adoption.
2. Create a separate v1 database namespace and endpoint. Buckets may be shared
   when existing objects and access policies are preserved. Never prune shared
   storage based only on the empty v1 database. Bundle history and policy are
   not backfilled: redeploy desired Bundles from their source artifacts.
3. Inspect the live `/version` response and existing schema. Confirm
   `infrastructureGeneration` is `1` before applying an in-place update.
4. Compare the previous deployment manifest and customized files with the target
   scaffold. Apply pending compatible migrations before code that depends on
   them, preserving existing data and migration history. The final pre-GA 1.0
   schema adds the `insights_overview` aggregate store and extends latest-event
   heads with release and app-version attribution. Existing 1.0 prerelease
   deployments must apply those schema additions before deploying the matching
   runtime; raw event history is not backfilled into aggregates. Metadata indexes
   and removal of the unused fingerprint-only index also belong to the 1.0.0
   baseline. For an already initialized RC installation, inspect and reconcile
   its actual schema; do not replay initialization over existing tables.
5. The runtime authenticates Release Catalog and versioned artifact requests with `x-api-key`. Preserve
   client API-key records and configure that header in the app. Provider admin
   credentials stay on the server or deployment machine.
6. Upgrade `hot-updater` and `@hot-updater/*` packages together. Do not deliver
   v1 React Native SDK JavaScript to a v0 native binary through OTA. Refresh Expo
   native projects with `expo prebuild` or bare iOS dependencies with `pod install`,
   then ship a new native build with the v1 SDK and endpoint.
7. Update automation that parsed v0 `bundle list/show` JSON: v1 returns raw
   internal rows. Roll back a v1 mobile release with another native build or a
   compatible v1 deployment. Never point v1 binaries at v0 infrastructure.
   Retire v0 only after an explicit adoption decision.

## Cloudflare

When migrating from generation 0, use a separate D1 database and Worker for
generation 1. Query the existing Worker, bindings, D1 migration history, R2 privacy
setting, secret names and `/version` before adopting resources. A missing version
response needs investigation.

For generation 1, compare the new Worker and Wrangler configuration with the
deployment. Preserve Worker name/URL, D1 and R2 identities, client API keys,
`STORAGE_DOWNLOAD_URL_SIGNING_KEY`, routes, custom domains and unrelated settings.
Keep `DB` and `BUCKET` bindings, `BUCKET_NAME`, cache settings and compatibility
date aligned with the supplied runtime. Apply only pending compatible D1
migrations, then deploy and verify. If code deployment fails after migration,
retain migration history and retry deployment. Do not rotate secrets on retry.
Confirm the D1 schema includes `insights_overview`, its release/scope/distribution
time indexes, the event processing marker, and the enriched head columns.

The 1.0.0 initialization SQL omits `releases_fingerprint_hash_idx`; fingerprint
Release lookup uses the scope index. If an older RC created the unused index,
remove it once with `DROP INDEX IF EXISTS releases_fingerprint_hash_idx;`. Keep
the scope and patch base/owner indexes. This index cleanup needs no table or
schema-version migration. Redeploy the Worker for the reverse patch endpoint.

## Supabase

A v0 project can be reused: v1 uses separate `hot_updater_v1_*` tables and the
`hot-updater-v1` function. Preserve v0 tables/functions. Inspect the v1 namespace
for partial or incompatible schema before applying migrations.

Inspect the live function, project reference, migration history, bucket privacy
and `/version`. Keep the project, function name/URL, bucket, API keys, unrelated
schema and customizations. Apply compatible pending SQL migrations first and
preserve their names/history through the chosen migration tool.
Confirm the v1 schema includes `hot_updater_v1_insights_overview`, its required
time indexes, and the enriched event-head columns before deploying the function.

Deploy the complete prepared Edge Function, Deno configuration and vendored
imports. Keep `verify_jwt=false`; the runtime authenticates `x-api-key`. If
deployment fails, verify migration results and retry the function deployment
without recreating the project or replaying completed migrations. Verify
`/ping`, `/version` and authenticated requests after readiness. Origin-only
Release Catalog checks still invoke the Edge Function.

The 1.0.0 initialization SQL omits the unused fingerprint-only index. On an
older RC installation, execute `DROP INDEX IF EXISTS
public.hot_updater_v1_releases_fingerprint_hash_idx;` once. Keep the scope and
patch indexes. No table or schema-version migration is needed for this cleanup.

The same initialization SQL includes the final commit RPC: deleting a missing
Channel is an atomic no-op even when other changes precede it. For an older RC,
apply that RPC definition with `CREATE OR REPLACE FUNCTION` and its accompanying
`REVOKE`/`GRANT` statements. Do not replay the initialization SQL or add another
versioned migration; preserve tables, data, permissions and recorded history.

## AWS

When migrating from generation 0, use separate DynamoDB, Lambda@Edge and CloudFront
resources for generation 1. Do not reuse a v0 Lambda name or distribution ID.
S3 can be shared with existing
policies preserved. Isolate v1 IAM roles and signing keys; the SSM path is
`/hot-updater/v1/<lambda-name>/keypair`. Keep the v0 Lambda/distribution available
for old binaries, and never use a v0 endpoint as rollback for v1 binaries.

For generation 1, confirm account/region, table/index schema, point-in-time
recovery, IAM permissions, distribution configuration/ETag, qualified Lambda ARN,
SSM parameter and public-key/group identities against the deployment record and
live endpoint. No SQL migration is required. Preserve S3,
DynamoDB data and API keys, SSM signing pair, trusted key group and endpoint.
No new table or secondary index is required for Release Insights; the runtime
stores bounded overview items under reserved keys in the existing v1 table.
Refresh the Lambda DynamoDB policy from the current scaffold, including
`_hot-updater#insights-overview#*` in its `dynamodb:LeadingKeys` condition.
Allowing `BatchGetItem` without this key range still rejects Insights reports.

Compare Lambda code/dependencies, IAM requirements and CloudFront specifications.
Publish a numbered Lambda version in `us-east-1`, wait for Active, then update
only the managed distribution behaviors using its current ETag. Apply the
API-key-aware cache/origin policies and Release Catalog behavior, preserving
custom domains and unrelated origins/behaviors. Wait for global propagation and
record the exact verified version. If the distribution update fails, inspect
and reuse the published Lambda version instead of recreating resources or keys.

No table or GSI replacement is required. Keep the existing patch-owner GSI.
The runtime maintains primary-table projections for bundle platform, patch base,
and release bundle/channel/platform/enabled/app-version filters in the same
transaction as canonical metadata. Projection writes count toward DynamoDB's
100-action transaction limit; split independent bulk operations if necessary.

For an existing 1.0 RC table without metadata projections, stop all metadata
writers, including older CLI and server processes. Run the following once from
the app with its established private AWS credentials and the target
`@hot-updater/aws` package installed:

```js
import { DynamoDBClient } from "@aws-sdk/client-dynamodb";
import { DynamoDBDocumentClient } from "@aws-sdk/lib-dynamodb";
import { migrateDynamoDBMetadataIndexes } from "@hot-updater/aws/iac";

const client = DynamoDBDocumentClient.from(new DynamoDBClient({}));
await migrateDynamoDBMetadataIndexes({
  client,
  tableName: process.env.HOT_UPDATER_DYNAMODB_TABLE_NAME,
});
```

Use the already configured table name and region; do not copy credentials into
source or chat. This explicit maintenance job visits every canonical metadata
page, writes projections, repairs bundle/patch totals, then writes the
`_hot-updater / metadata-indexes` version-1 marker. It does not visit Insights
history or S3 objects. If it fails, keep writers stopped and retry; the marker
is never written before completion. A new empty table initializes automatically.
Never manually mark an existing populated table as upgraded. Resume writes only
with the target plugin/server; older writers do not maintain these projections.

## Firebase

Use Firebase CLI 15.29.0 or newer with the generated Functions 7 runtime and
Admin SDK 14. Older emulators call the removed `functions.config()` API.

A v0 project can be reused: v1 uses separate `hot_updater_v1_*` Firestore
collections and the `hot-updater-v1` function. Leave v0 collections and the
`hot-updater` function intact. Inspect the project, function region/URL, runtime
identity, default Storage bucket, Firestore namespace/indexes and `/version`.

For generation 1, compare Functions runtime/dependencies and merge required
Firestore indexes with unrelated existing indexes. Wait for index readiness.
Preserve data, client API keys, storage, runtime identity, endpoint and CDN settings.
Confirm the `hot_updater_v1_insights_overview` collection query indexes and
summary-field index exemptions are deployed before the function starts writing
Release Insights aggregates.

Deploy `hot-updater-v1` in its existing region and verify the endpoint. A failed
deploy should be retried after checking status, using the same project and
completed indexes. Use the direct Function URL. Do not replace Firebase Hosting
configuration or the default Hosting site during the upgrade. Verify the actual
runtime identity has iam.serviceAccounts.signBlob on the runtime service account
itself (roles/iam.serviceAccountTokenCreator supplies it) and the IAM Service
Account Credentials API is enabled. Preserve existing grants and verify artifact
access when available.

Merge the scaffold's `firestore.indexes.json` with the deployed configuration,
preserving unrelated indexes. Deploy with `firebase deploy --only
firestore:indexes` and wait until all indexes are ready before deploying the
Function. The template includes platform/id bundle indexes, owner/base patch
indexes, both cursor directions for supported Release filter combinations,
scope/id reads and API-key list ordering. No document backfill or adapter-marker
change is required. Unsupported predicates fail instead of loading a collection.

## Standalone databases

Regenerate or migrate the standalone SQL, SQLite, and MongoDB schema before
deploying the matching server. SQL providers require `insights_overview`, its
release/scope/distribution time indexes, and enriched event-head columns.
MongoDB requires the corresponding overview collection indexes and transactions
on a replica set or sharded cluster. Existing raw events are preserved but are
not reconstructed into historical aggregates.

Standalone clients require the updated server for reverse patch lookup. Prisma
and MongoDB keep sorting and pagination in the backend, and MongoDB uses native
predicates for indexed finite-ID queries.

For existing native PostgreSQL and ORM installations, remove only the retired
`releases_fingerprint_hash_idx`: fingerprint Release lookup now uses `scope_key`.
Generated Prisma/Drizzle schemas and fresh schemas omit it. Apply the generated
ORM index migration, or use the appropriate statement below through the existing
database connection. The schema marker remains `1.0.0`; `db migrate` treats an
existing v1 schema as current, so it does not perform this optional index cleanup.

```sql
-- PostgreSQL / SQLite
DROP INDEX IF EXISTS releases_fingerprint_hash_idx;
-- MySQL
DROP INDEX releases_fingerprint_hash_idx ON releases;
-- CockroachDB
DROP INDEX IF EXISTS releases@releases_fingerprint_hash_idx;
```

For MongoDB, check `db.releases.getIndexes()` and drop the named index with
`db.releases.dropIndex("releases_fingerprint_hash_idx")` if present. Retain the
scope, patch owner/base, installation history, latest-event and overview indexes;
they still serve runtime queries. Retain the Firestore Release filter/cursor
composites as well: range pagination must not depend on equality-index merging.

## Verification

- Check `/version` for infrastructure generation 1 and the target server
  version. Run `hot-updater doctor --json --server-base-url <base-url>` from
  the app directory.
- Verify an authenticated client request and a known stored artifact when
  available. Record the actual deployed version only after verification, with
  the release file and applied migrations. Report native rebuild and OTA
  runtime validation separately.
- Verify missing and invalid API keys cannot resolve versioned artifacts. With a
  valid key, verify `artifactProtocolVersion: 1`, the complete original descriptor
  set, and target manifest. Exercise builtin reuse, OTA-to-OTA patch recovery,
  automatic tar.br selection and original-file fallback in a matching native app.
- Send one Insights report and verify the event append, latest-event head, and
  all affected overview summaries commit together. Retry the same event ID and
  verify counters do not change.
- For v0 to v1, verify the old endpoint still serves old binaries and the new
  native build uses v1. Test catalog fetch, artifact resolution, install,
  restart and rollback. The native SDK's local metadata migration does not
  migrate the old server database.
- Fetch a missing bundle, catalog and API-key hash; check that unrelated metadata
  collections/partitions are not read.
- List a filtered bundle page and a Release page in both cursor directions.
  On AWS, inspect key conditions to confirm the appropriate metadata projection.
- Hydrate a page with more than 30 patch owners on Firebase; verify no owners are
  lost and that the SDK's disjunction limit does not trigger a history scan.
- Replace patches, check child counts, then delete their base and verify cascades.
- Update an existing Release and verify its catalog and filtered list agree.
- Verify Insights aggregates and event pagination independently. Overview queries
  do not reconstruct metrics from raw event history or impose a 50,000-event cap.
