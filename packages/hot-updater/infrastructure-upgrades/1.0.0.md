# 1.0.0

Release Catalog infrastructure generation.

## Compatibility

Generation 0 cannot be upgraded in place. Create a separate generation 1
namespace and endpoint and ship the new endpoint in a new native build.
Preserve the old infrastructure for installed apps. Supabase and Firebase
projects can be reused with the separate namespaces described below.

For an existing generation 1 installation, preserve resource IDs, client API
keys, signing keys and endpoints. An unknown generation or partially incompatible
schema requires investigation before adopting or changing resources.

## Steps

1. For v0 to v1, record the old endpoint, resource IDs, configuration and
   credential locations, and back up metadata. Keep v0 endpoints and databases
   serving installed v0 binaries throughout adoption.
2. Create a separate v1 database namespace and endpoint. Buckets may be shared
   when existing objects and access policies are preserved. Never prune shared
   storage based only on the empty v1 database. Bundle history and policy are
   not backfilled: redeploy desired Bundles from their source artifacts.
3. Inspect the live `/version` response and existing schema. Confirm
   `infrastructureGeneration` is `1` before applying an in-place update.
4. Compare the previous deployment manifest and customized files with the target
   scaffold. Apply pending compatible migrations before code that depends on
   them, preserving existing data and migration history.
5. The runtime authenticates Release Catalog requests with `x-api-key`. Preserve
   client API-key records and configure that header in the app. Provider admin
   credentials stay on the server or deployment machine.
6. Upgrade `hot-updater` and `@hot-updater/*` packages together. Do not deliver
   v1 React Native SDK JavaScript to a v0 native binary through OTA. Refresh Expo
   native projects with `expo prebuild` or bare iOS dependencies with `pod install`,
   then ship a new native build with the v1 SDK and endpoint.
7. Update automation that parsed v0 `bundle list/show` JSON: v1 returns raw
   internal rows. Roll back a v1 mobile release with another native build or a
   compatible v1 deployment. Never point v1 binaries at v0 infrastructure.
   Retire v0 only after an explicit adoption decision.

## Cloudflare

When migrating from generation 0, use a separate D1 database and Worker for
generation 1. Query the existing Worker, bindings, D1 migration history, R2 privacy
setting, secret names and `/version` before adopting resources. A missing version
response needs investigation.

For generation 1, compare the new Worker and Wrangler configuration with the
deployment. Preserve Worker name/URL, D1 and R2 identities, client API keys,
`STORAGE_DOWNLOAD_URL_SIGNING_KEY`, routes, custom domains and unrelated settings.
Keep `DB` and `BUCKET` bindings, `BUCKET_NAME`, cache settings and compatibility
date aligned with the supplied runtime. Apply only pending compatible D1
migrations, then deploy and verify. If code deployment fails after migration,
retain migration history and retry deployment. Do not rotate secrets on retry.

## Supabase

A v0 project can be reused: v1 uses separate `hot_updater_v1_*` tables and the
`hot-updater-v1` function. Preserve v0 tables/functions. Inspect the v1 namespace
for partial or incompatible schema before applying migrations.

Inspect the live function, project reference, migration history, bucket privacy
and `/version`. Keep the project, function name/URL, bucket, API keys, unrelated
schema and customizations. Apply compatible pending SQL migrations first and
preserve their names/history through the chosen migration tool.

Deploy the complete prepared Edge Function, Deno configuration and vendored
imports. Keep `verify_jwt=false`; the runtime authenticates `x-api-key`. If
deployment fails, verify migration results and retry the function deployment
without recreating the project or replaying completed migrations. Verify
`/ping`, `/version` and authenticated requests after readiness. Origin-only
Release Catalog checks still invoke the Edge Function.

## AWS

When migrating from generation 0, use separate DynamoDB, Lambda@Edge and CloudFront
resources for generation 1. Do not reuse a v0 Lambda name or distribution ID.
S3 can be shared with existing
policies preserved. Isolate v1 IAM roles and signing keys; the SSM path is
`/hot-updater/v1/<lambda-name>/keypair`. Keep the v0 Lambda/distribution available
for old binaries, and never use a v0 endpoint as rollback for v1 binaries.

For generation 1, confirm account/region, table/index schema, point-in-time
recovery, IAM permissions, distribution configuration/ETag, qualified Lambda ARN,
SSM parameter and public-key/group identities against the deployment record and
live endpoint. No SQL migration is required. Preserve S3,
DynamoDB data and API keys, SSM signing pair, trusted key group and endpoint.

Compare Lambda code/dependencies, IAM requirements and CloudFront specifications.
Publish a numbered Lambda version in `us-east-1`, wait for Active, then update
only the managed distribution behaviors using its current ETag. Apply the
API-key-aware cache/origin policies and Release Catalog behavior, preserving
custom domains and unrelated origins/behaviors. Wait for global propagation and
record the exact verified version. If the distribution update fails, inspect
and reuse the published Lambda version instead of recreating resources or keys.

## Firebase

Use Firebase CLI 15.29.0 or newer with the generated Functions 7 runtime and
Admin SDK 14. Older emulators call the removed `functions.config()` API.

A v0 project can be reused: v1 uses separate `hot_updater_v1_*` Firestore
collections and the `hot-updater-v1` function. Leave v0 collections and the
`hot-updater` function intact. Inspect the project, function region/URL, runtime
identity, default Storage bucket, Firestore namespace/indexes and `/version`.

For generation 1, compare Functions runtime/dependencies and merge required
Firestore indexes with unrelated existing indexes. Wait for index readiness.
Preserve data, client API keys, storage, runtime identity, endpoint and CDN settings.

Deploy `hot-updater-v1` in its existing region and verify the endpoint. A failed
deploy should be retried after checking status, using the same project and
completed indexes. Use the direct Function URL. Do not replace Firebase Hosting
configuration or the default Hosting site during the upgrade. Verify the actual
runtime identity has iam.serviceAccounts.signBlob on the runtime service account
itself (roles/iam.serviceAccountTokenCreator supplies it) and the IAM Service
Account Credentials API is enabled. Preserve existing grants and verify artifact
access when available.

## Verification

- Check `/version` for infrastructure generation 1 and the target server
  version. Run `hot-updater doctor --json --server-base-url <base-url>` from
  the app directory.
- Verify an authenticated client request and a known stored artifact when
  available. Record the actual deployed version only after verification, with
  the release file and applied migrations. Report native rebuild and OTA
  runtime validation separately.
- For v0 to v1, verify the old endpoint still serves old binaries and the new
  native build uses v1. Test catalog fetch, artifact resolution, install,
  restart and rollback. The native SDK's local metadata migration does not
  migrate the old server database.
