# 1.0.0

Release Catalog, manifest artifact protocol v1, and storage engine infrastructure generation.

## Compatibility

This release uses infrastructure generation `1` and storage engine schema `1`.
Verify the live `/version` response, database schema and migration history before
adopting an existing installation. Preserve resource IDs, client API keys,
signing keys, endpoints and data. Stop on an unsupported or unknown generation,
engine version or schema; do not overwrite settings or recreate resources to
make a compatibility check pass.

The database must contain `schema.engine` = `1` before the server can read it.
Apply the supplied initialization schema to a new empty namespace. A populated
namespace without the expected settings needs investigation before any writes.
For generation 0, follow the
[upgrade guide](https://hot-updater.dev/docs/guides/upgrade-to-v1).

The SDK uses only `/artifacts/v1/:targetBundleId/from/:currentBundleId`. Each
response requires the target manifest and an original descriptor for every
target file. Optional `bundle.tar.br` integrity and size metadata live in the
signed manifest; no archive database columns or separate archive migration are
needed. Deploy matching server and native SDK builds. Native apps require the
matching SDK integration; no embedded-manifest build hook is required.

## From a release candidate

Recreate the database of a 1.0.0 release candidate deployment, and update the
server, app, and console together.

## Steps

1. Record the selected endpoint, resource IDs, configuration, credential
   locations and migration history. Back up existing metadata before changes.
2. Inspect the live `/version` response and existing schema. Confirm
   `infrastructureGeneration` is `1` and `schema.engine` is `1` before changing
   an existing installation.
3. Compare the previous deployment manifest and customized files with the target
   scaffold. Apply pending compatible migrations before code that depends on
   them, preserving existing data and migration history. If a recorded migration
   disagrees with the actual schema, stop and investigate rather than replaying
   it or clearing history.
4. The managed runtimes run `apiKeys()`, which authenticates Release Catalog and
   versioned artifact requests with `x-api-key`. Preserve client API-key records
   and configure that header in the app. Provider admin credentials stay on the
   server or deployment machine.
5. Keep `hot-updater` and `@hot-updater/*` packages on matching releases. When
   native dependencies change, refresh Expo native projects with `expo prebuild`
   or bare iOS dependencies with `pod install`, then ship a new native build.

## Cloudflare

Query the existing Worker, bindings, D1 migration history, R2 privacy setting,
secret names and `/version` before adopting resources. A missing version
response or incompatible schema needs investigation before changes.

For generation 1, compare the new Worker and Wrangler configuration with the
deployment. Preserve Worker name/URL, D1 and R2 identities, client API keys,
`STORAGE_DOWNLOAD_URL_SIGNING_KEY`, routes, custom domains and unrelated settings.
Keep `DB` and `BUCKET` bindings, `BUCKET_NAME`, cache settings and compatibility
date aligned with the supplied runtime. Apply only pending compatible D1
migrations, then deploy and verify. If code deployment fails after migration,
retain migration history and retry deployment. Do not rotate secrets on retry.
Before deploying the Worker, confirm that `private_hot_updater_settings` has
`schema.engine` = `1`; the Worker answers 503 until it does.

## Supabase

The runtime uses `hot_updater_v1_*` tables and the `hot-updater-v1` function.
Inspect that namespace for partial or incompatible schema before applying
migrations. Preserve unrelated tables and functions.

Inspect the live function, project reference, migration history, bucket privacy
and `/version`. Keep the project, function name/URL, bucket, API keys, unrelated
schema and customizations. The packaged scaffold and its doctor checks require
the `hot-updater-v1` function name. If an existing deployment uses another name,
report this verification limitation before proceeding; do not rename it or
replace its endpoint. Apply compatible pending SQL migrations first and preserve
their names/history through the chosen migration tool. A populated namespace
without `schema.engine` = `1`, or a mismatch between recorded migrations and the
actual schema, must be investigated before applying SQL.
Before deploying the function, confirm that the migration finished: its last
statements write `schema.engine` = `1` to
`hot_updater_v1_private_hot_updater_settings`, and the service-role-only
`hot_updater_v1_apply` RPC exists.

Deploy the complete prepared Edge Function, Deno configuration and vendored
imports. Keep `verify_jwt=false`; the runtime authenticates client requests. If
deployment fails, verify migration results and retry the function deployment
without recreating the project or replaying completed migrations. Verify
`/ping`, `/version` and authenticated requests after readiness. Origin-only
Release Catalog checks still invoke the Edge Function.

## AWS

Use installation-specific IAM roles and signing keys; the SSM path is
`/hot-updater/v1/<lambda-name>/keypair`. Preserve existing S3 objects and policies.

For generation 1, confirm account/region, table schema, point-in-time
recovery, IAM permissions, distribution configuration/ETag, qualified Lambda ARN,
SSM parameter and public-key/group identities against the deployment record and
live endpoint. Preserve S3, the SSM signing pair, trusted key group and endpoint.

The storage engine keeps one DynamoDB table keyed by string `pk` and `sk`,
with no secondary index. Check the table and its settings before writing; a
populated table must have `schema.engine` = `1`. Stop on an incompatible table
or engine value. For a new empty table, write its schema settings with
`migrateDynamoDB` or the scaffold's `dynamodb/schema-settings.json`; no SQL schema
migration is needed. The plugin answers 503 until the settings exist.
Refresh the Lambda DynamoDB policy from the current scaffold: its
`dynamodb:LeadingKeys` condition lists each table name and `<table>#*`,
including the batched Insights log partitions `aggregate_log_0` to
`aggregate_log_7` and `aggregate_lease`, and it allows
`dynamodb:BatchWriteItem`. For a managed setup, rerun `hot-updater init`, since
the IAM policy changed, and recreate release candidate data if needed.

Turn on the table's TTL on `_ttl` (init does, or
`aws dynamodb update-time-to-live --cli-input-json file://dynamodb/enable-ttl.json`):
the plugin stamps `_ttl` on every item of a row with retention, index copies
included, and DynamoDB deletes expired items without write cost. A table
with TTL on another attribute must drop it first.

Compare Lambda code/dependencies, IAM requirements and CloudFront specifications.
Publish a numbered Lambda version in `us-east-1`, wait for Active, then update
only the managed distribution behaviors using its current ETag. Apply the
cache/origin policies, whose cache keys hold the client-route headers, and the
Release Catalog behavior, preserving
custom domains and unrelated origins/behaviors. Wait for global propagation and
record the exact verified version. If the distribution update fails, inspect
and reuse the published Lambda version instead of recreating resources or keys.

## Firebase

Use Firebase CLI 15.29.0 or newer with the generated Functions 7 runtime and
Admin SDK 14. Older emulators call the removed `functions.config()` API.

The runtime keeps every item in the `hot_updater_v1` Firestore collection and
serves from the `hot-updater-v1` function. Preserve unrelated collections and
functions. Inspect the project, function region/URL, runtime identity, default
Storage bucket, Firestore indexes and `/version`. Nonempty `hot_updater_v1_*`
collections are an unsupported layout; preserve them and investigate before
adopting the project.

For generation 1, compare Functions runtime/dependencies and merge the
`(pk, sk)` composite indexes, in both directions, the `row` index exemption,
and the TTL policy on `expireAt` into the existing indexes; keep unrelated
indexes. Wait for index readiness. The TTL policy deletes each document of a
row past its table's retention, which the plugin stamps with `expireAt`.
Preserve storage, runtime identity, endpoint and CDN settings. Before running
`migrateFirebaseDatabase` or the scaffold's key script, read `schema.engine`
from the settings document in `hot_updater_v1` (`pk = private_hot_updater_settings`,
`row.key = schema.engine`). Its `row.value` must be the string `"1"` when present;
a missing marker is acceptable only for an empty namespace. Stop on an unsupported
value or unknown layout. The helper does not enforce this check and can overwrite
an unsupported marker. For a new empty namespace, write the settings with
`migrateFirebaseDatabase` before serving traffic; no SQL schema migration is
needed. Init and the scaffold's key script run this migration. The function
answers 503 until the settings exist.

Deploy `hot-updater-v1` in its existing region and verify the endpoint. A failed
deploy should be retried after checking status, using the same project and
completed indexes. Use the direct Function URL. Do not replace Firebase Hosting
configuration or the default Hosting site during the upgrade. Verify the actual
runtime identity has iam.serviceAccounts.signBlob on the runtime service account
itself (roles/iam.serviceAccountTokenCreator supplies it) and the IAM Service
Account Credentials API is enabled. Preserve existing grants and verify artifact
access when available.

## Standalone databases

Prepare the standalone SQL, SQLite, or MongoDB schema before deploying the
matching server. The Kysely adapter, the `postgres` plugin's
`sql/bundles.sql`, and `hot-updater db generate --sql` share one generated SQL
schema that ends with the settings rows, so apply it to a new empty database.
`sql/bundles.sql` holds core's tables only; `db generate --sql` adds the
tables of the plugins it finds in the server config. For adapters that own
table creation, `hot-updater db migrate` creates core's tables and those of
the server's configured plugins, such as `insights()` and `apiKeys()`. Prisma and
Drizzle own their table definitions: run `hot-updater db generate`, apply the
generated schema with Prisma or Drizzle migrations (or the ORM's push command),
then run `hot-updater db migrate` for settings and adapter fixups. Repeat that
sequence when adding plugin tables; `db migrate` does not create ORM-owned
tables. MongoDB requires transactions on a replica set or sharded cluster.

No scheduler is needed for retention: expired rows are removed by native TTL
or during writes. `hot-updater db migrate` creates the index each table with
retention needs, a TTL index on MongoDB.

## Verification

- Check `/version` for infrastructure generation 1 and the target server
  version. Run `hot-updater doctor --json --server-base-url <base-url>` from
  the app directory.
- Verify an authenticated client request and a known stored artifact when
  available. Record the actual deployed version only after verification, with
  the release file and applied migrations. Report native rebuild and OTA
  runtime validation separately.
- When the server takes a client credential, verify missing and invalid ones
  cannot resolve versioned artifacts. With a valid one, verify
  `artifactProtocolVersion: 1`, the complete original descriptor
  set, and target manifest. Exercise builtin reuse, OTA-to-OTA patch recovery,
  automatic tar.br selection and original-file fallback in a matching native app.
- With `insights()`, which the managed servers run, send one Insights report
  and verify the event append and latest-event head commit together. On
  DynamoDB and Firestore, overview summaries apply in batches: read them
  through the Console or the admin API, which applies pending batches first,
  and verify they count the report. Elsewhere they commit with the event.
  Retry the same event ID and verify counters do not change.
- Verify DynamoDB `describe-time-to-live` is ENABLED on `_ttl`, and the
  Firestore TTL policy on `expireAt` is active.
- In a matching native release build, test catalog fetch, artifact resolution,
  installation, restart and rollback. Report this separately from server readiness.
