# 1.0.0-rc.30

Daily observed bundle share in Release health.

## Compatibility

Infrastructure generation 1 and storage engine schema 1 are unchanged.
Insights schema advances from 1.2.0 to 1.3.0, adding `bundle_daily_heads` and
`insights_distribution_history`. Existing reports and aggregates are preserved.
Apply the additive migration before serving the new runtime. Earlier runtimes
expect the old plugin schema, so coordinate the server/Console upgrade and pause
report ingestion during migration; do not run mixed schema versions.

History begins with new observations after the upgrade. Existing latest-state
rows cannot reconstruct past daily distributions and must not be backfilled.
A day's last observed running bundle counts each reporting installation once.
Shares describe observed installations, not rollout completion or the entire
installed fleet. No client or native change is required.

## Steps

1. Verify generation, plugin schema settings, resource identities, and migration
   history. Back up the database and pause ingestion for the coordinated upgrade.
2. Upgrade matching packages and generate/review the additive migration using
   the existing provider or server-project database tooling. Preserve all data.
3. Apply only the pending migration and verify both new models and the
   `schema.insights` value `1.3.0`. Use the provider's migrations, not a manual
   settings-only edit on a SQL database.
4. Deploy the matching runtime and Console, resume reporting, and verify the
   observations below. A failed deployment after migration should be retried
   with the new runtime; do not revert only the schema marker.

## Cloudflare

A D1 schema migration is required for the new daily heads and history aggregate.
Generate the compatible migration from the provider runtime's schema, review and
apply it to the existing D1 database, then deploy the Worker. Preserve bindings,
R2, secrets, routes, and migration history. Do not replay initialization SQL.

## Supabase

A Postgres schema migration is required for the new daily heads and history
aggregate. Apply the compatible provider migration, including its transaction
RPC/schema changes, to the existing namespace before deploying the Edge Function.
Preserve authentication, storage, data, and migration history.

## AWS

No physical DynamoDB schema migration or new table is required. Refresh the
Lambda IAM policy from the new scaffold: its LeadingKeys must include the new
logical table partitions and their shards. Run the provider's compatible schema
settings migration to advance Insights to 1.3.0, then deploy the runtime.
Preserve the DynamoDB table, TTL, S3, signing keys, and CloudFront settings.

## Firebase

No physical Firestore schema migration or new collection is required. Run the
provider's compatible schema settings migration to advance Insights to 1.3.0,
then deploy the runtime. The new logical models use the existing key layout,
indexes, and TTL policy. Preserve all resources and credentials.

## Verification

- Check `/version`, plugin readiness, and infrastructure doctor after deployment.
- Report bundle A, download B, then apply B from one installation on the same
  UTC day. Download alone leaves A running; apply moves the single observation
  to B. Retrying a report must not add another observation.
- Report recovery to A and verify that the day's observation returns to A.
  Report B the next day and verify that yesterday still shows A.
- Query authenticated `GET /distribution-history?platform=ios&channel=<channel>&start=<UTC-day-ms>&end=<UTC-day-ms>`
  over at most 31 whole UTC days. Built-in and unknown bundles must remain in
  the denominator; days without observations have no percentage.
- Verify Console's Bundle share and Launch failures tabs, app-version filter,
  reporting-installation counts, and the unfinished current-day indication.
