# 1.0.0-rc.29

HTTP response diagnostics for the Release Catalog and artifact APIs.

## Compatibility

Infrastructure generation 1 and the existing Insights schema are unchanged.
Read the 1.0.0 baseline as context. A compatible generation 1 installation needs
no database recreation or schema migration. Preserve all data, resource IDs,
client API keys, signing keys, and endpoints.

The new client sends HTTP_RESPONSE events for successful and failed API
responses. Earlier server runtimes reject this event type with HTTP 400; the
client skips those diagnostics without changing update behavior. Upgrade the
server and Console before distributing the new client JavaScript.

## Steps

1. Verify the existing generation, schema, resource bindings, and migration history.
2. Compare the new scaffold with the existing customized deployment. Deploy its
   server runtime with the same configuration and credentials.
3. Upgrade Console and the app's SDK/Insights dependencies. HTTP response
   diagnostics are JavaScript changes and require no new native integration.
4. Verify ingestion, raw history, and unchanged usage/failure aggregates.

## Cloudflare

No schema migration is required. Deploy the scaffold Worker to the existing
Worker, preserving DB/BUCKET bindings, cache settings, secrets, routes, and URLs.

## Supabase

No schema migration is required. Redeploy the existing hot-updater-v1 Edge
Function with the scaffold runtime and retain authentication configuration.

## AWS

No schema migration or new IAM permission is required. Update the existing
Lambda runtime and preserve its DynamoDB, S3, signing, and distribution settings.

## Firebase

No schema migration or new collection is required. Update the existing server
runtime while preserving Firestore, Storage, signing, authentication, and TTL settings.

## Verification

- Check the actual /version and run infrastructure doctor against the new manifest.
- Send successful (200), cached (304), and failed (503) HTTP_RESPONSE reports.
  Verify status and raw body in Console and installation history; a retry with
  the same eventId must not create another event.
- Verify HTTP_RESPONSE records do not alter the installation's latest state,
  app usage, release activity, or update failure counts.
- Verify truncated bodies are marked, empty bodies remain empty, and unavailable
  bodies are distinguished. Binary update file downloads and telemetry requests
  are not part of these API response diagnostics.
