# 1.2.0

Core schema 1.2.0: the native build registry table.

## Compatibility

This release keeps infrastructure generation `1` and storage engine schema `1`.
Core's schema moves to `1.2.0`: it adds the `native_builds` table, the native
build registry where `hot-updater native-build android` and `native-build ios`
track every build, each with the native build key of its inputs (`build_key`),
by which a build with the same inputs is reused instead of built again, and
the store track a build was submitted to (`submitted_to`, `submitted_at_ms`,
`submitted_version`), which the Console shows. The
table is new: no existing table, column or index changes, and no existing row
is rewritten.

A server of this release answers 503 until its database records
`schema.core` = `1.2.0`, and a server of an earlier release answers 503 once
it does: migrate the database and deploy the matching server together. The
client routes, Release Catalog format and artifact protocols do not change.
Installed apps keep working with the new server, and the server keeps
answering every SDK release it answered before.

## Steps

1. Record the selected endpoint, resource IDs, configuration and migration
   history, and back up the database, as for any upgrade.
2. Upgrade `hot-updater` and every `@hot-updater/*` package to this release.
3. Run `npx hot-updater doctor` where `hot-updater.config.ts` names the
   deployment's database. It reports `SCHEMA_MIGRATION_PENDING` for a
   database an earlier release migrated.
4. Run `npx hot-updater doctor --fix`, which applies the provider's migration
   below, then redeploy the managed server from this release's scaffold.
   Doctor reports no schema issue once both are done.

## Cloudflare

`plugins/cloudflare/worker/migrations/0002_hot-updater_1.2.0.sql` creates the
new table and writes the settings rows. `hot-updater doctor --fix` applies
it through `d1Database`'s API token and records it in `d1_migrations`, as
`wrangler d1 migrations apply` does; applying it with Wrangler instead is
equivalent. Then deploy the Worker from this release. Keep the bindings,
secrets, routes and R2 bucket. A native build's artifact is stored in the same
R2 bucket under `native-builds/`.

## Supabase

`supabase/migrations/0002_hot-updater_1.2.0.sql` creates the new
`hot_updater_v1_native_builds` table with their row-level security, grants the
service role access, and lets the `hot_updater_v1_apply` RPC write it. It
ends with the settings rows. `hot-updater doctor --fix` pushes it with
`supabase db push`, which needs the Supabase access token or CLI login and
the database password. Then deploy the `hot-updater-v1` function from this
release. The project's Storage upload file size limit, which the Free plan
keeps at 50 MB, also caps the native build artifacts the CLI can upload.

## AWS

DynamoDB needs no schema change: the table keeps its `pk` and `sk` keys.
`hot-updater doctor --fix` writes the settings rows. Refresh the Lambda
DynamoDB policy from the current scaffold, whose `dynamodb:LeadingKeys`
condition now also lists `native_builds` and `native_builds#*`, by rerunning
`hot-updater init` for a managed setup, then publish the Lambda from this
release as the 1.0.0 file describes.

## Firebase

Firestore needs no index change: the new table's items use the same `(pk,
sk)` indexes in the `hot_updater_v1` collection. `hot-updater doctor --fix`
writes the settings rows. Then deploy the `hot-updater-v1` function from this
release.

## Vercel

The PostgreSQL database gets the new table and the settings rows from
`hot-updater doctor --fix`, as `hot-updater db migrate` creates them. Then
redeploy the Vercel project from this release.

## Azure

Cosmos DB needs no container change: the new table's items share the
container's partition. `hot-updater doctor --fix` writes the settings rows.
Then deploy the Function App from this release.

## Standalone databases

A self-hosted server's database gets the new table from `hot-updater db
migrate` in the server's project. Prisma and Drizzle own their table
definitions: run `hot-updater db generate`, apply it with the ORM, then
`hot-updater db migrate`. Deploy the server from this release afterwards. A
CLI that reaches the server through `standaloneRepository` asks for that
upgrade when the server has no native build routes.

## Databases migrated before native build keys and submissions

A database that applied a prerelease `0002_hot-updater_1.2.0.sql`, or a
1.2.0 prerelease's `hot-updater db migrate`, can have `native_builds` without
the `build_key` column and its `byBuildKey` index, or without the
`submitted_to`, `submitted_at_ms` and `submitted_version` columns, and
already records `schema.core` = `1.2.0`. Migrations only create missing
tables and doctor reads the settings rows, so neither `hot-updater doctor
--fix` nor `db migrate` adds them: run the statements below that the table is
missing once, before the server of this release reads the table. Each column
is nullable: the builds registered before it keep `NULL`, are never reused,
and show no store submission.

D1, with `wrangler d1 execute <database> --remote --command "…"` or the
Cloudflare dashboard's console:

```sql
ALTER TABLE "native_builds" ADD COLUMN "build_key" TEXT;
CREATE INDEX IF NOT EXISTS "native_builds_byBuildKey" ON "native_builds" ("scope_key", "build_key", "id");
ALTER TABLE "native_builds" ADD COLUMN "submitted_to" TEXT;
ALTER TABLE "native_builds" ADD COLUMN "submitted_at_ms" INTEGER;
ALTER TABLE "native_builds" ADD COLUMN "submitted_version" TEXT;
```

Supabase, in the SQL editor:

```sql
ALTER TABLE "hot_updater_v1_native_builds" ADD COLUMN IF NOT EXISTS "build_key" varchar(69) COLLATE "C";
CREATE INDEX IF NOT EXISTS "hot_updater_v1_native_builds_byBuildKey" ON "hot_updater_v1_native_builds" ("scope_key", "build_key", "id");
ALTER TABLE "hot_updater_v1_native_builds" ADD COLUMN IF NOT EXISTS "submitted_to" varchar(16) COLLATE "C", ADD COLUMN IF NOT EXISTS "submitted_at_ms" bigint, ADD COLUMN IF NOT EXISTS "submitted_version" varchar(255) COLLATE "C";
```

PostgreSQL (Vercel, `@hot-updater/postgres`, and Kysely):

```sql
ALTER TABLE "native_builds" ADD COLUMN IF NOT EXISTS "build_key" varchar(69) COLLATE "C";
CREATE INDEX IF NOT EXISTS "native_builds_byBuildKey" ON "native_builds" ("scope_key", "build_key", "id");
ALTER TABLE "native_builds" ADD COLUMN IF NOT EXISTS "submitted_to" varchar(16) COLLATE "C", ADD COLUMN IF NOT EXISTS "submitted_at_ms" bigint, ADD COLUMN IF NOT EXISTS "submitted_version" varchar(255) COLLATE "C";
```

MySQL (Kysely):

```sql
ALTER TABLE `native_builds` ADD COLUMN `build_key` varchar(69) CHARACTER SET ascii COLLATE ascii_bin, ADD INDEX `native_builds_byBuildKey` (`scope_key`, `build_key`, `id`);
ALTER TABLE `native_builds` ADD COLUMN `submitted_to` varchar(16) CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_bin, ADD COLUMN `submitted_at_ms` bigint, ADD COLUMN `submitted_version` varchar(255) CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_bin;
```

SQLite (Kysely) takes the D1 statements. Prisma and Drizzle projects run
`hot-updater db generate` and apply the change with the ORM. MongoDB's `db
migrate` creates the index, and DynamoDB, Firestore and Cosmos DB need
nothing: their documents take the new field as they are written.

## Verification

- Run `npx hot-updater doctor` and confirm it reports no schema issue and
  each settings row at this release's version, `schema.core` = `1.2.0`
  among them.
- Check `/version` for infrastructure generation 1 and this release's server
  version, and verify an authenticated update check as before.
- Build a release app with `native-build`, which tracks it, then confirm the build is found for
  its platform, channel and fingerprint or app version, that its built-in
  bundle is listed among the bundles with no release, and that a rerun of
  `doctor --fix` keeps it.
- Run the same `native-build` again without changes: it reuses the tracked
  build (`Reusing native build <id> (key nbk1:…; storage)`) instead of
  building.
- Submit a build with `hot-updater testflight` or `hot-updater google-play
  upload`, then confirm the Console's Native builds tab shows it as on
  TestFlight or Play internal, with the store's version and build number.
