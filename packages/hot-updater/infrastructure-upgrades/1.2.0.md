# 1.2.0

Core schema 1.2.0: the native build registry table.

## Compatibility

This release keeps infrastructure generation `1` and storage engine schema `1`.
Core's schema moves to `1.2.0`: it adds the `native_builds` table, the native
build registry where `hot-updater native-build android` and `native-build ios`
track every build, each with the native build key of its inputs (`build_key`),
by which a build with the same inputs is reused instead of built again, and
the build number its artifact reports (`build_number`), and the store track a
build was submitted to (`submitted_to`, `submitted_at_ms`,
`submitted_version`), which the Console shows. The
table is new: no existing table, column or index changes, and no existing row
is rewritten.

A server of this release answers 503 until its database records
`schema.core` = `1.2.0`, and a server of an earlier release answers 503 once
it does: migrate the database and deploy the matching server together. The
client routes, Release Catalog format and artifact protocols do not change.
Installed apps keep working with the new server, and the server keeps
answering every SDK release it answered before. While a server answers 503,
an update check fails and apps keep running their current bundle.

## Order

The 503 window is the time between the migration and the server deploy, so
run them back to back, without a person in between:

- A deployment `hot-updater init` created runs
  `npx hot-updater init --provider <provider> --from-env-file .env.hotupdater`
  once. It applies the migration, then redeploys the server from this release,
  so the window is the deploy. `hot-updater doctor --fix` does not migrate
  such a database ahead of its server: it migrates it only when
  `--server-base-url` shows the server at `1.2.0` or later, the case of a
  server deployed another way first, as an agent upgrade does.
- A server of your own migrates as it deploys: run `hot-updater db migrate`
  in the server's project in the same deploy step. Given the server's
  `--server-base-url`, `doctor --fix` refuses to migrate while that server
  runs an earlier release.

## Steps

1. Record the selected endpoint, resource IDs, configuration and migration
   history, and back up the database, as for any upgrade.
2. Upgrade `hot-updater` and every `@hot-updater/*` package to this release.
3. Run `npx hot-updater doctor --server-base-url <url>` with the app's server
   URL, where `hot-updater.config.ts` names the deployment's database. It
   reports `SCHEMA_MIGRATION_PENDING` (`schema.core` is `"1.0.0"`, expected
   `"1.2.0"`) and `Infrastructure update required: 1.2.0+`, and each names
   the command below.
4. For a deployment `hot-updater init` created, whose `.env.hotupdater`
   records `HOT_UPDATER_INIT_PROVIDER`, run the command doctor names:

   ```sh
   npx hot-updater init --provider <provider> --from-env-file .env.hotupdater
   ```

   `--from-env-file` reports every input it lacks before it changes a
   resource, such as a credential init saved only with consent. Set those in
   the environment for the run, or run `npx hot-updater init` and answer its
   prompts. For a server of your own, deploy it from `@hot-updater/server`
   `1.2.0` and migrate its database as it deploys; see "Standalone
   databases".
5. Run `npx hot-updater doctor --server-base-url <url>` again. It reports no
   schema issue and `Infrastructure is up to date.`

## Cloudflare

Init applies `plugins/cloudflare/worker/migrations/0002_hot-updater_1.2.0.sql`
with `wrangler d1 migrations apply --remote`, which creates the new table,
writes the settings rows and records the file in `d1_migrations`, then
deploys the Worker from this release with `wrangler deploy`. It keeps the
bindings, secrets, routes and R2 bucket. With the Worker already at this
release, `hot-updater doctor --fix --server-base-url <url>` applies the same
file through `d1Database`'s API token instead. A native build's artifact is
stored in the same R2 bucket under `native-builds/`.

## Supabase

Init pushes `supabase/migrations/0002_hot-updater_1.2.0.sql` with `supabase
db push`, which needs the Supabase access token or CLI login and the database
password, then deploys the `hot-updater-v1` Edge Function from this release.
The migration creates the new `hot_updater_v1_native_builds` table with its
row-level security, grants the service role access, lets the
`hot_updater_v1_apply` RPC write it, and ends with the settings rows. With
the function already at this release, `hot-updater doctor --fix
--server-base-url <url>` pushes the same file. The project's Storage upload
file size limit, which the Free plan keeps at 50 MB, also caps the native
build artifacts the CLI can upload.

## AWS

DynamoDB needs no schema change: the table keeps its `pk` and `sk` keys. Init
writes the settings rows, puts the Lambda role's DynamoDB policy, whose
`dynamodb:LeadingKeys` condition now also lists `native_builds` and
`native_builds#*`, publishes the Lambda@Edge function from this release and
associates it with the CloudFront distribution. The function serves only the
client routes, which do not read the new table; the policy keeps the role in
step with the managed server's tables. CloudFront replaces the function at each edge location
over several minutes, so an edge location still running 1.1.x answers 503
until it is replaced.

## Firebase

Firestore needs no index change: the new table's items use the same `(pk,
sk)` indexes in the `hot_updater_v1` collection. Init writes the settings
rows, then deploys the `hot-updater-v1` function from this release.

## Vercel

Init creates the new table and writes the settings rows in the PostgreSQL
database, as `hot-updater db migrate` does, then redeploys the Function from
this release.

## Azure

Cosmos DB needs no container change: the new table's items share the
container's partition. Init writes the settings rows, then deploys the
Function App from this release.

## Standalone databases

A self-hosted server's database gets the new table from `hot-updater db
migrate` in the server's project, run as the server of this release deploys.
Prisma and Drizzle own their table definitions: run `hot-updater db
generate`, apply it with the ORM, then `hot-updater db migrate`. In the app
project, `hot-updater doctor --fix` runs the same migration for Kysely and
MongoDB, but not while `--server-base-url` shows the server at an earlier
release. A CLI that reaches the server through `standaloneRepository` asks
for that upgrade when the server has no native build routes.

## Verification

- Run `npx hot-updater doctor --server-base-url <url>` and confirm it
  reports no schema issue, the server at this release and `Infrastructure is
  up to date.`
- Verify an authenticated update check as before.
- Build a release app with `native-build`, which tracks it, then confirm the build is found for
  its platform, channel and fingerprint or app version, that its built-in
  bundle is listed among the bundles with no release, and that a rerun of
  `doctor --fix` keeps it.
- Run the same `native-build` again without changes: it reuses the tracked
  build (`Reusing native build <id> (key nbk1:…; storage)`) instead of
  building.
- Submit a build with `hot-updater testflight` or `hot-updater google-play
  upload`, then confirm the Console's Native builds tab shows it as on
  TestFlight or Play internal, with the store's version and build number,
  and that a second run reuses the build and skips the upload: `Already on
  TestFlight since … as …`.
