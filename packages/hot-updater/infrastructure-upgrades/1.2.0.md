# 1.2.0

Core schema 1.2.0: the native build registry and iOS device registry tables,
and on SQL databases an index on Insights events.

## Compatibility

This release keeps infrastructure generation `1` and storage engine schema `1`.
Core's schema moves to `1.2.0`: it adds the `native_builds` table, the native
build registry where `hot-updater native-build android` and `native-build ios`
track every build, each with the native build key of its inputs (`build_key`),
by which a build with the same inputs is reused instead of built again, and
the build number its artifact reports (`build_number`), and the store track a
build was submitted to (`submitted_to`, `submitted_at_ms`,
`submitted_version`), which the Console shows, and whether it is marked as what
the store sells (`is_store_build`, whose scope `store_build_scope_key` holds
for that build alone, with the unique index `byStoreBuild` that keeps one per
scope), which deploys patch from, whether it is a sandbox build
(`is_sandbox`), the URL scheme a sandbox build registers
(`sandbox_url_scheme`), how an `.ipa` was exported (`export_method`), and
the app version its artifact reports whatever the update strategy
(`native_app_version`). It also adds the `ios_devices` and `ios_device_account` tables, the iOS device
registry and the one Apple account it belongs to: the iPhones and iPads a team asks to install ad hoc builds on, which
the Console requests and approves and an ad hoc `native-build ios` registers
with Apple. The tables, their columns and their
indexes all come with this release's migration. On a SQL database, the
migration also adds the index `bundle_events__byBundle__key` to the existing
Insights table `bundle_events__byBundle`. From 1.1, no other table, column or
index changes, and no existing row is rewritten. On PostgreSQL (Supabase,
Vercel, or a server of your own), Insights writes to that table wait while the
index builds, so the more events it holds, the longer they wait during the
migration.

A server of this release answers 503 until its database records
`schema.core` = `1.2.0`, and a server of an earlier release answers 503 once
it does: migrate the database and deploy the matching server together. The
client routes, Release Catalog format and artifact protocols do not change.
Installed apps keep working with the new server, and the server keeps
answering every SDK release it answered before. While a server answers 503,
an update check fails and apps keep running their current bundle.

## Order

The 503 window is the time between the migration and the server deploy, so
run them back to back, without a person in between:

- A deployment `hot-updater init` created runs
  `npx hot-updater init --provider <provider> --from-env-file .env.hotupdater`
  once. It applies the migration, then redeploys the server from this release,
  so the window is the deploy.
- A deployment from `hot-updater agent infra` applies the scaffold's
  migration and deploys its server in the same order, in one step.
- A server of your own migrates as it deploys: run `hot-updater db migrate`
  in the server's project in the same deploy step.

An ad hoc `native-build ios` reads the iOS device registry before it builds,
so it fails on a database without the table, and through
`standaloneRepository` on a server without the `/ios-devices` admin routes.
Migrate and deploy the server before upgrading the CLI that builds.

Once the database is migrated, a CLI of 1.1 that opens it directly refuses to
run and names `hot-updater db migrate`. Instead, upgrade the CLI to this
release on every machine and CI job that runs it. Never run a 1.1 CLI's
`db migrate` on the migrated database: it writes 1.1's schema version back,
and every server of this release answers 503 until a `db migrate` of this
release runs again. From this release, `db migrate` and init refuse a
database a newer release migrated, and write nothing.

This release removes `hot-updater doctor --fix`. Doctor only reports, and
names the command for each issue: the init above for a managed deployment's
schema and server.

## Steps

1. Record the selected endpoint, resource IDs, configuration and migration
   history, and back up the database, as for any upgrade.
2. Upgrade `hot-updater` and every `@hot-updater/*` package to this release.
3. Run `npx hot-updater doctor --server-base-url <url>` with the app's server
   URL, where `hot-updater.config.ts` names the deployment's database. It
   reports `SCHEMA_MIGRATION_PENDING` (`schema.core` is `"1.0.0"`, expected
   `"1.2.0"`) and `Infrastructure update required: 1.2.0+`, and each names
   the command below.
4. For a deployment `hot-updater init` created, whose `.env.hotupdater`
   records `HOT_UPDATER_INIT_PROVIDER`, run the command doctor names:

   ```sh
   npx hot-updater init --provider <provider> --from-env-file .env.hotupdater
   ```

   `--from-env-file` reports every input it lacks before it changes a
   resource, such as a credential init saved only with consent. Set those in
   the environment for the run, or run `npx hot-updater init` and answer its
   prompts. For a server of your own, deploy it from `@hot-updater/server`
   `1.2.0` and migrate its database as it deploys; see "Standalone
   databases".

5. Run `npx hot-updater doctor --server-base-url <url>` again. It reports no
   schema issue and `Infrastructure is up to date.`

## Credentials with secret()

A config of 1.1 reads every value with `process.env` and keeps working as
it is. The init above rewrites a managed config: it names the resources it
resolved, and replaces each credential it reads, such as
`process.env.HOT_UPDATER_CLOUDFLARE_API_TOKEN!` or a `secretEnv` helper,
with `secret("<name>")` from `hot-updater`, which reads the environment and
`.env.hotupdater` first, then the config's `secrets` adapter. A config init
doesn't manage changes the same way by hand:

```ts
import { defineConfig, secret } from "hot-updater";

export default defineConfig({
  database: d1Database({
    databaseId: "<database-id>",
    accountId: "<account-id>",
    cloudflareApiToken: secret("HOT_UPDATER_CLOUDFLARE_API_TOKEN"),
  }),
  // build, storage and plugins stay as they are
});
```

`signing.privateKey`, `signing.keystore`, and `signing.ascApiKey` take
`secret("<name>")` too. Bundle signing's
`{ enabled: true, privateKeyPath }` keeps working as it is.

## Credentials in a team store

To share the credentials with a team:

1. Set `secrets` in `hot-updater.config.ts` to a team store, such as
   `infisical()` from `hot-updater`, `secretsManager()` from
   `@hot-updater/aws`, or `keyVault()` from `@hot-updater/azure`.
2. Run `npx hot-updater secrets import`. It stores the credentials, and
   `HOT_UPDATER_API_KEY`, from `.env.hotupdater` and reads them back.
3. Delete their lines from `.env.hotupdater`, or keep them to override the
   store on your machine. `npx hot-updater doctor` lists where each comes
   from.

A config that still reads a credential with `process.env` while `secrets` is
a team store is named by doctor: run the init above to rewrite it.

## Signing adapters

`awsKmsSigning`, `googleCloudKmsSigning`, and `remoteSigning` from
`hot-updater/signing` are removed, with the `hot-updater/signing` entry.
`deploy` refuses a config that still sets one, rather than deploy unsigned.
Sign with an RSA key in the secrets store instead:

```ts
// 1.1
import { awsKmsSigning } from "hot-updater/signing";
signing: awsKmsSigning({ keyId: "<key-arn>", region: "<region>" }),

// 1.2
import { secret } from "hot-updater";
signing: secret("bundle-signing-key"),
```

```sh
npx hot-updater secrets issue bundle-signing-key
```

A KMS key never leaves the KMS, so this is a new key: run
`npx hot-updater keys export-public` and ship a new native build before you
deploy with it. Installed apps that embed the old public key reject bundles
signed with the new one. With the old key's PEM, run
`npx hot-updater secrets put bundle-signing-key <key.pem>` instead, which
keeps the key the apps embed.

## Cloudflare

Init applies `plugins/cloudflare/worker/migrations/0002_hot-updater_1.2.0.sql`
with `wrangler d1 migrations apply --remote`, which creates the new tables,
adds the `bundle_events__byBundle__key` index, writes the settings rows and
records the file in `d1_migrations`, then deploys the Worker from this
release with `wrangler deploy`. It keeps the bindings, secrets, routes and R2
bucket. A native build's artifact is
stored in the same R2 bucket under `native-builds/`.

## Supabase

Init pushes `supabase/migrations/0002_hot-updater_1.2.0.sql` with
`supabase db push`, which needs the Supabase access token or CLI login and the database
password, then deploys the `hot-updater-v1` Edge Function from this release.
The migration creates the new tables with their row-level security, grants
the service role access, lets the `hot_updater_v1_apply` RPC write them, adds
the `hot_updater_v1_bundle_events__byBundle__key` index, and ends with the
settings rows. The
project's Storage upload
file size limit, which the Free plan keeps at 50 MB, also caps the native
build artifacts the CLI can upload.

## AWS

DynamoDB needs no schema change: the table keeps its `pk` and `sk` keys. Init
writes the settings rows, puts the Lambda role's DynamoDB policy, whose
`dynamodb:LeadingKeys` condition now also lists `native_builds` and
`native_builds#*`, publishes the Lambda@Edge function from this release and
associates it with the CloudFront distribution. The function serves only the
client routes, which do not read the new table; the policy keeps the role in
step with the managed server's tables. CloudFront replaces the function at each edge location
over several minutes, so an edge location still running 1.1.x answers 503
until it is replaced.

The distribution also stops caching 500, 502, 503 and 504 answers
(`CustomErrorResponses` with `ErrorCachingMinTTL: 0` and an empty
`ResponsePagePath` and `ResponseCode`, so no page replaces the server's
answer), on a new distribution and on the existing one init updates.

## Firebase

Firestore needs no index change: the new table's items use the same
`(pk, sk)` indexes in the `hot_updater_v1` collection. Init writes the settings
rows, then deploys the `hot-updater-v1` function from this release.

## Vercel

Init creates the new tables, adds the Insights index and writes the settings
rows in the PostgreSQL database, as `hot-updater db migrate` does, then
redeploys the Function from this release.

## Azure

Cosmos DB needs no container change: the new table's items share the
container's partition. Init writes the settings rows, then deploys the
Function App from this release.

## Standalone databases

A self-hosted server's database gets the new tables, and a SQL database the
Insights index, from `hot-updater db migrate` in the server's project, run as
the server of this release deploys.
Prisma and Drizzle own their table definitions: run
`hot-updater db generate`, apply it with the ORM, then `hot-updater db migrate`. Doctor in
the app project names these commands. `db migrate` now checks that every
table and index the schema declares exists before it writes the settings
rows, and names what is missing; doctor reports it as
`SCHEMA_TABLES_MISSING`.

The Drizzle schema `db generate` writes now matches what `drizzle-kit push`
reads back, so the push after upgrading adds only the new tables and the
Insights index, without a data-loss prompt, and a second push plans nothing.
On PostgreSQL its columns leave out `COLLATE "C"`, which `db migrate` sets.
If you apply the schema with `drizzle-kit generate` and `drizzle-kit migrate`,
edit the migration `generate` writes after upgrading before you apply it. It
declares every existing table again: on PostgreSQL it changes every string
column's type and re-creates every primary key, and on SQLite it rebuilds
every table by copying its rows. `drizzle-kit migrate` runs it in one
transaction, so every Hot Updater table would stay locked until it ends. Keep
only the statements that create `native_builds`, `ios_devices` and
`ios_device_account`, the indexes on those three tables, and
`bundle_events__byBundle__key`, and delete every other statement. The
database already matches the rest, and the snapshot beside the migration
records the new schema, so the next `generate` has nothing to write. Then run
`drizzle-kit migrate` and `hot-updater db migrate`.

On MySQL, apply the Drizzle schema with `drizzle-kit generate` and
`drizzle-kit migrate`, since push cannot read MySQL's character sets. Before
this release drizzle-kit could not create Hot Updater's tables on MySQL: their
key names were longer than MySQL allows, so a push or migration stopped after
`api_keys`, `bundle_event_heads` and `bundle_events`, before the settings
table, and the server answered 503. Drop those tables where a database has
them, since they hold no rows, and remove a migration of that schema that
failed with `npx drizzle-kit drop`. Then generate and migrate.

A CLI that reaches the server through `standaloneRepository` asks
for that upgrade when the server has no native build routes.

## Verification

- Run `npx hot-updater doctor --server-base-url <url>` and confirm it
  reports no schema issue, the server at this release and
  `Infrastructure is up to date.`
- Verify an authenticated update check as before.
- Build a release app with `native-build`, which tracks it, then confirm the build is found for
  its platform, channel and fingerprint or app version, that its built-in
  bundle is listed among the bundles with no release.
- Run the same `native-build` again without changes: it reuses the tracked
  build (`Reusing native build <id> (key nbk1:…; storage)`) instead of
  building.
- Submit a build with `hot-updater testflight` or
  `hot-updater google-play upload`, then confirm the Console's Native builds tab shows it as on
  TestFlight or Play internal, with the store's version and build number,
  and that a second run reuses the build and skips the upload:
  `Already on TestFlight since … as …`.
