Hot Updater's philosophy is to be infrastructure-agnostic: your team chooses
where OTA runs, which database it uses, and where bundles live. Hot Updater
v1.0 supplies integrations for a platform's managed database, storage, and
functions. You can also add OTA to an existing backend and use the Console
for everyday update management.

## Revisiting the cached read path

In [Codemagic's stress-test video](https://www.youtube.com/watch?v=-sYn7MZDw78),
Hot Updater slows down at around 250 requests per second, while Patch
handles 1,000 requests per second. Codemagic attributes the gap to Hot
Updater querying a database for each check and Patch serving a
pre-generated manifest through a CDN.

That result describes the earlier deployment. Hot Updater v1.0's
[Release Catalogs](/blog/v1) now also serve shared update metadata through
a CDN on Cloudflare, so the video's explanation no longer describes this
request path.

We maintain Hot Updater and ran this test ourselves, using the Hot Updater
v1.0 release candidate `1.0.0-rc.14` with real Cloudflare D1 and the preset's
client API-key policy. For the control, we generated a synthetic manifest
with Codemagic's serializer and served it through Cloudflare Workers Static
Assets. Both paths shared a hostname and connection pool to reduce
transport differences. We did not run a Patch deployment or reproduce its
storage, publishing, or SDK behavior.

We scheduled 1,000 requests per second for each path in three 12-second runs.
Each path completed all 36,000 requests with HTTP 200 and the expected
Bundle ID or package hash.

| Metric at 1,000 requests/s | Hot Updater v1.0 on Cloudflare | Codemagic Patch |
| --- | ---: | ---: |
| HTTP 200 + expected identifier | 36,000 / 36,000 | 36,000 / 36,000 |
| HTTP, timeout, or payload failures | 0 | 0 |
| p50, median of the three runs | 60.4 ms | 62.8 ms |
| p95, all three runs pooled | 176.7 ms | 176.5 ms |
| p99, all three runs pooled | 271.8 ms | 243.3 ms |
| CDN `HIT` responses | 35,981 (99.947%) | 36,000 (100%) |

*Codemagic Patch results are from the static manifest control described
above, not a full Patch deployment.*

All 81,000 measured requests passed, including the 250 and 500 requests/s
stages. Median latency and p95 were close; the static control had a lower
pooled p99. With one warmed URL per path, v1.0's cached Catalog delivery
kept up with this workload. These short runs did not test maximum capacity,
sustained production traffic, or performance across the complete products.
We wouldn't use these results to claim a speed advantage for Hot Updater.

## Use your platform's database, storage, and functions

Hot Updater's [provider presets](/docs/get-started/choose-provider) connect
OTA to services your team may already operate. The
[Supabase preset](/docs/managed/supabase) uses PostgreSQL, Storage, and Edge
Functions. The [Firebase preset](/docs/managed/firebase) uses Firestore,
Storage, and Cloud Functions. Each supplies the database and storage
integration together with the function that handles client requests.

The setup tools apply the provider's schema or indexes and deploy the
function. You still configure access and connect your app, but the
integration code is supplied. These deployments don't need a separate
Docker host for the OTA server.

The [Console](/docs/guides/console) gives your team a UI for managing rollout
and targeting, disabling bundles, and inspecting artifacts. Run it locally,
or [deploy an authenticated Console](/docs/guides/console-deployment) for
your team using the same backend resources.

Each preset has its own deployment and caching behavior. The benchmark
above covers one of those configurations.

Patch's [documented default installation](https://patch.codemagic.io/docs/install)
requires an SSH-accessible server with Docker and Docker Compose v2. It
runs Caddy, the API and release worker, PostgreSQL, and MinIO on that host.
That gives you a prescribed stack to install and operate for management
and publishing; published updates can still be delivered through storage
and a CDN independently of the API.

Patch can connect to [external PostgreSQL](https://patch.codemagic.io/docs/reference/configuration),
so the database does not have to run inside Compose. Its
[storage and delivery adapters](https://patch.codemagic.io/docs/setup/infrastructure)
also let you change object storage and CDN services around its application
stack: a
[Node.js server](https://github.com/codemagic-ci-cd/codemagic-patch/blob/f22294f7c2599b79979b8620e5cb6db4bf3bdf0a/server/package.json)
that [uses PostgreSQL directly](https://github.com/codemagic-ci-cd/codemagic-patch/blob/f22294f7c2599b79979b8620e5cb6db4bf3bdf0a/server/src/db/client.ts).

For the commit we compared, Patch's
[custom-deployment guide](https://github.com/codemagic-ci-cd/codemagic-patch/blob/f22294f7c2599b79979b8620e5cb6db4bf3bdf0a/docs/custom-deployment.md)
identifies Compose as the only supported self-hosting path. Deployments
outside Compose are reference material; separate API and worker services
are work in progress. An operator could adapt Patch to another hosting
platform, but that requires its own deployment and verification work.

For a Firebase team, this makes a practical difference. Using a GCS bucket
with Patch leaves its PostgreSQL-backed API and release worker to host.
Hot Updater supplies the Firestore and Cloud Functions integration too.
Both setups still need upgrades, credential management, and data recovery;
we haven't measured the maintenance effort for either.

## Fit OTA into an existing backend when you need to

If your team already has a backend it wants to reuse, you can run
Hot Updater [inside that server](/docs/custom/overview). Its handlers mount
in Hono, Express, or Elysia, with your authentication middleware protecting
management routes. Database integrations cover Kysely, Drizzle, Prisma,
and MongoDB. The [plugin system](/docs/concepts/plugin-system) lets you
choose database and storage independently.

That includes database choices such as [SQLite](/docs/custom/database/kysely)
and [MongoDB](/docs/custom/database/mongodb). A team with a transaction-capable
MongoDB deployment can keep OTA metadata there. An Express and Prisma team can add
Hot Updater's schema through its existing migration process and protect
management routes with its authentication middleware. The team still
implements the admin access policy, using the backend it already reviews
and deploys.

You can use [Docker](/docs/custom/hosting/docker) if containers fit your
operations, or deploy to a [serverless host](/docs/custom/hosting/vercel).
A custom environment needs a compatible runtime and database and storage
adapters; a provider we don't cover may require integration work.

## An MIT license without a usage threshold

Hot Updater uses the [MIT license](https://github.com/gronxb/hot-updater/blob/0dbbefb4c536053fb6369d51722d3c72b43a26a7/LICENSE).
You can use it commercially, modify it, and redistribute it as long as you
meet its notice requirements. There is no MAU-based license fee or
restriction on competing products. You still pay for your infrastructure.

Patch's SDK and CLI use Apache 2.0. Its server has different terms: the
[licensing summary for the commit we compared](https://github.com/codemagic-ci-cd/codemagic-patch/blob/f22294f7c2599b79979b8620e5cb6db4bf3bdf0a/LICENSING.md)
allows free use up to 1,000,000 monthly active devices requesting updates.
Above that, you need a commercial license. The server license restricts
competing use, though you can self-host it for your own commercial apps
within those terms. It also provides for a later transition to Apache 2.0,
under the
[full change-date terms](https://github.com/codemagic-ci-cd/codemagic-patch/blob/f22294f7c2599b79979b8620e5cb6db4bf3bdf0a/LICENSE)
in the license. We're comparing the terms that apply to this pinned
version now.

## When Patch fits

Patch offers an integrated installer and dashboard, plus
[commercial support and optional vendor hosting](https://patch.codemagic.io/docs/introduction/pricing).
That can suit a team that wants help adopting and operating Patch's stack.

Patch keeps published manifests and bundle URLs separate from the
management API. Codemagic [demonstrates delivery with that API offline](https://blog.codemagic.io/designing-scalable-ota-update-architecture/#simulated-crash-test),
while storage and the CDN remain available. Hot Updater's origin
dependencies vary by deployment. We didn't test whether the two systems
behave alike during an outage.

## Why we'd choose Hot Updater

These cached metadata results give us little reason to choose on speed.
We'd choose Hot Updater for a team that wants OTA to use the managed
platform it already operates. A provider preset includes the database,
storage, and function integration, with the Console for update management.
The team can keep using its platform's services without adopting a
separate PostgreSQL-backed application stack for OTA.

A team with an established backend can choose its database and run the OTA
handlers alongside its own routes, using the framework and authentication
it already maintains. Those choices reach further into the application
than Patch's documented storage and delivery adapters. MIT lets that team
modify and build on the system without a usage threshold or
competing-product restriction.

[Choose a provider preset](/docs/get-started/choose-provider) to set up the
OTA server in your cloud account, or follow the
[custom-server guide](/docs/custom/overview) to connect it to your backend.

<summary>Read path and comparison limits</summary>

### Why v1.0 behaves differently

[Release Catalogs](/blog/v1) compile release policy when it changes.
Devices fetch a shared Catalog and evaluate their installation state locally.
The [managed Cloudflare template](https://github.com/gronxb/hot-updater/blob/0dbbefb4c536053fb6369d51722d3c72b43a26a7/plugins/cloudflare/worker/wrangler.json)
enables Workers Cache. A Catalog response uses:

```http
Cache-Control: public, max-age=0, s-maxage=5
Vary: Accept-Encoding, x-api-key
```

On a [Workers Cache hit](https://developers.cloudflare.com/workers/cache/),
Cloudflare returns the response without running the Worker or looking up
anything in D1. On a miss, API-key validation reads D1, and a cold Catalog
adds another lookup. The server keeps a five-second Catalog cache and
merges concurrent loads of the same Catalog.

Codemagic also [clarified that the observed throughput was not a hard limit](https://www.reddit.com/r/reactnative/comments/1v2esog/hot_updater_vs_patch_ota_stress_test/).

### Scope

We tested one warmed URL per path, one API key, and one synthetic release
for a short period. That gives both paths plenty of cache reuse. v1.0 had
a five-second freshness window. We gave the static manifest a 300-second
window through a header in the harness; we didn't measure that value as
a Patch deployment default. The 12-second stages crossed v1.0's TTL but
never reached the manifest's expiry. Patch supports purging manifests
when publishing. We did not measure how long either system takes to get
a published update to a device.

The test also left out traffic across many apps or versions, cache purges
after publishing, rollout changes, origin failures, Insights reporting,
artifact resolution, downloads, and patch generation. A complete v1.0
update may need a separate artifact request, and the two response bodies
contain different information. We can't infer full SDK equivalence,
hosting costs, or outage behavior from these results.

In the Cloudflare configuration we tested, a Catalog request that reaches
the origin needs the Worker and D1. An update can also require a separate
artifact lookup. We didn't test how these dependencies affect delivery
during an outage.

The video doesn't identify the Hot Updater commit it tested or give enough
detail about its fixtures and request distribution for an exact rerun.
Our test can't explain that earlier slowdown or measure a speedup between
versions. It does show that v1.0 on Cloudflare can serve Catalog cache hits
without database work on each request.

### Request scheduling and statistics

- Both paths shared twelve persistent HTTP/2 sessions. Each stage started
  with twelve sequential warmup requests, which we excluded from the results.
- Each target received 250 requests/s for six seconds, 500 requests/s for
  six seconds, then three runs of 1,000 requests/s for twelve seconds each:
  40,500 measured requests per target. Stages ran sequentially. The order
  was v1.0/static, static/v1.0, v1.0/static, static/v1.0, then v1.0/static.
- A clock-based scheduler sent due requests approximately every two
  milliseconds, without waiting for earlier responses. After scheduling
  ended, it waited for pending responses. The harness used a ten-second
  HTTP/2 stream inactivity timeout, rather than an absolute request deadline.
- Requests sent `Accept-Encoding: identity`, with no query-string cache
  busters or client `If-None-Match` headers. We kept existing cache entries.
  The load generator made HTTP requests without running a React Native SDK.
- We measured latency from just before opening the HTTP/2 stream until the
  full response body arrived, before JSON validation. That includes network
  transit and transport queuing, but excludes dispatch lag. The raw data also
  records dispatch lag and scheduled-to-completion latency.
- Percentiles use nearest rank. We calculated the headline p95 from all
  36,000 request timings per target, rather than averaging the three p95 values.
- At 1,000 requests/s, the largest per-stage p99 dispatch lag was 7.54 ms.
  The final response arrived 163–347 ms after the nominal twelve-second
  window. Including that drain, completed throughput was 972–987 requests/s.
- We counted a sample as successful if it returned HTTP 200, parseable JSON,
  and the expected first Catalog Bundle ID or manifest target package hash.
  That check doesn't validate full SDK selection, rollback, or installation.
- All 19 non-HIT v1.0 responses in the 1,000 requests/s stages were
  `REVALIDATED`. CDN revalidation can retain diagnostic headers, so we can't
  use their D1 counters to calculate total queries, CPU consumption, or savings.
  One cold preflight response reported two D1 queries and two rows read.

Both targets had the same POP proportions, though network conditions could
still vary between stages. We didn't calculate confidence intervals or run
an equivalence test, so these observations don't establish identical
latency distributions.
