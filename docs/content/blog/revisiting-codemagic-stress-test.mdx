## Comparable cached delivery, different operating models

In [Codemagic's stress-test video](https://www.youtube.com/watch?v=-sYn7MZDw78),
Hot Updater starts slowing down at around 250 requests per second, while
Patch handles the tested 1,000 requests per second. The explanation is that
Hot Updater queries a database for each check, whereas Patch serves a
pre-generated manifest through a CDN.

Hot Updater v1.0's [Release Catalogs](/blog/v1) also serve shared update
metadata through a CDN on Cloudflare. The video's explanation does not
describe that current read path. This does not invalidate its observation
of the earlier deployment.

We maintain Hot Updater and ran this test ourselves. We used the **Hot
Updater v1.0 release candidate `1.0.0-rc.14`**, with real Cloudflare D1 and
the preset's client API-key policy. The control was a synthetic manifest
generated by Codemagic's serializer, served through **Cloudflare Workers
Static Assets, not a running Patch deployment**. Sharing the hostname and
connection pool reduced transport differences; it did not reproduce Patch's
storage, publishing, or SDK behavior.

At an offered **1,000 requests per second**, each path completed **36,000
requests across three 12-second runs**. Every response returned HTTP 200
and passed the expected Bundle ID or package-hash check.

| Metric at 1,000 requests/s | Hot Updater v1.0 | Static control using Patch's manifest format |
| --- | ---: | ---: |
| HTTP 200 + expected identifier | 36,000 / 36,000 | 36,000 / 36,000 |
| HTTP, timeout, or payload failures | 0 | 0 |
| p50, median of the three runs | 60.4 ms | 62.8 ms |
| p95, all three runs pooled | 176.7 ms | 176.5 ms |
| p99, all three runs pooled | 271.8 ms | 243.3 ms |
| CDN `HIT` responses | 35,981 (99.947%) | 36,000 (100%) |

Including the 250 and 500 requests/s stages, **all 81,000 measured requests
succeeded**. With one warmed URL per path, median latency and p95 were
close; pooled p99 favored the static control. This is evidence that v1.0's
cached Catalog delivery can keep up with this workload, **not proof of
equivalent product performance**. It gives us no reason to sell Hot Updater
on a speed advantage. Maximum capacity and sustained production traffic
were not tested.

The stronger reasons to choose Hot Updater concern what you can build with
it and what you need to operate.

## An MIT license without a usage threshold

Hot Updater uses the [MIT license](https://github.com/gronxb/hot-updater/blob/0dbbefb4c536053fb6369d51722d3c72b43a26a7/LICENSE).
It permits commercial use, modification, and redistribution, subject to its
notice requirements. It has no MAU-based license fee or restriction on
competing products.

Patch's SDK and CLI are Apache 2.0, but its **server has different terms**.
The [published licensing summary at the compared commit](https://github.com/codemagic-ci-cd/codemagic-patch/blob/f22294f7c2599b79979b8620e5cb6db4bf3bdf0a/LICENSING.md)
sets a free-use limit of **1,000,000 monthly active devices requesting
updates**, requires a commercial license above that, and restricts competing
use. Self-hosting for your own commercial apps is allowed within those terms.
The server license also provides a later transition to Apache 2.0; its
[full change-date terms](https://github.com/codemagic-ci-cd/codemagic-patch/blob/f22294f7c2599b79979b8620e5cb6db4bf3bdf0a/LICENSE)
govern that transition. This comparison concerns the pinned version's
current terms.

For Hot Updater, audience growth does not trigger a software license
threshold. Your chosen infrastructure still has its own costs.

## A serverless deployment in your cloud account

Hot Updater's [Cloudflare preset](/docs/managed/cloudflare) uses Workers,
D1, and R2. You can operate OTA delivery without maintaining a separate VM,
Docker Compose stack, or PostgreSQL server. The supplied
[provider presets](/docs/get-started/choose-provider) also cover AWS,
Supabase, and Firebase; their deployment and caching behavior differ.

Patch's [documented default installation](https://patch.codemagic.io/docs/install)
runs Caddy, its API and release worker, PostgreSQL, and MinIO on a Docker
host. Its [adapters](https://patch.codemagic.io/docs/setup/infrastructure)
support external storage and CDN choices, including R2 and CloudFront.
Hot Updater's advantage here is the supplied serverless deployment path:
a team already using Cloudflare can keep OTA infrastructure within those
managed services. Application upgrades, credentials, and data recovery
remain the operator's responsibility; we did not measure maintenance time
or total operating cost.

## Fit OTA into an existing backend

Hot Updater can also run [inside your own server](/docs/custom/overview).
Mount its handlers in Hono, Express, or Elysia, protect management routes
with your authentication middleware, and use the supported Kysely, Drizzle,
Prisma, or MongoDB integration. Database and storage are independently
selectable through the [plugin system](/docs/concepts/plugin-system).

That lets a team reuse its database tooling, authentication, and deployment
process instead of adding a separate OTA management service. You still
prepare Hot Updater's schema and implement the admin access policy. For a
team that already has a backend, that is a useful choice of integration
boundary.

## Where Patch remains a strong choice

Patch offers an integrated installer and dashboard, plus
[commercial support and optional vendor hosting](https://patch.codemagic.io/docs/introduction/pricing).
That can suit teams that prefer a supplied operating model over backend
integration.

Its architecture also separates published manifests and bundle URLs from
the management API. Codemagic [demonstrates delivery with that API offline](https://blog.codemagic.io/designing-scalable-ota-update-architecture/#simulated-crash-test);
storage and CDN availability are still required. Hot Updater's Cloudflare
path needs the Worker and D1 when a Catalog request reaches the origin,
and selecting an update can require a separate artifact lookup. Our test
did not establish equivalent outage behavior. Comparable cached latency
does not erase that architectural difference.

<summary>Read path and comparison limits</summary>

### Why v1.0 behaves differently

[Release Catalogs](/blog/v1) compile release policy when it changes. Devices
request a shared Catalog and evaluate their own installation state locally.
The [managed Cloudflare template](https://github.com/gronxb/hot-updater/blob/0dbbefb4c536053fb6369d51722d3c72b43a26a7/plugins/cloudflare/worker/wrangler.json)
enables Workers Cache. A Catalog response uses:

```http
Cache-Control: public, max-age=0, s-maxage=5
Vary: Accept-Encoding, x-api-key
```

On a [Workers Cache hit](https://developers.cloudflare.com/workers/cache/),
Cloudflare serves the response without invoking the Worker. Those requests
therefore perform no D1 lookup. On a miss, API-key validation still reads
D1; a cold Catalog adds another lookup. The server also has a five-second
Catalog cache and merges concurrent loads of the same Catalog.

Codemagic also [clarified that the observed throughput was not a hard limit](https://www.reddit.com/r/reactnative/comments/1v2esog/hot_updater_vs_patch_ota_stress_test/).

### Scope

This was a short test of **one warmed URL per path**, one API key, and one
synthetic release. It favors cache reuse. The two paths also had different
freshness windows: five seconds for v1.0 and 300 seconds for the static
manifest. We set the static control's 300-second header in the harness;
it is not a measured default from a Patch deployment. The 12-second stages
crossed v1.0's TTL, but did not test the manifest's 300-second expiry. Patch
supports purging manifests when publishing; this test does not compare
publication-to-device delay.

We did not measure many apps or versions, cache purges after publishing,
rollout changes, origin failures, Insights reporting, artifact resolution,
downloads, or patch generation. A complete v1.0 update may need a separate
artifact request. The different response bodies are not identical protocol
work. These results establish neither full SDK equivalence nor equivalent
hosting costs or outage behavior.

The video does not identify the tested Hot Updater commit or provide enough
fixture and request-distribution detail for an exact rerun. Our measurement
cannot establish the cause of its earlier slowdown or a version-to-version
speedup. The narrower correction is that the v1.0 Cloudflare read path can
serve Catalog cache hits without per-request database work.

### Request scheduling and statistics

- Twelve persistent HTTP/2 sessions were shared by both paths. Each stage
  started with twelve sequential warmup requests, excluded from the results.
- Each target received 250 requests/s for six seconds, 500 requests/s for
  six seconds, then three runs of 1,000 requests/s for twelve seconds each:
  40,500 measured requests per target. Stages ran sequentially. The order
  was v1.0/static, static/v1.0, v1.0/static, static/v1.0, then v1.0/static.
- A clock-based scheduler dispatched due requests every approximately two
  milliseconds without waiting for earlier responses. Pending responses
  were drained after scheduling ended. The harness set a ten-second HTTP/2
  stream inactivity timeout; this was not an absolute request deadline.
- Requests sent `Accept-Encoding: identity`, with no query-string cache
  busters or client `If-None-Match` headers. Existing cache entries were not
  purged. These were HTTP requests, not React Native SDK executions.
- Latency runs from immediately before opening the HTTP/2 stream to
  complete response-body receipt, before JSON validation. It includes
  network transit and any transport queuing, but excludes dispatch lag.
  The raw data records dispatch lag and scheduled-to-completion latency too.
- Percentiles use nearest rank. The headline p95 pools 36,000 request
  timings per target; it is not an average of the three p95 values.
- At 1,000 requests/s, the largest per-stage p99 dispatch lag was 7.54 ms.
  The final response arrived 163–347 ms after the nominal twelve-second
  window. Including that drain, completed throughput was 972–987 requests/s.
- A successful sample required HTTP 200, parseable JSON, and the expected
  first Catalog Bundle ID or manifest target package hash. This does not
  validate full SDK selection, rollback, or installation behavior.
- All 19 non-HIT v1.0 responses in the 1,000 requests/s stages were
  `REVALIDATED`. Diagnostic headers can survive CDN revalidation, so their
  D1 counters cannot establish total queries, CPU consumption, or savings.
  One cold preflight response reported two D1 queries and two rows read.

The matching POP proportions help comparison, but network conditions still
vary between sequential stages. No confidence interval or equivalence test
was calculated. The observations do not prove that the paths have identical
latency distributions.
