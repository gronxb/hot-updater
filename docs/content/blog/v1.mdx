An update check looks like a read, but it used to be a decision.

The server received an installation's current Bundle, minimum Bundle, cohort,
platform, channel, and compatibility target. It then asked the configured
database provider which update that particular installation should receive.
The answer was correct, but it was also difficult to share.

At small scale, that distinction is easy to ignore. At scale, it becomes the
shape of the bill: more app launches produce more origin executions and more
database decision queries—even when thousands of installations are asking
about the same Release policy.

Hot Updater 1.0 changes when that work happens, where it happens, and how we
observe the result.

## The hidden cost of a precise question

The old update-check URL included installation-specific state such as the
current Bundle and cohort. Two devices in the same channel and app version
could therefore produce different cache keys.

That created several recurring costs:

- **Infrastructure cost.** A burst of update checks could run the origin and
  database decision path almost once per request instead of sharing a cached
  response.
- **Provider cost.** SQL, Firestore, DynamoDB, D1, MongoDB, and custom providers
  each needed their own form of update-selection query. Moving the query
  changed where the work was billed, but not how it scaled.
- **Correctness cost.** Policy and installation state were read while requests
  were in flight. A slow response or artifact download needed additional
  protection to avoid committing a decision older than one the device had
  already accepted.
- **Operational cost.** Bundle bytes and delivery policy appeared to be one
  object. Promotion, rollback, policy edits, and deletion all had to work
  around that blurred ownership boundary.

We did not want a faster version of the same per-installation query. We wanted
routine update checks to stop asking installation-specific questions at the
origin.

## Pay for the decision when policy changes

Version 1.0 separates the system into three parts:

- A **Bundle** is immutable, installable content: archives, assets, patches,
  hashes, manifests, and signing identity.
- A **Release** references a Bundle and owns mutable delivery policy: channel,
  compatibility, rollout, cohorts, enablement, force update, and message.
- A **Release Catalog** is a deterministic desired-state projection compiled
  from Releases for one authority, platform, channel, and compatibility scope.

Deploying a Release or changing its policy compiles the affected Catalog ahead
of time. The Release mutation and Catalog generation commit atomically, so a
client cannot observe new policy without its matching projection.

This makes the read path intentionally boring. A cold origin request performs
one exact Catalog-row read. On providers with a shared cache, warm requests can
perform zero database reads and zero decision-origin work. Origin work grows
with cache fills per location and TTL instead of with individual installations.

Supabase's supported origin-only mode still invokes its Edge Function for each
check, but it serves an already compiled Catalog instead of running a
per-installation Postgres decision query.

The device evaluates its own current state, rollout bucket, cohort, and crash
history against the shared Catalog. It requests an artifact only when the
selected Bundle bytes differ. Generation high-water marks and atomic local
receipts prevent an older response or slower download from overwriting a newer
accepted decision.

The bet is simple: policy changes happen far less often than update checks. We
choose to spend more work on the uncommon write so the common read can be
shared, cached, and predictable.

## Fewer copies, fewer meanings

Separating Release policy from Bundle bytes reduces more than request cost.

Promotion creates a new Release for another channel while reusing the same
Bundle objects. Changing rollout or cohort targeting recompiles policy without
rewriting an artifact. Disabling a specific Release rolls affected devices
back to their previous compatible enabled Release—or to the built-in Bundle—
without inventing another copy of the bytes.

The CLI now makes that ownership visible:

```bash
# Inspect delivery policy
npx hot-updater release list --channel production --platform ios

# Promote without copying Bundle bytes
npx hot-updater release promote <release-id> --target production

# Roll back an exact Release
npx hot-updater release disable <release-id>
```

Bundle commands manage artifacts and report their Release references. Release
commands manage delivery. The ambiguous top-level, Bundle-targeted `rollback`
command is gone, and storage pruning can reason about live references before
reclaiming objects.

Database providers also become smaller in responsibility. They persist the
official Bundle, Release, Catalog, Channel, Analytics, and access-key domains
and provide conditional atomic commits. They no longer implement their own
desired-state selector. That removes a class of provider-specific behavior we
otherwise had to implement, optimize, and verify repeatedly.

## A cheaper read still needs a feedback loop

Moving installation-specific selection to the device removes it from the
server's request path. It does not remove the operator's need to know what
happened.

That is why Analytics is a built-in server domain in 1.0 rather than a separate
plugin. With `HotUpdater.init({ analytics: true })`, an app reports its outcome
after it is ready. Reporting is best-effort: an Analytics failure is a warning
and never blocks startup or rolls back device state.

The Console can use those reports to answer practical questions:

- **How many installations are reporting?** View active installations over
  24 hours, 7 days, or 30 days.
- **Which Bundle are they actually on?** See the latest reported Bundle
  distribution and how that distribution moves over time.
- **Is a rollout behaving as expected?** Compare the configured rollout with
  the observed share among reporting installations.
- **Did the update stick?** Separate successful `UPDATE_APPLIED` transitions
  from `RECOVERED` transitions that moved away from a Bundle after recovery.
- **Did policy change without new bytes?** `RELEASE_ADOPTED` distinguishes
  adopting a new Release that references the same Bundle from downloading and
  installing an update.
- **What happened to one installation?** Search by installation ID, user ID, or
  username and inspect its latest platform, app version, channel, cohort,
  Bundle, status, and transition history.

Release and Bundle IDs are recorded directionally, so Analytics can describe a
movement from one policy and artifact identity to another instead of guessing
a Release from a Bundle ID.

These numbers are operational evidence, not an analytics warehouse. They cover
devices that opted in and successfully reported, not every installed copy of
the app. An observed Bundle share is therefore not proof of the exact global
rollout percentage, and a missing event is not proof that an installation
failed. Built-in aggregation is deliberately bounded so observability cannot
become an unbounded database workload of its own.

## The cost we chose to keep

This architecture is not free.

The write path is more demanding: it strongly reads affected Releases,
compiles a deterministic Catalog, and conditionally commits Release revisions
and Catalog generations together. Catalogs retain the history needed for safe
rollback and reject a mutation rather than silently truncating when the
canonical payload exceeds 256 KiB.

The protocol boundary is also intentionally clean. Managed v0 infrastructure
cannot be upgraded in place. Supporting every mixed generation would keep the
old routes, schemas, cache keys, and migration behavior alive indefinitely—and
put that compatibility cost back into the request path we are simplifying.

The supported migration is a parallel cutover:

1. Keep the v0 endpoint running for installed v0 binaries.
2. Upgrade all `hot-updater` and `@hot-updater/*` packages together.
3. Run `npx hot-updater init` with fresh v1 provider resources.
4. Update automation from Bundle policy commands to Release commands.
5. Verify the new endpoint with `npx hot-updater doctor`.
6. Publish a new native build with the v1 SDK and endpoint.

Do not deliver v1 `@hot-updater/react-native` JavaScript to a v0 native binary
through OTA. The v1 receipt and rollback model requires the v1 native module.

Read the [v1 upgrade guide](/docs/guides/upgrade-to-v1) before provisioning, or
explore [how Release Catalogs work](/docs/concepts/how-it-works) in detail.

## Do less, know more

Hot Updater 1.0 moves cost away from the operation performed on every launch.
Policy is compiled when it changes, shared when it is read, selected with local
installation context, and measured after the app becomes ready.

The server does less work per check. Providers own fewer decisions. Operators
get better evidence about what devices actually did. That is the trade we
wanted 1.0 to make.
