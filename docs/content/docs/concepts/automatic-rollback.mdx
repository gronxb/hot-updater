## What is Automatic Rollback?

Automatic rollback is the safety mechanism that prevents a bad OTA bundle from trapping users in a crash loop.

When a new bundle is installed, Hot Updater does not trust it immediately. It launches that bundle in a temporary state first, keeps the last known-good bundle as a fallback, and only treats the new bundle as safe after startup succeeds.

This happens automatically when you use `HotUpdater.wrap()`. For custom manual
flows without a root wrapper, call [`HotUpdater.init()`](/docs/react-native-api/init)
when your runtime considers the app ready.

## Core Mechanism

Hot Updater manages two roles during rollout:

- **Staging bundle**: the newly installed bundle waiting to be verified
- **Stable bundle**: the last bundle that was already known to start successfully

The flow is:

1. **Install the update**
   - The downloaded bundle becomes the new staging bundle.
   - The previously working bundle is kept as the fallback, if one exists.
2. **Launch the staging bundle**
   - On the next app start, Hot Updater loads the staging bundle first.
3. **Verify startup**
   - If the app reaches its first successful render, the launch is treated as successful.
   - The staging bundle becomes the current trusted bundle.
   - With [`verifyOnAppReady`](#errors-caught-by-an-error-boundary) on, this happens when `notifyAppReady()` runs instead.
4. **Recover on failure**
   - If the app crashes before that point, or exits before its first content, the staging bundle is treated as failed. With `verifyOnAppReady`, an exit after first content leaves it on trial.
   - On the next launch, Hot Updater automatically returns to the last stable bundle.

## What Counts as a Failed Launch?

A bundle is considered failed if it cannot complete startup.

In practice, that means the app never reaches the point where Hot Updater can confirm that the new bundle started successfully.

Typical examples include:

- a JavaScript error during startup
- a native crash while the new bundle is loading
- a fatal error before the first screen appears
- a JavaScript thread hang followed by the user or OS killing the app before the first render

This is why Hot Updater must be configured with `HotUpdater.wrap()` or
`HotUpdater.init()` for rollback support. These APIs connect bundle verification
to the app lifecycle.

Before loading an unverified staging bundle, Hot Updater persists a launch-in-progress
record. The first native content appearance clears it. If it remains on the next
cold start, Hot Updater rolls back even when no crash marker was written. There is
no timeout that interrupts a running JavaScript thread: recovery occurs after the
app restarts. A user or OS termination before the first render also counts as a
failed launch, even if the bundle would otherwise have finished loading.

This protection requires a native app build containing the updated SDK; an OTA
bundle alone cannot add it to an already installed native binary.

## Errors Caught by an Error Boundary

A render error that an error boundary catches is not a crash. The boundary's
fallback screen is itself first content, so by default Hot Updater treats the
launch as successful and keeps the bundle.

To roll such a bundle back:

1. Turn on `verifyOnAppReady`. First content then only clears the
   launch-in-progress record, and the staging bundle stays on trial until
   `notifyAppReady()` runs. `HotUpdater.init()` calls it one frame after it is
   called, and `HotUpdater.wrap()` one frame after its first commit. With a
   `fallbackComponent`, that first commit is the fallback, so `wrap()` does
   not cover the app's first render. Use `init()` there instead.
2. Call `HotUpdater.init()` from an effect in the first screen you want
   verified, not at module scope. Everything that renders before that call is
   covered.
3. In the error boundary, call
   [`HotUpdater.reportBundleFailure()`](/docs/react-native-api/reportBundleFailure),
   then `HotUpdater.reload()`. Until the reload, `updateBundle()` returns
   `false`, because a newly installed bundle would replace the failed one and
   the reload would launch it instead of rolling back. A download that was
   already running is not stopped.

| Setup        | Setting                                                                    |
| ------------ | -------------------------------------------------------------------------- |
| Expo         | Plugin option `"verifyOnAppReady": true`                                   |
| iOS          | `Info.plist` key `HOT_UPDATER_VERIFY_ON_APP_READY` set to `true`           |
| Android      | Manifest `<meta-data>` `com.hotupdater.VERIFY_ON_APP_READY` set to `true`  |
| Brownfield   | The `verifyOnAppReady` argument of `HotUpdater.configure`                  |

Changing the setting needs a new native build.

With `verifyOnAppReady` on:

- A bundle whose launches never reach `notifyAppReady()` stays on trial on
  every cold start, with crash rollback armed. Hot Updater never promotes it,
  and rolls it back only if a launch crashes or hangs before its first content. That happens when the app never calls `init()`, or hangs
  after its first content.
- If the app is killed between first content and `notifyAppReady()`, the
  bundle stays on trial and is tried again on the next launch.
- Installing another bundle while one is on trial replaces it, so the one on
  trial is never promoted. `HotUpdater.wrap()` waits for `notifyAppReady()`
  before installing. In a manual flow, call `updateBundle()` from
  `onNotifyAppReady` or later.

## What Happens During Rollback?

When rollback happens, Hot Updater:

- stops using the failed staging bundle
- restores the previous stable bundle when one exists
- falls back to the embedded bundle when there is no stable OTA fallback
- records the failed bundle in crash history

This lets users reopen the app normally instead of hitting the same startup failure again.

## Managing Crashed Bundles

Hot Updater keeps a crash history for bundles that failed startup and triggered recovery.

### getCrashHistory()

Returns the bundle IDs that were marked as failed and rolled back.

```tsx
import { HotUpdater } from "@hot-updater/react-native";

function checkCrashedBundles() {
  const crashedBundles = HotUpdater.getCrashHistory();

  if (crashedBundles.length > 0) {
    console.log("Crashed bundles:", crashedBundles);
    // Send to your monitoring service
  }
}
```

You can use this to:

- monitor deployment health
- identify which bundle IDs failed in production
- send rollback events to analytics or error tracking tools

### clearCrashHistory()

Clears the crash history so a previously failed bundle ID can be retried again.

```tsx
import { HotUpdater } from "@hot-updater/react-native";

async function retryFailedBundle() {
  HotUpdater.clearCrashHistory();
  console.log("Crash history cleared");
}
```

<Callout type="warn">
Only clear crash history after fixing the underlying issue. Otherwise the same broken bundle can be applied again.
</Callout>

### Crash History Blocking

When a bundle fails startup, Hot Updater adds that exact bundle ID to crash history and blocks it from being applied again. This prevents repeated crash loops from the same broken deployment.

To deploy a fixed version:

1. Fix the bug in your code
2. Deploy again with a new bundle ID
3. The new bundle ID bypasses the crash history

If you need to retry the same bundle ID:

1. Verify the bundle is fixed
2. Call `clearCrashHistory()` to reset the blocked list
3. Redeploy the bundle

## In One Sentence

Hot Updater only trusts a new bundle after it launches successfully once. Until then, it keeps a working fallback and can automatically recover if startup fails.
