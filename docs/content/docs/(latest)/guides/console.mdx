Use the console for:

- Bundle rollout and targeting management
- Bundle disable and force-update controls
- Advanced immutable artifact inspection
- Quick access to git history for updates

<video src={"/docs/console/console.mp4"} controls autoPlay loop muted />

`hot-updater console` runs on localhost. For a persistent HTTPS console that
works without a developer's computer, clone the standalone host and follow
[Console deployment](/docs/guides/console-deployment). Both use the same
`@hot-updater/console` package and read your server definition.

## Configuration (Optional)

Console configuration does not change bundle delivery settings or artifacts.

`hot-updater console` follows `server` in `hot-updater.config.ts`. With the
path to your server definition, it opens the definition's database and storage
and runs its plugins; with `standaloneRepository`, it reaches the server
through its admin handler. Set console options next to `server`:

| Option           | Description                                              | Default |
| ---------------- | -------------------------------------------------------- | ------- |
| `console.gitUrl` | Enables commit shortcuts by linking to git commit hashes | -       |
| `console.port`   | Sets the console server port                             | `1422`  |

```ts title="hot-updater.config.ts"
import { defineConfig } from "hot-updater";

export default defineConfig({
  console: { // [!code ++]
    port: 3000, // [!code ++]
  }, // [!code ++]
  build: ...,
  server: "./hotUpdater.ts",
});
```

The console shows the built-in pages of the
[server plugins](/docs/custom/server-plugins) the server runs: the Insights
pages with `insights()`, and API key management with `apiKeys()`. It hides each
one when the server does not run its plugin. A deployed console reads the same
server definition; see
[Console deployment](/docs/guides/console-deployment#point-at-your-server).

## Usage

The Bundles list and its detail sheet show an **ID** that matches
[`HotUpdater.getBundleId()`](/docs/react-native-api/getBundleId) on the device.
Promoted updates have their own IDs even when they reuse the same files.

Start the local console:

```package-install
npx hot-updater console
```

## Security model

The CLI Console binds to loopback. With a server definition, it loads the one
`server` points at, with its database and storage adapters, on its own server,
and calls no Hot Updater HTTP handler.

When `server` is `standaloneRepository`, the Console's server calls the Hot
Updater server's admin handler instead. Point `baseUrl` at the exact admin root
(for example, `https://example.com/hot-updater/admin`) and put the admin bearer
token in server-side `commonHeaders`. Never expose that token to Console
browser code or a React Native app.

A deployed Console has two independent boundaries: its Console auth adapter
authenticates browser users, while the framework middleware in front of
`handlers.admin` authenticates Console-to-server requests. The Console's own
`/api/*` routes belong to the Console application and are not the Hot Updater
admin API. Through the standalone repository, the Console reads the server's
Insights overview, events, installations, and update failures from the admin
handler. App usage, Release health, bundle activity, and API key management
need the server definition.

Use Bundle commands for automation and CI scripts:

```package-install
npx hot-updater bundle list --platform ios
npx hot-updater bundle show <id>
npx hot-updater bundle disable <id> -y
npx hot-updater bundle enable <id> -y
npx hot-updater bundle update <id> --force-update true -y
npx hot-updater bundle update <id> --rollout-cohort-count 500 -y
npx hot-updater bundle update <id> --target-cohorts qa,dogfood -y
```

Add `--json` to `bundle list`, `bundle show`, or `bundle update` when
another tool needs raw internal row data. Its field names follow the database
schema rather than the human-readable Bundle terminology.

### Preview and protect automated changes

Before changing delivery policy, read the public Bundle's current `revision`
with `bundle show <id> --json`. Preview the same policy change without writing:

```bash
npx hot-updater bundle show <id> --json
npx hot-updater bundle update <id> --rollout-cohort-count 500 --expected-revision <revision> --dry-run --json
```

A dry run compiles the proposed Catalog and checks its limits, without asking
for confirmation. It does not reserve the revision or save the change. After
reviewing the result, apply the same options with the revision you read:

```bash
npx hot-updater bundle update <id> --rollout-cohort-count 500 --expected-revision <revision> --yes --json
```

`update`, `enable`, `disable`, and `delete` accept `--expected-revision`. If
another operator changes that Bundle first, the stale mutation fails. Re-read
the Bundle and review its policy before retrying; do not remove the revision
check just to make a retry succeed.

For existing Catalog projection problems, run
[`doctor`](/docs/guides/doctor#check-release-catalogs), and `doctor --fix` to
rebuild the stale catalogs it reports.

### Advanced artifact diagnostics

Advanced diagnostics shows each bundle's **Artifact ID**: the uploaded files the
bundle uses. A promoted bundle shares its source's artifact. Deleting the last
bundle that uses an artifact deletes the artifact's record too, with the
patches built on it; `bundle delete --json` names it in `deletedArtifactId`.
The stored files stay until the [Storage Cleanup](/docs/guides/storage-cleanup)
workflow previews and deletes them.

## Insights

The Bundles list and detail show lifetime **Downloads**, **Known launches**,
and **Known crashes**, with a crash rate, and the detail shows **Download
failures** with their rate. Open Insights to inspect release health and update
failures for a selected period, reporting installations, and event history.
Events are kept for 90 days and daily totals for 13 months.

Follow the [Insights guide](/docs/guides/insights) to configure reporting,
identify an installation, verify an applied update, and interpret the counts.

## Rollback

Disabling a bundle removes it from delivery selection. Affected installations
move to the previous compatible enabled bundle or to the app's built-in bundle
when no compatible bundle remains. The result can vary by app version,
fingerprint, and cohort, so verify the scope shown by the Console before
confirming.

## Force Update

Setting a bundle's `shouldForceUpdate` value to `true` marks it for immediate
application when selected. In the [custom update flow](/docs/guides/custom-update),
check `shouldForceUpdate` and call `HotUpdater.reload()` after a successful
download. The optional [`HotUpdater.wrap`](/docs/react-native-api/wrap) flow
reloads after staging by default; `reloadOnForceUpdate: false` defers it.

## Promote

Promotion creates a new bundle ID in the target channel while reusing the same
uploaded artifact:

```package-install
npx hot-updater bundle promote <source-id> --target <channel>
```

No Storage object is uploaded or copied. The promoted update has a new ID
and rollout seed, is enabled, starts at a 100% numeric rollout, and has no
target cohorts. The command previews those defaults before confirmation. A
`--action move` promotion also disables the source bundle atomically.

## Git URL

You can set the git URL in the `hot-updater.config.ts` file.

```ts title="hot-updater.config.ts"
import { defineConfig } from "hot-updater";

export default defineConfig({
  console: {
    gitUrl: "<your-repo>", // e.g. https://github.com/gronxb/hot-updater // [!code ++]
  },
});
```

The commit hash links to the corresponding commit in your repository.
