## Store secrets in GitHub Actions secrets

`githubActions()` from `hot-updater/secrets` stores the keys `secrets put`
stores or a sign-in issues in a GitHub repository's
[Actions secrets](https://docs.github.com/en/actions/how-tos/write-workflows/choose-what-workflows-do/use-secrets),
or in one of its environments' secrets, where its workflows read them.

```ts title="hot-updater.config.ts (partial)"
import { defineConfig } from "hot-updater";
import { githubActions } from "hot-updater/secrets";

export default defineConfig({
  secrets: githubActions({ environment: "production" }),
  nativeBuild: {
    ios: {
      release: {
        bundleIdentifier: "com.example.app",
        scheme: "ExampleApp",
        // Stored as, and read in a workflow from, HOT_UPDATER_ASC_API_KEY.
        signing: { ascApiKey: "secret:asc-api-key" },
      },
    },
  },
  // build, storage, database and plugins stay as they are
});
```

| Option        | Description                                                                                                             |
| ------------- | ----------------------------------------------------------------------------------------------------------------------- |
| `repo`        | The repository, as `owner/name`. Defaults to the GitHub repository of the project's `origin` remote.                    |
| `environment` | Stores in this environment's secrets instead of the repository's. The environment must exist. Defaults to none.         |
| `token`       | The token to store with. Defaults to [your token](#provide-a-token).                                                    |

`set` encrypts each value for the repository's or the environment's public key,
as GitHub requires, and stores it under the name's environment variable name:
`secret:asc-api-key` as `HOT_UPDATER_ASC_API_KEY`, and `CLOUDFLARE_API_TOKEN`
as itself. Each credential is one
[JSON value](/docs/concepts/secrets#sign-native-builds-with-secrets), up to
GitHub's 48 KB.

GitHub never returns a secret's value, so the adapter reads only inside a
workflow run, where the workflow sets each secret as an environment variable.
Outside a workflow it reads nothing: a local build reads the credential from
its [environment variables](/docs/guides/native-build#provide-signing-credentials)
instead.

## Provide a token

The adapter stores with the first of:

1. the `token` option;
2. `GH_TOKEN`, then `GITHUB_TOKEN`, in the environment or `.env.hotupdater`,
   unless it is a workflow's token;
3. `gh auth token`, the login of [GitHub CLI](https://cli.github.com/)'s
   `gh auth login`.

A workflow's `GITHUB_TOKEN` can't store secrets: GitHub gives it no permission
on secrets. In CI, the adapter never runs `gh`, and without another token it
refuses to store. Store the secrets from your machine, or pass a personal
access token as `token`.

The CLI masks the token and every value in its output, and sends them only to
`https://api.github.com`, following no redirects.

## Grant least privilege

A [fine-grained personal access token](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens#creating-a-fine-grained-personal-access-token)
for only that repository needs one repository permission:

| Secrets                 | Permission                   |
| ----------------------- | ---------------------------- |
| The repository's        | Secrets: Read and write      |
| An environment's        | Environments: Read and write |

A classic token, and `gh auth login`'s, needs the `repo` scope. Creating an
environment needs admin access to the repository, which the adapter never
asks for: create the environment in the repository's settings first, and add
its protection rules there.

## Read secrets in GitHub Actions

Set each secret as the environment variable of its name, in the job that
builds. A job with `environment` reads that environment's secrets, and the
repository's:

| Secret                                | Workflow `env`                                                                      |
| ------------------------------------- | ----------------------------------------------------------------------------------- |
| `secret:asc-api-key`                  | `HOT_UPDATER_ASC_API_KEY: ${{ secrets.HOT_UPDATER_ASC_API_KEY }}`                   |
| `secret:release-keystore`             | `HOT_UPDATER_RELEASE_KEYSTORE: ${{ secrets.HOT_UPDATER_RELEASE_KEYSTORE }}`         |
| `secret:play-service-account`         | `HOT_UPDATER_PLAY_SERVICE_ACCOUNT: ${{ secrets.HOT_UPDATER_PLAY_SERVICE_ACCOUNT }}` |
| `secretEnv(["CLOUDFLARE_API_TOKEN"])` | `CLOUDFLARE_API_TOKEN: ${{ secrets.CLOUDFLARE_API_TOKEN }}`                         |

```yaml title=".github/workflows/native-release.yml (partial)"
- uses: gronxb/hot-updater/actions/native-build@v1.2.0
  env:
    HOT_UPDATER_ASC_API_KEY: ${{ secrets.HOT_UPDATER_ASC_API_KEY }}
  with:
    platform: ios
    scheme: release
    upload: testflight
```

[Build and upload from CI](/docs/guides/ci-native-build#environment-variables)
has the complete workflow for both platforms.

Set the secrets only on the steps that need them, and keep an environment's
secrets behind its protection rules, away from pull request workflows that run
untrusted code.
