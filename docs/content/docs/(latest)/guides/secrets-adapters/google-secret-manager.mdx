## Add the adapter

`secretManager()` from `@hot-updater/firebase`, the package of
`firebaseStorage` and `firebaseDatabase`, keeps each name as the secret
`<prefix><name>` in Google Cloud Secret Manager and reads its `latest`
version:

```package-install
npm install @hot-updater/firebase firebase-admin --save-dev
```

```ts title="hot-updater.config.ts (partial)"
import { secretManager } from "@hot-updater/firebase";
import { defineConfig } from "hot-updater";

export default defineConfig({
  secrets: secretManager({ projectId: "my-project" }),
  // build, storage, database and plugins stay as they are
});
```

| Option        | Default                          | What it does                                                                                                                                     |
| ------------- | -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| `projectId`   | Required                         | The Google Cloud project ID or number that holds the secrets                                                                                     |
| `prefix`      | `"hot-updater-"`                 | Put before each name: `secret("asc-api-key")` reads the secret `hot-updater-asc-api-key`. Letters, digits, `-`, and `_`                             |
| `credentials` | Application Default Credentials | Anything with `getAccessToken()`, such as a `GoogleAuth` or firebase-admin's `cert(serviceAccount)`, or a function that returns an access token |

A credential is one
[JSON value](/docs/concepts/secrets#sign-native-builds-with-secrets) per
secret. The adapter calls Secret Manager's REST API with
`google-auth-library`, which firebase-admin already installs. It loads on the
first read or write, so a config that only uses `firebaseStorage` never
loads it, and the Cloud Function and init builds don't include it.

- A secret that does not exist, or has no versions, reads as missing.
- A refused request fails the command with the role it needs. When the
  project has the Secret Manager API turned off, it says to turn it on:

  ```bash
  gcloud services enable secretmanager.googleapis.com --project=my-project
  ```

- `set` creates the secret when it does not exist, adds the value as a new
  version, and waits until `latest` resolves to it, which can lag for a few
  seconds. Then it destroys the versions it added before, which the secret's
  `hot-updater-versions` annotation lists, so the secret keeps one active
  version and stays in Secret Manager's
  [free tier](https://cloud.google.com/secret-manager/pricing) of six. A
  version added any other way, such as in the Cloud Console, is never
  touched.
- Every value it reads or stores, and every access token it signs with, is
  masked in the CLI's output.

Without `credentials`, it signs with `CLOUDSDK_AUTH_ACCESS_TOKEN` or
`GOOGLE_OAUTH_ACCESS_TOKEN` as it is, then Application Default Credentials:
`gcloud auth application-default login` on your machine, the Workload
Identity Federation file `google-github-actions/auth` writes in CI, a service
account key in `GOOGLE_APPLICATION_CREDENTIALS`, or the runtime's service
account.

## Grant least privilege

| Who                                              | Grant                                                                                                                                                       |
| ------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A CI job that builds or deploys                  | `roles/secretmanager.secretAccessor` on each secret it reads                                                                                               |
| The developer who runs `secrets put` or signs in | The custom role below on the secrets, and `secretmanager.secrets.create` on the project for a secret that does not exist yet |

`set` checks its permissions on the secret before it adds a version:
`secretmanager.secrets.get` and `secretmanager.secrets.update` for the
annotation, and `secretmanager.versions.add`, `.access`, and `.destroy`. A
custom role holds exactly those:

```bash
gcloud iam roles create hotUpdaterSecretsWriter --project=my-project \
  --title="Hot Updater secrets writer" \
  --permissions=secretmanager.secrets.get,secretmanager.secrets.update,secretmanager.versions.add,secretmanager.versions.access,secretmanager.versions.destroy
gcloud secrets add-iam-policy-binding hot-updater-asc-api-key --project=my-project \
  --role=projects/my-project/roles/hotUpdaterSecretsWriter \
  --member=user:you@example.com
```

## Read secrets in GitHub Actions

Create a Workload Identity pool and a provider for your repository, and let
the CI service account read the build's secrets:

```bash
gcloud iam workload-identity-pools create github --project=my-project \
  --location=global
gcloud iam workload-identity-pools providers create-oidc my-app \
  --project=my-project --location=global --workload-identity-pool=github \
  --issuer-uri=https://token.actions.githubusercontent.com \
  --attribute-mapping=google.subject=assertion.sub,attribute.repository=assertion.repository \
  --attribute-condition="assertion.repository == 'my-org/my-app'"
gcloud iam service-accounts create hot-updater-ci --project=my-project
gcloud iam service-accounts add-iam-policy-binding \
  hot-updater-ci@my-project.iam.gserviceaccount.com \
  --role=roles/iam.workloadIdentityUser \
  --member="principalSet://iam.googleapis.com/projects/PROJECT_NUMBER/locations/global/workloadIdentityPools/github/attribute.repository/my-org/my-app"
for secret in hot-updater-release-keystore hot-updater-play-service-account; do
  gcloud secrets add-iam-policy-binding "$secret" --project=my-project \
    --role=roles/secretmanager.secretAccessor \
    --member=serviceAccount:hot-updater-ci@my-project.iam.gserviceaccount.com
done
```

The job asks GitHub for an OIDC token (`id-token: write`), and
`google-github-actions/auth` writes the federation file the adapter reads.
Because the adapter is given the project, it signs in without looking the
project up, so the service account needs no Resource Manager role:

```yaml title=".github/workflows/native-release.yml (partial)"
permissions:
  contents: read
  id-token: write

# ...in the job, after npm ci:
- uses: google-github-actions/auth@7c6bc770dae815cd3e89ee6cdf493a5fab2cc093 # v3
  with:
    workload_identity_provider: projects/PROJECT_NUMBER/locations/global/workloadIdentityPools/github/providers/my-app
    service_account: hot-updater-ci@my-project.iam.gserviceaccount.com
- uses: gronxb/hot-updater/actions/native-build@v1.2.0
  with:
    platform: android
    scheme: release
    submit: play-internal
```

has the complete workflow.
