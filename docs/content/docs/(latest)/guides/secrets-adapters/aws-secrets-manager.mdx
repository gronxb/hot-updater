## Add the adapter

`secretsManager()` from `@hot-updater/aws`, the package of `s3Storage` and
`dynamoDB`, keeps each name as the secret `<prefix><name>` in AWS Secrets
Manager:

```package-install
npm install @hot-updater/aws --save-dev
```

```ts title="hot-updater.config.ts (partial)"
import { secretsManager } from "@hot-updater/aws";
import { defineConfig } from "hot-updater";

export default defineConfig({
  secrets: secretsManager({ region: "ap-northeast-2" }),
  // build, storage, database and plugins stay as they are
});
```

| Option        | Default          | What it does                                                                                                     |
| ------------- | ---------------- | ---------------------------------------------------------------------------------------------------------------- |
| `region`      | Required         | The region the secrets are in                                                                                    |
| `prefix`      | `"hot-updater/"` | Put before each name: `secret("asc-api-key")` reads the secret `hot-updater/asc-api-key`                            |
| `credentials` | The SDK's chain  | `{ accessKeyId, secretAccessKey, sessionToken? }`, or a function that returns them |
| `endpoint`    | The region's     | An HTTPS endpoint, such as a VPC endpoint                                                                        |

Each secret holds one value: a credential is one
[JSON value](/docs/concepts/secrets#sign-native-builds-with-secrets), and a
binary secret reads as its base64. The AWS SDK loads on the first read or
write, so a config that only uses `s3Storage` never loads it, and the
providers' Lambda and init builds don't include it.

- A secret that does not exist, or has no `AWSCURRENT` version, reads as
  missing.
- A missing permission fails the command, naming the action the identity
  needs; expired or invalid credentials fail it with how to sign in again; a
  secret scheduled for deletion fails it with the
  `aws secretsmanager restore-secret` command that brings it back.
- `set` puts a new version of the secret, and creates it with the
  description "Stored by Hot Updater." when it does not exist. It adds no
  tags. AWS moves `AWSCURRENT` to the new version, keeps the previous one as
  `AWSPREVIOUS`, and removes older versions itself.
- Values never go on a command line, and every value it reads or stores,
  and the secret key of the `credentials` you pass, is masked in the CLI's
  output.

Without `credentials`, the AWS SDK finds them itself: `AWS_ACCESS_KEY_ID`
and its siblings, which `aws-actions/configure-aws-credentials` sets in
GitHub Actions, then a profile, AWS SSO, or an instance role. Only one of
`AWS_ACCESS_KEY_ID` and `AWS_SECRET_ACCESS_KEY` set is an error, not a reason
to try a profile:

```bash
aws sso login --profile release
AWS_PROFILE=release npx hot-updater apple login
```

## Grant least privilege

CI only reads. Give its role `secretsmanager:GetSecretValue` on the prefix:

```json title="IAM policy: read"
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": "secretsmanager:GetSecretValue",
      "Resource": "arn:aws:secretsmanager:ap-northeast-2:123456789012:secret:hot-updater/*"
    }
  ]
}
```

Whoever stores secrets, with `secrets put` or a sign-in that issues a key,
also needs `secretsmanager:PutSecretValue`, and `secretsmanager:CreateSecret`
for a secret that does not exist yet. `GetSecretValue` stays: a sign-in
reads the key back after storing it.

```json title="IAM policy: read and store"
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": [
        "secretsmanager:GetSecretValue",
        "secretsmanager:PutSecretValue",
        "secretsmanager:CreateSecret"
      ],
      "Resource": "arn:aws:secretsmanager:ap-northeast-2:123456789012:secret:hot-updater/*"
    }
  ]
}
```

Secrets Manager encrypts with the account's `aws/secretsmanager` key unless
you choose another. A secret encrypted with a customer managed KMS key also
needs `kms:Decrypt` on that key to read, and `kms:GenerateDataKey` to store,
in the identity's policy or the key's.

## Read secrets in GitHub Actions

[GitHub Actions OIDC](https://docs.github.com/en/actions/how-tos/secure-your-work/security-harden-deployments/oidc-in-aws)
exchanges the workflow's identity for short-lived credentials of a role, so
the repository stores no AWS key. Trust the role only from the expected
repository and environment:

```json title="IAM role trust policy"
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": {
        "Federated": "arn:aws:iam::123456789012:oidc-provider/token.actions.githubusercontent.com"
      },
      "Action": "sts:AssumeRoleWithWebIdentity",
      "Condition": {
        "StringEquals": {
          "token.actions.githubusercontent.com:aud": "sts.amazonaws.com",
          "token.actions.githubusercontent.com:sub": "repo:example/app:environment:production"
        }
      }
    }
  ]
}
```

Attach the read policy to the role, and let the workflow request an ID token:

```yaml title=".github/workflows/native-release.yml (partial)"
permissions:
  contents: read
  id-token: write

# ...in the job, after npm ci:
- uses: aws-actions/configure-aws-credentials@e6de054238d6b7531b4efff3b6587d9aade6a06c # v6
  with:
    role-to-assume: arn:aws:iam::123456789012:role/hot-updater-ci
    aws-region: ap-northeast-2
- uses: gronxb/hot-updater/actions/native-build@v1.2.0
  with:
    platform: ios
    scheme: release
    submit: testflight
```

Keep the role away from pull request workflows that run untrusted code.
[Build and upload from CI](/docs/guides/ci-native-build#read-secrets-from-a-secrets-store)
has the complete workflow.
