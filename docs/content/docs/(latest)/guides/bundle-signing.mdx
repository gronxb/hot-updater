## Why Bundle Signing?

Bundle signing lets the native app reject an OTA artifact whose signed bytes
were changed or were not authorized by the configured signing key. Hot Updater
uses RSA-SHA256 signatures and embeds only the public key in the app.

Signing authenticates artifact content. It does not authorize release
targeting, prevent rollback to an older correctly signed artifact, or replace
review and access controls around publishing.

The private key is the deployment authority. Local PEM signing is the standard
baseline when the deploy environment protects that key. When your threat model
requires stronger custody, prefer a remote signing service where the private
key is non-exportable and the deploy process submits only a message to sign.

| Signer           | Use case            | Custody                                           |
| ---------------- | ------------------- | ------------------------------------------------- |
| Local PEM        | Standard baseline   | Exportable key managed by your deploy environment |
| AWS KMS          | Hardened production | Non-exportable AWS KMS key                        |
| Google Cloud KMS | Hardened production | Non-exportable Google Cloud KMS key               |
| Remote endpoint  | Service-dependent   | Defined by the compatible signing service         |

Local PEM signing is the normal industry baseline used by systems such as Expo
and CodePush when the deploy environment protects the private key. KMS signing
is a hardened option when non-exportable custody and workload identity justify
the additional provider setup. GitHub Actions is an identity source rather
than a signing service; use its OIDC token with a compatible KMS signer.

> **Important**: Release a native app containing the public key before you
> deploy signed bundles. An app without the matching public key rejects them.

## Choose and Roll Out a Signer

Signing is independent of storage and database selection. Cloudflare and
Supabase users can call AWS KMS or Google Cloud KMS directly from the protected
deploy job; do not proxy KMS through a Worker or Edge Function. Use local PEM
signing when its simpler exportable-key custody fits your threat model.

`hot-updater init` does not create or enable a signing key. Signing remains an
explicit opt-in:

1. Provision a dedicated RSA signing key for each app and environment, and pin
   its exact identifier or immutable version when the provider supports one.
2. Export its SPKI public key to `keys/public-key.pem` and commit that file
   for public-key-only builds. Local signing can also derive it from the private key.
3. Enable the built-in local config or add the matching signing plugin to
   `hot-updater.config.ts`.
4. Run `npx hot-updater keys export-public`, or `npx expo prebuild` for Expo.
5. Release the native app, then begin signed OTA deployments.

All official signers require RSA keys of at least 2048 bits. Prefer 3072 or
4096 bits for newly provisioned keys.

## Hardened: AWS KMS

[AWS KMS asymmetric keys](https://docs.aws.amazon.com/kms/latest/developerguide/symmetric-asymmetric.html)
perform signing without returning the private key. Create an RSA key with
`SIGN_VERIFY` usage, export its public key, and give the deploy identity only
the permissions it needs to use that key.

### 1. Create the signing key

The following example creates a 4096-bit RSA key and writes its public key as
SPKI PEM. The public key is not secret.

```bash
mkdir -p keys

KEY_ARN=$(aws kms create-key \
  --key-spec RSA_4096 \
  --key-usage SIGN_VERIFY \
  --description "Hot Updater bundle signing" \
  --query KeyMetadata.Arn \
  --output text)

aws kms get-public-key \
  --key-id "$KEY_ARN" \
  --query PublicKey \
  --output text \
  | openssl base64 -d -A \
  | openssl pkey -pubin -inform DER -out keys/public-key.pem
```

Save the immutable key ARN in deployment configuration. Do not use an alias
that can silently move to another key: its public key would no longer match
the key embedded in existing apps.

### 2. Keep the public key with the project

Ignore only a legacy local private key, not the entire directory:

```txt title=".gitignore"
keys/private-key.pem
```

Commit `keys/public-key.pem`. Expo and native builds need this public file, and
there is no security benefit in hiding it. If your existing `.gitignore`
contains `keys/`, remove that entry or add an exception for the public key.

### 3. Configure the provider

Install the optional AWS KMS SDK in the project that runs the deploy command:

```bash
npm install @aws-sdk/client-kms --save-dev
```

```ts title="hot-updater.config.ts"
import { defineConfig } from "hot-updater";
import { awsKmsSigning } from "hot-updater/signing";

export default defineConfig({
  // ...other config
  signing: awsKmsSigning({
    // A key ARN is an identifier, not a secret. Pin the exact key.
    keyId:
      "arn:aws:kms:ap-northeast-2:123456789012:key/00000000-0000-0000-0000-000000000000",
    region: "ap-northeast-2",
    publicKeyPath: "./keys/public-key.pem",
  }),
});
```

`awsKmsSigning` uses the AWS SDK default credential chain. Prefer a short-lived
workload identity instead of putting long-lived credentials in
`hot-updater.config.ts`. An explicit HTTPS `endpoint` is available for private
KMS endpoints; HTTP is accepted only for loopback testing.

Hot Updater compares provider signatures with `publicKeyPath` before upload.
A mismatched provider, public key, or algorithm fails the deployment.

### 4. Embed the public key and release the app

For React Native CLI projects, write the public key to the native projects:

```bash
npx hot-updater keys export-public
```

For Expo projects, run prebuild. The Expo config plugin reads only the checked-in
public key in provider mode; it does not need AWS credentials or private key
material.

```bash
npx expo prebuild
```

Then build and release the native app before the first signed OTA deployment.

### 5. Deploy with GitHub Actions OIDC

Use [GitHub Actions OIDC](https://docs.github.com/en/actions/how-tos/secure-your-work/security-harden-deployments/oidc-in-aws)
to exchange the workflow identity for short-lived AWS credentials. Restrict
the IAM trust policy to the expected repository and protected branch, tag, or
GitHub environment.

For signing, the deploy role needs access only to the pinned key. Add storage
and database permissions separately for the providers used by your project.

```json title="IAM policy"
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": "kms:GetPublicKey",
      "Resource": "arn:aws:kms:ap-northeast-2:123456789012:key/00000000-0000-0000-0000-000000000000"
    },
    {
      "Effect": "Allow",
      "Action": "kms:Sign",
      "Resource": "arn:aws:kms:ap-northeast-2:123456789012:key/00000000-0000-0000-0000-000000000000",
      "Condition": {
        "StringEquals": {
          "kms:MessageType": "RAW",
          "kms:SigningAlgorithm": "RSASSA_PKCS1_V1_5_SHA_256"
        }
      }
    }
  ]
}
```

```yaml title=".github/workflows/deploy.yml"
permissions:
  contents: read
  id-token: write

jobs:
  deploy:
    runs-on: ubuntu-latest
    environment: production
    steps:
      - name: Check out the reviewed source
        uses: actions/checkout@d23441a48e516b6c34aea4fa41551a30e30af803 # v6

      - name: Set up Node.js
        uses: actions/setup-node@249970729cb0ef3589644e2896645e5dc5ba9c38 # v6
        with:
          cache: npm
          node-version: 22

      - name: Install the locked dependency graph
        run: npm ci

      - name: Authenticate to AWS
        uses: aws-actions/configure-aws-credentials@e6de054238d6b7531b4efff3b6587d9aade6a06c # v6
        with:
          role-to-assume: arn:aws:iam::123456789012:role/hot-updater-deploy
          aws-region: ap-northeast-2

      - name: Deploy signed bundle
        run: npx --no-install hot-updater deploy -p ios
```

Use environment protection rules and required reviewers for the signing job.
The example pins actions to the commits behind their v6 releases; review and
update those pins deliberately when upgrading.

KMS prevents private-key extraction, but it cannot decide whether code is safe.
Any dependency or script running with `kms:Sign` can request signatures. Treat
the build and deploy dependency graph as part of the trusted signing boundary,
and run the signing workflow only from reviewed protected refs. Avoid granting
signing credentials to pull-request workflows, especially
`pull_request_target` jobs that execute untrusted code.

## Signing Protocol and Remote Calls

Hot Updater signs the 32 decoded bytes of each SHA-256 file hash using
RSA PKCS#1 v1.5 with SHA-256. The AWS KMS provider therefore uses:

- `MessageType: RAW`
- `SigningAlgorithm: RSASSA_PKCS1_V1_5_SHA_256`
- the decoded file-hash bytes as `Message`

Do not substitute `DIGEST` or an RSA-PSS algorithm. Existing iOS and Android
verifiers expect the exact protocol above.

Google Cloud KMS preserves the same signature semantics by submitting
`SHA-256(message)` to its digest API.

`remoteSigning` uses the authenticated `/_hot-updater/signing` protocol.
Requests and responses pin the protocol version, RSA-SHA256 algorithm, and
SHA-256 fingerprint of the SPKI public key. The client rejects redirects and
locally verifies every returned signature.

Use `remoteSigning` for a compatible signing service that is not represented by
an official provider plugin. The endpoint URL is normalized to the managed
signing path, and the dedicated token defaults to
`HOT_UPDATER_SIGNING_TOKEN`.

Use a separate signing key and token for each app and environment. Possession
of a remote signing token grants an online signing oracle for arbitrary
32-byte content-hash messages. The signature authenticates only artifact
content; app, environment, platform, channel, targeting, release context, and
rollback policy are not included in the signed message. Enforce those controls
in the protected deployment workflow and do not share a signer across trust
boundaries.

```ts title="hot-updater.config.ts"
import { defineConfig } from "hot-updater";
import { remoteSigning } from "hot-updater/signing";

export default defineConfig({
  // ...other config
  signing: remoteSigning({
    endpoint: "https://signer.example.com",
    publicKeyPath: "./keys/public-key.pem",
  }),
});
```

A custom service can mount the matching Web API handler from the root
`@hot-updater/plugin-core` entrypoint. Keep key access inside the `sign`
callback and return `404` for unrelated routes:

```ts title="signing-service.ts"
import { createBundleSigningHandler } from "@hot-updater/plugin-core";

export const handleRequest = async (request: Request, env: Env) =>
  (await createBundleSigningHandler({
    request,
    publicKey: env.HOT_UPDATER_SIGNING_PUBLIC_KEY,
    token: env.HOT_UPDATER_SIGNING_TOKEN,
    sign: (message) => env.signWithKmsOrHsm(message),
  })) ?? new Response("Not found", { status: 404 });
```

The handler authenticates both metadata and signing requests, accepts only the
versioned 32-byte signing contract, and verifies the returned signature before
responding. Key isolation, authorization, rate limits, and audit logging remain
the responsibility of the service and its `sign` implementation.

Remote providers receive one request for each distinct signed hash. Repeated
identical hashes are memoized, including hashes shared by multiple artifact
references. Resolving the provider public key adds a separate request. Account
for KMS latency, request quotas, availability, and cost. Provider errors fail
the deployment; Hot Updater does not fall back to an unsigned bundle.

## Hardened: Google Cloud KMS

Google Cloud projects, including Firebase projects, can use Cloud KMS without
exporting the private key. Pin a full CryptoKeyVersion resource name; a moving
alias would stop matching the public key embedded in installed apps.

Create an asymmetric signing key version using an RSA PKCS#1 SHA-256 algorithm,
then export only that version's public key:

```bash
mkdir -p keys

gcloud kms keyrings create hot-updater --location=global
gcloud kms keys create bundle-signing \
  --location=global \
  --keyring=hot-updater \
  --purpose=asymmetric-signing \
  --default-algorithm=rsa-sign-pkcs1-4096-sha256
gcloud kms keys versions get-public-key 1 \
  --location=global \
  --keyring=hot-updater \
  --key=bundle-signing \
  --output-file=keys/public-key.pem
```

```bash
npm install @google-cloud/kms --save-dev
```

`@google-cloud/kms` 6 requires Node.js 22 or later. This requirement applies
only to deploy environments that use `googleCloudKmsSigning`; the other signing
options retain Hot Updater's Node.js 20.19 baseline.

```ts title="hot-updater.config.ts"
import { defineConfig } from "hot-updater";
import { googleCloudKmsSigning } from "hot-updater/signing";

export default defineConfig({
  // ...other config
  signing: googleCloudKmsSigning({
    keyVersion:
      "projects/PROJECT/locations/LOCATION/keyRings/RING/cryptoKeys/KEY/cryptoKeyVersions/1",
    publicKeyPath: "./keys/public-key.pem",
  }),
});
```

The provider uses Application Default Credentials. Locally, authenticate ADC;
in Google Cloud, use an attached service account; in GitHub Actions, use
Workload Identity Federation. Grant the key-level
`roles/cloudkms.signerVerifier` role, or a custom role limited to signing and
reading the public key. Only RSA PKCS#1 SHA-256 key versions are accepted.

## Expo and EAS Build

Expo embeds the public key during `expo prebuild`:

```ts title="hot-updater.config.ts"
import { defineConfig } from "hot-updater";
import { awsKmsSigning } from "hot-updater/signing";

export default defineConfig({
  signing: awsKmsSigning({
    keyId: "arn:aws:kms:REGION:ACCOUNT_ID:key/KEY_ID",
    region: "REGION",
    publicKeyPath: "./keys/public-key.pem",
  }),
  // ...other config
});
```

When prebuild runs, the `@hot-updater/expo` config plugin:

1. Reads `publicKeyPath`
2. Validates the public key
3. Embeds it in the iOS and Android native configuration

With a signing plugin or an explicit local `publicKeyPath`, EAS does not need
the private key or KMS signing credentials. Do not upload a
private key with EAS Secrets, add it to `eas.json`, or use `.easignore` to send
`keys/private-key.pem` to the build worker. Ensure `keys/public-key.pem` is
included in the build input.

## Local Private Key

Use the built-in local config when you accept responsibility for an exportable
private key. The v0 usage is unchanged: enable signing and provide the private
key path. No signing plugin or separate public key file is required to sign:

```ts title="hot-updater.config.ts"
import { defineConfig } from "hot-updater";

export default defineConfig({
  signing: {
    enabled: true,
    privateKeyPath: "./keys/private-key.pem",
  },
  // ...other config
});
```

Omit `signing` or set `signing: { enabled: false }` to disable signing. A local
config without `enabled: true` does not automatically enable signing.

`publicKeyPath` is optional for local signing. Set it to pin the expected key
and let Expo/native builds read only the public file. If supplied, the file
must exist and match the signing private key; an invalid or mismatched pin is
an error, not a reason to fall back. AWS/GCP/remote signing plugins still require
this path.

For a public-key-only build and a CI-specific private key location:

```ts title="hot-updater.config.ts"
import { defineConfig } from "hot-updater";

export default defineConfig({
  signing: {
    enabled: true,
    privateKeyPath:
      process.env.HOT_UPDATER_SIGNING_PRIVATE_KEY_PATH ??
      "./keys/private-key.pem",
    publicKeyPath: "./keys/public-key.pem",
  },
  // ...other config
});
```

Without `publicKeyPath`, `keys export-public` and `doctor` derive the public
key from `privateKeyPath`, falling back to the generated `public-key.pem` in
the same directory when the private key cannot be read. Signing itself always
requires the configured private key.

Expo also preserves the v0 source order when `publicKeyPath` is omitted:
`HOT_UPDATER_PRIVATE_KEY` (PEM or file path), then `privateKeyPath`, then the
generated sibling public key. The environment variable is a prebuild
compatibility feature, not a deploy signing-key override. Ensure it matches
the deployment key. Prefer an explicit `publicKeyPath` for EAS so native builds
do not need private material; it takes precedence over those legacy sources.

Generate a local pair only when you accept responsibility for backing up and
protecting the exportable private key:

```bash
npx hot-updater keys generate --output ./keys --key-size 4096
```

The command creates `private-key.pem` with owner-only permissions and
`public-key.pem`. It refuses to replace an existing key pair. Keep the private
file out of Git, EAS build inputs, artifacts, caches, and logs. Keep and commit
the public file and set `publicKeyPath` so Expo can embed it without reading
the private key.

For CI, use a protected secret manager and materialize the private file
only outside the workspace for the duration of the trusted signing job. A PEM
retrieved from a secret manager is still available to that process and is less
isolated than a KMS or HSM-backed remote signer.

If local PEM custody is required in GitHub Actions, store it as a secret in a
protected GitHub Environment with required reviewers. Write the secret beneath
`runner.temp`, keep the checked-in public key path explicit, and remove the
temporary file even when deployment fails. Avoid a broadly available
repository or organization secret for production signing authority.

```yaml title=".github/workflows/deploy.yml"
jobs:
  deploy:
    runs-on: ubuntu-latest
    environment: production
    permissions:
      contents: read
    env:
      HOT_UPDATER_SIGNING_PRIVATE_KEY_PATH: ${{ runner.temp }}/hot-updater-signing/private-key.pem
    steps:
      - uses: actions/checkout@d23441a48e516b6c34aea4fa41551a30e30af803 # v6
      - uses: actions/setup-node@249970729cb0ef3589644e2896645e5dc5ba9c38 # v6
        with:
          node-version: 22

      - run: npm ci

      - name: Materialize the signing key
        env:
          HOT_UPDATER_SIGNING_PRIVATE_KEY: ${{ secrets.HOT_UPDATER_SIGNING_PRIVATE_KEY }}
        run: |
          install -m 700 -d "$(dirname "$HOT_UPDATER_SIGNING_PRIVATE_KEY_PATH")"
          printf '%s' "$HOT_UPDATER_SIGNING_PRIVATE_KEY" > "$HOT_UPDATER_SIGNING_PRIVATE_KEY_PATH"
          chmod 600 "$HOT_UPDATER_SIGNING_PRIVATE_KEY_PATH"

      - run: npx --no-install hot-updater deploy -p ios

      - name: Remove the signing key
        if: always()
        run: rm -f "$HOT_UPDATER_SIGNING_PRIVATE_KEY_PATH"
```

Prefer GitHub OIDC with a KMS signer when available because the workflow then
receives short-lived signing authorization instead of exportable key material.

## Manual Public Key Configuration

`npx hot-updater keys export-public` writes the public key to:

- iOS: `Info.plist` → `HOT_UPDATER_PUBLIC_KEY`
- Android: application metadata in `AndroidManifest.xml` →
  `com.hotupdater.PUBLIC_KEY`

If either native project already contains a different or invalid public key,
the command prints the old and new fingerprints and defaults to cancelling the
replacement. Review the native-first rotation sequence below before accepting
the prompt. `--yes` explicitly accepts that trust-anchor replacement; it is not
required when the same key is already embedded.

For custom native paths, configure `platform`:

```ts title="hot-updater.config.ts"
export default defineConfig({
  platform: {
    android: {
      androidManifestPaths: [
        "android/app/src/main/AndroidManifest.xml",
        "android/app/src/prod/AndroidManifest.xml",
      ],
    },
    ios: {
      infoPlistPaths: ["ios/MyApp/Info.plist", "ios/MyAppPro/Info.plist"],
    },
  },
});
```

Or add the public key manually.

**iOS** (`Info.plist`):

```xml
<key>HOT_UPDATER_PUBLIC_KEY</key>
<string>-----BEGIN PUBLIC KEY-----\nMIIB...your-key...\n-----END PUBLIC KEY-----</string>
```

**Android** (`AndroidManifest.xml`, inside `<application>`):

```xml
<meta-data
    android:name="com.hotupdater.PUBLIC_KEY"
    android:value="-----BEGIN PUBLIC KEY-----\nMIIBIjANBgkq...your-key...\n-----END PUBLIC KEY-----" />
```

Remove embedded public keys with:

```bash
npx hot-updater keys remove [--yes]
```

## Console

The Hot Updater Console provides read-only inspection of bundle signing. It
reads the checked-in public key to show whether signing is configured, the
provider and algorithm, and the public-key fingerprint. It does not call the
remote signer or store, return, generate, activate, rotate, or delete private
keys.

For v0 local config without `publicKeyPath`, Console looks for the generated
`public-key.pem` beside the private key path, but never reads the private key.
If no public file is available, inspection is unavailable even though local
signing can still work. Supply `publicKeyPath` when the public file is elsewhere.

A hosted Console does not need KMS credentials or remote signing tokens for
this inspection. Do not grant its runtime permission to sign. Provider and
signature health are verified by the deploy command, which already runs inside
the trusted signing boundary.

## Configuration States

| `signing` config | Native public key     | Result                        |
| ---------------- | --------------------- | ----------------------------- |
| Omitted or local `enabled: false` | Not present | Normal unsigned updates |
| Omitted or local `enabled: false` | Present | Updates rejected |
| Local `enabled: true` or signing plugin | Present and matching | Signed updates verified |
| Local `enabled: true` or signing plugin | Missing or mismatched | Deployment or update rejected |

Config and native files must match. Hot Updater fails closed rather than
installing an unsigned or unverifiable update.

## Key Rotation

Hot Updater currently embeds one public key in each native app and the `sig:`
format does not include a key ID. Moving a KMS alias or replacing a PEM in place
is therefore not a safe transparent rotation: installed apps with the old
public key reject bundles signed by the new key.

For a planned migration:

1. Create a new signing key without changing the active key
2. Export and record its public-key fingerprint
3. Release a new native app containing the new public key
4. Keep the old signer available for updates targeting old app versions
5. Switch each supported app cohort only after it trusts the new public key
6. Retire the old signer after those cohorts no longer receive updates

Console inspection does not provide an Activate or Rotate action because the
current single-key protocol cannot make that operation safe. Seamless rotation
requires a future multi-key or key-ID protocol.

If the active private key is compromised, an OTA update cannot teach existing
apps to trust a new key safely. Disable the compromised signer, stop OTA
publishing, and release a new native app through the app store.

## Troubleshooting

### PublicKeyNotConfigured

The native app was released without a public key. Export or embed the public
key, rebuild the native app, and release it before deploying signed bundles.

### Signature Verification Failed

The provider, checked-in public key, and native public key must represent the
same key. Compare their SPKI SHA-256 fingerprints. With KMS, also verify that
the configured key ARN was not replaced with an alias and that it is an RSA
`SIGN_VERIFY` key.

### AWS KMS AccessDenied

Confirm that the deploy job received an OIDC role restricted to the expected
repository and environment, and that the role has `kms:GetPublicKey` and
`kms:Sign` on the exact key ARN.
