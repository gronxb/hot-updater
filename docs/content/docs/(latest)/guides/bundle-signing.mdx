## Why Bundle Signing?

Bundle signing lets the native app reject an OTA artifact whose signed bytes
were changed or were not authorized by the signing key. Hot Updater signs
with RSA-SHA256 and embeds only the public key in the app.

Signing authenticates artifact content. It does not authorize release
targeting, prevent rollback to an older correctly signed artifact, or replace
review and access controls around publishing.

The private key is the deployment authority: whoever can read it can publish
bundles every installed app accepts. Keep it in the config's
[`secrets` adapter](/docs/concepts/secrets), and give it only to the machines
and people that deploy.

> **Important**: Release a native app containing the public key before you
> deploy signed bundles. An app without the matching public key rejects them.

## Set Up Signing

<a id="local-private-key" />
<a id="choose-and-roll-out-a-signer" />

`hot-updater init` does not create or enable a signing key. Create one and
store it as the secret `bundle-signing-key`:

```bash
npx hot-updater secrets issue bundle-signing-key
```

The command creates an RSA key of 4096 bits, stores it through the config's
`secrets` adapter, reads it back, and prints its public key's fingerprint,
the SHA-256 of its SPKI. It adds the shorthand to a config without `signing`:

```ts title="hot-updater.config.ts"
import { defineConfig, secret } from "hot-updater";

export default defineConfig({
  signing: secret("bundle-signing-key"), // [!code ++]
  // ...other config
});
```

`signing: secret("bundle-signing-key")` is the shorthand of
`{ enabled: true, privateKey: secret("bundle-signing-key") }`. The secret
holds the RSA private key in PEM. With the default
[`localSecrets()`](/docs/guides/secrets-adapters/local-secrets) adapter it is
the `HOT_UPDATER_BUNDLE_SIGNING_KEY` environment variable, such as a CI
secret, or else the file the command stored in your home directory. A
`.env.hotupdater` value is one line: put the PEM in double quotes with `\n`
for its line breaks. The CLI reads the secret once per run, masks it in its
output, and keeps it in memory only. A deploy whose secret is missing fails
and names where it looked.

A key already stored is kept: installed apps reject bundles signed with a new
key. `--replace` creates a new one; follow [Key Rotation](#key-rotation)
first. Without a terminal, the command creates a key only in a team store,
since a key kept on a CI runner would be lost with it.

To store a key you already have instead, such as one in a file:

```bash
npx hot-updater secrets put bundle-signing-key ./keys/private-key.pem
```

It takes an RSA key of 2048 bits or more, PKCS#1 or PKCS#8, stores it as
PKCS#8, and prints the same fingerprint. The key stays the same, so installed
apps keep verifying its bundles.

Then embed the public key and release the app:

1. Run `npx hot-updater keys export-public` for React Native CLI projects.
   For Expo, export it to a file and set `publicKeyPath` in the
   `@hot-updater/expo` app plugin ([Expo and EAS Build](#expo-and-eas-build)).
2. Release the native app, then begin signed OTA deployments.

### Read the Key from a File

To keep the key in a file instead of a secret, set `privateKeyPath`:

```ts title="hot-updater.config.ts"
signing: {
  enabled: true,
  privateKeyPath: "./keys/private-key.pem",
},
```

Keep the file out of Git, EAS build inputs, artifacts, caches, and logs.

### Unsigned and Refused Configs

Without `signing`, bundles are unsigned, and `deploy` and `doctor` say so:

```txt
Bundles are unsigned.
To sign them, run: npx hot-updater secrets issue bundle-signing-key
```

`signing: { enabled: false }` turns signing off without the warning.

`signing` takes the shorthand, `{ enabled: true, privateKey: secret("<name>") }`,
`{ enabled: true, privateKeyPath }`, or `{ enabled: false }`. `deploy`
refuses any other value, rather than deploy unsigned bundles, and `doctor`
shows the same line:

```txt
signing takes secret("bundle-signing-key").
Store your key: npx hot-updater secrets put bundle-signing-key <key.pem>
```

The public key is derived from the private key. Keys are RSA of at least 2048
bits, with SPKI PEM public keys (`BEGIN PUBLIC KEY`). Deploy verifies the
native trust anchor before upload and rejects a missing, invalid, or
mismatched one.

This validation checks the current project's native files or evaluated Expo
configuration. It cannot inspect already installed binaries. A successful
deploy check does not replace releasing the native app with the matching public
key before targeting it with signed updates.

## Expo and EAS Build

Expo owns the native trust anchor through its app config plugin. If the public
key file is not already present, export it from the signing key configured in
`hot-updater.config.ts`:

```bash
npx hot-updater keys export-public --output ./keys/public-key.pem
```

It writes a new SPKI PEM file without changing native files. The output path must not exist; `--yes`
does not overwrite an existing file. For a key rotation, export to a new path
and follow [Key Rotation](#key-rotation) before switching the app's trust anchor.

Reference the public file in the Expo app config:

```jsonc title="app.json"
{
  "expo": {
    "plugins": [
      [
        "@hot-updater/expo",
        {
          "channel": "production",
          "publicKeyPath": "./keys/public-key.pem", // [!code ++]
        },
      ],
    ],
  },
}
```

Run prebuild after configuring the public key:

```bash
npx expo prebuild
```

`publicKeyPath` is relative to the Expo project root. During prebuild, the
plugin validates the RSA SPKI key and embeds it in the iOS and Android native
configuration. The file is also included automatically in both native
fingerprints, so changing the trust anchor requires a new native target. The
plugin evaluates `hot-updater.config.ts` for the update strategy, but reads the
trust anchor only from `publicKeyPath`. It does not read the signing key. Keep config evaluation independent of signing
credentials so native builds can run without them.

The deploy and doctor commands resolve the evaluated Expo config and compare
this trust anchor with the signing key's public key. Missing,
invalid, or mismatched keys fail closed, including in CNG projects without
checked-in `ios` or `android` directories.

Do not upload a private key with EAS Secrets, add it to `eas.json`, or use
`.easignore` to send `keys/private-key.pem` to the build worker. Ensure the
public key file is included in the build input.

Build and release the native app before deploying its first signed OTA bundle.

## Manual Public Key Configuration

For React Native CLI projects, export the signing key's public key into the
native projects:

```bash
npx hot-updater keys export-public
```

The command writes the public key to:

- iOS: `Info.plist` → `HOT_UPDATER_PUBLIC_KEY`
- Android: application metadata in `AndroidManifest.xml` →
  `com.hotupdater.PUBLIC_KEY`

If either native project already contains a different or invalid public key,
the command prints the old and new fingerprints and defaults to cancelling the
replacement. Review the native-first rotation sequence below before accepting
the prompt. `--yes` explicitly accepts that trust-anchor replacement; it is not
required when the same key is already embedded.

For custom native paths, configure `platform`:

```ts title="hot-updater.config.ts"
import { defineConfig } from "hot-updater";

export default defineConfig({
  // [!code ++:11]
  platform: {
    android: {
      androidManifestPaths: [
        "android/app/src/main/AndroidManifest.xml",
        "android/app/src/prod/AndroidManifest.xml",
      ],
    },
    ios: {
      infoPlistPaths: ["ios/MyApp/Info.plist", "ios/MyAppPro/Info.plist"],
    },
  },
});
```

Or add the public key manually.

**iOS** (`Info.plist`):

```xml title="ios/<your-app>/Info.plist"
<!-- [!code ++:2] -->
<key>HOT_UPDATER_PUBLIC_KEY</key>
<string>-----BEGIN PUBLIC KEY-----\nMIIB...your-key...\n-----END PUBLIC KEY-----</string>
```

**Android** (`AndroidManifest.xml`, inside `<application>`):

```xml title="android/app/src/main/AndroidManifest.xml"
<!-- [!code ++:3] -->
<meta-data
    android:name="com.hotupdater.PUBLIC_KEY"
    android:value="-----BEGIN PUBLIC KEY-----\nMIIBIjANBgkq...your-key...\n-----END PUBLIC KEY-----" />
```

Build and release the native app before deploying its first signed OTA bundle.

For React Native CLI projects, remove embedded public keys with:

```bash
npx hot-updater keys remove [--yes]
```

For Expo, remove `publicKeyPath` from the `@hot-updater/expo` app plugin and
run `npx expo prebuild`. The plugin removes the embedded keys; `keys remove`
alone does not change the Expo configuration and prebuild would restore them.

Removing the key from local native files does not change already installed
apps; they still require signed bundles. To disable verification for a future
native release, remove the key, rebuild, and release that app before targeting
it with unsigned bundles.

## Keep the Public Key with the Project

If `.gitignore` contains `keys/`, replace that whole-directory rule with rules
that include only the public file before committing it:

```txt title=".gitignore"
# [!code --]
keys/
# [!code ++:2]
keys/*
!keys/public-key.pem
```

For EAS uploads, copy your existing `.gitignore` rules into `.easignore`, then
append these rules to include only the public key ([EAS ignore-file
documentation](https://docs.expo.dev/build-reference/easignore/)):

```txt title=".easignore"
# Keep your existing ignore rules above
# [!code ++:3]
!/keys/
/keys/*
!/keys/public-key.pem
```

Existing ignore rules are not rewritten automatically.

## Deploy from CI

With `signing: secret("bundle-signing-key")` and `localSecrets()`, give the
deploy job the key as `HOT_UPDATER_BUNDLE_SIGNING_KEY`. No key file is written.

In GitHub Actions, store the key as a secret in a protected GitHub
Environment with required reviewers, rather than a repository or
organization secret every workflow can read.

```yaml title=".github/workflows/deploy.yml"
on:
  workflow_dispatch:

jobs:
  deploy:
    runs-on: ubuntu-latest
    environment: production
    permissions:
      contents: read
    steps:
      - uses: actions/checkout@d23441a48e516b6c34aea4fa41551a30e30af803 # v6
      - uses: actions/setup-node@249970729cb0ef3589644e2896645e5dc5ba9c38 # v6
        with:
          node-version: 22

      - run: npm ci

      - run: npx --no-install hot-updater deploy -p ios
        env:
          HOT_UPDATER_BUNDLE_SIGNING_KEY: ${{ secrets.HOT_UPDATER_BUNDLE_SIGNING_KEY }}
```

With another `secrets` adapter, the job authenticates to that store as its
guide shows, and the CLI reads `bundle-signing-key` from it.

## Console

Configure signing and manage keys through the Hot Updater CLI. Local and
hosted Consoles do not inspect signing configuration or manage signing keys,
and a hosted Console needs no signing key. The deploy command checks the key
where it deploys.

## Configuration States

| `signing` config                 | Native public key     | Result                                  |
| -------------------------------- | --------------------- | --------------------------------------- |
| Omitted                          | Not present           | Unsigned updates, with a deploy warning |
| `enabled: false`                 | Not present           | Unsigned updates                        |
| Omitted or `enabled: false`      | Present               | Updates rejected                        |
| `secret(...)` or `enabled: true` | Present and matching  | Signed updates verified                 |
| `secret(...)` or `enabled: true` | Missing or mismatched | Deployment or update rejected           |
| Any other value                  | Any                   | Deployment refused                      |

Config and native files must match. Hot Updater fails closed rather than
installing an unsigned or unverifiable update.

## Key Rotation

Hot Updater currently embeds one public key in each native app and the `sig:`
format does not include a key ID. Replacing the key in place is therefore not
a safe transparent rotation: installed apps with the old public key reject
bundles signed by the new key.

For a planned migration:

1. Create a new signing key under a new name, such as
   `npx hot-updater secrets issue bundle-signing-key bundle-signing-key-2`,
   without changing the active key
2. Export and record its public-key fingerprint
3. Release a new native app containing the new public key
4. Keep the old key available for updates targeting old app versions, using
   matching signing keys and non-overlapping app-version or fingerprint targets
5. Switch each supported app cohort only after it trusts the new public key
6. Retire the old key after those cohorts no longer receive updates

Seamless rotation requires a future multi-key or key-ID protocol.

If the active private key is compromised, an OTA update cannot teach existing
apps to trust a new key safely. Revoke the compromised key's secret, stop OTA
publishing, and release a new native app through the app store.

## Troubleshooting

### PublicKeyNotConfigured

The native app was released without a public key. Export or embed the public
key, rebuild the native app, and release it before deploying signed bundles.

### Signature Verification Failed

The signing key's public key and the embedded native public key must match.
If using Expo, verify `publicKeyPath` in the `@hot-updater/expo` app plugin.
Compare its SPKI SHA-256 fingerprint with the one `secrets issue` or
`secrets put` printed for the signing key.
