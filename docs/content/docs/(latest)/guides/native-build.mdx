## Overview

`hot-updater build:android` and `hot-updater build:ios` build the native app
from a scheme in `hot-updater.config.ts`. Each build compiles in the values
that select its OTA updates, and prints them with the artifact:

| Value         | What the build compiles in                                                                         |
| ------------- | -------------------------------------------------------------------------------------------------- |
| Artifact      | The `.apk`, `.aab`, `.ipa` or simulator `.app`, copied to the output path                          |
| Min bundle ID | The ID of the bundle built into the app, which only newer bundles replace (the nil UUID in Debug)  |
| Fingerprint   | The native fingerprint, with the [fingerprint strategy](/docs/guides/update-strategies/fingerprint) |
| App version   | The native app version, with the [app version strategy](/docs/guides/update-strategies/app-version) |
| Channel       | The default channel that [`channel set`](/docs/guides/channel-management) wrote                    |

The build reads the app version and channel from the artifact it built, so
the values a flavor, build type, `versionNameSuffix`, `xcconfig` or
`extraParams` sets are the ones it reports. On Android it reads them with the
SDK's `aapt2`.

`hot-updater run:android` and `hot-updater run:ios` build the same schemes and
install the app on a device, emulator or simulator.

## Prerequisites

- The platform toolchain: the Android SDK and the project's Gradle wrapper, or
  Xcode with CocoaPods.
- A Hot Updater setup that a release build already passes: the
  [App Setup](/docs/get-started/app-setup) native integration and the
  [default channel](/docs/guides/channel-management).
- With the fingerprint strategy, the build updates `fingerprint.json` before
  it compiles. With the app version strategy, delete any `fingerprint.json` first
  (`hot-updater doctor --fix` does), or the app reports the fingerprint
  strategy.

## Configure schemes

Add one scheme per artifact under `nativeBuild.android` and `nativeBuild.ios`.
Keep the other settings of `hot-updater.config.ts` as they are.

```ts title="hot-updater.config.ts (partial)"
import { defineConfig } from "hot-updater";

export default defineConfig({
  // build, storage, database and plugins stay as they are
  nativeBuild: {
    android: {
      release: {
        packageName: "com.example.app",
        // An .aab by default; aab: false builds an .apk.
        signing: { keystore: "vault:release-keystore" },
      },
      previewApk: {
        packageName: "com.example.app",
        aab: false,
        signing: { keystore: "vault:release-keystore" },
      },
    },
    ios: {
      release: {
        bundleIdentifier: "com.example.app",
        scheme: "ExampleApp",
        installPods: true,
        signing: { ascApiKey: "vault:asc-api-key" },
      },
      simulator: {
        bundleIdentifier: "com.example.app",
        scheme: "ExampleApp",
        installPods: true,
        simulator: true,
      },
    },
  },
});
```

Android schemes build the `Release` variant unless `variant` names another,
such as `stagingRelease`. iOS schemes build the `Release` configuration unless
`configuration` names another.

An iOS scheme without `simulator` archives the app and exports an `.ipa`. It
needs `signing.ascApiKey`, which exports for App Store Connect, or an
`exportOptionsPlist` for another export method.

## Provide signing credentials

`signing` names a secret in the
[console's vault](/docs/guides/console-deployment/vault) as `vault:<name>`,
which the CLI resolves while it builds. The build resolves it only when it
signs: a Debug variant keeps the debug keystore, and a simulator build signs
nothing. A scheme without `signing` keeps the project's own signing settings.

The CLI reaches the vault with `HOT_UPDATER_CONSOLE_URL` and
`HOT_UPDATER_VAULT_TOKEN`, a token whose scope allows `read` on the secret.
[Secrets in the CLI](/docs/guides/secrets) covers storing secrets and
issuing tokens.

These environment variables override the vault for one credential: when any
of a credential's variables is set, the build reads that credential from them
and never asks the console for it.

| Credential      | Environment variables                                                                                                                                   |
| --------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Android keystore | `HOT_UPDATER_ANDROID_KEYSTORE_PATH` (or `HOT_UPDATER_ANDROID_KEYSTORE_BASE64`), `HOT_UPDATER_ANDROID_KEYSTORE_PASSWORD`, `HOT_UPDATER_ANDROID_KEY_ALIAS`, `HOT_UPDATER_ANDROID_KEY_PASSWORD` |
| App Store Connect API key | `HOT_UPDATER_ASC_KEY_PATH` (or `HOT_UPDATER_ASC_KEY`, the `.p8` contents), `HOT_UPDATER_ASC_KEY_ID`, `HOT_UPDATER_ASC_ISSUER_ID`                  |

The CLI writes a keystore or key given as contents to a temporary file that
only your user can read, and deletes it when the build ends. It masks passwords
in its output.

The Android build passes the keystore to Gradle as the signing properties
Android Studio uses for signed builds, so it signs both `.apk` and `.aab`
whatever the variant's `signingConfig` says. The iOS build signs with automatic
signing: `xcodebuild` uses the App Store Connect API key to create or update
certificates and provisioning profiles. The Xcode project needs its
development team (`DEVELOPMENT_TEAM`), in the project or in `extraParams`.

## Build

```package-install
npx hot-updater build:android --scheme release
```

```package-install
npx hot-updater build:ios --scheme simulator
```

The build copies its output to `.hot-updater/output/build/<platform>/<scheme>`,
or to `--output-path`, and prints the artifact and its values:

```txt
◆  Built Android bare
    Artifact:      /path/to/app/.hot-updater/output/build/android/release/app-release.aab
    Kind:          aab
    Min bundle ID: 019a0f8e-7c41-7000-8000-02c5f1a9e3b7
    Fingerprint:   4f1c0d6b2e9a…
    Channel:       production
```

A Debug build reports the nil UUID as its min bundle ID, as its native SDK
does: an Android variant or iOS configuration whose name ends in `Debug`.

Every build gets its own min bundle ID: an iOS and an Android build never
share one, and two builds of one platform get different IDs even when they
start in the same millisecond.

Install a simulator `.app` with
`xcrun simctl install booted <path-to-app>`, and an `.apk` with
`adb install <path-to-apk>`.

## Register a build

Add `--register` to record a release build in the native build registry of
the server that `database` and `storage` in `hot-updater.config.ts` name, with
the same credentials `hot-updater deploy` uses:

```package-install
npx hot-updater build:android --scheme release --register
```

After the build, the CLI:

1. Takes the JavaScript bundle the native build compiled in out of the
   artifact, byte for byte: `assets/index.android.bundle` in an `.apk`,
   `base/assets/index.android.bundle` in an `.aab`, and `main.jsbundle` in an
   `.ipa` or `.app`.
2. Uploads the artifact to `native-builds/<platform>/<build id>/` in your
   storage. A simulator `.app` is uploaded as one `.app.zip` archive.
3. Uploads that JavaScript bundle as the build's built-in bundle: a bundle
   whose ID is the build's min bundle ID and whose manifest lists only that
   file, at the path an OTA bundle's manifest gives it (`index.ios.bundle` or
   `index.android.bundle`), in the shared asset storage.
4. Registers the build and its built-in bundle in one database write. When
   that write fails, the CLI deletes the uploaded artifact again; the built-in
   bundle's files are left to `storage prune`.

A registered build is found by its platform, its default channel, and its
fingerprint or, with the app version strategy, its exact app version: the
newest build of that scope.

The built-in bundle is not an OTA update. No Release publishes it, so no
device downloads it, and no update check changes. The bundle totals leave it
out, a release of it and its deletion are refused, `hot-updater doctor --fix`
keeps it, and `storage prune` keeps its files and the artifact.

A Debug build loads its JavaScript from Metro and has no built-in bundle, so
`--register` refuses it. A self-hosted server reached through
`standaloneRepository` needs the native build routes of this release's
`@hot-updater/server`; an older one answers `404`, and the CLI asks you to
upgrade it before it uploads anything.

Every official storage adapter streams the artifact to storage except
`standaloneStorage`, which reads it into memory to post it to your server. A
Supabase project's Storage upload file size limit, 50 MB on the Free plan,
caps the artifact size.

## Upload to TestFlight

Add `--upload testflight` to upload the `.ipa` to App Store Connect, which
lists it in TestFlight:

```package-install
npx hot-updater build:ios --scheme release --upload testflight
```

The upload authenticates with an App Store Connect API key: the scheme's
`signing.ascApiKey`, or else the vault's `asc-api-key` secret. The
`HOT_UPDATER_ASC_KEY*` environment variables in
[Provide signing credentials](#provide-signing-credentials) override it. The
CLI resolves the key before the build starts, so a missing key fails before
the build does, and deletes the key's temporary file when the upload ends.
Certificates and provisioning profiles stay with the build's signing.

Before it builds, the CLI refuses a scheme whose build App Store Connect
would not take: a simulator scheme, a configuration whose name ends in
`Debug`, an `exportOptionsPlist` whose `method` is not `app-store-connect`
(or `app-store`), and a scheme with neither `signing.ascApiKey` nor an
`exportOptionsPlist`, which only archives.

After the build, and after `--register` when you pass both, the CLI:

1. Reads the bundle ID, version (`CFBundleShortVersionString`) and build
   number (`CFBundleVersion`) from the `.ipa`'s `Info.plist`.
2. Finds the App Store Connect app with that bundle ID. Create the app in
   App Store Connect first; the key must belong to its team.
3. Uploads the `.ipa` with the App Store Connect API's build uploads.
4. Waits up to 30 minutes for App Store Connect to accept the build, and
   prints the warnings and errors it reports.

App Store Connect takes each build number once per version: raise
`CFBundleVersion` for every build you upload. When an upload fails, the build
stays at its output path. A build that App Store Connect is still processing
after 30 minutes appears in TestFlight once processing finishes, at the URL
the CLI prints.

## Run on a device

```package-install
npx hot-updater run:android --scheme previewApk
```

```package-install
npx hot-updater run:ios --scheme release
```

`run:android` installs an `.apk` scheme on every connected device, and starts
the first emulator when none is connected. `run:ios` runs on the first booted
simulator or device, or else on the first simulator. Pass
`--device <name or ID>` to pick one, or `-i` to choose from a list. An iOS
device build signs with the scheme's `signing.ascApiKey` when it sets one.

## Command options

| Option                    | Commands            | Description                                     |
| ------------------------- | ------------------- | ----------------------------------------------- |
| `-s, --scheme <scheme>`   | all                 | The `nativeBuild` scheme to build               |
| `-i, --interactive`       | all                 | Choose the scheme, and with `run:*` the device  |
| `-o, --output-path <dir>` | `build:*`           | Where to copy the build output                  |
| `--register`              | `build:*`           | Register the release build, its artifact and built-in bundle |
| `--upload testflight`     | `build:ios`         | Upload the `.ipa` to App Store Connect for TestFlight |
| `-d, --device [device]`   | `run:*`             | The device name or ID to run on                 |
| `--port <port>`           | `run:android`       | The Metro port the device reaches with `adb reverse` |
