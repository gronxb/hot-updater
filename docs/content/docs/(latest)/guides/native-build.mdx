## Overview

`hot-updater native-build android` and `hot-updater native-build ios` build
the native app from a scheme in `hot-updater.config.ts`, and track it in Hot
Updater: the build, its artifact, and the JavaScript bundle it compiled in are
recorded with your server, where they serve as a patch base, a preview build,
and a Console install link. Each build compiles in the values that select its
OTA updates, and prints them with the artifact:

| Value         | What the build compiles in                                                                                                                                |
| ------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Artifact      | The `.apk`, `.aab`, `.ipa` or simulator `.app`, copied to the output path                                                                                 |
| Min bundle ID | The ID of the bundle built into the app, which only newer bundles replace (the nil UUID in Debug)                                                         |
| Fingerprint   | The native fingerprint, with the [fingerprint strategy](/docs/guides/update-strategies/fingerprint)                                                       |
| App version   | The native app version, with the [app version strategy](/docs/guides/update-strategies/app-version)                                                       |
| Channel       | The [default channel](/docs/guides/channel-management): what `channel set` wrote, or in an Expo project the `@hot-updater/expo` config plugin's `channel` |

The build reads the app version and channel from the artifact it built, so
the values a flavor, build type, `versionNameSuffix`, `xcconfig` or
`extraParams` sets are the ones it reports. On Android it reads them with the
SDK's `aapt2`.

To run the app on a device, emulator or simulator, install the artifact, as
[Build](#build) shows, or use your framework's run command.

## Prerequisites

- The platform toolchain: the Android SDK and the project's Gradle wrapper, or
  Xcode with CocoaPods.
- A Hot Updater setup that a release build already passes: the
  [App Setup](/docs/get-started/app-setup) native integration and the
  [default channel](/docs/guides/channel-management).
- With the fingerprint strategy, the build updates `fingerprint.json` before
  it compiles. With the app version strategy, delete any `fingerprint.json` first
  (`hot-updater doctor --fix` does), or the app reports the fingerprint
  strategy.

## Configure schemes

Add one scheme per artifact under `nativeBuild.android` and `nativeBuild.ios`.
Keep the other settings of `hot-updater.config.ts` as they are.

```ts title="hot-updater.config.ts (partial)"
import { defineConfig } from "hot-updater";

export default defineConfig({
  // build, storage, database and plugins stay as they are
  nativeBuild: {
    android: {
      release: {
        packageName: "com.example.app",
        // An .aab by default; aab: false builds an .apk.
        signing: { keystore: "secret:release-keystore" },
      },
      previewApk: {
        packageName: "com.example.app",
        aab: false,
        signing: { keystore: "secret:release-keystore" },
      },
    },
    ios: {
      release: {
        bundleIdentifier: "com.example.app",
        scheme: "ExampleApp",
        installPods: true,
        signing: { ascApiKey: "secret:asc-api-key" },
      },
      simulator: {
        bundleIdentifier: "com.example.app",
        scheme: "ExampleApp",
        installPods: true,
        simulator: true,
      },
    },
  },
});
```

Android schemes build the `Release` variant unless `variant` names another,
such as `stagingRelease`. iOS schemes build the `Release` configuration unless
`configuration` names another.

An iOS scheme without `simulator` archives the app and exports an `.ipa`. It
needs `signing.ascApiKey`, which exports for App Store Connect, or an
`exportOptionsPlist` for another export method.

## Provide signing credentials

`signing` names a secret as `secret:<name>`, which the CLI reads from the
config's [`secrets` adapter](/docs/custom/cli-configuration#secrets) while it
builds. The build resolves it only when it signs: a Debug variant keeps the
debug keystore, and a simulator build signs nothing. A scheme without `signing`
keeps the project's own signing settings.

The adapter holds each credential as one JSON value:
`{"keyId","issuerId","p8"}` for an App Store Connect API key, with the `.p8`
file's PEM; `{"keystore","storePassword","keyAlias","keyPassword"}` for a
keystore, the keystore file in base64; and a Play service account's own JSON
key file. With the default
[`localSecrets()`](/docs/guides/secrets-adapters/local-secrets), set the JSON
in an environment variable, `HOT_UPDATER_ASC_API_KEY` for
`secret:asc-api-key` and `HOT_UPDATER_` before any other name, upper-cased
with `_` for every character but letters and digits, or let `apple login`,
`google-play login`, or `secrets put` store it in a file in your home
directory.
[Secrets](/docs/concepts/secrets) covers storing them.

These environment variables override the adapter for one credential: when any
of a credential's variables is set, the build reads that credential from them
and never asks the adapter for it.

| Credential                | Environment variables                                                                                                                                                                        |
| ------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Android keystore          | `HOT_UPDATER_ANDROID_KEYSTORE_PATH` (or `HOT_UPDATER_ANDROID_KEYSTORE_BASE64`), `HOT_UPDATER_ANDROID_KEYSTORE_PASSWORD`, `HOT_UPDATER_ANDROID_KEY_ALIAS`, `HOT_UPDATER_ANDROID_KEY_PASSWORD` |
| App Store Connect API key | `HOT_UPDATER_ASC_KEY_PATH` (or `HOT_UPDATER_ASC_KEY`, the `.p8` contents), `HOT_UPDATER_ASC_KEY_ID`, `HOT_UPDATER_ASC_ISSUER_ID`                                                             |
| Play service account      | `HOT_UPDATER_PLAY_SERVICE_ACCOUNT_PATH` (or `HOT_UPDATER_PLAY_SERVICE_ACCOUNT_JSON`, the JSON key file's contents), for [`--submit play-internal`](#upload-to-google-play)                   |

The CLI writes a keystore or key given as contents to a temporary file that
only your user can read, and deletes it when the build ends. It masks passwords
in its output. A build resolves the credentials it signs and uploads with
before the build adapter's prebuild, so a missing one fails before anything is
built; the error names where the adapter keeps it, the command that stores the
credential once, and these variables. [Build and upload from CI](/docs/guides/ci-native-build)
runs builds that read them in CI, which never signs in.

### Sign in with your Apple Account

An iOS build that needs an App Store Connect API key, for
`signing.ascApiKey` or [`--submit testflight`](#upload-to-testflight), and
finds none issues one. In a terminal, sign in with your Apple Account when
asked: Hot Updater asks for its email, password, and two-factor code, and
signs in with asc, the open-source
[App Store Connect CLI](https://github.com/rorkai/App-Store-Connect-CLI)
(MIT). The password goes only to that asc process, in its environment. With
no trusted device at hand, enter any wrong code once: Apple texts a code to
your phone, and Hot Updater asks for it. Hot Updater then creates a team API
key with the Admin role in that team, named `hot-updater <date>`, stores it
under the name the build resolves
([where an issued key goes](#where-an-issued-key-goes)), and continues the
build. It keeps only the issued key: neither the password nor the Apple
session is saved.

The Admin role lets `xcodebuild` create cloud-managed distribution
certificates and provisioning profiles, so the Mac needs no signing identity
of its own, and lets the build upload to TestFlight. Creating it needs the
Account Holder or Admin role in the team.

To sign in ahead of a build, such as before CI's first build, run
`apple login`, the shortcut for
[`secrets issue asc-api-key`](/docs/concepts/secrets#issue-a-key-with-a-sign-in),
which does the same sign-in without building:

```package-install
npx hot-updater apple login
```

It keeps a key the adapter already holds; `secrets issue asc-api-key
--replace` issues a new one and names the old key to revoke at App Store
Connect → Users and Access → Integrations, which Hot Updater never revokes
itself.

CI (`CI` is set, even on a terminal a runner allocates) and other builds
without a terminal use the stored key and never sign in. A build that finds no
key there stops with that command.

Before it asks for your Apple Account, the CLI checks everything that could
fail afterwards, in this order: a `HOT_UPDATER_ASC_KEY*` override or a key the
`secrets` adapter holds is used as it is; and CI and runs without a terminal
stop with the command above. On a machine without a key, it says that signing
in issues a new one, and how to
[share one key across machines](/docs/concepts/secrets#share-a-key-across-machines)
instead. When the issued key surely went nowhere, the CLI revokes it again,
so no key is left that nothing holds.

The CLI uses the `asc` on your `PATH` when it is version 5.16.1 or later, and
otherwise downloads asc 5.16.1 from its GitHub release into
`~/Library/Caches/hot-updater`, checked against the release's published
SHA-256. asc runs with its session, config, and the key's `.p8` in a
temporary directory only your user can read, which the CLI deletes when it
is done, and never reads your `~/.asc` or keychain.

The Android build passes the keystore to Gradle as the signing properties
Android Studio uses for signed builds, so it signs both `.apk` and `.aab`
whatever the variant's `signingConfig` says. The iOS build signs with automatic
signing: `xcodebuild` uses the App Store Connect API key to create or update
certificates and provisioning profiles. The Xcode project needs its
development team (`DEVELOPMENT_TEAM`), in the project or in `extraParams`.
In CI (`CI` is set), the archive and the export sign in a keychain of the
build's own, and the CLI revokes the development certificates Xcode created
in it before deleting it, as
[What a CI build does](/docs/guides/ci-native-build#what-a-ci-build-does)
describes.

### Where an issued key goes

A key Hot Updater issues after an Apple or Google sign-in goes where builds
read it, as one JSON value:

- With the default [`localSecrets()`](/docs/guides/secrets-adapters/local-secrets),
  to `~/.hot-updater/secrets/<project-key>/<name>.json`, a file only your user
  can read, outside the project. The next build on the machine reads it, with
  no step in between.
- With an adapter that stores values, through the adapter, read back once
  stored. One that does not read it back on your machine, such as a
  write-only store, also gets a copy in the `localSecrets()` store, which
  builds on your machine read after the adapter.

Each machine keeps its own key: on another machine a sign-in issues a new one.
After issuing, the CLI prints where to revoke the keys nothing uses anymore,
App Store Connect's Integrations page (Team Keys) or the service account's
keys in Google Cloud. To use one key on every machine and in CI, see
[Share a key across machines](/docs/concepts/secrets#share-a-key-across-machines).

For CI, store the same value as a repository secret and map it into the job,
as in [Build and upload from CI](/docs/guides/ci-native-build):

```yaml
env:
  HOT_UPDATER_ASC_API_KEY: ${{ secrets.HOT_UPDATER_ASC_API_KEY }}
```

With `localSecrets()`, when the sign-in runs at a terminal, the project's `origin`
(or another remote) is on GitHub, and you have a token (`GH_TOKEN` or
`GITHUB_TOKEN`, or the GitHub CLI's `gh auth token`), the CLI offers once to
store the key as that secret too. Declining keeps the key on your machine
alone, and a failed write says so. To store it by hand, copy the file:

```bash
gh secret set HOT_UPDATER_ASC_API_KEY < ~/.hot-updater/secrets/<project-key>/asc-api-key.json
```

## Build

```package-install
npx hot-updater native-build android --scheme release
```

```package-install
npx hot-updater native-build ios --scheme simulator
```

Without `--scheme`, the CLI asks which scheme at a terminal, and in CI or
without a terminal stops with the schemes to pass.

The build copies its output to `.hot-updater/output/build/<platform>/<scheme>`,
or to `--output-path`, and prints the artifact and its values:

```txt
◆  Built Android bare
    Artifact:      /path/to/app/.hot-updater/output/build/android/release/app-release.aab
    Kind:          aab
    Min bundle ID: 019a0f8e-7c41-7000-8000-02c5f1a9e3b7
    Fingerprint:   4f1c0d6b2e9a…
    Channel:       production
```

A Debug build reports the nil UUID as its min bundle ID, as its native SDK
does: an Android variant or iOS configuration whose name ends in `Debug`.

Every build gets its own min bundle ID: an iOS and an Android build never
share one, and two builds of one platform get different IDs even when they
start in the same millisecond.

Install a simulator `.app` with
`xcrun simctl install booted <path-to-app>`, and an `.apk` with
`adb install <path-to-apk>`.

The build writes the whole output of `xcodebuild` or Gradle to a log in
`.hot-updater/log`, such as `.hot-updater/log/10261157-ios-simulator-build.log`.
When the build fails, the CLI prints why on stderr: `xcodebuild`'s `error:`
lines and the commands that failed, or Gradle's `What went wrong` block, or
without those, the output's last 40 lines, then the log's path. With
`--json`, stdout keeps only the JSON.

```txt
■  Build failed
│
■  /path/to/app/ios/App/AppDelegate.swift:12:5: error: cannot find 'missingSymbol' in scope
│  ** BUILD FAILED **
│  The following build commands failed:
│  	SwiftCompile normal arm64 /path/to/app/ios/App/AppDelegate.swift (in target 'App' from project 'App')
│  (1 failure)
│
│  Build log: .hot-updater/log/10261157-ios-simulator-build.log
```

## How a build is tracked

Every native build is tracked in the native build registry of the server that
`database` and `storage` in `hot-updater.config.ts` name, with the same
credentials `hot-updater deploy` uses. Before it builds, and before any Apple
or Google sign-in, the CLI checks that it can: it asks the registry for the
build's scope, or, when the build adapter's prebuild has yet to generate the
native project, for its newest build, and reads back the artifact of a build
the registry already tracks there. When the database or the storage can't be reached, it stops in
seconds, naming which, and builds nothing.

After the build, the CLI:

1. Takes the JavaScript bundle the native build compiled in out of the
   artifact, byte for byte: `assets/index.android.bundle` in an `.apk`,
   `base/assets/index.android.bundle` in an `.aab`, and `main.jsbundle` in an
   `.ipa` or `.app`.
2. Uploads the artifact to `native-builds/<platform>/<build id>/` in your
   storage. A simulator `.app` is uploaded as one `.app.zip` archive.
3. Uploads that JavaScript bundle as the build's built-in bundle: a bundle
   whose ID is the build's min bundle ID and whose manifest lists only that
   file, at the path an OTA bundle's manifest gives it (`index.ios.bundle` or
   `index.android.bundle`), in the shared asset storage.
4. Registers the build and its built-in bundle in one database write. When
   that write fails, the CLI deletes the uploaded artifact again; the built-in
   bundle's files are left to `storage prune`.

The Console's **Native builds** page lists tracked builds; see
[Native builds in the Console](#native-builds-in-the-console).

A registered build is found by its platform, its default channel, and its
fingerprint or, with the app version strategy, its exact app version: the
newest build of that scope.

The built-in bundle is not an OTA update. No Release publishes it, so no
device downloads it, and no update check changes. The bundle totals leave it
out, a release of it and its deletion are refused, `hot-updater doctor --fix`
keeps it, and `storage prune` keeps its files and the artifact. It is deleted
with its build; see [Delete a build](#delete-a-build).

`hot-updater deploy` uses it as a Hermes patch base: it adds the built-in
bundle of the newest registered build of the deploy's channel, platform, and
fingerprint or exact app version to the patch bases, so a fresh install's first
OTA downloads a `.bsdiff` patch instead of the complete Hermes bundle. The app
checks its packaged Hermes file against the hash registered from the artifact
before it patches, and downloads the complete file when they differ. See
[Bundle Diffing](/docs/guides/bundle-diffing#first-ota-update).

A Debug build loads its JavaScript from Metro and has no built-in bundle, so
the CLI does not track it, and says so before it builds; `--json` reports
`registration: { skipped: "debug" }`. When tracking fails after the build,
the CLI exits with the artifact's path, and submits it to no store. A
self-hosted server reached through `standaloneRepository` needs the native
build routes of this release's `@hot-updater/server`; an older one answers
`404`, and the CLI asks you to upgrade it before it builds.

Every official storage adapter streams the artifact to storage except
`standaloneStorage`, which reads it into memory to post it to your server. A
Supabase project's Storage upload file size limit, 50 MB on the Free plan,
caps the artifact size.

## Native builds in the Console

The Console's **Native builds** page lists the tracked builds, newest first,
with each build's channel, its fingerprint or app version, its built-in
bundle, and its commit. Pick a channel to list only the builds that embed it,
such as `/native-builds?channel=pr-130` for a pull request's builds. A row
opens the build's page, `/native-builds/<build id>`:

- **Install**: an `.apk` shows a QR code of the artifact's storage URL, which
  a phone opens without signing in to the Console, and the `adb install`
  command. A simulator `.app` shows the `xcrun simctl install` command. An
  `.aab` installs through Google Play or bundletool, and an `.ipa` through
  Xcode, Apple Configurator, or [TestFlight](#upload-to-testflight). Every
  build downloads through `/api/native-builds/<build id>/download`, which
  answers with a fresh storage URL on each request, so the link never
  expires. A browser that opens it without a Console session goes to the
  build's page, which signs it in and comes back to the build.
- **Build number**: the `CFBundleVersion` or `versionCode` the artifact
  reports, which the list shows as `build 66` too.
- **Store**: for a build `testflight` or `google-play upload` submitted, the
  store track and the store's version and build number, with when it was
  submitted. The list marks those builds too.
- **Built-in bundle**: the build's min bundle ID, the base its OTAs patch
  from, how many bundles patch from it, and whether it is the newest build of
  its scope. `deploy` patches from the newest build of a scope, so a
  superseded build links to the build that replaced it.
- **Served now**: the releases the update check offers an install of this
  build now, newer than its built-in bundle, and whether each one's first OTA
  downloads as a patch or as the full bundle.
- **Patches from this build**: the bundles with a patch from its built-in
  bundle, and each patch's size.

A bundle's detail sheet links to the newest build of its release's scope, and
says whether the bundle has a patch from it. Deleting a build stays with
[`native-build delete`](#delete-a-build).

## Reuse a build

Each build computes a native build key, `nbk1:` and a SHA-256, of every input
that can change the artifact, after the build adapter's prebuild and, for an
iOS scheme with `installPods: true`, after `pod install`, so the key holds the
`Podfile.lock` the pods resolved to even when the prebuild generates `ios/`, as
`expo prebuild` does:

- every file of the git repository as a commit would record it, staged or
  not, except the build output, `cacheDir`, and `.hot-updater`;
- the files git ignores that the build reads: the native project's ignored
  files except what builds write (`build`, `Pods` but its `Manifest.lock`,
  `.gradle`, `.cxx`), a generated Xcode project by its structure, whatever
  object IDs `pod install` gives it,
  `.env*` files, the package manager's install state, the files of each
  native package installed in `node_modules`, and the ignored files of each
  package of the repository the app depends on, such as generated codegen
  sources or a built `lib/`;
- what autolinking links, asked with the command the native project runs:
  React Native CLI's `config` (`rock config` with Rock, and
  `expo-modules-autolinking react-native-config` in an Expo app), and
  `expo-modules-autolinking resolve` for the Expo modules. The config it
  prints counts without this machine's directories, so linking a package,
  dropping one, or changing a `sourceDir`, podspec, or script phase rebuilds;
  and each linked package counts file by file, wherever autolinking finds it
  and wherever its native code is: all its files in `node_modules` or outside
  the repository, its ignored files in the repository, never what builds
  write or the other platform's folder;
- the scheme's settings and the files it names, such as `xcconfig` and
  `exportOptionsPlist`, the artifact's kind, the channel, and the fingerprint
  or app version;
- who signs: the release keystore's certificate and alias, or the App Store
  Connect API key's ID, the export method, and the installed provisioning
  profiles a manual export names;
- the tools: Xcode and its SDK, CocoaPods, or the JDK, the Android SDK's
  installed components, and Gradle's machine-wide properties, with Node.js,
  the OS, the architecture, and Hot Updater's version;
- the environment variables the build reads: `EXPO_PUBLIC_*`, `RCT_*`,
  `ORG_GRADLE_PROJECT_*`, `HOT_UPDATER_*`, `NODE_ENV`, `BABEL_ENV`,
  `ENVFILE`, and each name the Gradle files, the Podfile, the Xcode project,
  and the Babel, Metro, and app configs read.

Passwords, tokens, and other credentials never enter the key, nor this
machine's directories, so another machine computes the same key from the same
inputs. The key is not the [fingerprint](/docs/guides/update-strategies/fingerprint):
the fingerprint changes only with the native interface JavaScript runs
against, and decides which OTA updates a build takes; the key changes with
anything that changes the artifact.

With the key, the CLI looks for a build to reuse before it builds:

1. The registry's newest build of the scope tracked with this key, whose
   artifact your storage still holds. The CLI copies it to the output path,
   from this machine when it has it, else downloaded from storage, and builds,
   tracks, and uploads nothing.
2. Otherwise, this machine's cached build with this key, such as a
   `--dry-run`'s: it is tracked with the min bundle ID it was built with.
3. Otherwise, it builds, and tracks the build with its key.

```txt
◆  Reusing native build 019a0f8e-7c41-7000-8000-0000000000b1 (key nbk1:3f9c2a71d0e4…; storage)
    Artifact: .hot-updater/output/build/android/release/app-release.aab
```

```txt
●  Building: no tracked build has this key; changed since this machine's cached build: src/App.tsx, ios/Podfile.lock, $EXPO_PUBLIC_API_URL (key nbk1:8b01e6c9f27d…)
```

This machine keeps the newest build of each platform and scheme in
`<cacheDir>/native-build/<platform>/<scheme>`, which the next build replaces;
`cacheDir: null` turns that copy off. A build whose inputs no key can cover
always builds, and says why: a Debug build, a project outside git,
autolinking that can't run, pods
without `ios/Podfile.lock` on a scheme that doesn't set `installPods`, Swift packages without `Package.resolved`, a
dynamic Gradle dependency version (`1.+`) without a `gradle.lockfile`, a file
that reads environment variables by a computed name, an export method that
signs for a list of devices, or a provisioning profile not installed on this
machine. `--no-cache` builds anyway, after a change outside the project no key
covers, and still tracks the build with its key.

A reused build has the same build number (`CFBundleVersion` or
`versionCode`), and App Store Connect and Google Play take each build number
once. So with `--submit`, as in `testflight` and `google-play upload`, a
reused build is uploaded only when the store doesn't have it yet:

- A tracked build already submitted to that store is skipped without asking
  the store:
  `Already on TestFlight since 2026-10-27 04:02 UTC as 1.7.0 (66). Bump the build number to upload a new build.`
- A reused build with no submission recorded is looked up in the store. An
  `.ipa` whose build number App Store Connect already has, or an `.aab` whose
  version code Google Play's internal track releases, is skipped the same
  way, and recorded on the build.
- When the store refuses the build number anyway, because a build with that
  number came from another upload or tool, the CLI skips with the same line
  instead of the store's error, and records nothing, since the store's build
  may be another artifact.

Each skip exits 0, so rerunning a CI job that already submitted its build
succeeds. With `--json`, the last line has `submission: { destination,
skipped: "already-submitted", existing }`, where `existing` has the
`destination`, the store's `version` label, `submittedAtMs` (null when the
store said so), and `source` (`recorded` or `store`). Bump the build number
to upload a new build. With `--json`, the last line also has `cache: { hit,
key, uncacheable, changed }`: `hit` is `storage`, `local`, or null.

Preview jobs keep finding builds by scope with
[`native-build find`](#find-a-build), whatever their key.

## Rehearse a build

`--dry-run` builds, but records and submits nothing, as `npm publish
--dry-run` does:

```package-install
npx hot-updater native-build ios --scheme release --submit testflight --dry-run
```

It resolves the scheme, the app version or fingerprint, and the channel, runs
the tracking check read-only, and reads the store key `--submit` would use
without signing in or issuing one. Then it builds, keeps the artifact on this
machine, and prints what it would have recorded and where it would have
submitted the build. It writes no record, uploads nothing to your storage, and
submits to no store. A missing store key is reported, the build still runs,
and the command exits with an error at the end. With `--json`, the last line
has `dryRun: true`, `registration: { skipped: "dry-run" }`, and
`submission: { skipped: "dry-run", destination }`.

## Find a build

`hot-updater native-build find` prints the newest registered build that a
build of the project would match, as a
[pull request preview](/docs/guides/pull-request-previews) does before it
builds:

```package-install
npx hot-updater native-build find -p ios -s release
```

It reads the native projects and writes nothing to them. With the Expo build
adapter it reads the app version and channel `expo prebuild` would write from
the Expo config, with the project's own config plugins, and doesn't run
prebuild; `ios/` and `android/` stay as they are. A product flavor's own
`versionName` in `android/` still overrides the Expo version, as it does in
the build. Other adapters read
`ios/` and `android/` as they are. Only when no native project declares an
app version, and the build adapter can't tell, does it run the adapter's
prebuild, and it says so first.

`-c, --channel` names the channel the build embeds, instead of the native
project's default channel, and `--json` prints the scope and the build, or
`null`.

## Delete a build

Delete a registered build you no longer need, such as a finished QA build:

```package-install
npx hot-updater native-build delete <build id>
```

The command shows the build and asks before it deletes it. It then deletes
the build and its built-in bundle from the database, then the artifact from
storage. Bundles deployed with a `.bsdiff` patch from the built-in bundle lose
that patch, so a device with that build installed downloads the complete
bundle; installed apps keep working. The built-in bundle's files stay until
[`hot-updater storage prune`](/docs/guides/storage-cleanup) deletes them.

The database goes first, so no registered build names a deleted artifact.
When the artifact's deletion fails, the command prints its storage URI and
exits with status 1; delete that object from storage. A build that isn't
registered deletes nothing, and the command succeeds, so a cleanup job can
run again. A channel a native build embeds as its default channel can be
deleted once its builds are.

Add `-y, --yes` to skip the confirmation; without a terminal, the command
refuses to ask and exits with status 1. Add `--json` to print the result,
with `artifactDeleted`.

A self-hosted server reached through `standaloneRepository` needs this
release's `@hot-updater/server`; an older one answers `404`, and the CLI asks
you to upgrade it.

## Upload to TestFlight

`testflight` builds the `.ipa`, tracks it, and uploads it to App Store
Connect, which lists it in TestFlight:

```package-install
npx hot-updater testflight
```

It is the shortcut for `native-build ios --scheme <scheme> --submit
testflight`, which runs the same build. It builds the one `nativeBuild.ios`
scheme whose build TestFlight takes, skipping simulator, `Debug`, unsigned,
and archive-only schemes and ones that export for another method, and says
which; with several, it asks which one at a
terminal, and in CI or without a terminal it stops and lists them. It takes
only `--scheme`: for `--json`, `--output-path`, or `--dry-run`, run the full
command:

```package-install
npx hot-updater native-build ios --scheme release --submit testflight
```

The upload authenticates with an App Store Connect team API key, which has a
key ID and an issuer ID (App Store Connect → Users and Access → Integrations →
Team Keys), with the Admin, App Manager, or Developer role: the scheme's
`signing.ascApiKey`, or else the `secrets` adapter's `asc-api-key`. The
`HOT_UPDATER_ASC_KEY*` environment variables in
[Provide signing credentials](#provide-signing-credentials) override it.
Without one, [sign in with your Apple Account](#sign-in-with-your-apple-account)
when asked, and the CLI issues and stores it before it builds
([where an issued key goes](#where-an-issued-key-goes)). The
CLI resolves the key before the build adapter's prebuild (such as
`expo prebuild`) and the build, so a missing key fails before either runs, and
deletes the key's temporary file when the upload ends.
Certificates and provisioning profiles stay with the build's signing.
[Build and upload from CI](/docs/guides/ci-native-build) uploads from a CI job
with the stored key.

Before the prebuild, the CLI also refuses, saying why, a scheme whose build
App Store Connect would not take: a simulator scheme, a configuration whose
name ends in `Debug`, a scheme that turns code signing off
(`CODE_SIGNING_ALLOWED` or `CODE_SIGNING_REQUIRED` left `NO` after the
overrides the build applies: `extraParams` settings, then its `xcconfig` and
each `-xcconfig` in `extraParams`, in order), a scheme with neither `signing.ascApiKey` nor an
`exportOptionsPlist`, which only archives, and an `exportOptionsPlist` whose
`method` is not `app-store-connect` (or `app-store`). An `exportOptionsPlist`
the prebuild writes is checked after the prebuild, before the build.

After the build is tracked, the CLI:

1. Reads the bundle ID, version (`CFBundleShortVersionString`) and build
   number (`CFBundleVersion`) from the `.ipa`'s `Info.plist`.
2. Finds the App Store Connect app with that bundle ID. Create the app in
   App Store Connect first; the key must belong to its team.
3. Uploads the `.ipa` with the App Store Connect API's build uploads.
4. Waits up to 30 minutes for App Store Connect to accept the build, and
   prints the warnings and errors it reports.

App Store Connect takes each build number once per version: raise
`CFBundleVersion` for every build you upload. When an upload fails, the build
stays at its output path. A build that App Store Connect is still processing
after 30 minutes appears in TestFlight once processing finishes, at the URL
the CLI prints.

Once App Store Connect accepts the build, the CLI records it on the tracked
build, and the Console's [Native builds](#native-builds-in-the-console) tab
shows it as on TestFlight with its version and build number, such as
`1.7.0 (66)`. A build still processing is recorded by the next run with the
same inputs, which finds it on TestFlight instead of uploading it again. A
failed upload and `--dry-run` record nothing. A build number App Store Connect
already has, from this or another upload, is skipped with `Already on
TestFlight as 1.7.0 (66). Bump the build number to upload a new build.`; see
[Reuse a build](#reuse-a-build).

## Upload to Google Play

`google-play upload` builds the `.aab`, tracks it, and releases it to Google
Play's internal testing track:

```package-install
npx hot-updater google-play upload
```

It is the shortcut for `native-build android --scheme <scheme> --submit
play-internal`, which runs the same build. It builds the one
`nativeBuild.android` scheme whose build Google Play takes, skipping `.apk`
(`aab: false`) and `Debug` schemes, and says which; with several, it asks which
one at a terminal, and in CI or without a terminal it stops and lists them. It
takes only `--scheme`: for `--json`, `--output-path`, or `--dry-run`, run the
full command:

```package-install
npx hot-updater native-build android --scheme release --submit play-internal
```

The upload authenticates with the `secrets` adapter's `play-service-account`, the
JSON key file of a Google Cloud service account.
`HOT_UPDATER_PLAY_SERVICE_ACCOUNT_PATH` (or
`HOT_UPDATER_PLAY_SERVICE_ACCOUNT_JSON`, the file's contents) overrides it.
The CLI resolves it before the build adapter's prebuild (such as
`expo prebuild`) and the build, so a missing one fails before either runs, and
keeps it in memory: it writes the service account to no file.

When the adapter has no `play-service-account` yet, sign in with Google when
asked. In a terminal, the CLI opens Google's sign-in page in your browser and
prints its address, asks for the app's package name and your Play Console
developer account ID (the number after `/developers/` in Play Console's
address), and lets you pick a Google Cloud project or create one. Then it:

1. Checks that the Google Account administers the developer account and that
   Google Play has the app, before it changes anything.
2. Enables the IAM and Google Play Android Developer APIs in the project, and
   creates the service account `hot-updater-play` there.
3. Adds the service account to Play Console as a user that may view the app
   and release it to testing tracks.
4. Creates the service account's JSON key, stores it as
   `play-service-account` ([where an issued key goes](#where-an-issued-key-goes)),
   and continues with the build, which uploads with it.

Google's own page asks for your password, and the CLI keeps only the issued
key. When the key surely went nowhere, the CLI deletes the key again; the service
account and its Play Console access stay, and the next run reuses them.
Builds without a terminal, such as CI, use the stored key and never sign in:
when it is missing, they fail with the command to run once in a terminal,
`npx hot-updater google-play login` (the shortcut for
`secrets issue play-service-account`), which does the same
sign-in without building and keeps a key the adapter already holds;
`secrets issue play-service-account --replace` issues a new key and names the
old one to delete under the service account's keys in Google Cloud. The sign-in needs a Google OAuth client of your
own, of type Desktop app, in `HOT_UPDATER_GOOGLE_OAUTH_CLIENT_ID` and
`HOT_UPDATER_GOOGLE_OAUTH_CLIENT_SECRET`, until Hot Updater ships one; without
it, the CLI stops before opening the browser.

Before the prebuild, the CLI also refuses a scheme whose build Google Play
would not take as a release: an `.apk` scheme (`aab: false`) and a variant whose name
ends in `Debug`. Before it uploads, it refuses an `.aab` signed with the Android
debug keystore, as a release build type left on `signingConfigs.debug` is: set
the scheme's `signing.keystore`, or a release signing config in Gradle.

After the build is tracked, the CLI:

1. Reads the application ID from the `.aab`'s manifest with `aapt2`, with the
   suffixes flavors and build types add, or else uses the scheme's
   `applicationId`.
2. Opens an edit with the Google Play Developer API and uploads the `.aab`.
3. Releases the bundle's version code to the `internal` track and commits the
   edit. When any step fails, it deletes the edit, so nothing is released.

Create the app in Play Console and upload its first `.aab` there by hand:
Google takes a new app's first `.aab` only in Play Console, and the API
releases the builds after it.

To use a service account of your own instead, invite its email under Users
and permissions with permission to release to testing tracks, enable the
Google Play Android Developer API in its Google Cloud project, and store its
key with `secrets put play-service-account --kind play-service-account
--service-account <file>`.

Google Play takes each version code once: raise `versionCode` for every build
you upload. On an app Play Console has not published yet, Google Play takes
only draft releases, so the internal release is a draft that you roll out in
Play Console. When the app's state requires it, the CLI commits without
sending the changes for review, and you send them for review in Play Console.
When an upload fails, the build stays at its output path, and nothing is
recorded. Once Google Play takes the bundle, the CLI records it on the tracked
build, and the Console's [Native builds](#native-builds-in-the-console) tab
shows it as on Play internal with its version name and code, such as
`1.7.0 (66)`. A version code Google Play already has is skipped with
`Already on Google Play internal testing as 1.7.0 (66). Bump the build number to upload a new build.`;
see [Reuse a build](#reuse-a-build).
[Build and upload from CI](/docs/guides/ci-native-build) uploads from a CI job
with the stored service account.

## Command options

`native-build ios` and `native-build android` take:

| Option                    | Description                                                                               |
| ------------------------- | ----------------------------------------------------------------------------------------- |
| `-s, --scheme <scheme>`   | The `nativeBuild` scheme to build; without it, a prompt at a terminal                     |
| `-o, --output-path <dir>` | Where to copy the build output                                                            |
| `--submit testflight`     | `ios`: upload the `.ipa` to App Store Connect for TestFlight                              |
| `--submit play-internal`  | `android`: release the `.aab` to Google Play's internal testing track                     |
| `--dry-run`               | Build, but record and submit nothing ([Rehearse a build](#rehearse-a-build))              |
| `--no-cache`              | Build even when a tracked or cached build has the same key ([Reuse a build](#reuse-a-build)) |
| `--json`                  | Print the build, its record or why it has none, and its submission as JSON, the last line |

The commands of the registry, `native-build find` and `native-build delete`,
are described in [Find a build](#find-a-build) and
[Delete a build](#delete-a-build).
