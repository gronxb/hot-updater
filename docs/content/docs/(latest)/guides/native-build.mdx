## Overview

`hot-updater build:android` and `hot-updater build:ios` build the native app
from a scheme in `hot-updater.config.ts`. Each build compiles in the values
that select its OTA updates, and prints them with the artifact:

| Value         | What the build compiles in                                                                          |
| ------------- | --------------------------------------------------------------------------------------------------- |
| Artifact      | The `.apk`, `.aab`, `.ipa` or simulator `.app`, copied to the output path                           |
| Min bundle ID | The ID of the bundle built into the app, which only newer bundles replace (the nil UUID in Debug)   |
| Fingerprint   | The native fingerprint, with the [fingerprint strategy](/docs/guides/update-strategies/fingerprint) |
| App version   | The native app version, with the [app version strategy](/docs/guides/update-strategies/app-version) |
| Channel       | The default channel that [`channel set`](/docs/guides/channel-management) wrote                     |

The build reads the app version and channel from the artifact it built, so
the values a flavor, build type, `versionNameSuffix`, `xcconfig` or
`extraParams` sets are the ones it reports. On Android it reads them with the
SDK's `aapt2`.

`hot-updater run:android` and `hot-updater run:ios` build the same schemes and
install the app on a device, emulator or simulator.

## Prerequisites

- The platform toolchain: the Android SDK and the project's Gradle wrapper, or
  Xcode with CocoaPods.
- A Hot Updater setup that a release build already passes: the
  [App Setup](/docs/get-started/app-setup) native integration and the
  [default channel](/docs/guides/channel-management).
- With the fingerprint strategy, the build updates `fingerprint.json` before
  it compiles. With the app version strategy, delete any `fingerprint.json` first
  (`hot-updater doctor --fix` does), or the app reports the fingerprint
  strategy.

## Configure schemes

Add one scheme per artifact under `nativeBuild.android` and `nativeBuild.ios`.
Keep the other settings of `hot-updater.config.ts` as they are.

```ts title="hot-updater.config.ts (partial)"
import { defineConfig } from "hot-updater";

export default defineConfig({
  // build, storage, database and plugins stay as they are
  nativeBuild: {
    android: {
      release: {
        packageName: "com.example.app",
        // An .aab by default; aab: false builds an .apk.
        signing: { keystore: "secret:release-keystore" },
      },
      previewApk: {
        packageName: "com.example.app",
        aab: false,
        signing: { keystore: "secret:release-keystore" },
      },
    },
    ios: {
      release: {
        bundleIdentifier: "com.example.app",
        scheme: "ExampleApp",
        installPods: true,
        signing: { ascApiKey: "secret:asc-api-key" },
      },
      simulator: {
        bundleIdentifier: "com.example.app",
        scheme: "ExampleApp",
        installPods: true,
        simulator: true,
      },
    },
  },
});
```

Android schemes build the `Release` variant unless `variant` names another,
such as `stagingRelease`. iOS schemes build the `Release` configuration unless
`configuration` names another.

An iOS scheme without `simulator` archives the app and exports an `.ipa`. It
needs `signing.ascApiKey`, which exports for App Store Connect, or an
`exportOptionsPlist` for another export method.

## Provide signing credentials

`signing` names a secret as `secret:<name>`, which the CLI reads from the
config's [`secrets` adapter](/docs/custom/cli-configuration#secrets) while it
builds. The build resolves it only when it signs: a Debug variant keeps the
debug keystore, and a simulator build signs nothing. A scheme without `signing`
keeps the project's own signing settings.

The adapter holds each credential as one JSON value:
`{"keyId","issuerId","p8"}` for an App Store Connect API key, with the `.p8`
file's PEM; `{"keystore","storePassword","keyAlias","keyPassword"}` for a
keystore, the keystore file in base64; and a Play service account's own JSON
key file. With the default `env()`, set the JSON in an environment variable:
`HOT_UPDATER_ASC_API_KEY` for `secret:asc-api-key`, and `HOT_UPDATER_` before
any other name, upper-cased with `_` for every character but letters and
digits.
[Secrets](/docs/concepts/secrets) covers storing them.

These environment variables override the adapter for one credential: when any
of a credential's variables is set, the build reads that credential from them
and never asks the adapter for it.

| Credential                | Environment variables                                                                                                                                                                        |
| ------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Android keystore          | `HOT_UPDATER_ANDROID_KEYSTORE_PATH` (or `HOT_UPDATER_ANDROID_KEYSTORE_BASE64`), `HOT_UPDATER_ANDROID_KEYSTORE_PASSWORD`, `HOT_UPDATER_ANDROID_KEY_ALIAS`, `HOT_UPDATER_ANDROID_KEY_PASSWORD` |
| App Store Connect API key | `HOT_UPDATER_ASC_KEY_PATH` (or `HOT_UPDATER_ASC_KEY`, the `.p8` contents), `HOT_UPDATER_ASC_KEY_ID`, `HOT_UPDATER_ASC_ISSUER_ID`                                                             |
| Play service account      | `HOT_UPDATER_PLAY_SERVICE_ACCOUNT_PATH` (or `HOT_UPDATER_PLAY_SERVICE_ACCOUNT_JSON`, the JSON key file's contents), for [`--upload play-internal`](#upload-to-google-play)                   |

The CLI writes a keystore or key given as contents to a temporary file that
only your user can read, and deletes it when the build ends. It masks passwords
in its output. A build resolves the credentials it signs and uploads with
before the build adapter's prebuild, so a missing one fails before anything is
built; the error names where the adapter keeps it, the command that stores the
credential once, and these variables. [Build and upload from CI](/docs/guides/ci-native-build)
runs builds that read them in CI, which never signs in.

### Sign in with your Apple Account

An iOS build that needs an App Store Connect API key, for
`signing.ascApiKey` or [`--upload testflight`](#upload-to-testflight), and
finds none issues one. In a terminal, sign in with your Apple Account when
asked: Hot Updater asks for its email, password, and two-factor code, and
signs in with asc, the open-source
[App Store Connect CLI](https://github.com/rorkai/App-Store-Connect-CLI)
(MIT). The password goes only to that asc process, in its environment. With
no trusted device at hand, enter any wrong code once: Apple texts a code to
your phone, and Hot Updater asks for it. Hot Updater then creates a team API
key with the Admin role in that team, named `hot-updater <date>`, stores it
under the name the build resolves
([where an issued key goes](#where-an-issued-key-goes)), and continues the
build. It keeps only the issued key: neither the password nor the Apple
session is saved.

The Admin role lets `xcodebuild` create cloud-managed distribution
certificates and provisioning profiles, so the Mac needs no signing identity
of its own, and lets the build upload to TestFlight. Creating it needs the
Account Holder or Admin role in the team.

To sign in ahead of a build, such as before CI's first build, run
`apple login`, the shortcut for
[`secrets issue asc-api-key`](/docs/concepts/secrets#issue-a-key-with-a-sign-in),
which does the same sign-in without building:

```package-install
npx hot-updater apple login
```

It keeps a key the adapter already holds; `--replace` issues a new one and
names the old key to revoke at App Store Connect → Users and Access →
Integrations, which Hot Updater never revokes itself.

CI (`CI` is set, even on a terminal a runner allocates) and other builds
without a terminal use the stored key and never sign in. A build that finds no
key there stops with that command.

Before it asks for your Apple Account, the CLI checks everything that could
fail afterwards, in this order: a `HOT_UPDATER_ASC_KEY*` override or a key the
`secrets` adapter holds is used as it is; CI and runs without a terminal stop
with the command above; and the key needs somewhere to go, the adapter when it
stores values, or else its file under `cacheDir`. When the issued key surely
went nowhere, the CLI revokes it again, so no key is left that nothing holds.

The CLI uses the `asc` on your `PATH` when it is version 5.16.1 or later, and
otherwise downloads asc 5.16.1 from its GitHub release into
`~/Library/Caches/hot-updater`, checked against the release's published
SHA-256. asc runs with its session, config, and the key's `.p8` in a
temporary directory only your user can read, which the CLI deletes when it
is done, and never reads your `~/.asc` or keychain.

The Android build passes the keystore to Gradle as the signing properties
Android Studio uses for signed builds, so it signs both `.apk` and `.aab`
whatever the variant's `signingConfig` says. The iOS build signs with automatic
signing: `xcodebuild` uses the App Store Connect API key to create or update
certificates and provisioning profiles. The Xcode project needs its
development team (`DEVELOPMENT_TEAM`), in the project or in `extraParams`.
In CI (`CI` is set), the archive and the export sign in a keychain of the
build's own, and the CLI revokes the development certificates Xcode created
in it before deleting it, as
[What a CI build does](/docs/guides/ci-native-build#what-a-ci-build-does)
describes.

### Where an issued key goes

A key Hot Updater issues after an Apple or Google sign-in goes where builds
read it:

- When the `secrets` adapter stores values, the CLI stores the key through it
  as one JSON value, reads it back, and builds read it from there, CI's
  included. A store that does not read it back on your machine, such as
  [`githubActions()`](/docs/guides/secrets-adapters/github-actions) outside a
  workflow, keeps the key for CI, and the CLI also writes a copy to the file
  below. Builds on your machine read it from the key's own variables
  (`HOT_UPDATER_ASC_KEY`, `HOT_UPDATER_ASC_KEY_ID`, `HOT_UPDATER_ASC_ISSUER_ID`,
  or `HOT_UPDATER_PLAY_SERVICE_ACCOUNT_JSON`), which the CLI reads before any
  adapter.
- When the adapter is read-only, such as the default `env()`, the CLI writes
  the key to `<cacheDir>/issued/<name>.json` (`node_modules/.hot-updater` unless
  `cacheDir` sets another directory), a file only your user can read in a
  directory git ignores. It prints the file's path and the variables to store
  it in, never the key: `HOT_UPDATER_ASC_API_KEY` or
  `HOT_UPDATER_PLAY_SERVICE_ACCOUNT` (the name's variable, as
  [`env()`](/docs/guides/secrets-adapters/env) reads it) set to the file's contents, in the
  environment or `.env.hotupdater`, or the key's own variables from
  [Provide signing credentials](#provide-signing-credentials). The build that
  signed in continues with the key from the file, so its upload goes through.
  Store the key, then delete the file: a later sign-in for the same name
  refuses to replace it, since the key it holds is still valid.

For CI, store the same value as a repository secret and map it into the job,
as in [Build and upload from CI](/docs/guides/ci-native-build):

```yaml
env:
  HOT_UPDATER_ASC_API_KEY: ${{ secrets.HOT_UPDATER_ASC_API_KEY }}
```

With `env()`, when the project's `origin` (or another remote) is on GitHub and
you have a token (`GH_TOKEN` or `GITHUB_TOKEN`, or the GitHub CLI's
`gh auth token`), the CLI offers once to store the key as that secret with
[`githubActions()`](/docs/guides/secrets-adapters/github-actions). Declining
leaves the file as it is, and a failed write says so and leaves it too.

The CLI writes the file only after a sign-in, and never revokes a key it wrote
there.

## Build

```package-install
npx hot-updater build:android --scheme release
```

```package-install
npx hot-updater build:ios --scheme simulator
```

The build copies its output to `.hot-updater/output/build/<platform>/<scheme>`,
or to `--output-path`, and prints the artifact and its values:

```txt
◆  Built Android bare
    Artifact:      /path/to/app/.hot-updater/output/build/android/release/app-release.aab
    Kind:          aab
    Min bundle ID: 019a0f8e-7c41-7000-8000-02c5f1a9e3b7
    Fingerprint:   4f1c0d6b2e9a…
    Channel:       production
```

A Debug build reports the nil UUID as its min bundle ID, as its native SDK
does: an Android variant or iOS configuration whose name ends in `Debug`.

Every build gets its own min bundle ID: an iOS and an Android build never
share one, and two builds of one platform get different IDs even when they
start in the same millisecond.

Install a simulator `.app` with
`xcrun simctl install booted <path-to-app>`, and an `.apk` with
`adb install <path-to-apk>`.

## Register a build

Add `--register` to record a release build in the native build registry of
the server that `database` and `storage` in `hot-updater.config.ts` name, with
the same credentials `hot-updater deploy` uses:

```package-install
npx hot-updater build:android --scheme release --register
```

After the build, the CLI:

1. Takes the JavaScript bundle the native build compiled in out of the
   artifact, byte for byte: `assets/index.android.bundle` in an `.apk`,
   `base/assets/index.android.bundle` in an `.aab`, and `main.jsbundle` in an
   `.ipa` or `.app`.
2. Uploads the artifact to `native-builds/<platform>/<build id>/` in your
   storage. A simulator `.app` is uploaded as one `.app.zip` archive.
3. Uploads that JavaScript bundle as the build's built-in bundle: a bundle
   whose ID is the build's min bundle ID and whose manifest lists only that
   file, at the path an OTA bundle's manifest gives it (`index.ios.bundle` or
   `index.android.bundle`), in the shared asset storage.
4. Registers the build and its built-in bundle in one database write. When
   that write fails, the CLI deletes the uploaded artifact again; the built-in
   bundle's files are left to `storage prune`.

The Console's **Preview** page lists registered builds and downloads them; see
[Preview Builds](/docs/guides/preview-builds).

A registered build is found by its platform, its default channel, and its
fingerprint or, with the app version strategy, its exact app version: the
newest build of that scope.

The built-in bundle is not an OTA update. No Release publishes it, so no
device downloads it, and no update check changes. The bundle totals leave it
out, a release of it and its deletion are refused, `hot-updater doctor --fix`
keeps it, and `storage prune` keeps its files and the artifact. It is deleted
with its build; see [Delete a build](#delete-a-build).

`hot-updater deploy` uses it as a Hermes patch base: it adds the built-in
bundle of the newest registered build of the deploy's channel, platform, and
fingerprint or exact app version to the patch bases, so a fresh install's first
OTA downloads a `.bsdiff` patch instead of the complete Hermes bundle. The app
checks its packaged Hermes file against the hash registered from the artifact
before it patches, and downloads the complete file when they differ. See
[Bundle Diffing](/docs/guides/bundle-diffing#first-ota-update).

A Debug build loads its JavaScript from Metro and has no built-in bundle, so
`--register` refuses it. A self-hosted server reached through
`standaloneRepository` needs the native build routes of this release's
`@hot-updater/server`; an older one answers `404`, and the CLI asks you to
upgrade it before it uploads anything.

Every official storage adapter streams the artifact to storage except
`standaloneStorage`, which reads it into memory to post it to your server. A
Supabase project's Storage upload file size limit, 50 MB on the Free plan,
caps the artifact size.

## Find a build

`hot-updater native-build find` prints the newest registered build that a
build of the project would match, as a
[pull request preview](/docs/guides/pull-request-previews) does before it
builds:

```package-install
npx hot-updater native-build find -p ios -s release
```

It reads the native projects and writes nothing to them. With the Expo build
adapter it reads the app version and channel `expo prebuild` would write from
the Expo config, with the project's own config plugins, and doesn't run
prebuild; `ios/` and `android/` stay as they are. A product flavor's own
`versionName` in `android/` still overrides the Expo version, as it does in
the build. Other adapters read
`ios/` and `android/` as they are. Only when no native project declares an
app version, and the build adapter can't tell, does it run the adapter's
prebuild, and it says so first.

`-c, --channel` names the channel the build embeds, instead of the native
project's default channel, and `--json` prints the scope and the build, or
`null`.

## Delete a build

Delete a registered build you no longer need, such as a finished QA build:

```package-install
npx hot-updater native-build delete <build id>
```

The command shows the build and asks before it deletes it. It then deletes
the build and its built-in bundle from the database, then the artifact from
storage. Bundles deployed with a `.bsdiff` patch from the built-in bundle lose
that patch, so a device with that build installed downloads the complete
bundle; installed apps keep working. The built-in bundle's files stay until
[`hot-updater storage prune`](/docs/guides/storage-cleanup) deletes them.

The database goes first, so no registered build names a deleted artifact.
When the artifact's deletion fails, the command prints its storage URI and
exits with status 1; delete that object from storage. A build that isn't
registered deletes nothing, and the command succeeds, so a cleanup job can
run again. A channel a native build embeds as its default channel can be
deleted once its builds are.

Add `-y, --yes` to skip the confirmation; without a terminal, the command
refuses to ask and exits with status 1. Add `--json` to print the result,
with `artifactDeleted`.

A self-hosted server reached through `standaloneRepository` needs this
release's `@hot-updater/server`; an older one answers `404`, and the CLI asks
you to upgrade it.

## Upload to TestFlight

`testflight` builds the `.ipa`, registers it, and uploads it to App Store
Connect, which lists it in TestFlight:

```package-install
npx hot-updater testflight
```

It is the shortcut for `build:ios --scheme <scheme> --upload testflight
--register`, which runs the same build. Without `--scheme`, it builds the one
`nativeBuild.ios` scheme whose build TestFlight takes, skipping simulator,
`Debug`, and archive-only schemes, and says which; with several, it asks which
one at a terminal, and in CI or without a terminal it stops and lists them
for `--scheme`. It registers the build, so it becomes a patch base
`native-build find` sees; `--no-register` only uploads. `--json` and
`--output-path` work as with `build:ios`.

To upload a build without registering it, or from a scheme of your choice,
add `--upload testflight` to `build:ios`:

```package-install
npx hot-updater build:ios --scheme release --upload testflight
```

The upload authenticates with an App Store Connect team API key, which has a
key ID and an issuer ID (App Store Connect → Users and Access → Integrations →
Team Keys), with the Admin, App Manager, or Developer role: the scheme's
`signing.ascApiKey`, or else the `secrets` adapter's `asc-api-key`. The
`HOT_UPDATER_ASC_KEY*` environment variables in
[Provide signing credentials](#provide-signing-credentials) override it.
Without one, [sign in with your Apple Account](#sign-in-with-your-apple-account)
when asked, and the CLI issues and stores it before it builds; with a read-only
adapter, it writes the key to a file and the same build uploads with it from
there ([where an issued key goes](#where-an-issued-key-goes)). The
CLI resolves the key before the build adapter's prebuild (such as
`expo prebuild`) and the build, so a missing key fails before either runs, and
deletes the key's temporary file when the upload ends.
Certificates and provisioning profiles stay with the build's signing.
[Build and upload from CI](/docs/guides/ci-native-build) uploads from a CI job
with the stored key.

Before the prebuild, the CLI also refuses a scheme whose build App Store
Connect would not take: a simulator scheme, a configuration whose name ends in
`Debug`, and a scheme with neither `signing.ascApiKey` nor an
`exportOptionsPlist`, which only archives. After the prebuild, which may write
the `exportOptionsPlist`, and before the build, it refuses one whose `method`
is not `app-store-connect` (or `app-store`).

After the build, and after `--register` when you pass both, the CLI:

1. Reads the bundle ID, version (`CFBundleShortVersionString`) and build
   number (`CFBundleVersion`) from the `.ipa`'s `Info.plist`.
2. Finds the App Store Connect app with that bundle ID. Create the app in
   App Store Connect first; the key must belong to its team.
3. Uploads the `.ipa` with the App Store Connect API's build uploads.
4. Waits up to 30 minutes for App Store Connect to accept the build, and
   prints the warnings and errors it reports.

App Store Connect takes each build number once per version: raise
`CFBundleVersion` for every build you upload. When an upload fails, the build
stays at its output path. A build that App Store Connect is still processing
after 30 minutes appears in TestFlight once processing finishes, at the URL
the CLI prints.

## Upload to Google Play

Add `--upload play-internal` to upload the `.aab` to Google Play and release
it to the internal testing track:

```package-install
npx hot-updater build:android --scheme release --upload play-internal
```

The upload authenticates with the `secrets` adapter's `play-service-account`, the
JSON key file of a Google Cloud service account.
`HOT_UPDATER_PLAY_SERVICE_ACCOUNT_PATH` (or
`HOT_UPDATER_PLAY_SERVICE_ACCOUNT_JSON`, the file's contents) overrides it.
The CLI resolves it before the build adapter's prebuild (such as
`expo prebuild`) and the build, so a missing one fails before either runs, and
keeps it in memory: it writes the service account to no file.

When the adapter has no `play-service-account` yet, sign in with Google when
asked. In a terminal, the CLI opens Google's sign-in page in your browser and
prints its address, asks for the app's package name and your Play Console
developer account ID (the number after `/developers/` in Play Console's
address), and lets you pick a Google Cloud project or create one. Then it:

1. Checks that the Google Account administers the developer account and that
   Google Play has the app, before it changes anything.
2. Enables the IAM and Google Play Android Developer APIs in the project, and
   creates the service account `hot-updater-play` there.
3. Adds the service account to Play Console as a user that may view the app
   and release it to testing tracks.
4. Creates the service account's JSON key, stores it as
   `play-service-account` ([where an issued key goes](#where-an-issued-key-goes)),
   and continues with the build, which uploads with it.

Google's own page asks for your password, and the CLI keeps only the issued
key. When the key surely went nowhere, the CLI deletes the key again; the service
account and its Play Console access stay, and the next run reuses them.
Builds without a terminal, such as CI, use the stored key and never sign in:
when it is missing, they fail with the command to run once in a terminal,
`npx hot-updater google-play login` (the shortcut for
`secrets issue play-service-account`), which does the same
sign-in without building, keeps a key the adapter already holds, and with
`--replace` issues a new key and names the old one to delete under the service
account's keys in Google Cloud. The sign-in needs a Google OAuth client of your
own, of type Desktop app, in `HOT_UPDATER_GOOGLE_OAUTH_CLIENT_ID` and
`HOT_UPDATER_GOOGLE_OAUTH_CLIENT_SECRET`, until Hot Updater ships one; without
it, the CLI stops before opening the browser.

Before the prebuild, the CLI also refuses a scheme whose build Google Play
would not take as a release: an `.apk` scheme (`aab: false`) and a variant whose name
ends in `Debug`.

After the build, and after `--register` when you pass both, the CLI:

1. Reads the application ID from the `.aab`'s manifest with `aapt2`, with the
   suffixes flavors and build types add, or else uses the scheme's
   `applicationId`.
2. Opens an edit with the Google Play Developer API and uploads the `.aab`.
3. Releases the bundle's version code to the `internal` track and commits the
   edit. When any step fails, it deletes the edit, so nothing is released.

Create the app in Play Console and upload its first `.aab` there by hand:
Google takes a new app's first `.aab` only in Play Console, and the API
releases the builds after it.

To use a service account of your own instead, invite its email under Users
and permissions with permission to release to testing tracks, enable the
Google Play Android Developer API in its Google Cloud project, and store its
key with `secrets put play-service-account --kind play-service-account
--service-account <file>`.

Google Play takes each version code once: raise `versionCode` for every build
you upload. On an app Play Console has not published yet, Google Play takes
only draft releases, so the internal release is a draft that you roll out in
Play Console. When the app's state requires it, the CLI commits without
sending the changes for review, and you send them for review in Play Console.
When an upload fails, the build stays at its output path.
[Build and upload from CI](/docs/guides/ci-native-build) uploads from a CI job
with the stored service account.

## Run on a device

```package-install
npx hot-updater run:android --scheme previewApk
```

```package-install
npx hot-updater run:ios --scheme release
```

`run:android` installs an `.apk` scheme on every connected device, and starts
the first emulator when none is connected. `run:ios` runs on the first booted
simulator or device, or else on the first simulator. Pass
`--device <name or ID>` to pick one, or `-i` to choose from a list. An iOS
device build signs with the scheme's `signing.ascApiKey` when it sets one.

## Command options

| Option                    | Commands        | Description                                                  |
| ------------------------- | --------------- | ------------------------------------------------------------ |
| `-s, --scheme <scheme>`   | all             | The `nativeBuild` scheme to build                            |
| `-i, --interactive`       | all             | Choose the scheme, and with `run:*` the device               |
| `-o, --output-path <dir>` | `build:*`       | Where to copy the build output                               |
| `--register`              | `build:*`       | Register the release build, its artifact and built-in bundle |
| `--json`                  | `build:*`       | Print the build and its registration as JSON, the last line  |
| `--upload testflight`     | `build:ios`     | Upload the `.ipa` to App Store Connect for TestFlight        |
| `--upload play-internal`  | `build:android` | Upload the `.aab` to Google Play's internal testing track    |
| `-d, --device [device]`   | `run:*`         | The device name or ID to run on                              |
| `--port <port>`           | `run:android`   | The Metro port the device reaches with `adb reverse`         |

The commands of the registry, `native-build find` and `native-build delete`,
are described in [Find a build](#find-a-build) and
[Delete a build](#delete-a-build).
