## Turn on the vault

The console serves the vault of `vault()`, Hot Updater's vault plugin, at
`/_hot-updater/vault/v1/`, and signs bundles with the vault's bundle signing
keys at `/_hot-updater/signing`. [Set up the vault](/docs/guides/vault) walks
through turning it on: the master key in the console's runtime environment,
`vault()` in `console.config.ts` and `hot-updater.config.ts` but not in your
server, the vault's tables, the secrets, and CI's tokens.

The console is the only place secrets are decrypted and encrypted. The CLI
reads and stores secrets through the routes below with a vault token, and
issues and revokes tokens over the database. It never opens a value itself,
even where the master key is set or a server definition passes
`vault({ masterKey })`. [Secrets in the CLI](/docs/guides/secrets) covers its
commands.

A console whose `database` is `standaloneRepository(...)` serves no vault: the
secrets live in the server's database, which only a console over that database
opens. Its vault routes answer `404 vault_unavailable`.

## Manage secrets

**Vault** in the console's sidebar lists the secrets by name, kind, version,
and last update, with what each shows without its values, such as a key ID,
a keystore's alias, or a bundle signing key's size and the start of its public
key's SHA-256. **Add secret** picks a kind and asks for its files and
fields. A new secret is named after its kind, and a config references it by
name, such as `vault:asc-api-key`, or `vault:widget-keystore` for a second
keystore.

Values are write-only. The console never shows or copies a stored value:
**Overwrite** stores a new version from values you enter again, and
**Delete** removes the secret with its values. The vault keeps the last five
versions of each secret, and a value holds up to 64 KB of JSON.

Without a master key, `HOT_UPDATER_VAULT_MASTER_KEY` or, after a rotation,
`HOT_UPDATER_VAULT_MASTER_KEYS`, the page shows the vault as locked, names the
keys its secrets were saved with, and offers no add or overwrite. Listing, deleting, and tokens keep working.
The first secret a console stores ties the vault to its key: the vault keeps
a check value sealed under it. From then on, a console with another key is
locked, even once every secret is deleted, so two consoles with different keys
never write into one vault. Restore the vault's key rather than generating a
new one, or [rotate](#rotate-the-master-key) to a new one.
A database without the vault's tables shows the console's migration notice
with the command that adds them.

Each kind's value, as the resolve route returns it. Files are their bytes in
base64:

| Kind                   | Value                                                                                                                                         |
| ---------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| `asc-api-key`          | `{ p8, keyId, issuerId }`, the App Store Connect API key's `.p8` file and its ids                                                             |
| `android-keystore`     | `{ keystore, storePassword, keyAlias, keyPassword }`                                                                                          |
| `play-service-account` | `{ serviceAccount }`, the service account's JSON key file                                                                                     |
| `bundle-signing-key`   | `{ privateKey }`, an unencrypted RSA private key of 2048, 3072, or 4096 bits in PEM (PKCS#8 or PKCS#1), which the resolve route never returns |
| `deploy-credentials`   | Environment variable names and their values, such as `{ "HOT_UPDATER_S3_SECRET": "..." }`                                                     |
| `generic`              | Environment variable names and their values                                                                                                   |

`parseVaultSecretValue(kind, value)` from `@hot-updater/server/plugins` checks
a value's shape, and `vaultSecretMetadata(kind, value)` returns what the
console shows of it. For a bundle signing key, the console also stores
`bits` and `publicKeySha256`, the SHA-256 of its public key, which this
prints for the `public-key.pem` your app ships:

```bash
openssl pkey -pubin -in keys/public-key.pem -outform DER | openssl dgst -sha256
```

## Issue vault tokens

The **Tokens** tab issues, lists, and revokes vault tokens. A token the
console issues reads values, signs bundles, writes values, or any of them,
for the secrets in its scope, named by secret or by kind, and expires after
30 days, 90 days, a year, or never. Bundle signing keys are offered only with
**Sign bundles** or **Write values**: the routes below never return their
values, so reading reaches none, and signing reaches nothing else.
[`hot-updater secrets token create`](/docs/guides/secrets#issue-a-vault-token)
issues the same tokens from the CLI. Every user the console signs in can
manage secrets and tokens.

The token shows once, with the console's address, as two CI variables. CI
sends the token to the routes below:

```bash
HOT_UPDATER_CONSOLE_URL=https://console.example.com
HOT_UPDATER_VAULT_TOKEN=hu_vault_...
```

A token that signs also shows as `HOT_UPDATER_SIGNING_TOKEN`, the signing
token `remoteSigning` sends to [the signing route](#sign-bundles).

The list shows each token's prefix, scope, expiry, and creation date.
Revoking one refuses its next request.

## Authenticate with a vault token

Send a vault token in every request:

```http
Authorization: Bearer hu_vault_...
```

The routes take no session cookie and no client API key, so the console's
sign-in and email allowlist never apply to them. The token's scope decides
which secrets a request reaches. An optional `x-hot-updater-ci-run` header,
such as a CI run URL, is kept in the audit log. Every response is
`Cache-Control: no-store`.

## List secrets

`GET /_hot-updater/vault/v1/secrets` returns the secrets the token's scope
reaches, for any of its actions, without values. A token that only writes
lists metadata this way and reads no value:

```json
{
  "secrets": [
    {
      "id": "sec-...",
      "name": "release-keystore",
      "kind": "android-keystore",
      "version": 3,
      "metadata": {},
      "createdAtMs": 1790000000000,
      "updatedAtMs": 1790000000000
    }
  ]
}
```

## Resolve values

`POST /_hot-updater/vault/v1/resolve` with `{ "names": [...] }`, 1 to 100
secret names of 1 to 64 letters, digits, dots, dashes, or underscores, returns
their current values in one response. The token's scope
must allow `read` on each:

```json
{
  "secrets": [
    {
      "name": "release-keystore",
      "kind": "android-keystore",
      "version": 3,
      "value": { "storePassword": "..." }
    }
  ],
  "errors": [
    {
      "name": "play-account",
      "code": "not_found",
      "message": "No secret is named play-account."
    }
  ]
}
```

- Any name outside the token's scope refuses the whole request with 403,
  whether or not a secret has it. A name with no secret is a `not_found` entry
  in `errors` only when the scope lists that name.
- A `bundle-signing-key` is never resolved, even in scope: the console signs
  bundles with it at `/_hot-updater/signing`.
- Each value is the version the token was authorized for. A secret rotated
  or replaced during the request is authorized again at its new version.
- Each value read and each refused name is written to the vault's audit log
  before the response is sent.

## Write a secret

`PUT /_hot-updater/vault/v1/secrets/:name` with `{ "kind", "value" }` stores
`value` as the secret's next version, or creates the secret when no secret
has the name. `value` is the kind's shape from the table above, files in
base64. The console encrypts it with its master key and answers with the
secret's metadata, never its value: `201 { "secret" }` for a new secret, or
`200 { "secret" }` for a new version.

```json
{
  "kind": "android-keystore",
  "value": {
    "keystore": "/u3+7QAAAAIAAAAB...",
    "storePassword": "...",
    "keyAlias": "upload",
    "keyPassword": "..."
  }
}
```

- The token's scope must allow `write` on the name or the kind, and on the
  secret the write replaces. Anything else refuses the request with 403,
  whether or not a secret has the name.
- `write` never returns a value. A `bundle-signing-key` can be written, such
  as one `hot-updater keys generate --vault` made, and is still never
  resolved.
- An optional `"expectedVersion"` stores the value only while the secret is at
  that version, and `0` only when no secret has the name, as
  `hot-updater keys generate --vault` and `hot-updater secrets import` send.
- A secret of another kind under the name, a secret at another version than
  `expectedVersion`, or a secret that changed during the request, is a 409.
- Each write, and each one the scope refuses, is written to the vault's audit
  log before the response is sent.

## Sign bundles

`GET` and `POST /_hot-updater/signing` serve the
[remote signing protocol](/docs/guides/signing/remote) of `remoteSigning`
from `hot-updater/signing` with a `bundle-signing-key` from the vault. A
deploy sends a vault token as the protocol's signing token,
`x-hot-updater-signing-token`, which `remoteSigning` reads from
`HOT_UPDATER_SIGNING_TOKEN`.
[Sign with the Console vault](/docs/guides/signing/remote#sign-with-the-console-vault)
sets it up.

- The token's scope must allow `sign` on exactly one bundle signing key, the
  key the console signs with. Scope a sign token by name to pick one key
  among several, such as one per app.
- The token is verified, and the key chosen, before the key is opened. `GET`
  returns the key's public key, and `POST` signs one 32-byte message.
- Each signature, and each verified token whose scope reaches no single key,
  is written to the vault's audit log before the response is sent. Public key
  requests are not logged.
- Refusals use the codes below. A request the protocol itself refuses, such
  as a malformed body, answers `{ "error" }` with 400 or 405.

## Rotate the master key

Rotation moves the vault to a new master key without decrypting any value.
Each stored version keeps its ciphertext; only its data key is wrapped again
under the new key.

1. Generate a key with `openssl rand -base64 32`, and give it a key ID: 1-32
   letters, digits, dots, dashes, or underscores, such as `2026-10`.
2. In the console's runtime environment, list it first in
   `HOT_UPDATER_VAULT_MASTER_KEYS`, as `kid:key` pairs separated by commas.
   The first key seals new values, and every listed key opens what was sealed
   under it. The key in `HOT_UPDATER_VAULT_MASTER_KEY` is the key ID
   `default`, so either list it as well:

   ```bash
   HOT_UPDATER_VAULT_MASTER_KEYS="2026-10:<new key>,default:<current key>"
   ```

   or keep `HOT_UPDATER_VAULT_MASTER_KEY` beside a list of the new key alone:
   when both are set, it follows the listed keys as `default`. Redeploy the
   console. A key ID listed twice, or a `default` in both that is not the same
   key, locks the vault with a message that names the variable.

3. Open **Vault → Master keys**. It lists each key with the stored versions
   under it. **Rewrap** moves them to the new key in batches of 100 and counts
   down until none are left. CI keeps resolving secrets while it runs, and
   writes during it are sealed under the new key.
4. When every version is under the new key, the vault forgets the old one,
   and the page says which keys can leave the environment. When nothing is
   stored under the old key, such as after every secret was deleted,
   **Finish rotation** does the same without moving anything. Remove them and
   redeploy:

   ```bash
   HOT_UPDATER_VAULT_MASTER_KEYS="2026-10:<new key>"
   ```

Every console that serves the vault needs the new key before the old one is
removed. A console that still holds only the old key is locked once the vault
forgets it. Versions under a key the console does not hold stay where they
are, and the page names that key, so add it after the new one and rewrap
again.

Rewrapping needs the master keys, so only the console runs it. The CLI never
rewraps, as it never reveals a value. Over the database,
`hotUpdater.api.vault.keys()` returns the same per-key counts, with whether
the vault still knows each key, and
`rewrap({ batch })` moves one batch and returns `{ rewrapped, remaining }`.

A vault whose key is lost cannot be opened or rotated. To start over with a
new key, delete the vault's rows from `vault_secrets` and
`vault_secret_versions`, including the `.master-keys` row that holds the key
checks, and store the secrets again.

## Errors

Refusals are `{ "error": { "code", "message" } }`:

| Status | Code                  | Cause                                                                                                                                                                                                                        |
| ------ | --------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 400    | `invalid_request`     | The resolve body is not `{ "names": [...] }` with 1 to 100 secret names, or a write's name, kind, or value is not one the vault takes                                                                                        |
| 401    | `unauthorized`        | No token, or a token that is unknown, revoked, or expired. For signing, no `x-hot-updater-signing-token`                                                                                                                     |
| 403    | `forbidden`           | The scope does not allow `read`, `write`, or `sign`, a name is out of scope, a resolved name is a `bundle-signing-key`, or a sign token reaches no bundle signing key or several                                             |
| 404    | `vault_unavailable`   | The console runs without `vault()`, or over `standaloneRepository(...)`                                                                                                                                                      |
| 409    | `conflict`            | The named secrets kept changing while the console read them, a write met a secret of another kind or another version than its `expectedVersion`, or the secret changed during a write or a signature; send the request again |
| 500    | `invalid_signing_key` | The bundle signing key is not an unencrypted RSA private key of 2048, 3072, or 4096 bits                                                                                                                                     |
| 503    | `vault_locked`        | No master key is set where the console runs, the master keys are malformed, a value was sealed under a key the console does not hold, or for a write, the console's keys are not the vault's                                 |

A 401 from the vault routes also carries
`WWW-Authenticate: Bearer realm="hot-updater-vault"`.
