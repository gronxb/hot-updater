description: "Create v1 infrastructure alongside v0, then move new native builds to it."

Hot Updater v1 is a new infrastructure generation. It separates immutable
Bundle artifacts from mutable Release policy and serves compiled Release
Catalogs. The v0 update-check protocol and database layout are not compatible
with this model.

<Callout type="warn">
  There is no in-place v0 database or protocol upgrade. Keep v0 metadata and
  endpoints intact, scaffold v1 alongside them, and ship the v1 endpoint in a
  new native app build.
</Callout>

## Compatibility boundary

| Combination                           | Supported | Action                                                               |
| ------------------------------------- | --------- | -------------------------------------------------------------------- |
| v0 native app → v0 infrastructure     | Yes       | Keep the old endpoint running while those binaries need OTA updates. |
| v0 native app → v1 infrastructure     | No        | v1 does not expose the v0 app-version or fingerprint routes.         |
| v1 native app → v0 infrastructure     | No        | Release Catalog and artifact routes are required.                    |
| v1 init → v0 database layout or endpoint | No      | Use a separate v1 database namespace and endpoint.                    |
| v1 native app → new v1 infrastructure | Yes       | This is the supported target.                                        |

Do not deliver v1 `@hot-updater/react-native` JavaScript to a v0 native binary
by OTA. Receipt and rollback behavior requires the v1 native module.

## Cutover procedure

### 1. Preserve v0

Record the v0 public endpoint, provider resource identifiers, configuration,
and credentials. Back up its metadata database. Do not delete or repurpose the
old resources: installed v0 binaries may still call that endpoint.

### 2. Scaffold v1 alongside v0

Upgrade all `hot-updater` and `@hot-updater/*` packages together, then run:

```bash
npx hot-updater init
```

Use a separate v1 database namespace and endpoint. Firebase and Supabase can
reuse the existing project: v1 uses `hot_updater_v1_*` collections or tables and
a separate `hot-updater-v1` function. Their init checks the v1 namespace rather
than rejecting a project merely because it contains v0 data. Cloudflare needs
a separate D1 database; init rejects a v0 D1 database or an existing v0 endpoint
instead of upgrading it.

Storage buckets do not have to be new, but preserve the access policies and
objects still needed by v0. Do not prune shared storage using only the v1
database while v0 binaries still need those artifacts.

The v1 scaffold starts with an empty Release history. Redeploy the releases you
want to serve from their source artifacts; v0 policy is not backfilled.

### 3. Update CLI automation to use console IDs

v1 separates immutable Bundle artifacts from mutable Release policy. Update
scripts before writers resume:

| v0 command or assumption | v1 command or meaning |
| --- | --- |
| `bundle list --channel ... --target-app-version ...` | Use `release list --channel ... --platform ...` for channel filtering. `bundle list` shows the same update IDs as the console. |
| `bundle show <bundle-id>` for rollout or enabled state | Use `bundle show <id>` or `release show <id>` with the console ID, also returned by `HotUpdater.getBundleId()`. |
| `bundle update <bundle-id>` | `release update <release-id>` |
| `bundle enable <bundle-id>` | `release enable <release-id>` |
| `bundle disable <bundle-id>` | `release disable <release-id>` |
| `bundle promote <bundle-id>` | `release promote <source-release-id> --target <channel>` |
| top-level `rollback <channel>` or `--target <bundle-id>` | Identify the exact Release and run `release disable <release-id>`. The Bundle-targeted rollback command is removed. |
| Delete an old Bundle directly | Disable and hard-delete every referencing Release, then run `bundle delete` and preview `storage prune`. |

Deploy and promote create independent update IDs. Multiple updates can reuse
the same files.

Promotion reuses Bundle bytes and never copies Storage objects. Its target
Release is enabled with a 100% numeric rollout, no target cohorts, and a new
rollout seed. Review that policy in the command preview before
confirming, especially when the source Release had a partial or QA-only rollout.

### 4. Verify the v1 endpoint

Run doctor against the generated public base URL:

```bash
npx hot-updater doctor --server-base-url https://updates.example.com
```

A v1 endpoint reports `infrastructureGeneration: 1` from `/version`. If the
marker is missing, doctor reports that in-place upgrade is blocked and directs
you back to init with new resources.

### 5. Publish a new native build

Refresh the native project before building. v1 requires its complete native
source set and does not support a stale v0 CocoaPods project.

For Expo projects, run:

```bash
npx expo prebuild
```

For bare React Native iOS projects, run:

```bash
cd ios && pod install && cd ..
```

Build and release the app with the v1 native SDK and the new v1 endpoint. Test
catalog fetch, artifact resolution, install, restart, and rollback before
making the release broadly available.

A store-delivered native upgrade can preserve the app's local sandbox even
though its server generation is fresh. The v1 native SDK therefore migrates
Bundle-ID-only metadata, reads retained local `BUNDLE_ID` artifacts, and keeps
the existing cohort identity. This on-device bridge does not read or migrate
the v0 server database or remote storage.

The endpoints remain parallel during adoption:

- Existing v0 binaries continue using the v0 endpoint.
- New v1 binaries use the v1 endpoint.

There is no server-side compatibility bridge between them.

## Rollback

To roll back a v1 mobile release, publish another native build or restore the
previous v1 deployment while keeping its endpoint and database generation.
Do not point v1 binaries at v0 infrastructure.

Removing the old v0 infrastructure is an operational decision based on your
remaining installed v0 population. Once removed, those binaries lose OTA
service but continue to launch their embedded or last installed bundle.
