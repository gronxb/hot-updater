## Plan the migration

Hot Updater v1 is a new infrastructure generation. It separates immutable
Bundle artifacts from mutable Release policy and serves compiled Release
Catalogs. The v0 update-check protocol and database layout are not compatible
with this model.

<Callout type="warn">
  There is no in-place v0 database or protocol upgrade. Keep v0 metadata and
  endpoints intact, scaffold v1 alongside them, and ship the v1 endpoint in a
  new native app build.
</Callout>

## Compatibility boundary

| Combination                           | Supported | Action                                                               |
| ------------------------------------- | --------- | -------------------------------------------------------------------- |
| v0 native app → v0 infrastructure     | Yes       | Keep the old endpoint running while those binaries need OTA updates. |
| v0 native app → v1 infrastructure     | No        | v1 does not expose the v0 app-version or fingerprint routes.         |
| v1 native app → v0 infrastructure     | No        | Release Catalog and artifact routes are required.                    |
| v1 setup → v0 database layout or endpoint | No     | Use a separate v1 database namespace and endpoint.                    |
| v1 native app → new v1 infrastructure | Yes       | This is the supported target.                                        |

Do not deliver v1 `@hot-updater/react-native` JavaScript to a v0 native binary
by OTA. Receipt and rollback behavior requires the v1 native module.

## Ask your agent to migrate

Install the [Hot Updater skill](/docs/guides/ai-agents) from your project:

```sh
npx skills@latest add hot-updater/skills
```

Then ask your coding agent:

```text
$hot-updater Migrate this project from Hot Updater v0 to v1 using the latest stable v1 release.
Inspect the app and existing provider first. Keep v0 endpoints and data available
for installed apps, and provision separate v1 infrastructure. Update the SDK,
build and provider packages, app URL and client authentication, existing signing
setup, and native/OTA build environment variables. Prepare a new native build
and verify OTA delivery, rollback, and Insights in a dedicated test channel.
Report the verified results and any remaining native release steps.
```

The agent discovers the app root, build system, provider and existing resources.
You can name your provider if you already know it; you do not need to collect
resource IDs first. Authenticate through provider login or private credential
storage when needed. Do not paste tokens or private keys into the conversation.

The agent installs `hot-updater` and the required `@hot-updater/*` packages
in the app's workspace, records their installed versions and keeps the lockfile.
Install the SDK and required plugins before generating infrastructure templates.
The [installation guide](/docs/get-started/installation) lists the package choices.

The installed CLI must support `hot-updater agent infra upgrade`. The agent
reads the generated upgrade instructions, applies the provider templates, and
merges the app configuration. Template generation alone does not deploy the
server or finish the migration. See [Agent Infrastructure](/docs/guides/agent-infrastructure)
for runtime requirements and the full workflow.

## Review the migration

Have the agent complete these steps and include their results in its report.

### 1. Preserve v0

Record the v0 public endpoint, provider resource identifiers, configuration,
and credential locations. Back up its metadata database. Keep the old resources
serving installed v0 binaries throughout adoption.

### 2. Provision v1 alongside v0

The agent uses `hot-updater agent infra upgrade`, reads the applicable versioned
upgrade files, and creates the required v1 resources with your provider tools.

Use a separate v1 database namespace and endpoint. Firebase and Supabase can
reuse the existing project: v1 uses `hot_updater_v1_*` collections or tables and
a separate `hot-updater-v1` function. Cloudflare needs a separate D1 database
and Worker. Keep each provider's v0 resources intact.

Managed initialization rejects selected v0 resources before mutating them.
Self-hosted SQL and MongoDB schema initialization also rejects v0 schema
markers; create schema `1.0.0` on empty storage using the selected adapter's
schema workflow. Do not erase a marker to force an in-place upgrade.

For AWS, create separate v1 DynamoDB, Lambda and CloudFront resources. Preserve
the old Lambda name and distribution ID in the v0 deployment configuration.
The v1 configuration must use the new `HOT_UPDATER_AWS_LAMBDA_NAME` and
`HOT_UPDATER_CLOUDFRONT_DISTRIBUTION_ID` after provisioning.

Storage buckets do not have to be new, but preserve the access policies and
objects still needed by v0. Do not prune shared storage using only the v1
database while v0 binaries still need those artifacts.

The v1 scaffold starts with an empty Bundle history. Redeploy the Bundles you
want to serve from their source artifacts; v0 policy is not backfilled.

### 3. Update the app URL, client key and build environment

Update the app's `HotUpdater.init()` or `HotUpdater.wrap()` configuration to use
the v1 server base URL. For example, replace a v0 URL ending in
`/api/check-update` with the new v1 base URL. The SDK appends the Release Catalog
and artifact routes itself. Preserve any base path required by your provider
or custom server.

Managed providers require the client API key in `requestHeaders["x-api-key"]`.
The agent registers or reuses that key in the new v1 infrastructure and connects
it to the app's build-time configuration. Only the client key belongs in the
app; Cloudflare, R2 and other provider credentials remain on the deployment
machine or server.

For an Expo app using public environment variables, the resulting setup can
look like this:

```tsx
import { HotUpdater } from "@hot-updater/react-native";

HotUpdater.init({
  baseURL: process.env.EXPO_PUBLIC_HOT_UPDATER_BASE_URL!,
  requestHeaders: {
    "x-api-key": process.env.EXPO_PUBLIC_HOT_UPDATER_API_KEY!,
  },
  insights: true,
});
```

Have the agent verify that both values reach native builds **and OTA bundle
builds**, including CI/EAS environments. Writing `HOT_UPDATER_API_KEY` to
`.env.hotupdater` alone does not configure the app runtime. Check the project's
environment-loading path and fail the build when required values are missing.
An app that skips initialization when its URL is absent can appear healthy
while OTA and Insights are inactive.

See the [Cloudflare guide](/docs/managed/cloudflare) for a managed-provider
example, or [API Key Authentication](/docs/custom/api-key-authentication) for
a custom server.

### 4. Update Expo configuration and preserve bundle signing

For Expo, replace the old `@hot-updater/react-native` entry in
`app.json` or `app.config.ts` **plugins** with `@hot-updater/expo`. Keep
`@hot-updater/react-native` installed as the runtime SDK. Preserve the app's
channel and other unrelated plugin options.

If the app already uses bundle signing, retain its signer only if it meets the
RSA minimum of 2048 bits and export the matching SPKI PEM public key. Weaker or
unsupported keys require a replacement through the
[native-first rotation procedure](/docs/guides/bundle-signing#key-rotation).
A signed Expo app's plugin entry looks like this:

```json title="app.json"
{
  "expo": {
    "plugins": [
      [
        "@hot-updater/expo",
        {
          "channel": "production",
          "publicKeyPath": "./keys/public-key.pem"
        }
      ]
    ]
  }
}
```

For an app without bundle signing, omit `publicKeyPath`. For a signed app,
include `keys/public-key.pem` in source control and native build inputs while
keeping private keys ignored. If `keys/` is ignored, replace that rule with
`keys/*` and `!keys/public-key.pem` so the public file can be included.

The Expo plugin reads `publicKeyPath` explicitly. Enabling signing in
`hot-updater.config.ts` alone does not embed the public key. For bare React
Native, have the agent export the public key to the native projects with
`hot-updater keys export-public`. Verify that the native key matches the
deployment signer before building. See [Bundle Signing](/docs/guides/bundle-signing).

Remove `publicKeyPath` from any local, KMS or remote `signing` configuration;
the signer derives its own public identity. Expo's app-plugin configuration
owns the native public file. Retaining the same signing key still requires a
new native build with the v1 SDK and endpoint. If the key changes, ship that
new native trust anchor before serving artifacts signed by the replacement
key to that app population.

### 5. Verify infrastructure and build the native app

The agent runs `hot-updater doctor --json --server-base-url <v1-base-url>` from
the app directory and the scaffold's `app/verify-server.mjs` helper, or the
[shared client-access check](/docs/guides/simulator-test#verify-client-access)
when using custom infrastructure. The new
`/version` response must report `infrastructureGeneration: 1` and the expected
server version. Verify an authenticated catalog request as well: a public
`/version` response alone does not prove the app's client key works.

After updating app configuration, the agent refreshes Expo native projects with
`npx expo prebuild`, or bare iOS dependencies with `pod install` from `ios/`.
Build a release binary containing the v1 native SDK, endpoint, client key and
the matching signing public key when signing is enabled.

### 6. Verify OTA on the new native build

Use a dedicated test channel and a release build whose channel and app-version
or fingerprint target match the test updates. Have the agent record:

- The old endpoint still serves a retained v0 binary.
- The new native build starts from its embedded bundle and applies a baseline
  v1 OTA update after restart.
- A second update changes JavaScript and an asset; both appear after restart.
  If bundle diffing is enabled, verify a partial update from the baseline.
- Disabling the test update restores the expected baseline on the next update
  check and reload; record the affected update IDs.
- A controlled startup failure in the test channel recovers to a working bundle.
- Insights reports the expected application and recovery outcomes when enabled.

Keep server deployment, native launch, OTA application and store release as
separate verification results. A successful upload with rollout 0 does not
prove that a device downloaded or applied the update.

### 7. Release the new native app

Ship the verified v1 native build before targeting it with production v1 OTA
updates. Update CI to use the v1 provider configuration, app build variables,
signer and compatibility target. Keep a separate v0 deployment configuration
for any OTA releases still needed by installed v0 binaries.

A store-delivered native upgrade can preserve the app's local sandbox even
though its server generation is fresh. The v1 native SDK migrates
Bundle-ID-only metadata, reads retained local `BUNDLE_ID` artifacts, and keeps
the existing cohort identity. Verify an upgrade from a retained v0 installation
without clearing app data. This on-device bridge does not migrate the v0 server
database or remote storage.

The endpoints remain parallel during adoption: existing v0 binaries use the v0
endpoint, and new v1 binaries use the v1 endpoint. There is no server-side
compatibility bridge between them.

## Update custom server and provider integrations

Managed users should apply their provider's v1 scaffold. If you maintain custom
server code or plugins, update these boundaries before connecting a v1 app:

| v0 surface | v1 replacement |
| --- | --- |
| Unified `createHandler`, `createHotUpdater().handler`, `HandlerOptions` | Separate `createHandlers(...).client/admin` or `createHotUpdater().handlers.client/admin`. Mount the admin handler behind framework authentication before the broader client mount. |
| `toNodeHandler(hotUpdater)` | Pass the individual handler, such as `toNodeHandler(hotUpdater.handlers.admin)`. |
| `storages`, `storagePlugins` | `storage: [storagePlugin]` in `createHotUpdater`. |
| Database/storage `() => plugin` thunks | Pass plugin objects directly to `createHotUpdater` and `defineConfig`. Built-in provider factories already return those objects. |
| `features.clientAccessKeys` | Required `clientAccess: { type: "api-key" }` or explicit `{ type: "public" }`. API-key mode uses `x-api-key`, or your configured `headerName`. |
| `features`, `features.bundles`, `features.updateCheck`, server Insights flags and `queryAccess` | Mount the handler surfaces explicitly. Client ingestion and admin query routes are always present; opt out of SDK reporting with `insights: false`. |
| Server `basePath` | Let the framework own the mount path and use that client root as the app's `baseURL`. |
| `authorityId`, server `cwd`, runtime request-context parameters | Remove these settings. Catalog identity is automatic; capture credentials, SDK clients and runtime bindings when constructing plugins. Handlers take one `Request`. |
| `standaloneRepository.baseUrl` pointing at a shared client root | Use the exact admin root, such as `https://example.com/hot-updater/admin`; fixed operations use paths relative to it. Remove a custom `routes.channels` override. |

The app receives the client API key, never the admin bearer token. Protect the
admin mount with middleware and fail startup if its credential is missing.
Follow the [framework recipes](/docs/custom/overview#server-frameworks) and
[API key lifecycle](/docs/custom/api-key-authentication).

The v0 `/app-version/...` and `/fingerprint/...` decision endpoints and
`Hot-Updater-SDK-Version` header contract are removed. The client reads
`/release-catalogs/app-version/:platform/:channelKey/:appVersion` or
`/release-catalogs/fingerprint/:platform/:channelKey/:fingerprintHash`, selects
locally, then resolves `/artifacts/:targetBundleId/from/:currentBundleId`.
Channel names are encoded into `channelKey`; neither Catalog path includes an
installation identity. Do not add an API-version prefix to these routes.
Persistent Channel management uses the authenticated admin root's
`/channels[/:id]`, not `/api/bundles/channels`.

### Database and storage implementations

Custom database providers implement the fixed `bundles`, `bundlePatches`,
`releases`, `releaseCatalogs`, `channels`, `insights` and `apiKeys` models,
plus ordered atomic `commit({ changes, expectations })` and optional `dispose`.
This replaces the factory/double-curried contract and top-level
`getBundleById`, `getBundles`, `getChannels`, `getUpdateInfo`, `commitBundle`
and `onUnmount`. Provider query DSLs and provider-owned update selection are
not extension points. Use the
[database conformance guide](/docs/database-plugins/custom-database).

`LegacyBundle` is removed. Delivery fields (`channel`, `enabled`,
`fingerprintHash`, `message`, `rolloutCohortCount`, `shouldForceUpdate`,
`targetAppVersion`, `targetCohorts`) belong to Release policy, while the immutable
Bundle row owns artifact data. Release and artifact UUIDv7 IDs are independent;
several Releases may reuse one artifact. Channels are persistent identities
referenced by `channel_id`. Represent patches only through `Bundle.patches`,
not `patchBaseBundleId`, `patchBaseFileHash`, `patchFileHash` or `patchStorageUri`.

Storage providers implement the flat `createStoragePlugin` object contract.
Replace `supportedProtocol` with `protocol`; remove `profiles.node`,
`profiles.runtime`, lifecycle hooks, runtime contexts and local-file-path
inputs. Each operation accepts and returns an object. `put` consumes a one-shot
Web stream; `get` returns `{ response }`, `getDownloadUrl` returns `{ url }`,
`exists` returns `{ exists }`, and single-object deletion returns
`{ deleted: true }`. Use `createStorageUri`/`parseStorageUri` and the
[storage contract](/docs/storage-plugins/custom-storage), including optional
explicit-key pruning. Fresh v1 assets use content hashes; do not rely on the
v0 mutable per-Bundle asset layout or its cleanup fallback.

### Replace removed provider exports

| Package and removed surface | Replacement |
| --- | --- |
| `@hot-updater/aws`: `s3Database` | `dynamoDB`; S3 stores artifacts. |
| `@hot-updater/aws`: `s3LambdaEdgeStorage` | `s3Storage`. |
| `@hot-updater/aws`: `withCloudFrontSignedUrl` | `s3Storage({ getDownloadUrl: cloudFrontDownloadUrl(...) })`; see [S3 download URLs](/docs/storage-plugins/aws). |
| `@hot-updater/cloudflare/worker`: context-derived database/storage | `d1Database(binding)` and `r2Storage({ bucket, bucketName, downloadUrlSigningKey })` with native bindings; see [Worker storage](/docs/storage-plugins/cloudflare). |
| `@hot-updater/cloudflare/worker`: `verifyJwtSignedUrl` | The server storage-download handler. |
| `@hot-updater/supabase`: root `supabaseEdgeFunctionDatabase` and `supabaseEdgeFunctionStorage` | `supabaseDatabase` and `supabaseStorage` from `@hot-updater/supabase/edge`. |
| `@hot-updater/js`: `verifyJwtSignedUrl`, `withJwtSignedUrl` | Provider-owned download URL handling or the server storage handler. |
| `@hot-updater/js`, `@hot-updater/postgres`: `getUpdateInfo` | Release Catalog compilation and exact reads, then device selection; disable the public Bundle for rollback. |
| `@hot-updater/plugin-core`: `createBlobDatabasePlugin` | A database that can atomically commit the fixed Release/Catalog models. |
| `@hot-updater/plugin-core`: `createNodeStoragePlugin`, `createRuntimeStoragePlugin`, `createUniversalStoragePlugin` | `createStoragePlugin` with flat operations. |
| `@hot-updater/plugin-core`: `createRequestUpdateBundleResolver`, `getRequestUpdateBundleSeeds` | `createRequestBundleResolver` for request-scoped artifact reads. |

Server-side `s3Storage` does not implicitly produce S3 presigned URLs. Configure
`downloadUrlSigningKey` or an explicit `getDownloadUrl` implementation. CLI-only
upload storage does not need a download URL resolver.

## Update app lifecycle handlers

Use `HotUpdater.init` with the [custom update flow](/docs/guides/custom-update),
or keep `HotUpdater.wrap` for automatic startup updates. Do not configure both;
mixed usage reports a one-time `console.error`. Replace any old
`wrap({ updateMode: "manual" })` integration with `init + checkForUpdate`.

Remove `resolver`, client `authorityId`, `HotUpdaterResolver`, resolver helper
types and `createDefaultResolver`. A custom GraphQL/RPC backend must expose the
v1 Catalog, artifact, Insights-event and `/version` HTTP protocol through an
adapter or proxy; configure that endpoint as `baseURL`.

Update `onNotifyAppReady` and direct `notifyAppReady()` consumers for the
[`NotifyAppReadyResult` union](/docs/react-native-api/notifyAppReady#return-value):
`STABLE` becomes `UNCHANGED`, applied transitions return `UPDATE_APPLIED`, and
recovery uses `fromBundleId`/`toBundleId` instead of `crashedBundleId`. Optional
`fromReleaseId`/`toReleaseId` carry selection identities. Handle each status
before reading transition fields. Lifecycle reporting is enabled by default
for both initialization APIs; set `insights: false` to opt out.

The positional `updateBundle(bundleId, fileUrl)` overload is removed. Prefer
`updateInfo.updateBundle()` from `checkForUpdate`, which resolves the selected
artifact and preserves the transition, or pass the complete parameter object
to the [direct API](/docs/react-native-api/updateBundle).

## Update deployment automation

The public CLI keeps the v0 Bundle workflow. The ID printed by deploy is the
same ID shown in the Console and returned by `HotUpdater.getBundleId()`:

| v0 command or assumption | v1 command or meaning |
| --- | --- |
| `bundle list --channel ... --target-app-version ...` | Unchanged; the rows use the Console ID. |
| `bundle show <bundle-id>` | `bundle show <id>` with the deploy or Console ID. |
| `bundle update <bundle-id>` | `bundle update <id>` |
| `bundle enable <bundle-id>` | `bundle enable <id>` |
| `bundle disable <bundle-id>` | `bundle disable <id>` |
| `bundle promote <bundle-id>` | `bundle promote <source-id> --target <channel>` |
| `bundle delete <bundle-ids...>` | Delete one disabled public Bundle at a time with `bundle delete <id>`. |
| `patch --bundle-id ... --base-bundle-id ...` | Prefer `--artifact-id` and `--base-artifact-id`; the old names remain deprecated aliases for Artifact IDs. |
| top-level `rollback <channel>` | Identify the exact ID and run `bundle disable <id>`. |
| Delete old immutable bytes directly | Delete the public bundle first, then use Advanced `bundle artifact delete <artifact-id>` and preview `storage prune`. |

Deploy and promote create independent update IDs. Multiple updates can reuse
the same files.

The command names remain familiar, but v0 JSON automation is not schema
compatible. In v1, `bundle list --json` and `bundle show --json` return raw
internal rows; update scripts that depended on the v0 `{ data, pagination }`
list wrapper or v0 Bundle DTO fields.

Promotion reuses uploaded bytes and never copies Storage objects. The target
bundle is enabled with a 100% numeric rollout, no target cohorts, and a new
rollout seed. Review those settings before confirming, especially when the
source bundle had a partial or QA-only rollout.

Use [`bundle preflight` and `--expected-revision`](/docs/guides/console#preview-and-protect-automated-changes)
before automated policy writes. Use
[`db catalog preflight` and `rebuild`](/docs/guides/doctor#check-release-catalogs)
to inspect and repair compiled projections; they do not migrate v0 policy.

## Rollback

To roll back a v1 mobile release, publish another native build or restore the
previous v1 deployment while keeping its endpoint and database generation.
Do not point v1 binaries at v0 infrastructure.

Removing the old v0 infrastructure is an operational decision based on your
remaining installed v0 population. Once removed, those binaries lose OTA
service but continue to launch their embedded or last installed bundle.
