## Set Up Local Signing

[Review the signing rollout](/docs/guides/bundle-signing#choose-and-roll-out-a-signer)
before adding a signer to an existing Hot Updater project.

Local signing fits development and small teams. Its private key can be
exported: anyone who can read it, a developer, a CI job, or anyone with read
access to the secret that holds it, can sign bundles every installed app
accepts. When several people or pipelines deploy, keep the key in
[AWS KMS](/docs/guides/signing/aws-kms) or
[Google Cloud KMS](/docs/guides/signing/google-cloud-kms) instead, where it
never leaves the KMS.

Read the private key through the config's
[`secrets` adapter](/docs/concepts/secrets) with `privateKey`:

```ts title="hot-updater.config.ts"
import { defineConfig } from "hot-updater";

export default defineConfig({
  // [!code ++:4]
  signing: {
    enabled: true,
    privateKey: "secret:bundle-signing-key",
  },
  // ...other config
});
```

With the default `envSecrets()` adapter, `secret:bundle-signing-key` is the
`HOT_UPDATER_BUNDLE_SIGNING_KEY` environment variable, in the environment or
`.env.hotupdater`, holding the RSA private key in PEM. A `.env.hotupdater`
value is one line: put the PEM in double quotes with `\n` for its line
breaks. The CLI reads the secret once per run, when it first derives the
public key or signs, masks it in its output, and keeps it in memory only: it
is never written to disk. A deploy whose secret is missing fails and names
where it looked.

To keep the key in a file instead, set `privateKeyPath`:

```ts title="hot-updater.config.ts"
signing: {
  enabled: true,
  privateKeyPath: "./keys/private-key.pem",
},
```

A local config sets `enabled: true` and exactly one of `privateKey` and
`privateKeyPath`; other shapes are rejected. Omit `signing` or set
`signing: { enabled: false }` to disable signing. Local signing derives its
public identity only from the private key.

## Generate the Key Pair

Generate the key pair and store its private key as the secret:

```bash
npx hot-updater keys generate --secret
```

`--secret <name>` names the secret, `bundle-signing-key` by default. When the
config's `secrets` adapter stores values, the command stores the private key
there and writes only `keys/public-key.pem`. When the adapter is read-only,
such as `envSecrets()`, it writes `keys/private-key.pem` with owner-only permissions
and prints the variable to store it as, such as a CI secret; delete the file
once it is stored. The command never replaces a secret it reads a value
from, since installed apps reject bundles signed with a new key: follow
[Key Rotation](/docs/guides/bundle-signing#key-rotation) instead. A
write-only store, such as
[GitHub Actions secrets](/docs/guides/secrets-adapters/github-actions) outside
a workflow, returns no value, so check that the name is unused there first.

Without `--secret`, the command writes both files for `privateKeyPath`:

```bash
npx hot-updater keys generate --output ./keys --key-size 4096
```

The command creates `private-key.pem` with owner-only permissions and
`public-key.pem`. It refuses to overwrite either existing file; use a fresh
output directory for an intentional rotation. Keep the private file out of
Git, EAS build inputs, artifacts, caches, and logs. Commit the public file and
reference it from the Expo app plugin when using Expo.

## Keep the Public Key with the Project

Newly generated keys inside the project add only the private-key path to
`.gitignore`. If `.gitignore` contains `keys/`, replace that whole-directory rule
with rules that include only the public file before committing it:

```txt title=".gitignore"
# [!code --]
keys/
# [!code ++:2]
keys/*
!keys/public-key.pem
```

For EAS uploads, copy your existing `.gitignore` rules into `.easignore`, then
append these rules to include only the public key ([EAS ignore-file
documentation](https://docs.expo.dev/build-reference/easignore/)):

```txt title=".easignore"
# Keep your existing ignore rules above
# [!code ++:3]
!/keys/
/keys/*
!/keys/public-key.pem
```

Existing ignore rules are not rewritten automatically.

## Embed the Public Key and Release the App

Follow the shared steps for [Expo and EAS Build](/docs/guides/bundle-signing#expo-and-eas-build)
or [React Native CLI](/docs/guides/bundle-signing#manual-public-key-configuration).
Build and release the native app before deploying its first signed OTA bundle.

When replacing an existing key, follow [Key Rotation](/docs/guides/bundle-signing#key-rotation)
before changing the signer used for installed apps.

## Deploy from CI

With `privateKey: "secret:bundle-signing-key"` and `envSecrets()`, give the deploy
job the key as `HOT_UPDATER_BUNDLE_SIGNING_KEY`. No key file is written.

If local PEM custody is required in GitHub Actions, store the key as a secret
in a protected GitHub Environment with required reviewers. Avoid a broadly
available repository or organization secret for production signing
authority: a key read from any secret store is still exportable, and is less
isolated than a KMS or HSM-backed signer.

```yaml title=".github/workflows/deploy.yml"
on:
  workflow_dispatch:

jobs:
  deploy:
    runs-on: ubuntu-latest
    environment: production
    permissions:
      contents: read
    steps:
      - uses: actions/checkout@d23441a48e516b6c34aea4fa41551a30e30af803 # v6
      - uses: actions/setup-node@249970729cb0ef3589644e2896645e5dc5ba9c38 # v6
        with:
          node-version: 22

      - run: npm ci

      - run: npx --no-install hot-updater deploy -p ios
        env:
          HOT_UPDATER_BUNDLE_SIGNING_KEY: ${{ secrets.HOT_UPDATER_BUNDLE_SIGNING_KEY }}
```

With another `secrets` adapter, the job authenticates to that store as its
guide shows, and the CLI reads `bundle-signing-key` from it.

Prefer GitHub OIDC with a KMS signer when available because the workflow then
receives short-lived signing authorization instead of exportable key material.
