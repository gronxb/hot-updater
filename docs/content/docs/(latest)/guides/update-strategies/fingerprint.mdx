## Why Choose Fingerprint?

Fingerprint matches OTA updates to a native build by hashing selected native
inputs. Deploy rejects a hash that differs from the saved `fingerprint.json`,
and the client selects updates matching the hash embedded in its binary.
Compatibility depends on covering the native interface your JavaScript calls.
App Version instead lets you specify compatible version targets manually.

Hot Updater hashes your native dependencies and the React Native version by
default. It excludes your app's own `ios/` and `android/` trees, so you add the
parts of them that JavaScript depends on through `fingerprint.extraSources`.

## Setup

### Install the Fingerprint Library

Hot Updater uses `@expo/fingerprint` to calculate native compatibility hashes.
It is an optional peer dependency of `hot-updater`, so install it in your app
project when using the Fingerprint strategy:

```package-install
npm install @expo/fingerprint --save-dev
```

`@expo/fingerprint` is a standalone Node.js
library that [supports bare React Native projects](https://expo.dev/blog/fingerprint-your-native-runtime).
You do not need to install `expo` or `expo-updates`, use Expo CLI, or migrate your
app to Expo. Hot Updater runs the library when generating and checking
fingerprints; it is not a runtime dependency of your app.

Install development dependencies in CI jobs that build or deploy with the
Fingerprint strategy too. Projects using `appVersion` do not need this package.

### Enable the Fingerprint Strategy

App Version is the default strategy. If you explicitly configured it, replace
that setting with `fingerprint`:

```typescript title="hot-updater.config.ts"
import { defineConfig } from "hot-updater";

export default defineConfig({
  updateStrategy: "appVersion", // [!code --]
  updateStrategy: "fingerprint", // [!code ++]
});
```

### Track the Native Interface

An OTA update replaces only JavaScript, so it stays compatible as long as the
native interface it calls stays the same. Hash that interface, not the native
implementation. Add two inputs of your own:

```typescript title="hot-updater.config.ts (partial)"
import { defineConfig } from "hot-updater";

export default defineConfig({
  updateStrategy: "fingerprint",
  fingerprint: {
    extraSources: [
      // Specs of your own native modules (codegenConfig.jsSrcsDir)
      "src/specs/**/*.{ts,tsx}",
      // Bump by hand for any other native change JavaScript depends on
      "native-compat.txt",
    ],
  },
  // Keep your existing build, storage, database, and plugins configuration.
});
```

- **Specs** are the files codegen reads for your own Turbo Modules and native
  components. Point the glob at the `jsSrcsDir` of `codegenConfig` in your
  `package.json`. Adding or changing a method changes the fingerprint.
- **The marker** is a text file you edit, for example from `1` to `2`, when
  JavaScript starts to depend on a native change the specs don't show: a module
  without a spec, a changed return value, a new permission or `Info.plist` key,
  or a manually linked native library.

Native implementation edits, build settings, and version or build number bumps
leave the fingerprint unchanged, so every store build with the same interface
receives the same OTA updates. Don't add `project.pbxproj` or `build.gradle`:
they hold the version and build number, so every store build would get a new
fingerprint and older builds would stop receiving updates. Don't add
`fingerprint.json`, `Info.plist`, or `AndroidManifest.xml` either;
`fingerprint create` writes the hash into them.

Use file paths or globs. A directory entry such as `"src/specs"` is ignored, and
a path that matches nothing adds no source, so check the sources listed in the
generated `fingerprint.json`. An array applies to both platforms; use
`{ ios: [...], android: [...] }` for platform-only inputs.

Before relying on it, add a method to a spec or change the marker, and run
`npx hot-updater doctor`. It should report that the fingerprint changed and
list that file; then restore the edit. A matching fingerprint only proves the tracked
inputs are unchanged; a native change you didn't record in a spec or the marker
is not blocked.

## Workflow

### Before App Store Submission

**Step 1: Generate Fingerprint**

Before building for App Store, generate the fingerprint:

```package-install
npx hot-updater fingerprint create
```

This creates a `fingerprint.json` file and embeds the hash in your native files:

- iOS: `ios/YourApp/Info.plist`
- Android: application metadata in
  `android/app/src/main/AndroidManifest.xml`

Example `fingerprint.json`:

```json title="fingerprint.json"
{
  "ios": {
    "hash": "11142b9062165fa48665f5efa095dd94e9e45eb0"
  },
  "android": {
    "hash": "c763ed5729a0bcccf23248ee0183ddf9016c2e6e"
  }
}
```

**Step 2: Build and Submit**

Build your app with the embedded fingerprint and submit to the App Store.

**Step 3: Deploy OTA Updates**

After your app is live, deploy JavaScript-only updates:

```package-install
npx hot-updater deploy -p ios
npx hot-updater deploy -p android
```

Hot Updater limits delivery to native builds with the same embedded fingerprint.
Use the [deployment sequence](/docs/guides/deploy#deploy-both-platforms) to stop
the second platform when the first deployment fails.

### When Native Code Changes

After changing a tracked native input, check whether the fingerprint changed:

```package-install
npx hot-updater doctor
```

Doctor compares `fingerprint.json` with the project's fingerprint now. When
they differ, it reports `FINGERPRINT_JSON_STALE` and lists the sources that
changed. Create a new fingerprint then, or run `doctor --fix`, which does the
same:

```package-install
npx hot-updater fingerprint create
```

After creating a new fingerprint, rebuild your app to embed it in the binary
before deploying OTA updates.

## Client Setup

Change the app's existing `checkForUpdate` strategy to `fingerprint` too. The
module below keeps initialization at module scope and shows the matching check:

Keep the `baseURL` and client key from [App setup](/docs/get-started/app-setup).
Managed providers require this client key; provider and admin credentials stay
out of the app.

```tsx title="updates.ts"
import { HotUpdater } from "@hot-updater/react-native";

export const hotUpdater = HotUpdater.init({
  baseURL: "https://your-update-server.com",
  requestHeaders: {
    "x-api-key": "<your-client-api-key>",
  },
  onError: (error) => console.error("Hot Updater failed:", error),
});

export async function checkForAppUpdate() {
  try {
    const updateInfo = await hotUpdater.checkForUpdate({
      updateStrategy: "appVersion", // [!code --]
      updateStrategy: "fingerprint", // [!code ++]
    });

    if (!updateInfo) return;

    const didUpdate = await updateInfo.updateBundle();
    if (didUpdate && updateInfo.shouldForceUpdate) {
      await hotUpdater.reload();
    }
  } catch (error) {
    console.error("Failed to prepare update:", error);
  }
}
```

Call `checkForAppUpdate()` from your app's startup, resume, or user action.
`init` configures the client; it does not check for updates. The helper stages
the selected update, and standard updates take effect on the next runtime
start. Follow [custom update flows](/docs/guides/custom-update) to add progress
and choose when to reload.

The client fetches the fingerprint Release Catalog:

```
GET {baseUrl}/release-catalogs/fingerprint/:platform/:channelKey/:fingerprintHash
```

It evaluates the catalog locally, then resolves the selected artifact through
`/artifacts/v2/:targetBundleId/from/:currentBundleId`.

## How It Works

<a id="javascriptui-changes--ota-update-safe" />

### JavaScript and UI Changes

Component logic, styles, screens, and API calls can be delivered over the air
when they remain compatible with the installed native code. If the tracked
inputs are unchanged, the fingerprint check permits deployment.

<a id="native-code-changes-️-rebuild-required" />

### Native Changes Require a Rebuild

New native modules, React Native upgrades, spec changes, and marker bumps
change the fingerprint and require a new binary. Deploy detects the hash
mismatch and exits:

```text
Fingerprint mismatch. 'hot-updater fingerprint create' to update fingerprint.json
```

Generate the new fingerprint, rebuild and release the native app with that hash,
then deploy updates for it. Generating a fingerprint alone does not rebuild
installed apps. An untracked native change leaves the hash unchanged and is
not blocked; bump the marker when JavaScript depends on it.

## Advanced

### Multiple App Targets

`fingerprint create` automatically handles standard React Native projects. Only configure custom paths if you have:

- iOS app extensions (widgets, share extensions)
- Multiple Android build variants
- Non-standard project structure

```typescript title="hot-updater.config.ts"
import { defineConfig } from "hot-updater";

export default defineConfig({
  updateStrategy: "fingerprint",
  // [!code ++:15]
  platform: {
    ios: {
      infoPlistPaths: [
        "ios/YourApp/Info.plist",
        "ios/YourAppWidget/Info.plist",
        "ios/YourAppExtension/Info.plist",
      ],
    },
    android: {
      androidManifestPaths: [
        "android/app/src/main/AndroidManifest.xml",
        "android/app/src/debug/AndroidManifest.xml",
      ],
    },
  },
});
```

The Android hash is stored as `com.hotupdater.FINGERPRINT_HASH` application
metadata.

Most projects can use the default paths.

### Test a fingerprint update

Follow [Test an OTA update](/docs/get-started/test-ota) with a Release build.
Keep the native inputs and fingerprint unchanged while editing JavaScript or
assets. Deploy without `-t`; the SDK and CLI use the matching fingerprint to
select the update.

If the check fails, use [client-access diagnostics](/docs/guides/doctor#check-client-access).
