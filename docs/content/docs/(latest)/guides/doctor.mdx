## Overview

Use `hot-updater doctor` to check the parts that must agree for OTA updates to
work:

- All Hot Updater packages use compatible versions
- React Native native files are connected to Hot Updater
- Your deployed infrastructure server is not outdated

Run it during setup, after upgrading Hot Updater, or when OTA updates behave
differently after a package update. It validates local configuration and server
version; complete [Test an OTA update](/docs/guides/simulator-test) to verify
actual device delivery and client authentication.

```package-install
npx hot-updater doctor
```

In an interactive terminal, the command asks for your server base URL. Press
Enter to skip the server check.

For AI agents and other automation, use JSON output:

```package-install
npx hot-updater doctor --json
```

`--json` does not prompt for the server URL. Pass `--server-base-url` when you
want the infrastructure check included.

## Check Native Setup

When `@hot-updater/react-native` is installed and native iOS or Android
directories exist, `doctor` checks:

- iOS `AppDelegate` uses `HotUpdater.bundleURL()`
- Android `MainApplication` uses `HotUpdater.getJSBundleFile(...)`
- If `updateStrategy` is `fingerprint`, `fingerprint.json` exists and native
  fingerprint hashes match it
- Signing settings match native public key entries

If any required native setting is missing, rebuild-time OTA configuration is not
healthy yet. Run the command shown by `doctor`, then rebuild the native app.

`doctor` does not require a default channel in native files. If
`HOT_UPDATER_CHANNEL` or `hot_updater_channel` exists, the command reports it as
context only.

For fingerprint projects, fix missing or stale native fingerprint settings with:

```package-install
npx hot-updater fingerprint create
```

## AI Agent Iteration

`doctor --json` returns structured issues that an agent can use without parsing
human-readable terminal output.

Each native issue includes:

- `code`: stable issue code, such as `MISSING_ANDROID_BUNDLE_PROVIDER`
- `platform`: `ios`, `android`, or `project`
- `paths`: related local files when available
- `fixability`: whether the issue is suitable for an agent loop
- `commands`: safe local commands when the fix is command-driven

Use `fixability` as the automation boundary:

| Fixability | Meaning                                                                                            |
| ---------- | -------------------------------------------------------------------------------------------------- |
| `auto`     | The agent may inspect and edit local project files, then rerun doctor.                             |
| `command`  | The agent may run the listed local command, then rerun doctor.                                     |
| `blocked`  | The repair requires external context/access beyond doctor’s local fixes. |

Native wiring, fingerprint creation, and native public key export/removal are
intended to be iterated locally by an agent. Infrastructure failures are marked
as blocked because applying migrations or redeploying a server usually depends
on provider credentials and environment-specific access. During a requested
setup or upgrade, an agent with that access should follow the generated
infrastructure instructions and verify the result. Pause only for a missing
prerequisite, uncertain remote state, or a new consequential decision.

Bundle index repair is only available when the active database adapter exposes
diagnostics hooks. Adapters without those hooks report `not-applicable`.

## Check Infrastructure

To check the deployed server in CI or a non-interactive shell, pass the public
update-check base URL.

```package-install
npx hot-updater doctor --server-base-url https://updates.example.com
```

`doctor` appends `/version` and checks:

```txt
https://updates.example.com/version
```

A passing version check confirms the server meets the installed CLI's
infrastructure requirement. It does not verify a client key, artifact download
or native update application. Use the provider's authenticated verification or
[agent server probe](/docs/guides/agent-infrastructure#verify-completion), then
complete the [OTA test](/docs/guides/simulator-test).

## Update Package Versions

If `doctor` reports version mismatches, install a compatible release channel
for the CLI, SDK and required plugins. For the published v1 prerelease, follow
[Install packages](/docs/get-started/installation) and select each package with
`@rc`. Package RC numbers differ; do not copy the CLI's exact version onto every
package. Keep the lockfile and rerun doctor after installation.

## Update Outdated Infrastructure

If your server is outdated, `doctor` prints:

```txt
Infrastructure update required. Deploy server infrastructure version x.x.x or newer.
```

For managed providers (`aws`, `cloudflare`, `supabase`, `firebase`), choose your
upgrade workflow. If the app/server is still on v0, follow
[Move from v0 to v1](/docs/guides/upgrade-to-v1) before applying templates.

With the [Hot Updater skill](/docs/guides/ai-agents) attached, ask your agent:

```text
$hot-updater Upgrade the server infrastructure at https://updates.example.com and verify it with doctor.
```

The agent identifies the provider and existing resources, generates templates
with `hot-updater agent infra upgrade`, and reads the relevant versioned upgrade
files before applying changes. If it needs access, authenticate through the
provider or a local credential file; keep secret values out of the conversation.
See [Agent Infrastructure](/docs/guides/agent-infrastructure#upgrade-an-existing-server).

  </Tab>

Install the compatible package set for the desired release first. Extract that
release's templates for your provider, for example:

```package-install
npx hot-updater infra scaffold --provider cloudflare
```

Read the returned `upgrades/README.md` and relevant version files, including
intermediate releases, for compatibility and migration order. Apply the required
steps, then use interactive init to deploy to the compatible existing resources:

```package-install
npx hot-updater init
npx hot-updater doctor --server-base-url https://updates.example.com
```

Use the actual server URL for verification. Preserve existing data, keys and
customizations, and follow any resource separation required by the upgrade files.

For a **self-hosted server using `createHotUpdater`**, update all Hot Updater
packages together, including `@hot-updater/server`, apply the relevant migrations,
then redeploy your server and verify it with doctor.

## Options

| Option                    | Description                                             |
| ------------------------- | ------------------------------------------------------- |
| `--server-base-url <url>` | Check deployed infrastructure at `<url>/version`.       |
| `--json`                  | Print a machine-readable result for agents and scripts. |
