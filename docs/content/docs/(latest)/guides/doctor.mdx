## Overview

Use `hot-updater doctor` to check the parts that must agree for OTA updates to
work:

- All Hot Updater packages use compatible versions
- React Native native files are connected to Hot Updater
- `fingerprint.json` still matches the project, for the fingerprint update
  strategy
- The app adds the client plugins that the server's plugins need
- The server's database has run the migrations its core and plugins need
- The server's release catalogs match their Releases
- Your deployed infrastructure server is not outdated
- Where each credential the config reads with `secret()` comes from

Doctor only reports: it writes nothing, and each issue names the command or
edit that [resolves it](#resolve-issues).

Run it during setup, after upgrading Hot Updater, or when OTA updates behave
differently after a package update. The ordinary command validates local
configuration and server version. The [scoped infrastructure checks](#verify-infrastructure-scaffolding)
also verify scaffold files and authenticated server access. Complete
[Test an OTA update](/docs/get-started/test-ota) to verify actual device delivery
and that the installed app sends its client key.

```package-install
npx hot-updater doctor
```

In an interactive terminal, the command asks for your server base URL. Press
Enter to skip the server check.

The last line counts what doctor found. A run with warnings only passes, with
exit code 0. A run with an error exits with code 1:

```txt
◆  All checks passed with 2 warnings.
└  Doctor complete.
```

```txt
└  Doctor found 1 error, 2 warnings.
```

For AI agents and other automation, use JSON output:

```package-install
npx hot-updater doctor --json
```

`--json` does not prompt for the server URL. Pass `--server-base-url` when you
want the infrastructure check included.

## Verify infrastructure scaffolding

Use an explicit scope when an agent or CI needs a completion gate. These checks
run without evaluating the app config and do not require a React Native app in
the current directory.

```bash
npx hot-updater doctor --scope scaffold --infra-dir ./infra --json
```

`scaffold` checks the selected directory against the templates packaged with the
invoked CLI: supported manifest identity and versions, required files and safe
paths, unresolved deployment placeholders, JSON syntax, and provider settings.
Provider checks cover Cloudflare DB/BUCKET bindings and runtime entry point,
Supabase Function authentication configuration, AWS catalog/artifact/version
routes and API-key cache separation, Firebase project/functions selection, the
Vercel rewrite to the supplied Function, and Azure's Function package and route
prefix.
Use the CLI version that generated the scaffold. An older scaffold requires its
matching CLI or a fresh upgrade scaffold; editing its version fields is not an
upgrade.

A newly extracted scaffold normally fails until resource placeholders are filled.
Doctor preserves custom settings and does not demand unchanged template hashes.
It derives required files from the installed CLI, so deleting a manifest entry
cannot hide a missing file. It never runs scripts from the scaffold.

After deployment, require the live server checks too:

```bash
npx hot-updater doctor --scope infrastructure --infra-dir ./infra --json \
  --server-base-url https://updates.example.com \
  --platform ios --channel production --app-version 1.0.0
```

For fingerprint projects, replace `--app-version` with `--fingerprint`. Provide
all target inputs explicitly. When the scaffolded server's plugins protect
client routes, as the managed servers' `apiKeys()` does, doctor reads the client
credential privately from the variable the scaffold's `clientAuth` names
(`HOT_UPDATER_API_KEY`), the app directory's `.env.hotupdater`, or scaffold
`app/client-credential.local`. Conflicting saved credentials block verification.

`infrastructure` reruns scaffold checks, rejects unresolved deployment records,
and verifies `/version` against the scaffold target. It checks the same Release
Catalog URL without a credential (401) and with the saved one (valid catalog
200 or the empty-catalog 404 marked `x-hot-updater-catalog: none`); when the
scaffolded server's client routes are public, it checks only that the catalog
answers without a credential. A 404 without that mark is a failure.
An agent-written `verifiedSteps` entry never replaces a live check.

Both scopes return `details.verification` with `schemaVersion: 1`, `scope`,
`checks`, and `notChecked`. Each check has a stable `code`, a `status` of `pass`,
`fail`, or `blocked`, and actionable `paths` and `resolution` when available. Exit code 0 and `success: true` require every check in the selected
scope to pass. A failed prerequisite leaves dependent checks blocked.

A `resolution` describes remediation; it does not grant or revoke provider
access. Agents may continue already authorized work and then rerun doctor. CI should
use the exit code as the gate, rather than parsing human-readable output or
accepting a recorded completion claim.

These scopes do not verify actual remote resource bindings or migration history,
local storage credentials/write access, artifact downloads, JS/native integration,
or native OTA execution. These boundaries appear in `notChecked`; a scope pass
must not be reported as native OTA success. Run the ordinary doctor for its
existing package/native checks and complete the provider checklist for the
remaining checks.

## Check Native Setup

When `@hot-updater/react-native` is installed and native iOS or Android
directories exist, `doctor` checks:

- iOS `AppDelegate` uses `HotUpdater.bundleURL()`
- Android `MainApplication` uses `HotUpdater.getJSBundleFile(...)`
- If `updateStrategy` is `fingerprint`, `fingerprint.json` exists, native
  fingerprint hashes match it, and it matches the project's fingerprint now
- Signing settings match native public key entries

The native status also shows each platform's app version, the version the
native project builds (`appVersion` in `details.native.ios` and
`details.native.android`). To read only the versions, such as in a release
script, run `hot-updater app-version --json`, which prints
`{ "android": ..., "ios": ... }` with `null` for a platform it can't read.

If a required native setting is missing, run the command shown by `doctor`,
then rebuild the native app.

When `doctor` cannot read the signing key, it reports the warning
`SIGNING_PUBLIC_KEY_UNAVAILABLE` with the reason and does not compare the
native public keys. A signing key the `secrets` adapter doesn't hold also fails
the [Secrets check](#check-secrets). Run doctor where the key's secret is set
to compare the keys.

Without `signing`, `doctor` warns as `deploy` does:

```txt
Bundles are unsigned.
To sign them, run: npx hot-updater secrets issue bundle-signing-key
```

A `signing` value `deploy` refuses, such as a removed signing adapter, is an
error with the same line:

```txt
signing takes secret("bundle-signing-key").
Store your key: npx hot-updater secrets put bundle-signing-key <key.pem>
```

`signing: { enabled: false }` turns signing off without a warning. `--json`
reports both as `details.signing`, with `type`, `message`, `next`, and
`command`.

`doctor` does not require a default channel in native files. If
`HOT_UPDATER_CHANNEL` in iOS `Info.plist` or `com.hotupdater.CHANNEL` in Android
manifest metadata exists, the command reports it as context only.

For fingerprint projects, doctor computes the project's fingerprint as
`fingerprint create` does, which hashes the native inputs and can take a few
seconds. When a platform's fingerprint differs from `fingerprint.json`, doctor
reports `FINGERPRINT_JSON_STALE` and lists the sources that changed, in
`changes` with `--json`. When the hash changed because the fingerprint engine
changed rather than a native input, it reports `FINGERPRINT_ENGINE_CHANGED`
instead and names both engines. A `fingerprint.json` that doesn't record the
current engine, because it predates recorded engines or another engine version
computes the same hash, gets the warning `FINGERPRINT_ENGINE_UNRECORDED`;
recording the engine keeps the fingerprint the same. When it cannot compute the
fingerprint, for example because `react-native config` fails, it reports
`FINGERPRINT_GENERATION_FAILED` with the reason.

Under the App Version strategy, a `fingerprint.json` left in the project is
`FINGERPRINT_JSON_UNUSED`: native builds embed its fingerprint, so the app
would report the fingerprint strategy. Delete it, or set `updateStrategy` to
`"fingerprint"` if that is the strategy you meant.

Fix missing or stale fingerprint settings with `fingerprint create`:

```package-install
npx hot-updater fingerprint create
```

## Check client plugins

A server plugin can name the client plugin an app adds for it, as `insights()`
names the [Insights client plugin](/docs/react-native-api/insights). In a
project that installs `@hot-updater/react-native` and sets `database` in
`hot-updater.config.ts`, `doctor` reads the client plugins that the server
plugins in the config's `plugins` name. It then warns `MISSING_CLIENT_PLUGIN`
for each client plugin that no source file in the project imports:

```text
The server runs a plugin whose client plugin insights the app does not add.
```

Import it from the module the warning names and pass it to
`HotUpdater.init({ plugins })`. When `doctor` cannot load the config's
`database` and `plugins`, it warns `CLIENT_PLUGINS_UNCHECKED` with the reason:
make them load, then rerun `doctor`.

## Resolve issues

Doctor writes nothing. Each issue's `resolution` says what resolves it, and
`commands` lists the commands to run when there are any:

| Issues                                                                                | What resolves it                                                                                                                                                                                                                  |
| ------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `SCHEMA_MIGRATION_PENDING`, on a deployment `hot-updater init` created                | `npx hot-updater init --provider <provider> --from-env-file .env.hotupdater`: it migrates the database and redeploys the server back to back. See [Check the database schema](#check-the-database-schema)                         |
| `SCHEMA_MIGRATION_PENDING`, on a server of your own                                   | `npx hot-updater db migrate <server file>` in the server's project; for Drizzle, Prisma, D1, and Supabase, `npx hot-updater db generate <server file>` and the database's tooling first                                         |
| `MISSING_FINGERPRINT_JSON`, `FINGERPRINT_JSON_STALE`, `FINGERPRINT_ENGINE_UNRECORDED` | `npx hot-updater fingerprint create`, then rebuild the app when the fingerprint changed                                                                                                                                           |
| `FINGERPRINT_JSON_UNUSED`                                                             | Delete `fingerprint.json`, then rebuild the apps, or set `updateStrategy` to `"fingerprint"`                                                                                                                                      |
| `MISSING_PUBLIC_KEY`, `PUBLIC_KEY_MISMATCH`                                           | `npx hot-updater keys export-public`, then rebuild and release the app. Apps already installed keep the previous key and reject bundles signed with the configured one                                                           |
| `FINGERPRINT_ENGINE_CHANGED`                                                          | Your choice: go back to the engine `fingerprint.json` records to keep updating the apps you shipped, or run `fingerprint create` and rebuild them                                                                                |
| `ORPHAN_PUBLIC_KEY`                                                                   | Your choice: `npx hot-updater keys remove`, or enable signing. Removing the key turns off signature verification in the app, which is wrong when signing is set up where this machine cannot see it, such as a variable only CI sets |
| `RELEASE_CATALOG_STALE`                                                               | Any release change in the scope, such as a deploy or `bundle update`, which recompiles its catalog. See [Check Release Catalogs](#check-release-catalogs)                                                                         |
| `RELEASE_CATALOG_IDENTITY_MISSING`                                                    | Restore the scope's catalog row from a backup                                                                                                                                                                                     |

Issues that need a code edit, such as the bundle provider or a client plugin,
name the edit. Infrastructure issues name the command that upgrades the server.

## AI Agent Iteration

`doctor --json` returns structured issues that an agent can use without parsing
human-readable terminal output.

Each native issue includes:

- `code`: stable issue code, such as `MISSING_ANDROID_BUNDLE_PROVIDER`
- `platform`: `ios`, `android`, or `project`
- `paths`: related local files when available
- `resolution`: what resolves it
- `commands`: the local commands to run, when it is resolved by commands

Native wiring, fingerprint creation, and native public key export/removal are
intended to be iterated locally by an agent: make the edit or run the command,
then rerun doctor. Migrating a database or redeploying a server usually depends
on provider credentials and environment-specific access. During a requested
setup or upgrade, an agent with that access should run the command doctor
names or follow the generated infrastructure instructions, and verify the
result. Pause only for a missing prerequisite, uncertain remote state, or a new
consequential decision.

## Check Infrastructure

To check the deployed server in CI or a non-interactive shell, pass the public
update-check base URL.

```package-install
npx hot-updater doctor --server-base-url https://updates.example.com
```

`doctor` appends `/version` and checks:

```txt
https://updates.example.com/version
```

Without `--server-base-url`, doctor checks the server an
[agent infrastructure scaffold](/docs/guides/agent-infrastructure) records in
the CLI's default output, `hot-updater-infra/<provider>/<scaffold>/deployment.json`,
and names that file in `details.infrastructure.recordedIn`. When no scaffold
there records a server, or they record more than one, doctor does not guess: it
reports `details.infrastructureUnchecked`, a warning that the server's version
was not checked, with the command that checks it. A scaffold written elsewhere
with `--output` is verified with `--scope infrastructure --infra-dir <dir>`.

A passing version check confirms the server meets the installed CLI's
infrastructure requirement. It does not verify a client key, artifact download
or native update application. Complete the [OTA test](/docs/get-started/test-ota)
to verify delivery through the app's actual configuration. For a separate server
check during agent provisioning, use the generated
[server probe](/docs/guides/agent-infrastructure#verify-completion).

## Check client access

If the app shows **Update failed**, check the connection settings before
changing your deployment:

1. Use the deployed base URL. Copy the full URL from provider setup,
   including any path prefix. The app must be able to reach it over HTTPS.
2. Pass the client key if your server requires one. Set the registered key
   in `HotUpdater.init`'s `requestHeaders`. Managed providers use `x-api-key`;
   a custom server may configure a different header or public access. Provider
   and admin credentials are not client keys.
3. Check the build environment. The value must be available when building
   both the native Release app and OTA bundles. `.env.hotupdater` configures
   the CLI; it is not automatically loaded into the mobile app. See
   [app configuration](/docs/get-started/app-setup#configure-the-update-client).
4. If using a key, check that it is still active. Inspect its metadata in the
   Console's API keys view. For a custom server, follow [API key management](/docs/custom/api-key-authentication#manage-api-keys).
   Listing a key confirms registration, not that the installed app sends it.

After correcting the initial app configuration, rebuild the Release app and
repeat [Test an OTA update](/docs/get-started/test-ota). Deploy a compatible test
update before checking: a new channel may not have a catalog yet.

For error details, inspect the `checkForUpdate` callback's `onError` value and
the request status in your server logs. A `401` points to the client key or
header. A `404` can mean an empty channel or an incorrect URL; it does not prove
authentication succeeded. Keep keys and request headers out of logs.

A successful download followed by the changed screen after restart verifies
the app's update path. A healthy `/version`, a key listing or a `null` check
result alone does not.

## Check the database schema

When `hot-updater.config.ts` sets `database`, doctor reads it once through the
schema fence, as the server does. The fence compares the database's settings
rows, such as `schema.core` and `schema.<plugin>` for each plugin in the
config's `plugins`, with what this CLI's core and those plugins expect. When a
row is missing or older, doctor reports `SCHEMA_MIGRATION_PENDING` with each
setting it found in `details.schema.settings`, and it checks the release
catalogs only once the schema passes. This happens after upgrading Hot Updater
to a release whose schema changed, or after adding a plugin to `plugins`.
Until then the server answers 503 and the Console shows a migration notice.

Doctor names the command that migrates the database. A server of an earlier
release answers 503 once its database is migrated, and a server of the new
release answers 503 until it is, so the migration and the server deploy run
back to back, with nothing in between:

| Database                                                                                                     | What doctor names                                                                                                                                                                 |
| ------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A deployment `hot-updater init` created: `.env.hotupdater` records the provider, and the config's database is the one init saved | `npx hot-updater init --provider <provider> --from-env-file .env.hotupdater`, which applies the release's migrations and then redeploys the server, so the 503 window is the deploy |
| Kysely, MongoDB, PostgreSQL, DynamoDB, Firestore, and Cosmos DB behind your own server                       | `npx hot-updater db migrate <server file>` in the server's project, as the server of the new release deploys                                                                      |
| Drizzle, Prisma, and D1 behind your own server                                                               | `npx hot-updater db generate <server file>`, the migration it writes applied with the ORM or `wrangler d1 migrations apply`, then `npx hot-updater db migrate <server file>`     |
| Supabase behind your own server                                                                              | `npx hot-updater db generate <server file>`, the migration it writes applied with `supabase db push`                                                                              |

Doctor compares the resource the config's database reaches, such as its D1
database ID or DynamoDB table, with the one init saved. When they differ, it
names your own server's command instead, since init replays against the saved
resources. When it cannot tell, such as for a Vercel database URL init saved
only with consent, it names both, each with its condition.

Doctor reads init's saved inputs from the environment first, as init does. The
command names `--from-env-file .env.hotupdater` only when that file holds
`HOT_UPDATER_INIT_PROVIDER`, `HOT_UPDATER_INIT_BUILD` and each input doctor
compared, with the values doctor read. When any came from the environment
instead, such as CI's variables or a file the config loads, the command names
`--build` and `--from-env-file <env file>`, and says that init needs those
values too.

When an agent infrastructure scaffold in `hot-updater-infra/<provider>/` keeps
the deployment, that is, its `deployment.json` records a deployed server on the
database the config names, and the config lists only the official plugins, the
scaffold's server runs, doctor names `npx hot-updater agent infra upgrade --provider
<provider> --build <build>` instead of init: apply the new scaffold as its
`upgrades/README.md` says, uploading the new server version and previewing it,
then migrating the database and deploying that version back to back. Running
init again would deploy at once, without that preview, and leave the scaffold
behind.

Init reports every input `.env.hotupdater` lacks, such as a credential it saved
only with consent, before it changes a resource: set those in the environment
for the run, or run `npx hot-updater init` and answer its prompts. Each
provider's migrations create core's tables and the official plugins'. Init
deploys only the official `insights()`, `apiKeys()` and `remoteConfig()`, and
sets the config's `plugins` to them, so while the config lists a plugin of your
own, doctor does not name init, which would drop it: remove the plugin from
`plugins` and run doctor again, or, if a server of your own runs it, migrate
the database as your own server's. While the schema is `SCHEMA_NEWER_THAN_CLI`,
`SCHEMA_NOT_MIGRATABLE` or `PLUGIN_SCHEMA_CHANGED`, an outdated server's
remediation names no command either: upgrading it would migrate the database
over those settings.

A setting newer than this CLI expects is `SCHEMA_NEWER_THAN_CLI`: the database
was migrated by a newer Hot Updater, and Hot Updater never moves a schema
back. Upgrade the CLI and the `@hot-updater` packages instead. A database Hot
Updater v1 cannot migrate in place, such as a v0 database, is
`SCHEMA_NOT_MIGRATABLE`.

A plugin of your own whose stored `schemaVersion` differs from the configured
one, such as `v1` against `v2`, is `PLUGIN_SCHEMA_CHANGED`. Hot Updater's
migrations create missing tables and change no existing one, so apply the
plugin's own migration for its changed tables first, then record its version
with `hot-updater db migrate` in the server's project. While any of these
issues stands, doctor names no migration, since a migration writes every
configured setting.

## Check Release Catalogs

When `hot-updater.config.ts` sets `database`, doctor opens it once for the
whole run and reads its release catalogs. It checks every scope that has a
catalog row or a Release, comparing each catalog with a rebuild from its
scope's Releases without writing, and reports each scope in
`details.releaseCatalogs.scopes`:

- `state`: `verified`, `stale`, `missing` (Releases but no catalog row), or
  `unchecked` (core could not compile it);
- `generation`: the stored catalog's, or `null` without a row;
- `byteSize` and `descriptorCount`: what its Releases compile to.

Devices read the catalog, not the Releases, so a catalog that differs from its
Releases is the error `RELEASE_CATALOG_STALE`. Every release change writes its
scope's catalog in the same transaction, so a stale catalog follows an edit made
outside Hot Updater or a partial restore of the database. Any release change in
the scope recompiles the catalog from all of its Releases: a deploy to it,
`bundle update`, or enabling or disabling a bundle:

```package-install
npx hot-updater bundle update <id> --message "<message>"
```

Then retry **Check and apply update** in the app and
[verify that it applies](/docs/get-started/test-ota#3-apply-it-in-the-app).

When doctor cannot reach the database, for example because the server's
credentials are not available where it runs, it warns
`RELEASE_CATALOGS_UNCHECKED` with the reason and does not fail: `success` stays
`true` for agents that gate on it. Without `database` in the config, doctor
skips the check.

A scope with Releases but no catalog row answers devices with 404. Doctor
reports it as the error `RELEASE_CATALOG_IDENTITY_MISSING`. Hot Updater never
creates the row: restore it from a backup before deploying,
since a new identity would not match the history devices already hold. A scope
core cannot compile is the error `RELEASE_CATALOG_CHECK_FAILED` with the
reason, beside what the other scopes report. These checks compare projections;
they do not recover missing source policy or replace a native OTA delivery
test.

To preview a proposed change to one Bundle's policy, use
[`bundle update --dry-run`](/docs/guides/console#preview-and-protect-automated-changes).

## Check secrets

Doctor lists each name the config reads with
[`secret()`](/docs/concepts/secrets#name-a-secret), and
where a command finds it: set by the environment, which wins, in the
`secrets` adapter, or missing. It reads the adapter once and writes nothing.

A missing name that a build or a deploy reads fails doctor, with the command
that imports the existing key:

```txt
■  release-keystore isn't in the infisical secrets adapter.
│  Check the name and your access, or import your key:
│  npx hot-updater secrets put release-keystore --kind android-keystore \
│    <upload.jks>
```

Builds read an iOS device scheme's `signing.ascApiKey`, a release variant's
`signing.keystore`, and `signing` while bundle signing is on. The Google Play
row then marks the package `upload keystore missing`, since its release has
nothing to sign with. That `✗` is the Secrets error's, counted once: the Google
Play row isn't a warning for it. In `--json`, each reference in
`details.secrets.references` has `required`, and a `message` when it is
required and missing; `details.googlePlay.packages[].missingKeystore` names the
same secret.

A missing name nothing reads yet, such as a simulator scheme's key, a debug
variant's keystore, or `signing` with `enabled: false`, is a warning, and the
run still passes. Its row says `missing, unused`, and the warning names the
command that stores each:

```txt
▲  debug-keystore isn't in the infisical secrets adapter.
│  No build or deploy reads it yet, so nothing fails.
│  Store it before a build or a deploy reads it:
│  npx hot-updater secrets put debug-keystore --kind android-keystore \
│    <upload.jks>
```

A missing name an adapter's `secret()` reads, such as a storage credential, is
a warning too, since the next deploy reads it. With a team store, a teammate
adds its variable to `.env.hotupdater` and runs
[`secrets import`](/docs/concepts/secrets#managed-projects):

```txt
▲  r2-access-key-id isn't in the infisical secrets adapter.
│  The next deploy will fail without it.
│  Set HOT_UPDATER_R2_ACCESS_KEY_ID in .env.hotupdater, then run:
│  npx hot-updater secrets import
```

In `--json`, these are a `SECRETS_MISSING_UNUSED` warning in
`details.secrets.issues` and a `DEPLOY_SECRETS_MISSING` warning in
`details.deploySecrets.issues`, with the same `message` and `resolution`. When
doctor can't read the adapter, it warns with the adapter's error instead.

With a team store, doctor also names a managed credential the config still
reads with `process.env`, which the store never supplies. For a deployment
`init` manages, it prints init's command, which rewrites the config. For one
an agent infrastructure scaffold keeps, or a config of your own, it links
[`secret()`](/docs/concepts/secrets#adapter-credentials)
instead: read those names with it in `hot-updater.config.ts`, and never run
init there.

## Update Package Versions

If `doctor` reports version mismatches, update the CLI, SDK and required
plugins to compatible stable versions using
[Install packages](/docs/get-started/installation). Keep the lockfile and rerun
doctor after installation.

## Update Outdated Infrastructure

With `--server-base-url`, doctor reads the server's `/version`. If the server
is older than the release this CLI needs, it prints the required version, why,
and the command that upgrades it:

```txt
■  Infrastructure update required: 1.2.0+
│  Core schema 1.2.0: the native build registry table and the tables of the
│  official plugins added beside it
│
●  Migrate the database and redeploy the server in one run:
│  npx hot-updater init --provider cloudflare --from-env-file .env.hotupdater
```

When doctor read init's saved inputs from the environment rather than
`.env.hotupdater`, such as CI's variables, the command names `<env file>`:
pass the file that holds them. When the database also has migrations to run,
the schema check names the command instead, once.

For a deployment `hot-updater init` created (`aws`, `cloudflare`, `supabase`,
`firebase`, `vercel`, `azure`), the command is init with the inputs it saved
in `.env.hotupdater`. It applies the release's migrations and redeploys the
server back to back, as the release's upgrade file describes; doctor does not
deploy servers. If the app/server is still on v0, follow
[Move from v0 to v1](/docs/guides/upgrade-to-v1) before applying templates.

## Options

| Option                    | Description                                                                                                    |
| ------------------------- | -------------------------------------------------------------------------------------------------------------- |
| `--server-base-url <url>` | Server base URL for version checks and scoped live catalog checks.                                             |
| `--json`                  | Print a machine-readable result for agents and scripts.                                                        |
| `--scope <scope>`         | Require `scaffold` or `infrastructure` verification.                                                           |
| `--infra-dir <directory>` | Exact directory returned by infrastructure scaffolding.                                                        |
| `--platform <platform>`   | `ios` or `android` for a live catalog check.                                                                   |
| `--channel <channel>`     | Actual app channel for a live catalog check.                                                                   |
| `--app-version <version>` | App-version catalog target; exclusive with fingerprint.                                                        |
| `--fingerprint <hash>`    | Fingerprint catalog target; exclusive with app version.                                                        |
