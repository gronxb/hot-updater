## Monitor app activity

Insights shows activity received from app installations: the last reported
update, completed downloads waiting to apply, successful applications, and recoveries. Use it after
[verifying your first OTA](/docs/get-started/test-ota) and while operating a
rollout.

## Turn on the server plugin

The server records reports through the `insights()`
[server plugin](/docs/custom/server-plugins). The managed AWS, Cloudflare,
Firebase, and Supabase servers run it. A custom server lists it in
`createHotUpdater`:

```ts title="src/hotUpdater.ts (excerpt)"
import { createHotUpdater } from "@hot-updater/server";
import { apiKeys } from "@hot-updater/server/plugins/api-keys";
import { insights } from "@hot-updater/server/plugins/insights";

export const hotUpdater = createHotUpdater({
  database,
  plugins: [insights(), apiKeys()], // [!code ++]
});
```

`insights()` accepts `POST /events` on the client handler and serves the
Insights queries on the admin handler. Its tables are part of the schema that
`hot-updater db migrate` and each provider's migration create, whichever
plugins the server runs. Without `insights()`, those routes answer `204` with
`x-hot-updater-insights: disabled` and the app's reports are not stored. The
server logs one warning, on the first report it drops, that names `insights()`.
To run without Insights on purpose, also set `insights: false` in
`HotUpdater.init`, so apps stop sending reports.

## Configure reporting

[`HotUpdater.init`](/docs/react-native-api/init) enables Insights by default.
The optional automatic [`wrap`](/docs/react-native-api/wrap) flow uses the same
reporting default.
Configure the client handler URL and the client API key from your infrastructure
setup. Reporting runs after the app-ready state is available:

```tsx title="App.tsx"
import { HotUpdater } from "@hot-updater/react-native";

HotUpdater.init({
  baseURL: "<your-update-server-url>",
  requestHeaders: {
    "x-api-key": "<client-api-key>",
  },
  // [!code ++:3]
  onNotifyAppReady: (result) => {
    console.log("App-ready state:", result.status);
  },
});
```

Call `init` once at the top level of your app's entry module. It configures
reporting without
starting an update check; use [custom update flows](/docs/guides/custom-update)
to check, download, and apply updates at your chosen time. Use one configuration
API per app. If your custom server intentionally uses
`clientAccess: "public"` instead of `apiKeys()`, omit the
client-key header. See [API key authentication](/docs/custom/api-key-authentication).

Set `insights: false` in your `init` or `wrap` options to disable client reporting.
Native app-ready handling and crash recovery still run, and the server's
Insights routes are unchanged. This setting does not delete reports already
stored.

Debug builds, where `__DEV__` is `true`, send no reports by default, so
development sessions do not mix into production Insights. To test reporting
from a debug build, opt in; in a release build, `{ debug: true }` behaves like
`true`:

```tsx
HotUpdater.init({
  baseURL: "<your-update-server-url>",
  insights: { debug: true }, // [!code ++]
});
```

The client reports these outcomes:

| Outcome | Meaning |
| --- | --- |
| `UNCHANGED` | A launch with no download or apply to report. This also reports a successful same-artifact Release adoption, which requires neither. |
| `UPDATE_DOWNLOADED` | The SDK verified and staged the bundle. The current runtime still runs the previous bundle until restart/reload. |
| `UPDATE_APPLIED` | Native app-ready state reports that an OTA transition became active. |
| `RECOVERED` | Native app-ready state reports recovery from a failed update. |

The server counts an installation's `UNCHANGED` reports once a UTC day. A
report that repeats the installation's latest report on the same UTC day, with
the same channel, platform, app version, bundle, Release, and user, records
nothing. An `UNCHANGED` report updates the installation's latest report and the
launch metrics, but the server keeps no event row for it, so event lists show
only downloads, applies, and recoveries.

Automatic startup reporting sends one report per JavaScript runtime. The automatic `wrap` flow defers `UNCHANGED` until its update check finds no update. A successful download reports `UPDATE_DOWNLOADED` instead. Custom flows using `init` may report `UNCHANGED` at startup followed by a download later. Repeated reports of the same pending selection are deduplicated within the runtime. Selecting a different pending bundle and then returning to an earlier one reports both changes.

Reporting is best effort and does not trigger rollback. A report that fails
with a network error, a timeout, `429`, or a `5xx` is retried in the
background, so a retry never delays app startup or an update: up to three
attempts in all, about 1 second and then 2 seconds apart, or after the
server's `Retry-After` (at most 30 seconds). Each attempt has its own
`requestTimeout`, and every attempt carries the same client `eventId`, a
UUIDv7, so the server counts a retried report once. A report refused with
another status, such as `400`, is not retried. Reports leave one at a time in
the order the app made them, so a retry never lands after a later report. The
SDK logs a warning when it drops a report. Retries live in memory: a report
still pending when the app closes or reloads is lost. `onNotifyAppReady`
receives local native state; it is not confirmation that the server received
an event.

The Console summarizes these reports in **App usage** and **Release health**.
Use an installation's event history to check whether a reported download was
followed by an apply or recovery report. A download count does not tell you how
many installations are still waiting to apply it.

## How the server accepts reports

`POST /events` takes one report as a JSON body of at most 16 KB. Fields the
server does not know are ignored, so a report from a newer SDK still records on
an older server; a known field with an invalid value is refused.

A report can carry an `eventId`: a lowercase UUIDv7 that the client creates
once for the report and sends again with every retry. The server stores the
report under that ID, so a retried report counts once, and a report under an
ID the server already stored changes nothing. Without an `eventId`, the server
creates the ID, and a retry counts as another report.

| Status | Meaning |
| --- | --- |
| `204` | Recorded, or already recorded under the same `eventId` |
| `400` | A missing or invalid field, including an `eventId` that is not a UUIDv7 |
| `413` | The body is larger than 16 KB |
| `503` | The database is busy; send the report again after the `Retry-After` seconds |

## Identify an installation

Read [`HotUpdater.getInstallId()`](/docs/react-native-api/getInstallId) in a
support log or debug screen. This stable local ID identifies one installation;
it is independent of the signed-in user.

Optionally attach your application's user ID and display name with
[`HotUpdater.setUser()`](/docs/react-native-api/setUser):

```tsx
HotUpdater.setUser({ userId: "user-123", username: "Alex" });

// On logout, clear the identity attached to future reports.
HotUpdater.setUser(null);
```

These calls illustrate separate login and logout actions. `setUser` persists
local identity for future reports; it does not send an event immediately. Set
identity before startup reporting if the first report must include it. Each
call replaces both fields, so omitting a field clears its previous value.

In **Insights → All events**, search by **User ID or installation ID**, then
select an installation to inspect its latest report and apply/recovery history.
The username supplies display context. Multiple installations associated with
one user remain separate records.

Reports include installation ID, platform, app version, channel, cohort,
fingerprint when present, and Bundle/Release transition identifiers. They also
include the user ID and username you configured. Keep these optional fields
consistent with your app's data policy and protect server access as described
in [Security](/docs/policy/security).

## Verify reporting

1. Launch a native build configured with the SDK, reachable client handler,
   and valid client key. Use a release build, or set
   `insights: { debug: true }` in a debug build. Copy its `getInstallId()`
   value.
2. In the Console's **Insights → All events**, search for that installation
   ID and open it. Its latest report shows the app version, channel, and
   platform. An `UNCHANGED` report is enough to verify startup reporting
   before the first OTA; it appears as the installation's latest report, not
   in the event list.
3. Deploy and apply a test update using the
   [OTA verification workflow](/docs/get-started/test-ota). Confirm the changed
   UI after the runtime restarts, then inspect its `UPDATE_APPLIED` event and
   reported update ID.

[`getBundleId()`](/docs/react-native-api/getBundleId) and
[`getActiveUpdateState()`](/docs/react-native-api/getActiveUpdateState) can
reflect a staged selection before its code is running. A selected ID alone is
not an applied-update check. Combine the running app's visible change with the
app-ready outcome and the server's received report.

If an expected report is absent, check that reporting is enabled (a debug
build also needs `insights: { debug: true }`), the app reached readiness, the
server runs `insights()`, and the handler URL and client header match the
deployed server. Inspect app logs for Insights warnings.
Server availability and filters affect what the Console can show; a missing
report does not prove that the update failed.

## Read the Console

Use [the local or deployed Console](/docs/guides/console). Where it reads
Insights depends on its database configuration:

- With a direct database, it runs `insights()` over that database, as the
  server does. `hot-updater console` loads the plugins that the project's
  `hotUpdater.plugins.ts` exports as `plugins`; `hot-updater init` writes that
  file for managed providers. A deployed Console takes `plugins` in its
  [configuration](/docs/guides/console-deployment#add-your-plugins). Without
  `insights()` there, the console hides Insights.
- With `standaloneRepository`, it reads Insights events and installations from
  the server's admin handler, and hides Insights when the server's admin
  `/version` does not list `insights()`. App usage, Release health, and bundle
  activity need a direct database configuration.

The Bundles list and detail show lifetime **Downloads**, **Active days**, and
**Known crashes** for each Release ID. These count received download reports,
each installation once for each UTC day it launched the release, and failed OTA
launch reports. Known crashes are launch failures that triggered recovery.
Their rate is known crashes divided by active days plus known crashes. Select
the summary to open Release health for that ID.

Insights opens on the `production` channel. **App usage** starts with
**All platforms** and a 24-hour period; **Release health** starts with **iOS**
and **7d**. Each card has its own **24h**, **7d**, or **30d** period selector.

Choose a **Channel** for both cards. **Usage platform** and **App version**
filter App usage; **Health platform** and the optional **Release ID** filter
Release health. Choose **Apply filters** to update the reports.

App usage shows one metric for the selected period: **DAU** for the last 24
hours, **WAU** for the last 7 days, or **MAU** for the last 30 days. Each counts
unique app installations with at least one matching activity report in that
rolling window. Multiple installations belonging to the same person count
separately. All event types count, including **No change**, as do reports
without a known bundle ID. Hover over, focus, or tap the metric's info icon to
see its definition.

The usage chart counts unique reporting installations in each interval: hourly
for 24h, every six hours for 7d, and daily for 30d. The period total deduplicates
installations across intervals, so it is not the sum of the chart points.
Distributions count each installation once, using the app version and platform
of its latest matching report. The server counts latest reports by UTC day, so a
distribution covers every UTC day the period touches, from 00:00 UTC of its
first day; the Console shows that date.

Select an app version in **Distribution**, or choose **View distribution**, to
see its bundle IDs, platforms, active installation counts, and share within each
app version. The detail view keeps the overview's reporting scope, supports
20 rows per page, and links each known ID to its bundle details. **Unknown bundle**
accounts for installations whose reported file has no observed deployment ID.
Period and filter selections survive navigation back to the overview.

![Bundle distribution by app version with sample data](/docs/console/insights-distribution.png)

**Release health** shows **Active installations**, **Active days**, **Failed
launches**, and **Crash rate** for the selected channel, health platform, and
period. Leave **Release ID** empty to include the whole scope, or enter one ID
to inspect that release. **Active installations** estimates the distinct
installations that reported in the scope, or that launched the selected
release. Launches count as daily active installations: **Active days** count
each installation once for each UTC day it launched, and once more on a day an
update applies or recovers. **Crash rate** is reported OTA launch failures
divided by active days plus failed launches in the same scope and period. The
chart shows daily active installations and failed launches. These period
totals are separate from the lifetime counters in the Bundles list and detail.

Open **All events** in the header, or **Event history** on Release health, to
browse downloads, applies, and recoveries from newest to oldest, 20 per page.
The Console starts with **7d**; select **30d** or **90d** for older reports.
Paging stops at the start of the selected range. A launch without an update is
not listed: it counts in App usage and Release health and shows as its
installation's latest report.

Like other analytics tools, event lists show raw reports only inside a time
range of at most 90 days: the admin `GET /events` route takes `sinceMs` and
`beforeReceivedAtMs`, lists the 90 days before `beforeReceivedAtMs` (by
default, now) when `sinceMs` is left out, and answers `400` for a longer
range. The server also counts reports per day, so a list skips quiet days
instead of reading each one.

These counts reflect received reports, not the full installed population.
Release health includes reports without a known Release ID when no ID filter
is set; selecting an ID limits it to reports attributed to that release. Every
overview period ends with the current UTC hour, so a report counts as soon as
the server records it, and a chart's last interval is still filling. The Console reads
hourly and daily totals that the server updates as it records each report; it
does not scan raw events. DAU, WAU, MAU, active users per interval, and active
installations are estimates from HyperLogLog sketches, typically within about
3%, and show with **≈**. Report counts, active days, and distributions are
exact.

## What Insights writes

Most reports are launches, and the server writes for an installation's
launches once a UTC day. Each report the server records is one transaction. On
DynamoDB, where a transactional write costs 2 write request units (WRU) per KB
of each item, one installation's reports cost:

| Report | Items | WRU |
| --- | --- | --- |
| First launch of a new installation | 15 | 40 |
| A later launch the same UTC day, on the same bundle | 0 | 0 |
| First launch of a later UTC day | 19 | 48 |
| `UPDATE_DOWNLOADED` | 19 | 42 |
| `UPDATE_APPLIED` | 26 | 54 |
| `RECOVERED` | 30 | 66 |

A first launch the day after an apply or a recovery takes 21 items and 52 WRU,
since it also moves the update's latest-report rows. Up to five items of a
report are HyperLogLog sketches of about 1 KB, at 4 WRU apiece; every other
item takes 2. A download, apply, or recovery stores its event with its index
copies; a launch stores none. Latest-report gauges count each installation in
the UTC day of its latest report, so they move only when that day or the
installation's bundle changes. An installation that launches every day
without updating costs about 48 WRU a day, however often it launches: 10,000
such installations write about 480,000 WRU a day. On Firestore each item is
one document write; SQL databases keep indexes themselves, so they write fewer
rows.

The managed AWS table caps writes at 100 WRU per second, about two first
launches of a day per second. A report the table throttles answers `503`, and
the SDK sends it again.
