## Monitor app activity

Insights shows activity received from app installations: the last reported
update, completed downloads waiting to apply, successful applications, and
recoveries. Use it after [verifying your first OTA](/docs/get-started/test-ota)
and while operating a rollout.

Reporting has two parts: the `insights()` server plugin stores reports, and the
[Insights client plugin](/docs/react-native-api/insights) sends them from the
app. Both come from `@hot-updater/plugin-insights`, which `@hot-updater/server`
and `@hot-updater/react-native` depend on and re-export, so there is nothing
extra to install.

## Turn on the server plugin

The server records reports through the `insights()`
[server plugin](/docs/custom/server-plugins). The managed AWS, Cloudflare,
Firebase, and Supabase servers run it. A custom server lists it in
`createHotUpdater`, and the app's `hot-updater.config.ts` lists it in `plugins`
too:

```ts title="src/hotUpdater.ts (excerpt)"
import { createHotUpdater } from "@hot-updater/server";
import { apiKeys } from "@hot-updater/server/plugins/api-keys";
import { insights } from "@hot-updater/server/plugins/insights";

export const hotUpdater = createHotUpdater({
  database,
  plugins: [insights(), apiKeys()], // [!code ++]
});
```

`insights()` accepts `POST /events` on the client handler and serves the
Insights queries on the admin handler. `hot-updater db migrate` creates its
tables for a server that runs it, and the migrations of the managed Cloudflare,
Supabase, AWS, and Firebase servers include them. Without `insights()`, the
server has no Insights routes: they answer `404`, and the app's reports are not
stored. An app with the Insights plugin then stops reporting for 24 hours at a
time; see
[when the server has Insights off](/docs/react-native-api/insights#when-the-server-has-insights-off).
On the server, `insights({ retention })` sets how long the plugin keeps data;
see [How long Insights keeps data](#how-long-insights-keeps-data).

## Add the client plugin

Pass `insights()` from `@hot-updater/react-native` to `plugins` in
[`HotUpdater.init`](/docs/react-native-api/init). Configure the client handler
URL and the client API key from your infrastructure setup:

```tsx title="src/hotUpdater.ts"
import { HotUpdater } from "@hot-updater/react-native"; // [!code --]
import { HotUpdater, insights } from "@hot-updater/react-native"; // [!code ++]

export const hotUpdater = HotUpdater.init({
  baseURL: "<your-update-server-url>",
  requestHeaders: {
    "x-api-key": "<client-api-key>",
  },
  plugins: [insights()], // [!code ++]
});
```

Call `init` once, at the top level of its own module, and export the instance
it returns. It configures reporting without starting an update check; use
[`hotUpdater.wrap`](/docs/react-native-api/wrap) or a
[custom update flow](/docs/guides/custom-update) to check, download, and apply
updates. If your custom server intentionally uses
`clientAccess: "public"` instead of `apiKeys()`, omit the client-key header.
See [API key authentication](/docs/custom/api-key-authentication).

An app without the plugin sends no Insights reports. Native launch
verification and crash recovery run either way. Debug builds, where `__DEV__`
is `true`, send nothing unless you create the plugin with
`insights({ debug: true })`, so development sessions stay out of production
Insights. The [plugin reference](/docs/react-native-api/insights) covers its
options, `setUser`, and the report format.

## What the app reports

The plugin reports these outcomes:

| Outcome | Meaning | Console label |
| --- | --- | --- |
| `UNCHANGED` | A launch with no download or apply to report. This also reports a successful same-artifact Release adoption, which requires neither. | **Launch**, or the change it made (below) |
| `UPDATE_DOWNLOADED` | The SDK verified and staged the bundle. The current runtime still runs the previous bundle until restart/reload. | **Downloaded** |
| `UPDATE_APPLIED` | Native app-ready state reports that an OTA transition became active. | **Launched** |
| `RECOVERED` | Native app-ready state reports recovery from a failed update. | **Crashed** |
| `UPDATE_FAILED` | An update check, download, or install failed, with its stage and reason. A server that does not accept this type answers `400`, and the plugin skips it. | **Update failed** |

The plugin sends `UNCHANGED` at most once a UTC day per installation. A later
launch or update check that day sends nothing, unless the channel, app
version, bundle, Release, or user ID changed, or a download or failure report
reached the server in between. Downloads, applies, and recoveries are not
limited this way. Each update failure, by stage, reason, target bundle, and original error message, is
reported at most once a UTC day, and a check that failed because the device was
offline is not reported. See
[what the plugin reports](/docs/react-native-api/insights#what-it-reports) for
the exact rules.

The server counts an installation's `UNCHANGED` reports once a UTC day. A
report that repeats the installation's latest report on the same UTC day, with
the same channel, platform, app version, bundle, Release, and user, records
nothing. An `UNCHANGED` report updates the installation's latest report and the
launch metrics. The server keeps it as an event only when it changes what the
installation runs, compared with that latest report:

| Change | Event list label |
| --- | --- |
| The installation's first report to this server | **First seen** |
| A new app version or native build | **App updated** |
| Another bundle, with no `UPDATE_APPLIED` report for it | **Launched** |
| Another Release of the bundle it already runs | **Release adopted** |
| Another channel | **Channel changed** |

A user switch moves only the latest report. Event lists therefore show
downloads, launches, crashes, update failures, and these changes, each once.
A launch that changes nothing is not listed.

Reporting is best effort and does not trigger rollback. A report that fails
with a network error, a timeout, `429`, or a `5xx` is retried in the
background, so a retry never delays app startup or an update. Every attempt
carries the same client `eventId`, so the server counts a retried report once;
see [delivery](/docs/react-native-api/insights#delivery) for the timing.
`onNotifyAppReady` receives local native state; it is not confirmation that
the server received an event.

When the server answers that Insights is off, the plugin sends nothing more in
that JavaScript runtime and nothing for 24 hours, then sends its next report.
After you turn on `insights()`, installations resume reporting within a day.

The Console summarizes these reports in **App usage** and **Release health**.
Use an installation's event history to check whether a reported download was
followed by an apply or recovery report. A download count does not tell you how
many installations are still waiting to apply it.

## Investigate update failures

In **Update failures**, compare the attempt and check failure rates with the
previous period of the same length. Changes are percentage points; unavailable
or partial previous data is not treated as zero. Check failures use affected
installations over active installations, while attempt failures use failed
reports over failed reports plus completed downloads.

**Errors to investigate** groups reports by their exact original message and
reported stage, reason, resource, HTTP status, origin code, and transport.
Select a message to inspect its stack, app and SDK versions, bundle, and
installation history. Select another occurrence to inspect that report's
context, or use **Copy report** to share its original fields for debugging.

These groups count only loaded raw reports, not the period's aggregate totals.
The Console reviews up to 500 recent events per request and offers **Load older
events** while more remain. The raw-history start is shown, respects retention,
and never extends beyond 90 days. The app also deduplicates daily failures, so
report counts are not the number of every exception thrown on devices.

Update the app's Insights plugin, server, and Console to collect and inspect
original messages and stacks. Existing reports that lack these fields cannot
recover the original cause; the Console labels those missing diagnostics.
This addition uses existing event metadata and needs no database migration.

## Inspect HTTP responses

Existing lifecycle reports can include the most recent catalog or artifact API
response, including successful, cached, and failed responses. In **All events**,
installation history, or an installation's latest report, select its HTTP status
to inspect the request path, original response text, and response timestamp.
Error investigation also shows the server response beside the client error.

The client keeps one bounded response snapshot locally, scoped to the app version
and channel, and attaches it only when an existing report is sent. Response
collection adds no requests, timers, or event records, and does not bypass launch
or failure deduplication. If the launch report was already sent before the update
check, that check's response appears on the next eligible report. The response
timestamp distinguishes that earlier response from the report's receipt time.
This is a diagnostic snapshot, not a complete request history.

Bodies are capped at 4 KiB of JSON-encoded text and marked when truncated. Empty
bodies and bodies that could not be read have different labels. Request headers
and URL query parameters are omitted. Native binary file downloads and Insights'
own reporting requests are not captured. Older servers ignore the extra metadata;
upgrade the server and Console to store and inspect it. No database migration is
required.

## How the server accepts reports

`POST /events` takes one report as a JSON body of at most 16 KB. Fields the
server does not know are ignored, so a report from a newer SDK still records on
an older server; a known field with an invalid value is refused.

A report can carry an `eventId`: a lowercase UUIDv7 that the client creates
once for the report and sends again with every retry. The server stores the
report under that ID, so a retried report counts once, and a report under an
ID the server already stored changes nothing. Without an `eventId`, the server
creates the ID, and a retry counts as another report.

| Status | Meaning |
| --- | --- |
| `204` | Recorded, or already recorded under the same `eventId` |
| `400` | A missing or invalid field, including an `eventId` that is not a UUIDv7 |
| `413` | The body is larger than 16 KB |
| `503` | The database is busy; send the report again after the `Retry-After` seconds |

## Identify an installation

Read [`hotUpdater.getInstallId()`](/docs/react-native-api/getInstallId) in a
support log or debug screen. This random ID identifies one installation; it is
independent of the signed-in user.

Optionally attach your application's user ID with the plugin's
[`setUser`](/docs/react-native-api/insights#set-the-user), on the instance
`HotUpdater.init` returns. Call it from your sign-in flow:

```ts
import { hotUpdater } from "./hotUpdater";

hotUpdater.insights.setUser({ userId: "user-123" });

// On logout, clear the user attached to later reports.
hotUpdater.insights.setUser(null);
```

These calls illustrate separate login and logout actions. `setUser` persists
the ID on the device for later reports; it does not send a report by itself.
The launch report waits for native launch verification, so a session restored
right after `init` is attached to the first report.

In **Insights → All events**, search by **User ID or installation ID**, then
select an installation to inspect its latest report and apply/recovery history.
Multiple installations associated with one user remain separate records.

Reports include installation ID, platform, app version, channel, cohort,
fingerprint when present, SDK version, and Bundle/Release transition
identifiers. They also include the user ID you set. Keep it consistent with
your app's data policy and protect server access as described in
[Security](/docs/policy/security).

## Verify reporting

1. Launch a native build configured with the SDK, the Insights plugin, a
   reachable client handler, and a valid client key. Use a release build, or
   create the plugin with `insights({ debug: true })` in a debug build. Copy
   its `getInstallId()` value.
2. In the Console's **Insights → All events**, search for that installation
   ID and open it. Its latest report shows the app version, channel, and
   platform. An `UNCHANGED` report is enough to verify startup reporting
   before the first OTA; it appears as the installation's latest report, not
   in the event list.
3. Deploy and apply a test update using the
   [OTA verification workflow](/docs/get-started/test-ota). Confirm the changed
   UI after the runtime restarts, then inspect its `UPDATE_APPLIED` event and
   reported update ID.

Only the first launch of a UTC day reports while nothing changes. Relaunching
the same build later that day sends nothing, so look up the installation by
its ID instead of waiting for another launch report.

[`getBundleId()`](/docs/react-native-api/getBundleId) and
[`getActiveUpdateState()`](/docs/react-native-api/getActiveUpdateState) can
reflect a staged selection before its code is running. A selected ID alone is
not an applied-update check. Combine the running app's visible change with the
app-ready outcome and the server's received report.

If an expected report is absent, check that the app passes the Insights plugin
to `init` (a debug build also needs `insights({ debug: true })`), the
app reached readiness, the server runs `insights()`, and the handler URL and
client header match the deployed server. Inspect app logs for Insights
warnings. An app that reported to a server without `insights()` waits up to 24
hours before it reports again; reinstall it to test right away. Server
availability and filters affect what the Console can show; a missing report
does not prove that the update failed.

## Read the Console

Use [the local or deployed Console](/docs/guides/console). It shows Insights
when its configuration lists `insights()` in `plugins`, as the server runs it:
`hot-updater console` reads `hot-updater.config.ts`, and a deployed Console its
[configuration](/docs/guides/console-deployment#connect-your-backend). Where
it reads Insights depends on its `database`:

- With a direct database, it runs `insights()` over that database, as the
  server does.
- With `standaloneRepository`, it reads the Insights overview, events,
  installations, update failures, and retention periods from the server's
  admin handler. App usage, Release health, and bundle activity need a direct
  database configuration.

The Bundles list and detail show lifetime **Downloaded**, **Launched**, and
**Crashed** for each Release ID, counting installations once each:

- **Downloaded**: got the release's bundle.
- **Launched**: ran it, by its `UPDATE_APPLIED` report or, when that report
  never arrived, its first report on the bundle.
- **Crashed**: crashed on it and rolled back to the bundle before.

A launch or crash whose download report never arrived counts that download
too. A download or `UPDATE_APPLIED` report of a bundle its installation
already ran, a repeat of the download it already reported, and a launch report
made before its latest report count nothing. Once every installation restarts, Downloaded equals
Launched plus Crashed; the bundle detail shows the downloads not launched yet,
waiting for a restart or passed over for a newer bundle. An installation that
comes back to a release counts again. A release of the built-in bundle shows
no downloads, since it ships with the app. The crash rate is crashed divided
by launched plus crashed, as in Release health. Select
the summary, or **View adoption** in the bundle detail, to open
[Release health](#release-health) on that release and the one deployed before
it, over the shortest period that covers the release's deployment: **24h**
within a day of it, **7d** within a week, else **30d**. The bundle detail also shows
**Download failures** since the release's first report, with their rate; see
[Update failures](#update-failures).

Insights opens on the `production` channel. **App usage** starts with
**All platforms** and a 24-hour period; **Release health** starts with **iOS**
and **24h**. Each card has its own **24h**, **7d**, or **30d** period selector,
and App usage also offers **12m**.

Choose a **Channel** for both cards. **Usage platform** and **App version**
filter App usage; **Health platform** filters Release health and Update
failures, and the optional **Release ID** focuses both on one release. Choose
**Apply filters** to update the reports.

App usage shows one metric for the selected period: **DAU** for the last 24
hours, **WAU** for the last 7 days, **MAU** for the last 30 days, or **YAU** for
the last 12 months. Each counts unique app installations with at least one
matching activity report in that window. The 24h, 7d, and 30d windows roll by
the hour; 12m covers 52 weeks of whole UTC days, ending with today, because
hourly totals are kept for 90 days and daily totals for 13 months. Multiple installations belonging to the same person count
separately. All reports count, including launches that change nothing, as do
reports without a known bundle ID. Hover over, focus, or tap the metric's info icon to
see its definition.

The usage chart counts unique reporting installations in each interval: hourly
for 24h, every six hours for 7d, daily for 30d, and weekly for 12m. The period total deduplicates
installations across intervals, so it is not the sum of the chart points.
Distributions count each installation once, using the app version and platform
of its latest matching report. The server counts latest reports by UTC day, so a
distribution covers every UTC day the period touches, from 00:00 UTC of its
first day; the Console shows that date.

Select an app version in **Distribution**, or choose **View distribution**, to
see its bundle IDs, platforms, active installation counts, and share within each
app version. The detail view keeps the overview's reporting scope, supports
20 rows per page, and links each known ID to its bundle details. **Built-in bundle**
shows installations that run the bundle their native build shipped, by its ID
(`MIN_BUNDLE_ID`), under that build's app version; a deployment that selected
the built-in bundle shows its ID with the same mark. **Unknown bundle** accounts
for the remaining installations without an observed deployment ID. Event and
installation details mark the built-in bundle the same way, including from an
SDK that doesn't report `MIN_BUNDLE_ID`: a built-in bundle's ID is its build
time with the random bits zeroed, which no deployed bundle's ID has.
Period and filter selections survive navigation back to the overview.

![Bundle distribution by app version with sample data](/docs/console/insights-distribution.png)

**Release health** follows bundle deployments after they ship: whether
installations apply them, and whether they crash. See
[Release health](#release-health).

Open **All events** in the header, or **Event history** on Release health, to
browse downloads, applies, recoveries, update failures, and the launches that
changed what an installation runs, from newest to oldest, 20 per page.
The Console starts with **7d**; select **30d** or **90d** for older reports.
Paging stops at the start of the selected range. A launch that changes nothing
is not listed: it counts in App usage and shows as its installation's latest
report.

Like other analytics tools, event lists show raw reports only inside a time
range of at most 90 days: the admin `GET /events` route takes `sinceMs` and
`beforeReceivedAtMs`, lists the 90 days before `beforeReceivedAtMs` (by
default, now) when `sinceMs` is left out, and answers `400` for a longer
range. The server also counts reports per day, so a list skips quiet days
instead of reading each one.

These counts reflect received reports, not the full installed population. Every
overview period ends with the current UTC hour, so a report counts as soon as
the server records it, and a chart's last interval is still filling. The Console reads
hourly and daily totals that the server updates as it records each report; it
does not scan raw events. On DynamoDB and Firestore, the server updates these
totals in batches (see [What Insights writes](#what-insights-writes)), and a
read applies pending batches first. A Console that cannot write to the database,
such as one with read-only credentials, shows totals that can leave out up to
one batching window of the latest reports, a minute by default. DAU, WAU, MAU, active users per interval, and active
installations are estimates from HyperLogLog sketches, typically within about
3%, and show with **≈**. Report counts and distributions are exact.

## Read from the CLI

`hot-updater insights` reads the same Insights from a terminal, CI, or an
agent. It finds the server as
[`hot-updater api-key`](/docs/custom/api-key-authentication#manage-api-keys)
does: `database` and `plugins` in `hot-updater.config.ts`, the server's admin
handler through `standaloneRepository`, or the server file you pass last, such
as `src/hotUpdater.ts`.

```bash
npx hot-updater insights overview -p ios -c production --window 7d
npx hot-updater insights failures --bundle <id>
npx hot-updater insights events --bundle <id> --outcome crashed
npx hot-updater insights installations <install-or-user-id>
```

- `overview` counts a channel's reporting installations and, with `--bundle`,
  the bundle's **Downloaded**, **Launched**, **Crashed**, and failed reports.
- `failures` shows the update failure rate, downloads and patch fallbacks, a
  channel's failed update checks, and failures by stage and reason.
- `events` lists reports newest first: all of them, a bundle's of one
  `--outcome` (`downloaded`, `launched`, `crashed`, or `failed`), or an
  installation's with `--install`. `--cursor` reads the next page.
- `installations` finds an installation by its install ID, and the
  installations whose user ID it is.

`--bundle` takes the ID shown in the Console or by `getBundleId()`, and reads
the platform and channel from the bundle; otherwise pass `-p` and `-c`.
`overview` and `failures` cover `--window`: `24h` by default, `7d`, or `30d`,
ending with the current UTC hour as the Console's periods do. Every command
takes `--json`. App usage and Release health stay in the Console.

## Update failures

An app reports `UPDATE_FAILED` when an update check, download, or install
fails. Its `metadata.failure` says where (`stage`: `check`, `download`, or
`install`) and why (`reason`: `network`, `http`, `invalid_response`,
`hash_mismatch`, `signature`, `patch`, `extract`, `storage`, or `unknown`), and
what else the client knew: the `resource` it was fetching, the `httpStatus`,
the storage origin's `originCode` (such as `ExpiredToken`), and the network
`transport` failure (such as `timeout`). A download report can say how the
bundle arrived (`delivery`: `patch`, `manifest`, or `archive`) and whether a
patch fell back (`patchFallback`).

The server never refuses a failure for what it cannot read: a value it does not
know reads as `unknown`, a missing or malformed `failure` counts as an unknown
stage and reason, and a malformed optional field is left out. It refuses only
a report without its identity, bundles, or a valid event ID. A failure changes
nothing an installation runs, so it is no launch and does not replace the
installation's latest report. Event lists and installation history show it with
its stage and reason. A failed check names the running bundle instead of a
target, so it counts for its channel and appears in no bundle's list.

In the Console, **Update failures** follows Release health's channel, platform,
Release ID, and period. Each kind of failure shows one rate, then its failure
reports and the installations they came from, estimated:

- **Downloads & installs** is the share of update attempts that failed: failed
  downloads and installs divided by themselves plus download reports. A client
  reports a failure at most once a UTC day for each stage, reason, and target
  bundle. When downloads tried a patch, a line says how many fell back to the
  changed files or the full archive.
- Without a Release ID, **Update checks** is the share of the channel's active
  installations with a failed update check. A check that gets no response,
  because the device is offline or the request timed out or was cancelled, is
  not reported.
- A rate shows its change from the previous period once a whole previous
  period was recorded.
- **Failures by stage and reason** lists each stage and reason with its share;
  expand one to see its HTTP statuses, origin codes, transports, and resources.
  A failure whose client classified none reads **No reason reported**. Such a
  client reports every failed check, offline ones included, so when these are
  most of the failures, the card says so.

The bundle detail's **Download failures** counts the release's failed
downloads and installs since its first report, with the same rate. On a
self-hosted server, the admin route
`GET /failures?platform=ios&channel=production&releaseId=<id>` answers a
release's failures since its first report; add `start` and `end`, in epoch
milliseconds, for a period of at most 30 days, which a channel without
`releaseId` needs. The server API is
`hotUpdater.api.insights.getUpdateFailures(input)`.

## How long Insights keeps data

`insights()` keeps each kind of data for a period, then deletes it:

| Data | Kept by default |
| --- | --- |
| Downloads, applies, recoveries, and update failures (raw events) | 90 days |
| Hourly totals, unique-installation sketches, and the update failure breakdown | 90 days |
| Daily totals, sketches, and latest-report distributions | 13 months (400 days) |
| An installation's latest report | 13 months after the installation last reports |
| Lifetime counters and failed installations per Release ID (Bundles list and detail) | Kept |

A managed server runs the official plugins with their default settings,
retention included. In a managed project, keep `plugins` in
`hot-updater.config.ts` as init writes it, the provider package's list:
plugins with other settings there would make the CLI prune with settings the
server doesn't use.

On a self-hosted server, set the periods on the plugin in the server's
`createHotUpdater`, and give the plugin the same settings in
`hot-updater.config.ts`, so the CLI prunes as the server does:

```ts
insights({ retention: { rawDays: 30, dailyDays: 400 } });
```

`rawDays` covers raw events and hourly totals; `dailyDays` covers daily
totals, distributions, and latest reports. Each is a whole number of days, at
least 1, and `dailyDays` is at least `rawDays`; lifetime counters are always
kept. A changed period applies at the next pruning pass on SQL databases. On
DynamoDB, Firestore, and MongoDB, which stamp each row's expiry as they write
it, rows already written keep theirs, and later writes take the new period.

Periods follow from what reads them. Event lists cover at most the raw
period, and overview periods up to 30 days read hourly totals. The 12m App
usage period reads daily totals. A read that reaches past what is kept says
so: the Console shows **Partial history** and marks totals as a lower bound.
An installation that stops reporting leaves the distributions when its latest
report expires. The Console reads the server's periods, including a
self-hosted server's through its admin API.

No scheduler is needed: expired data leaves by native TTL or during writes.

- **DynamoDB** deletes expired items with Time to Live on `_ttl`, at no write
  cost, usually within a few days of expiry. `hot-updater db migrate` and the
  managed AWS setup turn TTL on for the table.
- **Firestore** deletes expired documents with a TTL policy on `expireAt`,
  usually within 24 hours of expiry. The managed Firebase setup deploys the
  policy with `firestore.indexes.json`.
- **MongoDB** deletes expired documents with a TTL index on `_expireAt`,
  usually within a minute of expiry. `hot-updater db migrate` creates it.
- **PostgreSQL, MySQL, SQLite, Cloudflare D1, and Supabase** delete expired
  rows during writes. The write that takes the hourly lease in the settings
  table first deletes up to 500 expired rows a table, oldest first; other
  servers skip. While a pass still finds a full batch, the next one runs a
  minute later.

Reads never depend on deletion: expired rows that remain are outside every
period the Console reads.

## What Insights writes

Most reports are launches. The Insights plugin sends an installation's launch
at most once a UTC day while nothing changes, and the server writes for an
installation's launches once a UTC day. Each report the server records is one
transaction. On DynamoDB, where a transactional write costs 2 write request
units (WRU) per KB of each item, one installation's reports cost the following
when its totals are written in that transaction, as with
`aggregateBatching: false`:

| Report | Items | WRU |
| --- | --- | --- |
| First launch of a new installation | 14 | 36 |
| A later launch the same UTC day, on the same bundle | 0 | 0 |
| First launch of a later UTC day | 14 | 36 |
| `UPDATE_DOWNLOADED` | 18 | 40 |
| `UPDATE_APPLIED` | 21 | 42 |
| `RECOVERED` | 26 | 56 |
| `UPDATE_FAILED` for a download or install | 13 | 34 |
| `UPDATE_FAILED` for an update check | 8 | 20 |
| A launch on another bundle, with no `UPDATE_APPLIED` report for it | 25 | 58 |

A first launch the day after an apply or a recovery takes 16 items and 40 WRU,
since it also moves the update's latest-report rows. A download's patch
counters share the items that count it. An update failure moves no latest-report rows.
Up to four items of a report are HyperLogLog sketches of about 1 KB, at 4 WRU
apiece; every other item takes 2. A download, apply, recovery, or update
failure stores its event with its index copies; a launch stores one only when
it changes what the installation runs, so a daily launch on the same bundle
stores none. Latest-report gauges count each installation in
the UTC day of its latest report, so they move only when that day or the
installation's bundle changes. An installation that launches every day
without updating sends one report and costs about 36 WRU a day, however often
it launches: 10,000 such installations write about 360,000 WRU a day. On
Firestore each item is one document write; SQL databases keep indexes
themselves, so they write fewer rows.

DynamoDB and Firestore batch the totals by default. A report's transaction
writes its own items and one compressed log item of under 1 KB (2 WRU). A
compaction then applies many reports' totals together, one write for each total.
It runs after a report once a minute has passed since the last one, or before a
read. It then deletes the log items with `BatchWriteItem`, at 1 WRU each. A
long-lived server can set `aggregateBatching: { mode: "memory" }` to keep totals
in the process and write them every 15 seconds, with no log items. A crash
there loses up to one window; call `hotUpdater.flush()` before the process
exits. On DynamoDB Local, in 60 seconds of returning installations' first
launches of the day, with one report in ten a download or an apply:

| Reports per second | WRU per report, transactional | Log (default) | Memory |
| --- | --- | --- | --- |
| 1 | 38.1 | 10.5 | 10.8 |
| 10 | 35.5 | 8.1 | 5.5 |
| 100 | 29.9 | 8.0 | 4.9 |

Each report's own items take 5 WRU of these. The rest is its totals, which fall
from 25–33 WRU to about 3 WRU in log mode at 10 or more reports per second.
See [DynamoDB](/docs/database-adapters/aws#batched-insights-totals) and
[Firestore](/docs/database-adapters/firestore#batched-insights-totals).

The managed AWS table caps writes at 100 WRU per second. With batching, that is
about 12 reports per second; with totals in each transaction, almost three
first launches of a day per second. A report the table throttles answers `503`, and
the plugin sends it again.

## Release health

Release health follows bundle deployments of a channel and health platform
after they ship, on the card's timeline: hourly for **24h**, every six hours
for **7d**, and daily for **30d**. It starts with the two newest bundle
deployments; with a **Release ID**, it starts with that release and the one
deployed before it. Remove a bundle with its row's **×**, or choose **Add a
bundle** from the ten newest deployments; up to four bundles compare at once,
and **Show the newest 2** returns to the default. Each bundle is named by its
ID, as on the Bundles page, and keeps one color in both tabs; a vertical line
marks its deployment, and hovering or focusing its row highlights its lines. Each point counts the interval that ends there, so
a bundle's lines start after its deployment. The bundles and the open tab are kept in the page
URL. Rollbacks to the built-in bundle are not listed, since nothing downloads
them; the Bundles list counts their launches.

**Adoption** shows each bundle's installations per interval in its color: a
dashed line for those that downloaded it, and a solid line for those that
launched it. Downloads are the `UPDATE_DOWNLOADED` reports, and the downloads
a launch or crash implied when its download report never arrived. Launches are
the `UPDATE_APPLIED` reports, and the reports that first showed an
installation running the bundle when no `UPDATE_APPLIED` report came. After a forced
update the two lines nearly meet; otherwise launches follow downloads as apps
restart. After a new bundle is deployed, its lines rise and the bundle it
replaced stops being launched; a rollout to part of the installations keeps
both. Its table shows each bundle's downloads and launches in the period, the
counts the Bundles list keeps since the release's first report;
[Update failures](#update-failures) has the failed updates. How many
installations run a bundle now is in [Distribution](#read-the-console).

**Crashes** counts the launches that crashed on each bundle and recovered to
the bundle before, from their `RECOVERED` reports. Its table shows how many
installations **Crashed** on each bundle and its **Crash rate**: crashed
divided by launched plus crashed, since an installation that crashes never
reports running the bundle. When a bundle
crashes for **5%** of the installations that tried it, once at least 20 did,
Release health recommends rolling it back. **Roll back** disables its release,
as its bundle details do, so installations running it return to the previous
enabled bundle on their next update check; enable it again there to undo.
Insights counts crashes but keeps no crash reports: to see why a launch
crashed, use a crash reporter with an
[integration plugin](/docs/integration-plugins/sentry), which uploads each OTA
bundle's source maps.

Downloads, launches, and crashes count each installation once per bundle it
downloads, starts, or crashes on; one that comes back counts again. Release
health reads the hourly counts the server keeps for event lists, one bundle
and count at a time, so adding a bundle reads only that bundle: one count for
its downloads, and two for its launches: `UPDATE_APPLIED` reports and kept
launch reports. It needs no database migration.
