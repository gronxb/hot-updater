## How pruning works

`hot-updater storage prune` is reference-aware garbage collection. It reads all
bundle records and their manifests, lists the configured storage prefix, and
selects only objects that are no longer referenced.

It can remove:

- Orphaned bundle objects in both the legacy `<file-id>/...` layout and the
  current `bundles/<file-id>/...` layout.
- Patch objects that are no longer referenced, including orphaned patches under
  a target Bundle that is still live.
- Unreferenced content-addressed assets under `assets/sha256/...`.

Live bundle objects, referenced patches and assets, recently modified objects,
objects without a modification timestamp, and unknown files are protected.

<Callout type="info">
  Pruning is not a retention policy. Upgrading Hot Updater fixes new S3
  management scans without deleting live bundle records. Delete records you no
  longer need before pruning their objects.
</Callout>

## Remove policy references, then Bundle records

Channel, compatibility, enabled, and rollout fields belong to Releases. Start
by listing the Release policy you intend to retire:

```package-install
npx hot-updater release list --channel production --platform ios --limit 100 --json
```

Disable each selected Release, then hard-delete it. Hard deletion is separate
from operational rollback and is required only when you intend to make the
referenced Bundle eligible for garbage collection.

```package-install
npx hot-updater release disable <id> --yes
npx hot-updater release delete <id> --yes
```

A Bundle can be reused by multiple Releases, including Releases in other
channels. Obtain the file ID from Advanced diagnostics (or `bundle_id` in
`bundle show <id> --json`). Inspect its references and remove every Release
reference before deleting the immutable artifact record:

```package-install
npx hot-updater release list --bundle-id <file-id> --limit 1000 --json
npx hot-updater bundle delete <file-id> <another-file-id> --yes
```

`bundle delete` is rejected while any Release still references the Bundle. A
successful delete removes database records only. Shared assets, patch objects,
and Bundle files remain until a reference-aware prune confirms that no
remaining record uses them.

## Preview eligible objects

Run an explicit dry run first:

```package-install
npx hot-updater storage prune --dry-run
```

The preview shows each eligible object, its modification time, size, type, and
the total reclaimable size. The command fails closed if it cannot load all
bundle references or required manifests.

The default `--protect-newer-than 24h` window compares the current time with
each object's storage `lastModified` timestamp. It does **not** measure time
since the bundle record was deleted. Increase the window when deployments may
remain in flight for longer:

```package-install
npx hot-updater storage prune --dry-run --protect-newer-than 7d
```

Durations accept `m`, `h`, `d`, or `w`, such as `30m`, `24h`, `7d`, or `2w`.

## Delete eligible objects

Pause every deploy and patch process that writes to the same storage prefix,
then run:

```package-install
npx hot-updater storage prune --protect-newer-than 24h --yes
```

Before deletion, Hot Updater reloads bundle and manifest references and removes
objects from the candidate set if they became live.

`release promote` does not need to be paused for Storage safety. It creates a
new Release that reuses an existing Bundle and does not upload or copy Storage
objects.

<Callout type="warn">
  The configured database must own every object under the configured storage
  prefix. If databases or environments share a bucket, assign each one a
  separate storage `basePath` before pruning.
</Callout>

Storage pruning currently requires the `listObjects` and `deleteObjects`
management capabilities provided by `s3Storage`, including AWS S3 and
S3-compatible services such as Cloudflare R2. Other Storage plugins continue to
support deploy and runtime delivery but cannot use `storage prune` until they
implement those management operations.
