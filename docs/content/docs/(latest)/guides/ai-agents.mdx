## Complete setup with your agent

Use your coding agent to discover the app and existing infrastructure, complete
setup and report observable results. For terminal setup, use
[Set up manually](/docs/get-started/basic-usage). For a v0 app, follow
[Move from v0 to v1](/docs/guides/upgrade-to-v1) instead of a new-project setup.

## Attach the Skill

Install the [Hot Updater skill](https://github.com/hot-updater/skills/blob/main/skills/hot-updater/SKILL.md)
from the app's project directory:

```sh
npx skills@latest add hot-updater/skills
```

The skill gives the agent the workflow. Setup requires a compatible CLI and
access to your provider account. The request below authorizes package installation;
the agent verifies the CLI's version and commands before provisioning.

## Ask With `$hot-updater`

Ask for the complete setup and test:

```text
$hot-updater Install Hot Updater and set up this app, including its infrastructure.
Use HotUpdater.init with a custom flow; verify OTA and rollback in a native Release build on a test channel.
```

The agent can leave the provider choice until after discovery. It reuses suitable
existing resources and creates missing projects, databases, buckets and services
when its tools and access permit it. If a choice remains unresolved, use
[Choose infrastructure](/docs/get-started/choose-provider).

The shared [installation contract](/docs/get-started/installation) includes the
CLI, SDK, selected build/provider packages and helper runtime prerequisites.
The skill and generated [infrastructure instructions](/docs/guides/agent-infrastructure)
carry the discovery, provisioning and verification steps; the prompt only needs
to specify the desired app behavior and outcome.

## What the agent should complete

| Phase | Evidence to report |
| --- | --- |
| Inspect and install | App workspace, build system, provider and resolved package versions |
| Provision infrastructure | Actual resource identifiers, deployed base URL, server version and authenticated client request |
| Connect the app | Top-level init, explicit check/download/reload flow, native loading, client key, matching strategy/channel and signing key when enabled |
| Test OTA | Release app launch, visible JavaScript and asset changes after application, matching deployment ID and rollback result |
| Observe and hand off | Ready-to-copy HotUpdater.init configuration with the verified base URL and registered client x-api-key; received Insights when enabled; remaining store/native release steps and any specific blockers |

[Connect your app](/docs/get-started/app-setup) is the canonical integration
procedure. Prefer its custom `init` flow so check timing and reload behavior
fit the app. `init` alone does not download updates; preserve an existing
intentional wrapper flow or use `wrap` only when its automatic behavior is
wanted. Do not combine both initialization APIs.
[Test an OTA update](/docs/get-started/test-ota) defines the device checks. A generated scaffold, a successful doctor check or an uploaded bundle
alone does not prove that a device applied an OTA update.

If the agent cannot build or interact with the native app, it should complete
available setup work and identify the exact remaining device check.

After infrastructure verification, the agent finishes like `hot-updater init`:
it shows a `HotUpdater.init(...)` snippet with your deployed `baseURL` and the
actual client API key it issued or reused in `requestHeaders["x-api-key"]`.
This handoff also applies to infrastructure-only setup. See the
[completion example](/docs/guides/agent-infrastructure#verify-completion).

## Safety Rules

- Authenticate through the provider's login flow or private local/provider
  credential storage. Never paste tokens, passwords, private keys or credential
  JSON into the conversation. The agent verifies access without printing values.
- The app receives only its client API key. Provider, service-role, admin and
  signing credentials remain in the CLI/server or protected deployment job.
- Expect questions only for unresolved targets, missing login/access, billing
  activation or consequential choices the agent cannot infer.
- Use a dedicated test channel for the first OTA. Review the platform, channel
  and compatibility scope before changing a production release.

## Upgrade existing infrastructure

To update an existing server, ask:

```text
$hot-updater Upgrade this project's existing server to the latest stable release, preserving resources and verifying authenticated client access.
```

The agent follows
[Upgrade an existing server](/docs/guides/agent-infrastructure#upgrade-an-existing-server).
For v0, use the [migration workflow](/docs/guides/upgrade-to-v1).

## Deploy and diagnose after setup

```text
$hot-updater Deploy the current iOS app version to the staging channel and verify the result.
$hot-updater List iOS Bundles on the production channel.
$hot-updater Inspect this Bundle ID and its affected scope, then disable it and verify rollback.
$hot-updater Run doctor for this project's configured server and fix local setup issues.
```

Use [Doctor](/docs/guides/doctor) for structured `--json` diagnostics. Its
`auto`, `command` and `blocked` labels describe repair prerequisites; the agent
can continue an authorized infrastructure repair when the necessary access is
available. Public Bundle IDs drive normal operations; Artifact IDs are for
advanced storage and native crash diagnostics.
