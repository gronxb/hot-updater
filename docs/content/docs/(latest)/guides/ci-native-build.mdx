## Overview

A CI job builds the native apps with the same commands you run on your
machine, `native-build ios` and `native-build android`, with `--submit`.
Every build is tracked in Hot Updater, so the job needs the deploy
credentials your config reads. It never signs in to an Apple or Google account. The CLI reads
each credential through the config's [`secrets` adapter](/docs/concepts/secrets),
so the same `hot-updater.config.ts` builds on your machine and in CI:

| What the job needs        | Where the CLI reads it                                                                                                           |
| ------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| Android release keystore  | The secret `signing.keystore` names, such as `secret:release-keystore`, or the `HOT_UPDATER_ANDROID_KEYSTORE_*` variables        |
| App Store Connect API key | The secret `signing.ascApiKey` names, else `asc-api-key`, or the `HOT_UPDATER_ASC_KEY*` variables, for signing and TestFlight    |
| Play service account      | `play-service-account`, or the `HOT_UPDATER_PLAY_SERVICE_ACCOUNT_*` variables, for Google Play                                   |
| Deploy credentials        | The names your config reads with [`secretEnv`](/docs/concepts/secrets#deploy-credentials-with-secretenv), for tracking the build |

With [`envSecrets()`](/docs/guides/secrets-adapters/env-secrets), the default, the job's
environment holds them, from your CI provider's secrets. With a secrets store,
the job only signs in to the store, keyless through GitHub Actions OIDC where
the store allows it, and the store holds every value. [Add the
workflow](#add-the-workflow) has a complete workflow for each.

The CLI treats a run as CI when the `CI` environment variable is set, as
GitHub Actions, GitLab CI, CircleCI, Buildkite, Bitrise, and Codemagic set it,
or when it has no terminal. There it asks nothing and never starts a sign-in,
even on a terminal a runner allocates. It resolves every credential the build
signs and uploads with before the build adapter's prebuild, so a job without
one fails in seconds, with an error that names the missing credential, where
the adapter looks for it, and how to provide it.

## Get the keys once

Bring the keys you already have:

- An App Store Connect team API key with the Admin role, from **Users and
  Access → Integrations** in App Store Connect: its `.p8` file, key ID, and
  issuer ID.
- A Google Cloud service account's JSON key, with release access to the app
  in Play Console.
- The Android release keystore and its passwords.

Store the keys you have with
[`secrets put`](/docs/concepts/secrets#store-a-secret). Or let Hot Updater
issue the first two, on your machine only: in CI it never signs in. Run the
[`secrets issue`](/docs/concepts/secrets#issue-a-key-with-a-sign-in)
shortcuts:

```package-install
npx hot-updater apple login
npx hot-updater google-play login
```

`apple login` signs you in with your Apple Account once, as
[Sign in with your Apple Account](/docs/guides/native-build#sign-in-with-your-apple-account)
describes, and `google-play login` signs you in with Google
once, as [Upload to Google Play](/docs/guides/native-build#upload-to-google-play)
describes. Each keeps a key the adapter already holds; `secrets issue <kind>
--replace` issues a new one and names the old key to revoke once CI no longer
uses it. An adapter that stores values keeps the key, where CI reads it.
With `envSecrets()`, which never stores, the CLI writes the key to a file only your
user can read, prints the variables to store it in, and offers to store it as
a GitHub Actions secret
([where an issued key goes](/docs/guides/native-build#where-an-issued-key-goes)).

The App Store Connect API key is a team key with the Admin role: CI signs
with Xcode's cloud-managed distribution certificate, which only an Admin key
may use, and uploads with the same key.

## Add the workflow

The `native-build` action runs `native-build <platform> --scheme <scheme>
--submit <store> --json` with the job's environment, sets the build as its
outputs, and writes a summary of the job. Use the tag of the hot-updater
release your project installs. Each workflow below builds when you push a
version tag or run it by hand; pick the one for your `secrets` adapter.

The stores take each build number once: raise `CFBundleVersion` and
`versionCode` for every build you upload, such as from the tag or
`github.run_number` in a step before the build.

### Environment variables

With `envSecrets()`, or [`githubActions()`](/docs/guides/secrets-adapters/github-actions),
which stores under the same names, add each value in the repository's
**Settings → Secrets and variables → Actions** under its variable name. To
require a reviewer before a job reads them, add them to a protected
[environment](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/manage-environments)
instead. Each credential is one
[JSON value](/docs/concepts/secrets#sign-native-builds-with-secrets), stored
as a multi-line secret as it is:

| Secret                             | Holds                                                     |
| ---------------------------------- | --------------------------------------------------------- |
| `HOT_UPDATER_ASC_API_KEY`          | `secret:asc-api-key`, the App Store Connect API key       |
| `HOT_UPDATER_RELEASE_KEYSTORE`     | `secret:release-keystore`, the Android keystore           |
| `HOT_UPDATER_PLAY_SERVICE_ACCOUNT` | `play-service-account`, the Play service account JSON key |

```yaml title=".github/workflows/native-release.yml"
name: Native release

on:
  push:
    tags: ["v*"]
  workflow_dispatch:

permissions:
  contents: read

jobs:
  ios:
    runs-on: macos-latest
    environment: production
    steps:
      - uses: actions/checkout@d23441a48e516b6c34aea4fa41551a30e30af803 # v6
      - uses: actions/setup-node@249970729cb0ef3589644e2896645e5dc5ba9c38 # v6
        with:
          node-version: 24
          cache: npm
      - uses: actions/cache@v4
        with:
          path: ios/Pods
          key: pods-${{ runner.os }}-${{ hashFiles('ios/Podfile.lock') }}
      - run: npm ci
      - uses: gronxb/hot-updater/actions/native-build@v1.2.0
        env:
          HOT_UPDATER_ASC_API_KEY: ${{ secrets.HOT_UPDATER_ASC_API_KEY }}
          # ...and the deploy variables your config reads, which tracking needs
        with:
          platform: ios
          scheme: release
          submit: testflight

  android:
    runs-on: ubuntu-latest
    environment: production
    steps:
      - uses: actions/checkout@d23441a48e516b6c34aea4fa41551a30e30af803 # v6
      - uses: actions/setup-node@249970729cb0ef3589644e2896645e5dc5ba9c38 # v6
        with:
          node-version: 24
          cache: npm
      - uses: actions/setup-java@b843ebf9b913146b38da2eaa7aeddf76074ae1ad # v6
        with:
          distribution: temurin
          java-version: 17
          cache: gradle
      - run: npm ci
      - uses: gronxb/hot-updater/actions/native-build@v1.2.0
        env:
          HOT_UPDATER_RELEASE_KEYSTORE: ${{ secrets.HOT_UPDATER_RELEASE_KEYSTORE }}
          HOT_UPDATER_PLAY_SERVICE_ACCOUNT: ${{ secrets.HOT_UPDATER_PLAY_SERVICE_ACCOUNT }}
          # ...and the deploy variables your config reads, which tracking needs
        with:
          platform: android
          scheme: release
          submit: play-internal
```

A credential's own variables work too, such as `HOT_UPDATER_ASC_KEY`,
`HOT_UPDATER_ASC_KEY_ID`, and `HOT_UPDATER_ASC_ISSUER_ID`, or
`HOT_UPDATER_ANDROID_KEYSTORE_BASE64` and its passwords:
[Provide signing credentials](/docs/guides/native-build#provide-signing-credentials)
lists them. `HOT_UPDATER_ASC_KEY` also takes a key whose line breaks are
written as `\n`.

### AWS Secrets Manager

With [`awsSecretsManager()`](/docs/guides/secrets-adapters/aws-secrets-manager),
the job assumes a role through GitHub Actions OIDC, and the repository stores
no AWS key. Create the role with the trust policy and the read policy in
[Read secrets in GitHub Actions](/docs/guides/secrets-adapters/aws-secrets-manager#read-secrets-in-github-actions);
the deploy credentials `secretEnv` names for tracking the build come from Secrets
Manager too.

```yaml title=".github/workflows/native-release.yml"
name: Native release

on:
  push:
    tags: ["v*"]
  workflow_dispatch:

permissions:
  contents: read
  id-token: write

jobs:
  ios:
    runs-on: macos-latest
    environment: production
    steps:
      - uses: actions/checkout@d23441a48e516b6c34aea4fa41551a30e30af803 # v6
      - uses: actions/setup-node@249970729cb0ef3589644e2896645e5dc5ba9c38 # v6
        with:
          node-version: 24
          cache: npm
      - run: npm ci
      - uses: aws-actions/configure-aws-credentials@e6de054238d6b7531b4efff3b6587d9aade6a06c # v6
        with:
          role-to-assume: arn:aws:iam::123456789012:role/hot-updater-ci
          aws-region: ap-northeast-2
      - uses: gronxb/hot-updater/actions/native-build@v1.2.0
        with:
          platform: ios
          scheme: release
          submit: testflight
```

`configure-aws-credentials` sets the role's short-lived credentials in the
job's environment, where the adapter reads them; CI needs no AWS SDK. An
Android job takes the same two steps before the action.

### Google Secret Manager

With [`googleSecretManager()`](/docs/guides/secrets-adapters/google-secret-manager),
the job signs in through Workload Identity Federation, and the repository
stores no Google key. Create the pool, the provider, and the CI service
account as
[Read secrets in GitHub Actions](/docs/guides/secrets-adapters/google-secret-manager#read-secrets-in-github-actions)
shows.

```yaml title=".github/workflows/native-release.yml"
name: Native release

on:
  push:
    tags: ["v*"]
  workflow_dispatch:

permissions:
  contents: read
  id-token: write

jobs:
  android:
    runs-on: ubuntu-latest
    environment: production
    steps:
      - uses: actions/checkout@d23441a48e516b6c34aea4fa41551a30e30af803 # v6
      - uses: actions/setup-node@249970729cb0ef3589644e2896645e5dc5ba9c38 # v6
        with:
          node-version: 24
          cache: npm
      - uses: actions/setup-java@b843ebf9b913146b38da2eaa7aeddf76074ae1ad # v6
        with:
          distribution: temurin
          java-version: 17
          cache: gradle
      - run: npm ci
      - uses: google-github-actions/auth@7c6bc770dae815cd3e89ee6cdf493a5fab2cc093 # v3
        with:
          workload_identity_provider: projects/PROJECT_NUMBER/locations/global/workloadIdentityPools/github/providers/my-app
          service_account: hot-updater-ci@my-project.iam.gserviceaccount.com
      - uses: gronxb/hot-updater/actions/native-build@v1.2.0
        with:
          platform: android
          scheme: release
          submit: play-internal
```

`google-github-actions/auth` writes the federation file and sets
`GOOGLE_APPLICATION_CREDENTIALS`; the adapter exchanges the job's OIDC token
for a Google token itself, so CI needs no package. An iOS job takes the same
auth step before the action.

### Infisical

With [`infisical()`](/docs/guides/secrets-adapters/infisical), the job signs
in as a machine identity with GitHub Actions OIDC, and the repository stores
no Infisical credential. Create the identity with OIDC Auth and the
**Viewer** role as
[In GitHub Actions with OIDC](/docs/guides/secrets-adapters/infisical#in-github-actions-with-oidc)
shows, and save its ID as the repository variable
`INFISICAL_MACHINE_IDENTITY_ID`.

```yaml title=".github/workflows/native-release.yml"
name: Native release

on:
  push:
    tags: ["v*"]
  workflow_dispatch:

permissions:
  contents: read
  id-token: write

jobs:
  ios:
    runs-on: macos-latest
    environment: production
    env:
      INFISICAL_MACHINE_IDENTITY_ID: ${{ vars.INFISICAL_MACHINE_IDENTITY_ID }}
    steps:
      - uses: actions/checkout@d23441a48e516b6c34aea4fa41551a30e30af803 # v6
      - uses: actions/setup-node@249970729cb0ef3589644e2896645e5dc5ba9c38 # v6
        with:
          node-version: 24
          cache: npm
      - run: npm ci
      - uses: gronxb/hot-updater/actions/native-build@v1.2.0
        with:
          platform: ios
          scheme: release
          submit: testflight
```

The adapter requests the job's ID token itself and exchanges it for a
short-lived Infisical token. Outside GitHub Actions, set
`INFISICAL_UNIVERSAL_AUTH_CLIENT_ID` and
`INFISICAL_UNIVERSAL_AUTH_CLIENT_SECRET` from your CI's secrets instead
([In CI with Universal Auth](/docs/guides/secrets-adapters/infisical#in-ci-with-universal-auth)).

### Without the action

Any CI runs the command the action runs, with the credentials or the store's
sign-in in its environment. `testflight` and `google-play upload` are the
shortcuts for the store uploads:

```bash
npx --no-install hot-updater testflight --scheme release
# the same as
npx --no-install hot-updater native-build ios --scheme release --submit testflight

npx --no-install hot-updater google-play upload --scheme release
# the same as
npx --no-install hot-updater native-build android --scheme release --submit play-internal
```

In CI, pass `--scheme` when several schemes upload to TestFlight: it asks
nothing there.

## What a CI build does

1. It loads the config, with the deploy credentials `secretEnv` names for
   tracking the build, and checks that the database and storage answer before
   it builds.
2. Before the prebuild, it resolves every credential the build signs and
   uploads with through the `secrets` adapter, and checks that the stores
   would take the scheme's build. A missing or unreadable credential stops it
   here.
3. It writes the keystore and the `.p8` key as temporary files only the
   runner's user can read, keeps the service account in memory, and masks
   every value and the token in the log.
4. An iOS build that signs with the App Store Connect API key archives and
   exports in a keychain of its own: the CLI creates and unlocks it, makes it
   the default keychain ahead of the runner's, and restores the runner's
   keychains when the build ends. On a runner that starts empty, Xcode creates
   an Apple Development certificate for each build and keeps its private key
   in that keychain, so the CLI revokes the certificates it finds there
   through the App Store Connect API, then deletes the keychain with their
   keys. The export signs with the cloud-managed distribution certificate,
   which never leaves Apple. A scheme whose `exportOptionsPlist` exports for
   another method, such as `development`, may be signed with the certificate
   Xcode creates, so it builds in the runner's own keychains and keeps it.
5. It builds, tracks the build, submits it, and deletes the temporary files
   and the keychain.

A self-hosted macOS runner that keeps a signing identity in its login keychain
still uses it: the build's keychain comes first in the search list, and Xcode
creates a certificate only when it finds no identity. The default keychain
and the search list belong to the macOS user, so iOS builds under one user,
such as two runner instances, take turns signing: a build waits while another
holds the kernel lock on `~/Library/Caches/hot-updater/signing-keychain.lock`,
which a build that ends in any way releases. A cancelled build still revokes
its certificates and restores the keychains before it stops.

## When a credential is missing

A job without the Play service account stops before the build, without
signing in to Google. The error names the credential and where the `secrets`
adapter looks for it, says that Hot Updater signs in only at a terminal and
never in CI, gives the command that stores it once (`google-play login`), and lists
`HOT_UPDATER_PLAY_SERVICE_ACCOUNT_PATH` and
`HOT_UPDATER_PLAY_SERVICE_ACCOUNT_JSON`, the variables that provide it
instead. A missing keystore or App Store Connect API key fails the same way,
with its own variables. A store the job can't sign in to, or a role without
read access, fails with the store's reason.

<Callout type="info">
  Every build is tracked in the server's database and storage, so the job
  needs the deploy credentials your config reads. A Debug scheme's build is
  the exception: it has no built-in bundle to track.
</Callout>

## Inputs

| Input               | Default                        | Description                                                               |
| ------------------- | ------------------------------ | ------------------------------------------------------------------------- |
| `platform`          |                                | `ios`, on a macOS runner, or `android`. Required                          |
| `scheme`            |                                | The `nativeBuild.<platform>` scheme. Required                             |
| `submit`            |                                | `testflight` for iOS, `play-internal` for Android, or empty to only build |
| `working-directory` | `.`                            | The app's directory, with `hot-updater.config.ts`                         |
| `cli`               | `npx --no-install hot-updater` | The command that runs the project's CLI                                   |

The action takes no credential input: the CLI reads every credential through
the config's `secrets` adapter. It masks the job's `HOT_UPDATER_*` credential
variables in the log, field by field for a JSON value, and the CLI masks every
value it reads from a store. The action refuses `ios` on a runner that is not
macOS and an `upload` of the other platform's store. It sets `CI` for the
CLI, so a self-hosted runner that sets no `CI` never starts a sign-in either.

| Output          | Description                                                                                                         |
| --------------- | ------------------------------------------------------------------------------------------------------------------- |
| `artifact-path` | The built `.ipa`, `.aab`, `.apk`, simulator `.app`, or `.xcarchive`                                                 |
| `build`         | JSON of the build: platform, scheme, artifact path and kind, min bundle ID, channel, and fingerprint or app version |
| `native-build`  | JSON of the native build Hot Updater tracks, or `null` for a Debug build                                            |

Upload the artifact with `actions/upload-artifact` to keep it with the run:

```yaml
- uses: gronxb/hot-updater/actions/native-build@v1.2.0
  id: build
  with:
    # ...
- uses: actions/upload-artifact@v4
  with:
    name: android-release
    path: ${{ steps.build.outputs.artifact-path }}
```
