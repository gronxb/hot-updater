## Overview

A CI job builds the native apps with the same commands you run on your
machine, `build:ios` and `build:android`, with `--register` and
`--upload`. It never signs in to an Apple or Google account. The CLI reads
each credential through the config's
[`secrets` adapter](/docs/guides/secrets), `env()` by default, which reads the
job's environment: store each value once in your CI provider's secrets.

| What the job needs        | Where `env()` reads it                                                                                          |
| ------------------------- | --------------------------------------------------------------------------------------------------------------- |
| Android release keystore  | The secret `signing.keystore` names, such as `secret:release-keystore`, or the `HOT_UPDATER_ANDROID_KEYSTORE_*` variables |
| App Store Connect API key | The secret `signing.ascApiKey` names, or the `HOT_UPDATER_ASC_KEY*` variables, for signing and TestFlight       |
| Play service account      | `HOT_UPDATER_PLAY_SERVICE_ACCOUNT_JSON` or `HOT_UPDATER_PLAY_SERVICE_ACCOUNT_PATH`, for Google Play             |
| Deploy credentials        | The variables your config reads with [`secretEnv`](/docs/guides/secrets#deploy-credentials-with-secretenv), for `--register` |

The [native build guide](/docs/guides/native-build#provide-signing-credentials)
lists each credential's variables. A `.p8` key or service account stored as a
multi-line secret works as it is, and `HOT_UPDATER_ASC_KEY` also takes a key
whose line breaks are written as `\n`.

The CLI treats a run as CI when the `CI` environment variable is set, as
GitHub Actions, GitLab CI, CircleCI, Buildkite, Bitrise, and Codemagic set it,
or when it has no terminal. There it asks nothing and never starts a sign-in,
even on a terminal a runner allocates. It resolves every credential the build
signs and uploads with before the build adapter's prebuild, so a job without
one fails in seconds, with an error that names the missing credential and the
environment variables that provide it.

## Get the keys once

With `env()`, which reads and never stores, bring keys you already have:

- An App Store Connect team API key with the Admin role, from **Users and
  Access → Integrations** in App Store Connect: its `.p8` file, key ID, and
  issuer ID.
- A Google Cloud service account's JSON key, with release access to the app
  in Play Console.
- The Android release keystore and its passwords.

With a [`secrets` adapter](/docs/guides/secrets#write-a-secrets-adapter) that
stores values (`set`), Hot Updater can issue the first two for you, on your
machine only: in CI it never signs in. Run
[`secrets put`](/docs/guides/secrets#store-a-secret) without key files:

```package-install
npx hot-updater secrets put asc-api-key --kind asc-api-key
npx hot-updater secrets put play-service-account --kind play-service-account
```

`secrets put asc-api-key` signs you in with your Apple Account once, as
[Sign in with your Apple Account](/docs/guides/native-build#sign-in-with-your-apple-account)
describes, and `secrets put play-service-account` signs you in with Google
once, as [Upload to Google Play](/docs/guides/native-build#upload-to-google-play)
describes. Over a read-only adapter such as `env()`, both refuse before the
sign-in and name the variables that take a key you already have.

The App Store Connect API key is a team key with the Admin role: CI signs
with Xcode's cloud-managed distribution certificate, which only an Admin key
may use, and uploads with the same key.

In the repository's **Settings → Secrets and variables → Actions**, add each
value as a secret. To require a reviewer before a job reads them, add them to
a protected
[environment](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/manage-environments)
instead.

## Add the workflow

The `native-build` action runs `build:<platform> --scheme <scheme> --register
--upload <store> --json` with the job's environment, sets the build as its outputs,
and writes a summary of the job. This workflow builds both apps when you push
a version tag or run it by hand:

```yaml title=".github/workflows/native-release.yml"
name: Native release

on:
  push:
    tags: ["v*"]
  workflow_dispatch:

permissions:
  contents: read

jobs:
  ios:
    runs-on: macos-latest
    environment: production
    steps:
      - uses: actions/checkout@d23441a48e516b6c34aea4fa41551a30e30af803 # v6
      - uses: actions/setup-node@249970729cb0ef3589644e2896645e5dc5ba9c38 # v6
        with:
          node-version: 24
          cache: npm
      - uses: actions/cache@v4
        with:
          path: ios/Pods
          key: pods-${{ runner.os }}-${{ hashFiles('ios/Podfile.lock') }}
      - run: npm ci
      # The tag of the hot-updater release your project installs.
      - uses: gronxb/hot-updater/actions/native-build@v1.2.0
        env:
          HOT_UPDATER_ASC_KEY: ${{ secrets.HOT_UPDATER_ASC_KEY }}
          HOT_UPDATER_ASC_KEY_ID: ${{ secrets.HOT_UPDATER_ASC_KEY_ID }}
          HOT_UPDATER_ASC_ISSUER_ID: ${{ secrets.HOT_UPDATER_ASC_ISSUER_ID }}
          # ...and the deploy variables your config reads for --register
        with:
          platform: ios
          scheme: release
          upload: testflight

  android:
    runs-on: ubuntu-latest
    environment: production
    steps:
      - uses: actions/checkout@d23441a48e516b6c34aea4fa41551a30e30af803 # v6
      - uses: actions/setup-node@249970729cb0ef3589644e2896645e5dc5ba9c38 # v6
        with:
          node-version: 24
          cache: npm
      - uses: actions/setup-java@b843ebf9b913146b38da2eaa7aeddf76074ae1ad # v6
        with:
          distribution: temurin
          java-version: 17
          cache: gradle
      - run: npm ci
      - uses: gronxb/hot-updater/actions/native-build@v1.2.0
        env:
          HOT_UPDATER_ANDROID_KEYSTORE_BASE64: ${{ secrets.HOT_UPDATER_ANDROID_KEYSTORE_BASE64 }}
          HOT_UPDATER_ANDROID_KEYSTORE_PASSWORD: ${{ secrets.HOT_UPDATER_ANDROID_KEYSTORE_PASSWORD }}
          HOT_UPDATER_ANDROID_KEY_ALIAS: release
          HOT_UPDATER_ANDROID_KEY_PASSWORD: ${{ secrets.HOT_UPDATER_ANDROID_KEY_PASSWORD }}
          HOT_UPDATER_PLAY_SERVICE_ACCOUNT_JSON: ${{ secrets.HOT_UPDATER_PLAY_SERVICE_ACCOUNT_JSON }}
          # ...and the deploy variables your config reads for --register
        with:
          platform: android
          scheme: release
          upload: play-internal
```

The stores take each build number once: raise `CFBundleVersion` and
`versionCode` for every build you upload, such as from the tag or
`github.run_number` in a step before the build.

Without the action, the same job runs the command with those variables in its
environment:

```bash
npx --no-install hot-updater build:ios --scheme release --register --upload testflight
```

## What a CI build does

1. It loads the config, with the deploy credentials `secretEnv` names for
   `--register`.
2. Before the prebuild, it resolves every credential the build signs and
   uploads with through the `secrets` adapter, and checks that the stores
   would take the scheme's build. A missing or unreadable credential stops it
   here.
3. It writes the keystore and the `.p8` key as temporary files only the
   runner's user can read, keeps the service account in memory, and masks
   every value and the token in the log.
4. An iOS build that signs with the App Store Connect API key archives and
   exports in a keychain of its own: the CLI creates and unlocks it, makes it
   the default keychain ahead of the runner's, and restores the runner's
   keychains when the build ends. On a runner that starts empty, Xcode creates
   an Apple Development certificate for each build and keeps its private key
   in that keychain, so the CLI revokes the certificates it finds there
   through the App Store Connect API, then deletes the keychain with their
   keys. The export signs with the cloud-managed distribution certificate,
   which never leaves Apple. A scheme whose `exportOptionsPlist` exports for
   another method, such as `development`, may be signed with the certificate
   Xcode creates, so it builds in the runner's own keychains and keeps it.
5. It builds, registers the build, uploads it, and deletes the temporary files
   and the keychain.

A self-hosted macOS runner that keeps a signing identity in its login keychain
still uses it: the build's keychain comes first in the search list, and Xcode
creates a certificate only when it finds no identity. The default keychain
and the search list belong to the macOS user, so iOS builds under one user,
such as two runner instances, take turns signing: a build waits while another
holds the kernel lock on `~/Library/Caches/hot-updater/signing-keychain.lock`,
which a build that ends in any way releases. A cancelled build still revokes
its certificates and restores the keychains before it stops.

## When a credential is missing

A job without the Play service account stops before the build, without
signing in to Google. The error names the credential, says that Hot Updater
signs in only at a terminal and never in CI, and lists
`HOT_UPDATER_PLAY_SERVICE_ACCOUNT_PATH` and
`HOT_UPDATER_PLAY_SERVICE_ACCOUNT_JSON`, the variables that provide it. A
missing keystore or App Store Connect API key fails the same way, with its
own variables.

<Callout type="info">
  `--register` writes to the server's database, so a job that registers also
  sets the deploy variables your config reads.
</Callout>

## Inputs

| Input               | Default                        | Description                                                                                                  |
| ------------------- | ------------------------------ | ------------------------------------------------------------------------------------------------------------ |
| `platform`          |                                | `ios`, on a macOS runner, or `android`. Required                                                             |
| `scheme`            |                                | The `nativeBuild.<platform>` scheme. Required                                                                |
| `upload`            |                                | `testflight` for iOS, `play-internal` for Android, or empty to only build                                    |
| `register`          | `true`                         | Whether to register the build                                                                                |
| `working-directory` | `.`                            | The app's directory, with `hot-updater.config.ts`                                                            |
| `cli`               | `npx --no-install hot-updater` | The command that runs the project's CLI                                                                      |

The action refuses `ios` on a runner that is not macOS and an `upload` of the
other platform's store. It sets `CI` for the CLI, so a
self-hosted runner that sets no `CI` never starts a sign-in either.

| Output          | Description                                                                                                         |
| --------------- | ------------------------------------------------------------------------------------------------------------------- |
| `artifact-path` | The built `.ipa`, `.aab`, `.apk`, simulator `.app`, or `.xcarchive`                                                 |
| `build`         | JSON of the build: platform, scheme, artifact path and kind, min bundle ID, channel, and fingerprint or app version |
| `native-build`  | JSON of the registered native build, or `null` without `register`                                                   |

Upload the artifact with `actions/upload-artifact` to keep it with the run:

```yaml
- uses: gronxb/hot-updater/actions/native-build@v1.2.0
  id: build
  with:
    # ...
- uses: actions/upload-artifact@v4
  with:
    name: android-release
    path: ${{ steps.build.outputs.artifact-path }}
```
