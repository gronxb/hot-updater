The CLI reads signing and deploy credentials from the
[console's vault](/docs/guides/console-deployment/vault). A machine needs
only two environment variables, locally and in CI, and no sign-in:

```bash
HOT_UPDATER_CONSOLE_URL=https://console.example.com
HOT_UPDATER_VAULT_TOKEN=hu_vault_...
```

The console decrypts every value it serves and encrypts every value the CLI
stores. Its master key never leaves it.

## Issue a vault token

The console's **Tokens** tab issues tokens that read or write. The CLI
issues them too, over the database:

```package-install
npx hot-updater secrets token create --name ci-ios --secrets asc-api-key --actions read
```

| Option | Description |
| --- | --- |
| `--name <name>` | Identifies the token, such as the CI job that uses it |
| `--secrets <names>` | The secrets the token reaches, comma-separated |
| `--kinds <kinds>` | The kinds of secrets the token reaches, comma-separated. A kind covers every secret of it, including ones added later |
| `--actions <actions>` | What the token may do, comma-separated: `read`, `write` |
| `--expires-in-days <days>` | Days until the token expires. Without it, the token never expires |

A token reaches a secret when `--secrets` names it or `--kinds` lists its
kind. It needs at least one of them and one action:

- `read` resolves values for builds and deploys.
- `write` stores new values with `secrets put`. It never reads one back: a
  token that only writes sees each secret's metadata, never its value. It may
  write a `bundle-signing-key`, which the vault never resolves.

The token prints once. `secrets token list` lists tokens without their
plaintext (`--json` for JSON), and `secrets token revoke <id>` revokes one at
once (`-y` skips the prompt).

The token commands run like [`api-key`](/docs/custom/api-key-authentication):
over the `database` and `plugins` of `hot-updater.config.ts`, which must list
`vault()`, or over the server definition you pass as the last argument. They
need no master key. A config whose `database` is `standaloneRepository(...)`
cannot manage tokens: run them where the database is reachable.

## Store a secret

`secrets put` sends a value to the console, which encrypts it as the
secret's next version. The token needs `write` on the secret's name or kind:

```package-install
npx hot-updater secrets put asc-api-key --kind asc-api-key --p8 ./AuthKey_ABC123.p8 --key-id ABC123 --issuer-id 00000000-0000-0000-0000-000000000000
```

| Kind | Options |
| --- | --- |
| `asc-api-key` | `--p8 <file>`, `--key-id <id>`, `--issuer-id <id>` |
| `android-keystore` | `--keystore <file>`, `--key-alias <alias>`. The passwords come from `HOT_UPDATER_ANDROID_KEYSTORE_PASSWORD` and `HOT_UPDATER_ANDROID_KEY_PASSWORD`, or a hidden prompt |
| `play-service-account` | `--service-account <file>`, the JSON key file |
| `bundle-signing-key` | `--private-key <file>`, the PEM that `hot-updater keys generate` writes |
| `deploy-credentials`, `generic` | Variables as arguments: `NAME` copies `NAME` from the environment, and `NAME=value` stores the value given |

```package-install
npx hot-updater secrets put deploy --kind deploy-credentials S3_ACCESS_KEY_ID S3_SECRET_ACCESS_KEY
```

A value typed on the command line, such as `NAME=value`, stays in your shell
history. Prefer `NAME` with the variable set in the environment.

`secrets list` lists the secrets the token reaches with their kind, version,
and last update, without values (`--json` for JSON).

## Move .env.hotupdater into the vault

`hot-updater init` saves a provider's settings and credentials in
`.env.hotupdater`, which `hot-updater.config.ts` loads. `secrets import` moves
them into the vault, so the file, and CI, keep only the two connection
variables. The config needs no change.

1. Issue a token that writes and reads the secret the variables go to:

   ```package-install
   npx hot-updater secrets token create --name local --secrets deploy-credentials --actions read,write
   ```

2. Add `HOT_UPDATER_CONSOLE_URL` and `HOT_UPDATER_VAULT_TOKEN` to
   `.env.hotupdater`.

3. Import the file:

   ```package-install
   npx hot-updater secrets import .env.hotupdater
   ```

`secrets import` stores every variable that has a value as one
`deploy-credentials` secret named `deploy-credentials`, then removes those
variables, with the comment line above each, from the file. It asks first;
`-y` skips the prompt.

| Option | Description |
| --- | --- |
| `[file]` | The env file to move. Defaults to `.env.hotupdater` |
| `--name <name>` | The secret to store the variables in. Defaults to `deploy-credentials` |
| `-y, --yes` | Skip the confirmation prompt |

- These variables stay in the file: `HOT_UPDATER_CONSOLE_URL` and
  `HOT_UPDATER_VAULT_TOKEN`; `HOT_UPDATER_INIT_BUILD` and
  `HOT_UPDATER_INIT_PROVIDER`, which a later `init` reads;
  `HOT_UPDATER_API_KEY`, the client API key that ships in the app; and
  `HOT_UPDATER_VAULT_MASTER_KEY`, which never goes into the vault. So does a
  variable with an empty value.
- The import stores a new version of the secret, which replaces its whole
  value. It warns when the secret already sets variables the file does not.
- It refuses a variable another `deploy-credentials` or `generic` secret
  already sets.

While `HOT_UPDATER_CONSOLE_URL` and `HOT_UPDATER_VAULT_TOKEN` are set, in the
environment or `.env.hotupdater`, each command that loads
`hot-updater.config.ts` first sets the variables of the `deploy-credentials`
secrets the token reaches in `process.env`. The `process.env.HOT_UPDATER_*`
values that `init` wrote into the config come from the vault, and `deploy`
needs nothing else:

- A variable set in the environment or `.env.hotupdater` wins and never
  reaches the console.
- Each command lists the secrets once, and resolves them in one more request
  when it needs a variable.
- When the console is unreachable or refuses the token, the command fails at
  once and names the console's URL.

In CI, set the two variables as CI secrets, with a token that only reads:

```package-install
npx hot-updater secrets token create --name ci-deploy --secrets deploy-credentials --actions read
```

A variable that holds a path, such as `GOOGLE_APPLICATION_CREDENTIALS`, moves
as the path. The file it names stays where it is.

To run `hot-updater init` again, such as for an infrastructure update, run it
with the vault's variables. It saves its settings in `.env.hotupdater` again,
so import them again afterwards:

```package-install
npx hot-updater secrets env -- npx hot-updater init
```

## Sign native builds with vault secrets

A [native build](/docs/guides/native-build) names its signing credentials as
`vault:<name>`:

```ts title="hot-updater.config.ts"
nativeBuild: {
  android: {
    release: {
      packageName: "com.example.app",
      signing: { keystore: "vault:release-keystore" },
    },
  },
  ios: {
    release: {
      bundleIdentifier: "com.example.app",
      scheme: "ExampleApp",
      signing: { ascApiKey: "vault:asc-api-key" },
    },
  },
},
```

The build resolves the secrets it signs with in one request to the console,
writes their files as temporary files only your user can read, and deletes
them when it ends. A credential's environment variables, such as
`HOT_UPDATER_ASC_KEY_PATH`, override the vault for that credential, and the
build then never asks the console for it. The
[native build guide](/docs/guides/native-build#provide-signing-credentials)
lists them.

When the console is unreachable, refuses the token, or the two connection
variables are not set, the build fails at once. The error names the console's
URL and the environment variables that provide the credential without the
vault.

## Deploy credentials with vaultEnv

`vaultEnv` from `hot-updater` reads environment variables from the
vault's `deploy-credentials` and `generic` secrets where a config names them.
It returns a function, so loading the config stays synchronous and the
variables are read only when an adapter calls it, such as a credentials
provider:

```ts title="hot-updater.config.ts"
import { defineConfig, vaultEnv } from "hot-updater";
import { s3Storage } from "@hot-updater/aws";

const deploy = vaultEnv(["S3_ACCESS_KEY_ID", "S3_SECRET_ACCESS_KEY"]);

export default defineConfig({
  storage: s3Storage({
    bucketName: "bundles",
    region: "us-east-1",
    credentials: async () => {
      const env = await deploy();
      return {
        accessKeyId: env.S3_ACCESS_KEY_ID,
        secretAccessKey: env.S3_SECRET_ACCESS_KEY,
      };
    },
  }),
  // ...
});
```

- A name set in the environment wins and never reaches the vault. When every
  name is set, the console is not called.
- The other names come from the secrets that list them as variables. Each
  name must be in exactly one secret the token reaches, and the token needs
  `read` on it.
- Each call lists the secrets and resolves the ones it needs, two requests.
  Nothing is cached. A `deploy-credentials` variable that the CLI already set
  while loading the config is in the environment, so it needs no request.

## Run a command with vault variables

`secrets env` runs a command with the variables of every `deploy-credentials`
and `generic` secret the token reaches, and exits with the command's code. A
variable already set in the environment keeps its value:

```package-install
npx hot-updater secrets env -- ./scripts/upload-symbols.sh
```

## How the CLI handles values

- Nothing is cached, and nothing is written to disk but temporary files only
  your user can read, deleted when the command ends.
- Every value the CLI resolves or stores, and the vault token, is masked in
  its output.
- The CLI never decrypts a value itself, even where
  `HOT_UPDATER_VAULT_MASTER_KEY` is set.
