## How the vault works

`vault()`, Hot Updater's vault plugin, keeps credentials as ciphertext in your
database: App Store Connect API keys, Android keystores, Google Play service
accounts, bundle signing keys, and the variables of `.env.hotupdater`. Your
[console](/docs/guides/console-deployment) holds the master key and is the
only place a value is encrypted or decrypted. A machine that builds or
deploys, locally or in CI, keeps two environment variables:

```bash
HOT_UPDATER_CONSOLE_URL=https://console.example.com
HOT_UPDATER_VAULT_TOKEN=hu_vault_...
```

The CLI resolves each credential from the console when a command needs it,
and the console signs bundles itself, so the bundle signing key never leaves
it. A vault token reaches only the secrets and actions of its scope, and
revoking it refuses its next request.

You need a deployed console over your server's database adapter, such as
`d1Database(...)` or `kyselyAdapter(...)`. A console whose `database` is
`standaloneRepository(...)` serves no vault: the secrets live in the server's
database, which only a console over that database opens.

## Give the console a master key

Generate 32 random bytes in base64:

```bash
openssl rand -base64 32
```

Set the output as `HOT_UPDATER_VAULT_MASTER_KEY` in the console's **runtime**
environment, beside its [sign-in variables](/docs/guides/console-deployment#set-up-sign-in):

| Console host                                             | Where the master key goes                                                                                                                                                                                                                     |
| -------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| [Docker](/docs/guides/console-deployment/docker)         | Not `.env.production`, which holds the database credentials: a file of its own outside the repository, readable only by the user that starts the container and passed with a second `--env-file`, or a managed container service's runtime secret settings |
| [Vercel](/docs/guides/console-deployment/vercel)         | An environment variable of the project's Production environment                                                                                                                                                                              |
| [Netlify](/docs/guides/console-deployment/netlify)       | An environment variable with the **Functions** scope                                                                                                                                                                                          |
| [Cloudflare](/docs/guides/console-deployment/cloudflare) | A Worker secret in `.secrets.production.json`, or `npx wrangler secret put HOT_UPDATER_VAULT_MASTER_KEY`. The Worker's configuration reads it from its bindings: `vault({ masterKey: env.HOT_UPDATER_VAULT_MASTER_KEY })`, as in the next step |

Keep the master key out of CI and out of any file that holds your database
credentials: whoever holds both opens every secret. The console's runtime
needs both, so keep them in separate secret settings or files.
[`hot-updater doctor`](/docs/guides/doctor#check-the-vaults-master-key) warns
about an env file that holds both. Keep a copy of the key somewhere only you
can read, such as a password manager. The vault cannot be opened without it,
and no one can recover it.

To replace the key later, [rotate it](/docs/guides/console-deployment/vault#rotate-the-master-key):
the console wraps every stored value's key again, without decrypting the
values.

</Step>
<Step>

## Add vault() to the console and the CLI

List `vault()` in the `plugins` of `console.config.ts`, imported from
`@hot-updater/server/plugins`:

```ts title="console.config.ts (excerpt)"
import { defineConsoleConfig } from "@hot-updater/console";
import {
  apiKeys,
  insights,
  remoteConfig,
  vault, // [!code ++]
} from "@hot-updater/server/plugins";

export default defineConsoleConfig({
  // ...database and storage
  plugins: [apiKeys(), insights(), remoteConfig(), vault()], // [!code highlight]
});
```

On a Cloudflare Worker console, pass the Worker secret:
`vault({ masterKey: env.HOT_UPDATER_VAULT_MASTER_KEY })`. Elsewhere, `vault()`
reads `HOT_UPDATER_VAULT_MASTER_KEY` from the environment.

List it in the `plugins` of `hot-updater.config.ts` too, imported from
`hot-updater/plugins`:

```ts title="hot-updater.config.ts (excerpt)"
import { defineConfig } from "hot-updater";
import {
  apiKeys,
  insights,
  remoteConfig,
  vault, // [!code ++]
} from "hot-updater/plugins";

export default defineConfig({
  // ...build, storage, and database
  plugins: [apiKeys(), insights(), remoteConfig(), vault()], // [!code highlight]
});
```

The CLI then issues vault tokens over the config's database, and
[`doctor --fix`](/docs/guides/doctor#check-the-database-schema) creates the
vault's tables.

Don't add `vault()` to your server. It is the one plugin these two lists hold
that the server doesn't run: the server never reads a secret, and its
environment, which holds the database credentials, never holds the master
key. A managed server never runs it either. Every other plugin stays the
same in all three lists.

</Step>
<Step>

## Create the vault's tables

After you upgrade the Hot Updater packages, apply the migrations from the
project of `hot-updater.config.ts`:

```package-install
npx hot-updater doctor --fix
```

With a [managed](/docs/managed/supabase) database, `--fix` runs the
provider's migration files the database has not run, which add the vault's
tables: the Worker's migrations on Cloudflare D1, and `supabase db push` on
Supabase. On DynamoDB, Firestore, and Cosmos DB, it creates the missing
tables. Run it before you redeploy a managed server whose schema changed, as
the new server answers 503 until its database is migrated.

Over your own server's database adapter, `--fix` creates the vault's tables
as it creates any configured plugin's.
[Check the database schema](/docs/guides/doctor#check-the-database-schema)
lists what `--fix` runs for each database. Drizzle and Prisma create their own
tables, and the `db` commands read a server definition rather than
`hot-updater.config.ts`: run `hot-updater db generate <file>`, apply the
schema with your ORM, then `hot-updater db migrate <file>`, with a definition
file that lists `vault()` beside your server's plugins.

Redeploy the console. Its **Vault** page opens without a lock notice once the
master key is set and the tables exist.

</Step>
<Step>

## Store your secrets

Store each credential on the console's **Vault** page, or from the CLI. The
console encrypts what either sends; neither shows a stored value again.

<Tabs items={["Console", "CLI"]}>
<Tab value="Console">

Open **Vault → Secrets → Add secret**, pick a kind, and enter its files and
fields. A new secret is named after its kind, such as `android-keystore`.

| Kind                       | What you enter                                                                                                   |
| -------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| App Store Connect API key  | The `.p8` file, its key ID, and its issuer ID                                                                    |
| Android keystore           | The keystore file, its store password, key alias, and key password                                               |
| Google Play service account | The service account's JSON key file                                                                             |
| Bundle signing key         | The private key PEM your app's embedded public key verifies, such as `keys/private-key.pem`                     |
| Deploy credentials         | Each variable of `.env.hotupdater` as a name and a value                                                         |

</Tab>
<Tab value="CLI">

Issue a token that writes, which the CLI does over the database without a
master key, or in the console's **Tokens** tab:

```package-install
npx hot-updater secrets token create --name setup --kinds deploy-credentials,bundle-signing-key,asc-api-key,android-keystore,play-service-account --actions read,write --expires-in-days 1
```

Set `HOT_UPDATER_CONSOLE_URL` and that token as `HOT_UPDATER_VAULT_TOKEN` in
your shell or `.env.hotupdater`, then store each credential:

| Credential                                                        | Command                                                                                                                                                                                                              |
| ----------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Deploy credentials, the variables of `.env.hotupdater`            | [`npx hot-updater secrets import`](/docs/guides/secrets#move-envhotupdater-into-the-vault), which leaves only the two connection variables in the file                                                               |
| A new bundle signing key                                          | [`npx hot-updater keys generate --vault`](/docs/guides/signing/remote#sign-with-the-console-vault), which writes only `keys/public-key.pem`. Embed it, and release the native app before its first signed OTA update |
| The bundle signing key your app already embeds                    | `npx hot-updater secrets put bundle-signing-key --kind bundle-signing-key --private-key keys/private-key.pem`                                                                                                        |
| App Store Connect API key, Android keystore, Play service account | [`npx hot-updater secrets put <name> --kind <kind>`](/docs/guides/secrets#store-a-secret), such as `secrets put asc-api-key --kind asc-api-key --p8 ./AuthKey_ABC123.p8 --key-id ABC123 --issuer-id <id>`, with the kind's options |

Revoke the setup token when you are done, and give each machine and CI job
a token of its own, as the next steps do.

</Tab>
</Tabs>

Once the vault holds a bundle signing key, delete the local copy of its
private key. To change a stored credential later, **Overwrite** it on the
**Vault** page, or run `secrets put` with its name again: either stores its
next version.

</Step>
<Step>

## Point the config at the vault

Sign bundles with the console, and name the native build credentials by
secret:

```ts title="hot-updater.config.ts (excerpt)"
import { defineConfig } from "hot-updater";
import { remoteSigning } from "hot-updater/signing";

export default defineConfig({
  // ...build, storage, database, and plugins with vault()
  signing: remoteSigning({
    endpoint: "https://console.example.com",
  }),
  nativeBuild: {
    android: {
      release: {
        packageName: "com.example.app",
        signing: { keystore: "vault:android-keystore" },
      },
    },
    ios: {
      release: {
        bundleIdentifier: "com.example.app",
        scheme: "ExampleApp",
        installPods: true,
        signing: { ascApiKey: "vault:asc-api-key" },
      },
    },
  },
});
```

- `remoteSigning` reaches the console's `/_hot-updater/signing` with the token
  in `HOT_UPDATER_SIGNING_TOKEN`, and the console signs with the vault's
  bundle signing key. Its endpoint is the console's URL.
- `vault:<name>` names a secret by the name you stored it under. A secret is
  named after its kind unless you named it, such as `vault:android-keystore`.
- The variables `secrets import` moved stay in the config as
  `process.env.HOT_UPDATER_*`: while the two connection variables are set,
  [commands that use the database, storage, or signing](/docs/guides/secrets#move-envhotupdater-into-the-vault)
  set them from the vault before the config loads.

</Step>
<Step>

## Issue a token for each CI job

Give each job a token that reaches only what it needs: an OTA deploy reads
`deploy-credentials` and signs with `bundle-signing-key`, and a native build
reads `deploy-credentials` for `--register` with the credentials it signs and
uploads with.

<Tabs items={["Console", "CLI"]}>
<Tab value="Console">

Open **Vault → Tokens → Issue token**, and issue one token for each job:

| Field   | OTA deploy                                  | Native build                                                                           |
| ------- | ------------------------------------------- | -------------------------------------------------------------------------------------- |
| Name    | `ci-ota`                                    | `ci-native`                                                                            |
| Actions | **Read values**, **Sign bundles**           | **Read values**                                                                        |
| Secrets | `deploy-credentials`, `bundle-signing-key`  | `deploy-credentials`, `asc-api-key`, `android-keystore`, `play-service-account`        |
| Expires | 30 days, 90 days, a year, or never          | 30 days, 90 days, a year, or never                                                     |

The token shows once, with the console's URL, as the CI variables to set.

</Tab>
<Tab value="CLI">

```package-install
npx hot-updater secrets token create --name ci-ota --secrets deploy-credentials,bundle-signing-key --actions read,sign
npx hot-updater secrets token create --name ci-native --secrets deploy-credentials,asc-api-key,android-keystore,play-service-account --actions read
```

Each token prints once. Add `--expires-in-days` to make one expire, and see
[Issue a vault token](/docs/guides/secrets#issue-a-vault-token) for every
option.

</Tab>
</Tabs>

A token whose scope allows `sign` works as both `HOT_UPDATER_VAULT_TOKEN` and
`HOT_UPDATER_SIGNING_TOKEN`: reading never returns a bundle signing key, and
signing reaches nothing else.

</Step>
<Step>

## Deploy from GitHub Actions

In the repository's **Settings → Secrets and variables → Actions**, add
`HOT_UPDATER_CONSOLE_URL` as a variable, and the two tokens as the secrets
`HOT_UPDATER_OTA_VAULT_TOKEN` and `HOT_UPDATER_NATIVE_VAULT_TOKEN`. To require
a reviewer before a job reads them, add them to a protected
[environment](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/manage-environments)
instead. The workflows need no other secret.

This workflow deploys an OTA update for both platforms on each push to
`main`:

```yaml title=".github/workflows/ota.yml"
name: OTA update

on:
  push:
    branches: [main]

jobs:
  deploy:
    runs-on: ubuntu-latest
    environment: production
    permissions:
      contents: read
    env:
      HOT_UPDATER_CONSOLE_URL: ${{ vars.HOT_UPDATER_CONSOLE_URL }}
      HOT_UPDATER_VAULT_TOKEN: ${{ secrets.HOT_UPDATER_OTA_VAULT_TOKEN }}
      HOT_UPDATER_SIGNING_TOKEN: ${{ secrets.HOT_UPDATER_OTA_VAULT_TOKEN }}
    steps:
      - uses: actions/checkout@d23441a48e516b6c34aea4fa41551a30e30af803 # v6
      - uses: actions/setup-node@249970729cb0ef3589644e2896645e5dc5ba9c38 # v6
        with:
          node-version: 22

      - run: npm ci

      - run: npx --no-install hot-updater deploy -p ios
      - run: npx --no-install hot-updater deploy -p android
```

This workflow builds the native apps when you run it, registers each build,
and uploads it to TestFlight and Google Play's internal track:

```yaml title=".github/workflows/native.yml"
name: Native release

on:
  workflow_dispatch:

permissions:
  contents: read

env:
  HOT_UPDATER_CONSOLE_URL: ${{ vars.HOT_UPDATER_CONSOLE_URL }}
  HOT_UPDATER_VAULT_TOKEN: ${{ secrets.HOT_UPDATER_NATIVE_VAULT_TOKEN }}

jobs:
  ios:
    runs-on: macos-latest
    environment: production
    steps:
      - uses: actions/checkout@d23441a48e516b6c34aea4fa41551a30e30af803 # v6
      - uses: actions/setup-node@249970729cb0ef3589644e2896645e5dc5ba9c38 # v6
        with:
          node-version: 22

      - run: npm ci

      - run: npx --no-install hot-updater build:ios --scheme release --register --upload testflight

  android:
    runs-on: ubuntu-latest
    environment: production
    steps:
      - uses: actions/checkout@d23441a48e516b6c34aea4fa41551a30e30af803 # v6
      - uses: actions/setup-node@249970729cb0ef3589644e2896645e5dc5ba9c38 # v6
        with:
          node-version: 22
      - uses: actions/setup-java@b843ebf9b913146b38da2eaa7aeddf76074ae1ad # v6
        with:
          distribution: temurin
          java-version: 17

      - run: npm ci

      - run: npx --no-install hot-updater build:android --scheme release --register --upload play-internal
```

Each command resolves its credentials in one or two requests to the console,
writes the files it signs with as temporary files only the runner's user can
read, and deletes them when it ends. Every resolved value, and the token, is
masked in the job's log. When the console is unreachable or refuses the token,
the command fails at once and names the console's URL.

The same variables run these commands on your machine. `secrets import` left
the two connection variables in `.env.hotupdater`, with the setup token you
revoke afterwards. Issue a token for your machine as you issued `ci-ota`, and
set it in `.env.hotupdater` as both `HOT_UPDATER_VAULT_TOKEN` and
`HOT_UPDATER_SIGNING_TOKEN`, since `remoteSigning` reads only the latter:

```bash title=".env.hotupdater"
HOT_UPDATER_CONSOLE_URL=https://console.example.com
HOT_UPDATER_VAULT_TOKEN=hu_vault_...
HOT_UPDATER_SIGNING_TOKEN=hu_vault_...
```

</Step>

## Keep the vault healthy

| Task                  | Console                                              | CLI                                                                             |
| --------------------- | ---------------------------------------------------- | ------------------------------------------------------------------------------- |
| Change a credential   | **Overwrite** on **Vault → Secrets**                 | `npx hot-updater secrets put <name> --kind <kind> ...`                          |
| List secrets          | **Vault → Secrets**                                  | `npx hot-updater secrets list`                                                  |
| Delete a secret       | **Delete** on **Vault → Secrets**                    | None                                                                            |
| List and revoke tokens | **Vault → Tokens**                                  | `npx hot-updater secrets token list`, `npx hot-updater secrets token revoke <id>` |
| Rotate the master key | **Vault → Master keys**, then **Rewrap**             | None: only the console holds the master keys                                    |

CI reads a changed credential on its next run, and a revoked token is refused
at its next request. Revoke a token when a job no longer needs it or its CI
secret may have leaked.
[Rotate the master key](/docs/guides/console-deployment/vault#rotate-the-master-key)
covers `HOT_UPDATER_VAULT_MASTER_KEYS` and the rewrap. The
[Vault](/docs/guides/console-deployment/vault) page covers the console's
routes, kinds, and errors, and [Secrets in the CLI](/docs/guides/secrets)
every `secrets` command.
