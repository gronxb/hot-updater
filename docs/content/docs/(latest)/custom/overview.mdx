## Choose a custom server

Use a custom server when you need to own the backend code or integrate with an
existing ORM, framework or deployment process. If a supplied cloud deployment
fits your project, [choose a provider preset](/docs/get-started/choose-provider).

For one complete path, follow the [Hono, SQLite and R2 quick start](/docs/custom/quick-start).
You do not need to evaluate every adapter before starting. For an existing
backend, use the matching integration below and keep its established tooling.

## Architecture

| Part                    | Runs in                            | Responsibility                                                                                 |
| ----------------------- | ---------------------------------- | ---------------------------------------------------------------------------------------------- |
| `hot-updater.config.ts` | React Native project or deploy job | Build bundles, upload artifacts and send management requests through `standaloneRepository`.   |
| `createHotUpdater`      | Server project                     | Compile Release Catalogs and serve client and admin handlers using a direct database provider. |
| Database adapter        | Server project                     | Persist canonical rows, prepare the schema and commit changes atomically.                      |
| Storage plugin          | Deploy job and server              | Upload artifacts and resolve their stored locations for downloads.                             |

Pass database and storage plugin objects directly to `createHotUpdater` and
`defineConfig`. Provider factories such as `dynamoDB(options)` return those
objects. Capture SDK clients, bindings and credentials when constructing each
plugin; handlers take only a Web `Request`.

The mobile app uses the client base URL and a client API key. The CLI connects
to the separately protected admin base URL. The admin token and provider
credentials stay in server and deploy environments.

## Database adapters

Choose the adapter that matches your existing database tooling. Prepare its
schema before creating the first API key or serving requests.

| Adapter                                  | Schema preparation                                                                                           |
| ---------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| [Kysely](/docs/custom/database/kysely)   | Generate SQL for review, then use `hot-updater db migrate`.                                                  |
| [Drizzle](/docs/custom/database/drizzle) | Generate the Drizzle schema and apply it with Drizzle Kit.                                                   |
| [Prisma](/docs/custom/database/prisma)   | Generate/merge the Prisma models, regenerate the client and apply the schema with Prisma.                    |
| [MongoDB](/docs/custom/database/mongodb) | Use a replica set or sharded cluster with transactions enabled; apply indexes with `hot-updater db migrate`. |

For database tooling outside an ORM, use [SQL schema export](/docs/custom/database/sql-export).

## Server frameworks

Mount `handlers.admin` behind your framework's authentication, then mount
`handlers.client` at the client root. Follow the recipe for
[Hono](/docs/custom/frameworks/hono), [Express](/docs/custom/frameworks/express)
or [Elysia](/docs/custom/frameworks/elysia). Each recipe shows its framework's
middleware and mount ordering.

Handlers match paths relative to their mount. For example, mounting the client
handler at `/hot-updater` exposes `/hot-updater/version`; configure the app's
`baseURL` as `https://example.com/hot-updater`. The framework owns the external
prefix, including for signed storage-download URLs resolved against `baseURL`.

## Runtime policy

Every `createHotUpdater` configuration sets `clientAccess`. Use
`{ type: "api-key" }` to require a client key for Release Catalogs, artifact
resolution and Insights ingestion, or explicitly choose `{ type: "public" }`.

| Handler           | Routes and access                                                                                                                                                              |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `handlers.client` | Public `/version`; Release Catalogs, artifacts and `POST /events` follow `clientAccess`; signed storage-download routes are available when the storage provider supports them. |
| `handlers.admin`  | Bundle, Release, catalog, Channel, database-commit and Insights-query routes. Your framework authenticates every request before mounting this handler.                         |

Insights is built in. React Native clients report lifecycle events by default
and can opt out with `HotUpdater.init({ insights: false })`. Client API keys do
not grant admin or Insights-query access. See [API keys](/docs/custom/api-key-authentication)
for bootstrap and rotation, and the
[repository server contract](/docs/database-plugins/standalone#server-contract)
for the HTTP operations used by the CLI.

## Storage plugins

Use a storage plugin in the CLI and the matching runtime implementation in the
server's `storage` array. The URI scheme and bucket/key configuration must agree.
For example, an `s3Storage` deploy configuration needs an `s3Storage` server entry;
using R2 infrastructure alone does not make `s3://` and `r2://` interchangeable.

A server may retain multiple storage providers when old and new bundles coexist,
but register at most one plugin per URI scheme. Stored URIs use
`protocol://bucket/encoded/slash/key`. The matching plugin owns reads, download
URLs and exact deletion; an unowned HTTP(S) URI can be used directly.

Use [S3](/docs/storage-plugins/aws), [R2](/docs/storage-plugins/cloudflare),
[Supabase Storage](/docs/storage-plugins/supabase) or
[Firebase Storage](/docs/storage-plugins/firebase). Custom implementations follow
the [storage contract](/docs/storage-plugins/custom-storage). Install packages
used by the deployed server as runtime dependencies.

## CLI configuration

After the server and schema are ready, [connect the React Native project's CLI](/docs/custom/cli-configuration).
Configure the exact admin mount URL, its authentication headers and the same
storage location used by the server.

## Deploy and verify

Use your existing hosting process or follow the
[Docker](/docs/custom/hosting/docker) or [Vercel](/docs/custom/hosting/vercel)
recipe. Verify that `/version` responds and unauthenticated admin requests are
rejected, then [set up the mobile app](/docs/get-started/app-setup) with the
verified client URL and key. Finish by [testing an OTA update](/docs/get-started/test-ota)
in a release build.
