## Installation

Install the server and storage packages in the deployed server project. Install
the CLI packages in the React Native project that runs Hot Updater commands.

```package-install
npm install @hot-updater/server @hot-updater/aws
```

```package-install
npm install --save-dev @hot-updater/bare @hot-updater/aws @hot-updater/standalone hot-updater dotenv
```

## Architecture

Self-hosted mode lets you control the database layer while using existing cloud storage plugins.

**How it works:**

- **CLI**: Uses `standaloneRepository` in hot-updater.config.ts to send requests to your server
- **Server**: Handles database operations with `@hot-updater/server`
- **Storage**: Uses existing plugins (AWS S3, Supabase, Cloudflare R2, Firebase)

This approach gives you full control over metadata while leveraging reliable cloud storage.

## CLI Configuration

Configure your Hot Updater CLI to use the self-hosted database.

In the React Native project, create `.env.hotupdater` with the server's `R2_*`
storage values and `HOT_UPDATER_ADMIN_TOKEN`, and add it to `.gitignore`.

```typescript title="hot-updater.config.ts"
import { bare } from "@hot-updater/bare";
import { s3Storage } from "@hot-updater/aws";
import { standaloneRepository } from "@hot-updater/standalone";
import { defineConfig } from "hot-updater";
import { config } from "dotenv";

config({ path: ".env.hotupdater" });

const adminToken = process.env.HOT_UPDATER_ADMIN_TOKEN;
if (!adminToken) {
  throw new Error("HOT_UPDATER_ADMIN_TOKEN is required");
}

export default defineConfig({
  build: bare({ enableHermes: true }),
  storage: s3Storage({
    region: "auto",
    endpoint: process.env.R2_ENDPOINT,
    credentials: {
      accessKeyId: process.env.R2_ACCESS_KEY_ID!,
      secretAccessKey: process.env.R2_SECRET_ACCESS_KEY!,
    },
    bucketName: process.env.R2_BUCKET_NAME!,
  }),
  database: standaloneRepository({
    baseUrl: "http://localhost:3000/hot-updater/admin",
    commonHeaders: {
      Authorization: `Bearer ${adminToken}`,
    },
  }),
  updateStrategy: "appVersion",
});
```

## Storage Plugins

The server `storage` field accepts an array of flat storage objects. `get`
returns a Web `Response`, while `getDownloadUrl` returns either an absolute
HTTP(S) URL or a signed path relative to the Hot Updater server. The server
resolves a relative path against the incoming update-check request before
sending it to the client. How a provider produces or handles that value remains
inside its implementation.

Stored locations use the hierarchical
`protocol://bucket/encoded/slash/key` form. Providers use the shared
`createStorageUri` and `parseStorageUri` helpers so special characters
round-trip without flattening the key hierarchy.

1. When you run `npx hot-updater deploy` from your `hot-updater.config.ts`, the bundle is uploaded and a `storageUri` is saved to the database
2. When the API returns bundle information, the matching storage plugin turns the stored URI into an HTTP(S) URL
3. When diffing data is available, the server reads it directly from storage so the client can reuse unchanged files
4. React Native clients download the update files using the returned URLs

The CLI `storage` field uses the same flat contract for upload, exact deletion,
and reads. Edge providers such as Cloudflare Workers may use a separate runtime
subpath with the same public plugin name.

### Multiple Storage Plugins

`storage` is an array, allowing you to configure multiple storage providers simultaneously. Each plugin handles its specific storage URI protocol.

**Use cases:**

- Bundles stored across different storage providers
- Migrating between storage providers (old and new bundles coexist)
- Multi-region deployments with different storage backends

**Example with multiple plugins:**

```typescript title="src/hotUpdater.ts"
export const hotUpdater = createHotUpdater({
  database: kyselyAdapter({ db, provider: "sqlite" }),
  clientAccess: { type: "api-key" },
  storage: [
    s3Storage({
      /* AWS S3 config with download URL support */
    }),
    supabaseStorage({
      /* Supabase config */
    }),
    myCustomStorage({
      /* My Custom Storage */
    }),
  ],
});
```

The server automatically uses the correct plugin to decode each `storageUri`
based on its protocol.

Configure at most one storage plugin per URI scheme. A matching registered
plugin owns reads, URL generation, and exact deletion even for `http` or
`https`. Only when no plugin owns an HTTP(S) URI does Hot Updater use the direct
URL; an unowned non-HTTP scheme is unsupported.

## Runtime policy

`createHotUpdater` always exposes Insights ingestion and query capabilities.
React Native clients send lifecycle events by default and can opt out with
`HotUpdater.init({ insights: false })`.

Every server must explicitly set `clientAccess`. Use `{ type: "api-key" }` to
require authentication for update checks and Insights ingestion through
`database.models.apiKeys`, or `{ type: "public" }` to keep those
client routes public.

Release Catalog, artifact, storage-download, and `/version` routes are always
available on `handlers.client`. Bundle, Release, Release Catalog row, Channel,
database-commit, and Insights-query routes live exclusively on
`handlers.admin`. Expose that handler only through an authenticated framework
mount.

```typescript title="src/hotUpdater.ts"
export const hotUpdater = createHotUpdater({
  database: kyselyAdapter({ db, provider: "sqlite" }),
  clientAccess: { type: "api-key" },
  storage: [
    s3Storage({
      /* storage config */
    }),
  ],
});
```

Insights ingestion is available on `handlers.client` and queries are
available on `handlers.admin`. The server does not authenticate admin queries
itself; the framework middleware protecting the admin mount owns that decision.

<Callout type="warn">
**Recommendation: Match Your CLI Configuration**

For most use cases, use only the storage plugin that matches your CLI's `hot-updater.config.ts`.

**CLI (hot-updater.config.ts):**

```typescript
storage: s3Storage({ ... })
```

**Server (src/hotUpdater.ts):**

```typescript
storage: [s3Storage({ ... })]
```

This ensures consistency and simplifies configuration. Only use multiple plugins when you need to support bundles from different storage providers.

</Callout>

**Available official plugins:**

- [s3Storage](/docs/storage-plugins/aws) - AWS S3 and Cloudflare R2
- [supabaseStorage](/docs/storage-plugins/supabase) - Supabase Storage
- [firebaseStorage](/docs/storage-plugins/firebase) - Firebase Cloud Storage

## Database Adapters

Start by setting up your database adapter. Choose the ORM that fits your project:

- [Drizzle](/docs/custom/database/drizzle) - TypeScript ORM with SQL-like syntax
- [Prisma](/docs/custom/database/prisma) - Next-generation ORM with intuitive data modeling
- [Kysely](/docs/custom/database/kysely) - Type-safe SQL query builder
- [MongoDB](/docs/custom/database/mongodb) - Native MongoDB driver

Generate and apply the adapter's schema before serving requests. The exact
workflow differs by adapter: Kysely and MongoDB use `hot-updater db migrate`,
Drizzle uses the generated schema with Drizzle Kit, and Prisma merges its models
into `prisma/schema.prisma` before `prisma db push` applies them.

## Server Frameworks

After configuring your database, choose the framework that fits your stack:

- [Hono](/docs/custom/frameworks/hono) - Lightweight Web Standard framework
- [Express](/docs/custom/frameworks/express) - Popular Node.js framework
- [Elysia](/docs/custom/frameworks/elysia) - Modern Bun-first framework

## Key Features

- **Framework Agnostic**: Use Hono, Express, Elysia, or any Web Standard framework
- **ORM choice**: Drizzle, Prisma, Kysely, or native MongoDB driver
- **Database control**: PostgreSQL, SQLite, or MongoDB on your infrastructure
- **Cloud storage**: Leverage existing AWS S3, Cloudflare R2, Supabase, or Firebase storage
- **Type safety**: Full TypeScript support across all adapters
- **Operational control**: Add framework-specific authentication, lifecycle,
  and error handling for your deployment environment
