## Before connecting

Use this page after [agent setup](/docs/guides/ai-agents),
[manual setup](/docs/get-started/basic-usage), or connecting an existing server.
Both setup paths use the same app integration and
[OTA verification](/docs/get-started/test-ota).

Before editing, have the [required packages](/docs/get-started/installation)
installed, a deployed update server **base URL**, and its registered **client API
key** when authentication is enabled. Managed providers require this key.
Existing v0 apps must follow [Move from v0 to v1](/docs/guides/upgrade-to-v1)
for the migration steps.

## Configure the update client

Use `HotUpdater.init()` and a custom update flow so your app chooses when to
check, download and restart. Initialization configures the client and starts
native launch verification; it does **not** check for or download an update.

This complete example initializes after the root screen mounts. It enables an
explicit check after native readiness, downloads the selected update, then
waits for the user to choose **Restart to apply**:

```tsx title="App.tsx"
import { HotUpdater } from "@hot-updater/react-native";
import { useEffect, useRef, useState } from "react";
import { Button, Text, View } from "react-native";

export default function App() {
  const initialized = useRef(false);
  const [canCheck, setCanCheck] = useState(false);
  const [canReload, setCanReload] = useState(false);
  const [status, setStatus] = useState("Starting");

  useEffect(() => {
    if (initialized.current) return;
    initialized.current = true;
    HotUpdater.init({
      baseURL: "https://your-update-server-url",
      requestHeaders: {
        "x-api-key": "<your-registered-client-api-key>",
      },
      onNotifyAppReady: () => {
        setStatus("Ready to check");
        setCanCheck(true);
      },
      onError: () => setStatus("Startup verification failed"),
    });
  }, []);

  async function checkForUpdates() {
    if (!canCheck || canReload) return;
    setCanCheck(false);
    setStatus("Checking");
    try {
      let checkError: Error | undefined;
      const updateInfo = await HotUpdater.checkForUpdate({
        updateStrategy: "appVersion",
        onError: (error) => {
          checkError = error;
        },
      });
      if (checkError) throw checkError;
      if (!updateInfo) {
        setStatus("No update selected");
        return;
      }
      setStatus("Downloading");
      const downloaded = await updateInfo.updateBundle();
      if (!downloaded) throw new Error("Download failed");
      setCanReload(true);
      setStatus(
        updateInfo.shouldForceUpdate ? "Required update ready" : "Update ready",
      );
    } catch {
      setStatus("Update failed. Try again.");
    } finally {
      setCanCheck(true);
    }
  }

  return (
    <View>
      <Text>OTA baseline</Text>
      <Text>{status}</Text>
      <Text>Update ID: {HotUpdater.getBundleId()}</Text>
      <Button
        title="Check for updates"
        disabled={!canCheck || canReload}
        onPress={() => void checkForUpdates()}
      />
      {canReload && (
        <Button
          title="Restart to apply"
          onPress={() => {
            void HotUpdater.reload().catch(() => {
              setStatus("Restart failed. Try again.");
            });
          }}
        />
      )}
    </View>
  );
}
```

Call `init` once at your app's readiness boundary. If startup includes essential
bootstrap work, move initialization after that work succeeds. `init` returns
`void`; its [`onNotifyAppReady`](/docs/react-native-api/notifyAppReady) callback
reports the asynchronous native result. Export the root component directly and
do not combine `init` with `wrap`.

The example keeps checks behind a button. You can use the same sequence after
login, when returning to foreground or from your own update screen. Capture
`checkForUpdate`'s `onError`: a failed check can return `null`, so a `try/catch`
alone cannot distinguish every failure from “no update selected.” Always await
a successful `updateInfo.updateBundle()` before enabling restart.

Your custom flow controls reload timing, including for `shouldForceUpdate`.
This example labels required updates and waits for explicit restart. If your
product requires immediate application, use that flag to select an appropriate
reload point after the download succeeds. See
[Control update timing](/docs/guides/custom-update) for progress and lifecycle
patterns.

Replace the URL and client-key placeholders using your verified provider setup.
Keep any provider base path; the SDK appends the catalog and artifact routes.
Use the same `updateStrategy` in `checkForUpdate` and `hot-updater.config.ts`.
`appVersion` is the default; choose
[fingerprint](/docs/guides/update-strategies/fingerprint) when you want to track
native compatibility inputs.

The client key is intended for the app. Provider tokens, service-role keys,
admin bearer tokens and signing private keys stay in the deployment environment
or server. Never substitute one of those credentials for the client key.

### Supply values to native and OTA builds

`.env.hotupdater` configures local CLI/provider access; it is **not automatically
loaded into your app**. Connect the server URL and client key to your project's
app build configuration, and verify that both native builds and OTA bundle
builds receive them, including CI or EAS.

For Expo, public app variables can supply the two fields:

```tsx
baseURL: process.env.EXPO_PUBLIC_HOT_UPDATER_BASE_URL!,
requestHeaders: {
  "x-api-key": process.env.EXPO_PUBLIC_HOT_UPDATER_API_KEY!,
},
```

For bare React Native and Rock, use the project's existing build-time
configuration mechanism. Validate required values in the native and OTA build
pipelines; the TypeScript `!` operator alone does not check them at runtime.
A missing URL or key must not silently disable initialization.

### Reporting and custom update timing

[Insights](/docs/guides/insights) is enabled by default for `HotUpdater.init()`.
Set `insights: false` in its configuration to opt out. Native readiness and
received server reports are separate checks; confirm both after your first OTA.

Use the [update store](/docs/react-native-api/useHotUpdaterStore) to render
progress within your own UI. Your update flow can defer reload until navigation
is idle or the user has saved their work.

### Optional automatic wrapper

[`HotUpdater.wrap()`](/docs/react-native-api/wrap) remains supported when you
want its automatic launch check and update behavior. Use that wrapper instead
of the `init` flow above, preserving the same URL, client key and strategy.
Do not initialize with both APIs.

## Build Configuration

Setup configures bundling through the `build` field in `hot-updater.config.ts`.
Keep the selected build plugin alongside your existing storage and database settings.

<Tabs items={['Bare (React Native CLI)', 'Rock', 'Expo']}>
  <Tab value="Bare (React Native CLI)">

Use the Bare build plugin for standard React Native CLI projects:

```ts title="hot-updater.config.ts"
import { bare } from "@hot-updater/bare";
import { defineConfig } from "hot-updater";

export default defineConfig({
  build: bare({
    enableHermes: true,
  }),
  // ... storage and database
});
```

No additional Babel plugin setup is required.

  </Tab>
  <Tab value="Rock">

Use the Rock build plugin for Rock projects:

```ts title="hot-updater.config.ts"
import { rock } from "@hot-updater/rock";
import { defineConfig } from "hot-updater";

export default defineConfig({
  build: rock(),
  // ... storage and database
});
```

No additional Babel plugin setup is required.

  </Tab>
  <Tab value="Expo">

Use the Expo build plugin in `hot-updater.config.ts`:

```ts title="hot-updater.config.ts"
import { expo } from "@hot-updater/expo";
import { defineConfig } from "hot-updater";

export default defineConfig({
  build: expo(),
  // ... storage and database
});
```

Then add the config plugin to your `app.json`:

```json title="app.json"
{
  "expo": {
    "plugins": [
      [
        "@hot-updater/expo",
        {
          "channel": "ota-test"
        }
      ]
    ]
  }
}
```

Run prebuild to apply the native changes:

```package-install
npx expo prebuild
```

<Callout>
  For Expo projects, the config plugin automatically generates the native code
  configuration described in the next section.
</Callout>

<Callout type="info">

  dom`)](/docs/build-plugins/expo#expo-dom-components-use-dom) for the
  additional Babel plugin setup.
</Callout>

## Native Code Setup

Apply the marked Hot Updater changes to your existing native files. Preserve
your app's package/module names, registered packages and React Native bootstrap
code. Use the variant matching your project; do not replace the entire native
file with a sample application's boilerplate.

<Callout type="info">
  If you're using Expo with the plugin configured above, this step is handled
  automatically during prebuild.
</Callout>

For Java-based projects, modify your `MainApplication.java`:

```java title="android/app/src/main/java/com/<your-app-name>/MainApplication.java"
package com.hotupdaterexample;

import android.app.Application;
import com.facebook.react.PackageList;
import com.facebook.react.ReactApplication;
import com.facebook.react.ReactNativeHost;
import com.facebook.react.ReactPackage;
import com.facebook.react.defaults.DefaultNewArchitectureEntryPoint;
import com.facebook.react.defaults.DefaultReactNativeHost;
import com.facebook.soloader.SoLoader;
import java.util.List;
import com.hotupdater.HotUpdater;  // [!code ++]

public class MainApplication extends Application implements ReactApplication {

  private final ReactNativeHost mReactNativeHost =
      new DefaultReactNativeHost(this) {
        @Override
        public boolean getUseDeveloperSupport() {
          return BuildConfig.DEBUG;
        }

        @Override
        protected List<ReactPackage> getPackages() {
          @SuppressWarnings("UnnecessaryLocalVariable")
          List<ReactPackage> packages = new PackageList(this).getPackages();
          // Packages that cannot be autolinked yet can be added manually here, for example:
          return packages;
        }

        @Override
        protected String getJSMainModuleName() {
          return "index";
        }

        @Override // [!code ++]
        protected String getJSBundleFile() {  // [!code ++]
            return BuildConfig.DEBUG  // [!code ++]
                ? null  // [!code ++]
                : HotUpdater.Companion.getJSBundleFile(this.getApplication().getApplicationContext());  // [!code ++]
        }  // [!code ++]

        @Override
        protected boolean isNewArchEnabled() {
          return BuildConfig.IS_NEW_ARCHITECTURE_ENABLED;
        }

        @Override
        protected Boolean isHermesEnabled() {
          return BuildConfig.IS_HERMES_ENABLED;
        }
      };

  @Override
  public ReactNativeHost getReactNativeHost() {
    return mReactNativeHost;
  }

  @Override
  public void onCreate() {
    super.onCreate();
    SoLoader.init(this, /* native exopackage */ false);

    if (BuildConfig.IS_NEW_ARCHITECTURE_ENABLED) {
      // If you opted-in for the New Architecture, we load the native entry point for this app.
      DefaultNewArchitectureEntryPoint.load();
    }
    ReactNativeFlipper.initializeFlipper(this, getReactNativeHost().getReactInstanceManager());
  }
}
```

## Choose the native test channel

Use a dedicated channel such as `ota-test` for the first release-build test.
The Expo config above already selects it. For bare React Native or Rock, after
the native files exist, run:

```package-install
npx hot-updater channel set ota-test
```

Changing the embedded default channel requires a new native build. See
[Default Channel Setup](/docs/guides/channel-management) for custom native paths.
Before a store release, choose the channel that binary should use and rebuild.

## Prepare signing and compatibility

If this app uses [bundle signing](/docs/guides/bundle-signing), embed the matching
public key before building. Signing is opt-in; server provisioning alone does
not enable it. Preserve an existing signer and its public key.

For `appVersion`, record the native app version that the OTA will target. For
`fingerprint`, generate and embed the fingerprint before the native build using
the [fingerprint workflow](/docs/guides/update-strategies/fingerprint).

## Verify the integration

Run local and server diagnostics from the app directory:

```package-install
npx hot-updater doctor --json --server-base-url https://your-update-server-url
```

Resolve reported setup issues, then continue to
[Test an OTA update](/docs/get-started/test-ota). That test builds the native app
in Release mode and proves that a changed screen and asset reach the device.
Doctor checks configuration and server version; it does not prove OTA delivery.
