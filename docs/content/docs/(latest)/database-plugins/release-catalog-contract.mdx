## Status

This is the normative database-provider contract for Hot Updater schema
`1.0.1`. It replaces the #1141 contract that stored rollout policy on Bundle
rows and exposed an optional provider decision query.

The change is intentionally breaking. Removed members are not retained as
aliases.

## Responsibility boundary

```text
Bundle          immutable artifact identity and storage metadata
Release         rollout, compatibility, Channel, operation, and message policy
ReleaseCatalog  deterministic desired-state projection for one canonical scope
Database        canonical rows, strong reads, and atomic conditional commits
Server          catalog compiler and unversioned client routes
Device          catalog acceptance and local desired-state selection
```

A database provider persists official domains. It does not decide which
Release an installation should run.

## Public interface

```ts
interface DatabasePlugin {
  readonly name: string;
  readonly models: DatabaseModels;
  commit(input: DatabaseCommit): Promise<DatabaseCommitResult>;
  readonly dispose?: () => Promise<void>;
}

interface DatabaseModels {
  readonly bundles: BundleModel;
  readonly bundlePatches: BundlePatchModel;
  readonly releases: ReleaseModel;
  readonly releaseCatalogs: ReleaseCatalogModel;
  readonly channels: ChannelModel;
  readonly insights: InsightsModel;
  readonly apiKeys: ApiKeyModel;
}
```

The following are absent:

- `DatabasePlugin.queries` and `DatabaseQueries`;
- provider `getUpdateInfo` methods, SQL functions, or RPCs;
- provider callback transactions and generic public CRUD;
- Bundle policy fields and Bundle-to-Channel ownership;
- asynchronous Release writes followed by projection repair.

`createDatabasePlugin` may adapt a provider's internal CRUD and transaction
implementation, but those details are not public.

## Artifact models

`BundleModel.findMany` applies filtering and ordering before offset and limit.
Bundle rows contain only artifact fields: ID, platform, hashes, storage URIs,
manifest/asset information, Git commit, and artifact metadata.

Every Bundle row has a required `archive_byte_size`, and every Bundle-patch row
has a required `byte_size`. Both values are immutable non-negative
integers no larger than `Number.MAX_SAFE_INTEGER`. Provider CRUD hydration must
reject a missing, fractional, negative, or out-of-range value instead of
constructing a partial v1 Bundle.

`BundlePatchModel.findByBundleIds` returns all patch rows owned by the requested
Bundle IDs. It returns immediately for an empty owner list.

Manifest asset JSON may include optional `downloadByteSize` and
`downloadFileHash` fields. These are not database columns. `downloadByteSize`
describes the exact representation served to the client. When that differs
from the logical file, a valid lowercase SHA-256 `downloadFileHash` identifies
those exact served bytes and their content-addressed object key. For example, a
Brotli asset records the compressed payload size and hash while `fileHash`
continues to identify the logical installed file. Raw assets use the logical
`fileHash` key and may omit `downloadFileHash`. A missing or invalid
`downloadByteSize`, an invalid present `downloadFileHash`, or a missing hash for
a transformed representation keeps legacy resolution behavior and makes the
size comparison unknown; it does not invalidate the Bundle row.

A Bundle referenced by any Release cannot be deleted. Release policy changes
never mutate a Bundle.

### Artifact route selection

The server computes the normal manifest route as the exact UTF-8 byte length of
the stored target manifest text plus the primary download size of every changed
asset. Unchanged assets cost zero. A usable patch is primary only when it is
strictly smaller than a usable complete file when both sizes are known; a tie
uses the file. A retained patch remains primary when its required size is known
and the optional file size is unknown.

When the archive URL, archive size, and every primary size are known, a total
diff size equal to or larger than `archive_byte_size` produces the archive-only
response. Missing or invalid optional manifest metadata, or safe-integer sum
overflow, preserves the existing manifest-first response. No request-time
`HEAD` or storage metadata lookup is used, and this server-side decision does
not change native routes or public artifact response types. Exceptional patch
failure retains the existing patch-to-file-to-archive fallback and is not
included in the normal-path total.

## Release model

```ts
interface ReleaseModel {
  findById(id: string): Promise<ReleaseRow | null>;
  findMany(input: {
    beforeReleaseId?: string;
    bundleId?: string;
    channelId?: string;
    enabled?: boolean;
    platform?: "ios" | "android";
    limit: number;
  }): Promise<readonly ReleaseRow[]>;
  findManyByScope(input: {
    scopeKey: string;
    afterReleaseId?: string;
    limit: number;
    consistency: "strong";
  }): Promise<readonly ReleaseRow[]>;
}
```

`findMany` is a newest-first management query. `findManyByScope` is an
ascending, exclusive-keyset compiler scan over canonical primary storage. It
must be strongly consistent. A provider may not satisfy it with an eventual
secondary index or an unordered scan.

A Release has a canonical lowercase UUIDv7 `id`, a monotonically increasing
`revision`, one canonical `scope_key`, one Channel, platform, compatibility
strategy, rollout/target policy, operation lineage, and timestamps. Newly
authored Releases are `BUNDLE` Releases and reference a same-platform Bundle.
`EMBEDDED` kind and `ROLLBACK` operation values are accepted only to read
pre-1.0 development data; management APIs do not create them and the compiler
does not emit them into new catalogs. Operational rollback updates the current
Release to `enabled=false` without changing its ID.

## Catalog model

```ts
interface ReleaseCatalogModel {
  findByScopeKey(scopeKey: string): Promise<ReleaseCatalogRow | null>;
  findMany(input: {
    afterScopeKey?: string;
    limit: number;
  }): Promise<readonly ReleaseCatalogRow[]>;
}
```

The runtime read is an exact point lookup by scope key. The ordered list exists
for preflight, migration, and deterministic rebuild. Providers treat `payload`
as canonical opaque JSON and do not evaluate it.

Catalog rows include an automatically allocated opaque identity, strategy, Channel identity, platform,
optional fingerprint, generation, canonical hash, byte size, tombstone state,
and update time. A logical Release mutation increments every affected catalog
generation. An empty scope remains as a newer tombstone row; generation never
resets by deleting a catalog.

## Channels, Insights, and API keys

Channels use opaque IDs and exact case-sensitive names. Concurrent
`insert({ onConflict: "returnExisting" })` returns the canonical stored row.
An empty Channel remains visible. Its reference check and explicit deletion
are atomic against Releases.

Insights uses `record`, `listEvents`, `findInstallations`, `countInstallations`,
and `countEvents`. Core prepares reports and product views; providers own
atomic event/latest-state storage and fixed native queries. See the
[Insights contract](./custom-database#insights) for ordering and count semantics.
Transition rows carry directional Release identity alongside Bundle identity.
Old nullable Release IDs remain valid and are never inferred from Bundle ID.

API key creation is idempotent by hash. Lookup, stable list ordering, and
revocation semantics are unchanged.

## Declarative conditional commit

```ts
interface DatabaseCommit {
  readonly changes: readonly DatabaseChange[];
  readonly expectations?: readonly DatabaseCommitExpectation[];
}

type DatabaseCommitExpectation =
  | { model: "releases"; id: string; revision: number | null }
  | {
      model: "releaseCatalogs";
      scopeKey: string;
      generation: number | null;
    };
```

Release changes support insert, update, and delete. Catalog changes use
`{ model: "releaseCatalogs", operation: "put", row }`. Bundle, patch,
Channel, Insights, and API key changes retain their declared operations.

The provider performs these steps inside one short native transaction:

1. Check all expectations against canonical rows. `null` means absent.
2. Validate references and ordered changes.
3. Apply every change.
4. Commit all results together.

An expectation mismatch returns no writes:

```ts
{
  committed: false,
  conflict: {
    changeIndex: -1,
    reason: "version_conflict",
    model: "releases" | "releaseCatalogs",
    key: string,
    expectedVersion: number | null,
    actualVersion: number | null,
  },
}
```

An expected missing update or referenced delete reports its original
`changeIndex`. Constraint, validation, connection, and provider failures reject
the Promise. A provider without an atomic conditional primitive rejects before
its first write.

## Compiler snapshot protocol

Compilation deliberately occurs outside the write transaction:

```text
strongly read current Release revisions and catalog generations
  -> strongly keyset-page every affected Release scope
  -> apply requested mutation in memory
  -> compile, canonicalize, hash, and size-check catalogs
  -> conditionally commit Release changes and all catalog rows
  -> retry a bounded VERSION_CONFLICT
```

The generation expectation invalidates a paged read series crossed by a
concurrent mutation. Providers must not hold a transaction open while parsing
or compiling a large history.

The compiler keeps a bounded 11-artifact frontier for newer update and crash
selection, plus the complete compatible enabled Release spine needed to find
the predecessor of any active Release. Rollback candidates ignore rollout and
target cohorts, matching the v0 selector. This rollback spine is intentionally
linear in compatible enabled history. It is never silently truncated; if the
canonical catalog exceeds 256 KiB, the Release mutation fails before the atomic
commit and the previous Release/catalog state remains unchanged.

Required provider mappings:

| Provider              | Strong compiler read                                  | Conditional write                                   |
| --------------------- | ----------------------------------------------------- | --------------------------------------------------- |
| DynamoDB              | base-table scope partition with `ConsistentRead=true` | `TransactWrite` condition checks                    |
| Firestore             | strong server document/query reads                    | transaction preconditions                           |
| PostgreSQL/Supabase   | ordered primary reads                                 | revision/generation predicates in one transaction   |
| D1                    | ordered primary reads                                 | batch whose failed predicate aborts every statement |
| MongoDB               | deterministic majority reads                          | short write transaction with predicates             |
| Drizzle/Kysely/Prisma | adapter's ordered canonical query                     | adapter's real transaction and affected-row checks  |

## Schema 1.0.1 bootstrap and upgrade

`hot-updater db migrate` creates schema `1.0.1` on empty storage, upgrades
complete `1.0.0` storage additively, and no-ops at `1.0.1`. The upgrade preserves
events and latest installation rows while adding Insights indexes and exact
identity collations. Advance `schema.core` only after success. Regenerate ORM
artifacts with `hot-updater db generate` and apply emitted companion collation
SQL for Prisma PostgreSQL/MySQL.

1. On empty storage, create the seven models with their indexes and references.
2. On complete `1.0.0`, apply the supported Insights upgrade without resetting data.
3. Record `schema.core = 1.0.1` after creation or successful upgrade.

There is no populated v0 Bundle-policy backfill. Managed initialization rejects
v0 infrastructure before mutating it. The earlier unreleased `1.0.0` shape
without required archive/patch sizes is also outside this additive Insights
upgrade: preserve a backup and reconcile missing artifact metadata explicitly.
A complete `1.0.0` database must not be recreated for this upgrade.

DynamoDB and Firebase use their documented provider migration entry points for
existing Insights index keys and canonical installation IDs. Stop old ingestion
writers while upgrading, and deploy required indexes before starting the new
runtime. Provider prerequisites and query costs are documented in the
[custom provider guide](./custom-database#insights).

## Runtime route boundary

The shared device endpoints are:

```text
GET /release-catalogs/app-version/:platform/:channelKey/:canonicalAppVersion
GET /release-catalogs/fingerprint/:platform/:channelKey/:fingerprintHash
GET /artifacts/:targetBundleId/from/:currentBundleId
```

Catalog URLs contain no installation state. Successful catalog responses are
short-lived shared-cacheable and vary by content encoding and `x-api-key`.
Authentication errors, missing/incomplete catalogs, and server errors are
`private, no-store`. Artifact resolution remains Bundle-keyed and private.

Catalog identity is allocated by the shared compiler on the first atomic commit
and retained across mutations, rebuilds, and tombstones. Plugins persist it
unchanged; applications and server configuration do not supply it. Backups must
include Catalog rows: rebuilding a missing row from existing Releases would lose
its identity and generation history, so that operation requires restoring the row.
Custom GraphQL, RPC, or other transports must sit behind an HTTP adapter or
proxy that exposes these v1 routes. Successful shared responses must keep a
stable cache partition; responses affected by arbitrary request context must
remain `private, no-store`.

The v0 app-version and fingerprint update-check routes are not exposed. Old
native binaries must continue using a separate v0 endpoint during a parallel
cutover.

## Standalone boundary

Standalone is a remote management repository, not a complete
`DatabasePlugin`. Its models expose Bundles, patches, Releases, catalogs, and
Channels through canonical server routes. The server owns Insights, client
keys, strong compiler reads, and the real conditional transaction.

## Acceptance criteria

The contract is complete only when:

- the public database surface has `name`, `models`, `commit`, and optional
  `dispose`, with no `queries` property;
- every provider implements all seven models;
- Release scope paging is strong, ordered, and keyset-based;
- Release revision and catalog generation conflicts roll back the whole
  envelope;
- catalog GETs perform one exact read and no Release/Bundle scan;
- empty-scope generations persist as tombstones;
- schema bootstrap creates 1.0.1, upgrades complete 1.0.0 without data loss,
  and rejects unsupported v0 markers;
- public conformance, provider integration, v0 generation guards, managed
  runtime, and standalone verification suites pass.
