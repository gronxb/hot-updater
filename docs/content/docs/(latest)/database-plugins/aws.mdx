## Installation

```package-install
npm install @hot-updater/aws --save-dev
```

## Create the table

The [managed AWS setup](/docs/managed/aws#step-2-configure-aws) supports an AI
agent or the interactive CLI. Both workflows create or validate the DynamoDB
table, and write its schema settings, before configuring the app.

For custom installations, create one on-demand table keyed by string `pk` and
`sk`, with no secondary index:

```bash
aws dynamodb create-table \
  --table-name hot-updater \
  --billing-mode PAY_PER_REQUEST \
  --deletion-protection-enabled \
  --on-demand-throughput MaxReadRequestUnits=4000,MaxWriteRequestUnits=100 \
  --attribute-definitions \
    AttributeName=pk,AttributeType=S \
    AttributeName=sk,AttributeType=S \
  --key-schema \
    AttributeName=pk,KeyType=HASH \
    AttributeName=sk,KeyType=RANGE
```

Then write the schema settings the plugin checks before its first read.
`dynamoDB()` answers 503 until they exist:

```typescript
import { migrateDynamoDB } from "@hot-updater/aws";

await migrateDynamoDB({ tableName: "hot-updater", region: "us-east-1" });
```

When the table is missing, `migrateDynamoDB` also creates it, on demand and
without deletion protection, which suits DynamoDB Local. A table with the
`hot-updater-update-index` secondary index comes from a 1.0 release candidate;
create a new table for 1.0.

The same table stores all seven official database domains: Bundles, Bundle
patches, Releases, Release Catalogs, Channels, Insights events, and API keys.
`dynamoDB()` provides all seven models directly; there is no
component registry or feature migration to compose before serving traffic:

```typescript
import { dynamoDB } from "@hot-updater/aws";
import { createHotUpdater } from "@hot-updater/server";

const database = dynamoDB({
  tableName: "hot-updater",
  region: "us-east-1",
});
const hotUpdater = createHotUpdater({
  database,
  clientAccess: { type: "api-key" },
});
```

The built-in Insights event and query routes are always available.
`clientAccess` is required. The `api-key` policy protects update checks and
event ingestion with keys stored through the database's official API key model.

## Configuration

```typescript
interface DynamoDBConfig {
  tableName: string;
  region?: string;
  endpoint?: string;
  apiBasePath?: string;
  cloudfrontDistributionId?: string;
  shouldWaitForInvalidation?: boolean;
  credentials?: {
    accessKeyId: string;
    secretAccessKey: string;
  };
}
```

If `credentials` is omitted, the AWS SDK default credential chain is used. This
lets you rely on local AWS CLI sessions, `AWS_PROFILE`, shared config files, or
other standard AWS credential sources.

When `cloudfrontDistributionId` is set, a successful database commit containing
a Bundle or Bundle-patch change submits an invalidation for
`/release-catalogs/*` by default. Commits that change only Releases, Release
Catalogs, Channels, Insights, or API keys do not trigger this
adapter-level invalidation. Override `apiBasePath` only when a custom deployment
mounts the catalog routes elsewhere. Set `shouldWaitForInvalidation: true` when
a deployment or E2E flow must wait for CloudFront propagation; it defaults to
`false`.

## Usage

```typescript title="hot-updater.config.ts"
import { dynamoDB } from "@hot-updater/aws"; // [!code ++]
import { defineConfig } from "hot-updater";

export default defineConfig({
  database: dynamoDB({ // [!code ++]
    tableName: "hot-updater", // [!code ++]
    region: "us-east-1", // [!code ++]
    credentials: { // [!code ++]
      accessKeyId: process.env.AWS_ACCESS_KEY_ID, // [!code ++]
      secretAccessKey: process.env.AWS_SECRET_ACCESS_KEY, // [!code ++]
    }, // [!code ++]
  }), // [!code ++]
});
```

## Complete example

This example combines storage and database with your existing build plugin:

```typescript
import { dynamoDB, s3Storage } from "@hot-updater/aws";
import { defineConfig } from "hot-updater";
import { build } from "./build";

const credentials = {
  accessKeyId: process.env.AWS_ACCESS_KEY_ID,
  secretAccessKey: process.env.AWS_SECRET_ACCESS_KEY,
};

export default defineConfig({
  build,
  updateStrategy: "appVersion",
  storage: s3Storage({
    region: "us-east-1",
    credentials,
    bucketName: "my-bundles-bucket",
  }),
  database: dynamoDB({
    tableName: "hot-updater",
    region: "us-east-1",
    credentials,
  }),
});
```

## Custom server usage

Use `dynamoDB` with `createHotUpdater` for self-hosted servers:

```typescript title="src/hotUpdater.ts"
import { dynamoDB } from "@hot-updater/aws"; // [!code ++]
import { createHotUpdater } from "@hot-updater/server";

const hotUpdater = createHotUpdater({
  database: dynamoDB({ // [!code ++]
    tableName: process.env.AWS_DYNAMODB_TABLE_NAME!, // [!code ++]
    region: process.env.AWS_REGION!, // [!code ++]
    credentials: { // [!code ++]
      accessKeyId: process.env.AWS_ACCESS_KEY_ID!, // [!code ++]
      secretAccessKey: process.env.AWS_SECRET_ACCESS_KEY!, // [!code ++]
    }, // [!code ++]
  }), // [!code ++]
  clientAccess: { type: "api-key" },
});
```

The Lambda or server role reads with `BatchGetItem` and `Query`, and writes
with `TransactWriteItems`, which needs `PutItem`, `UpdateItem`, `DeleteItem`,
and `ConditionCheckItem` on the table. Every item's partition key is a table
name, or a table name followed by `#` for its index items, so a
`dynamodb:LeadingKeys` condition can scope the role to Hot Updater's items; the
managed setup's policy lists them.

Reads are strongly consistent. Each row is one item, and each index a row
belongs to adds an item holding a copy of it, written in the same transaction.
A unique lookup, such as an API key by its hash, is one point read.

DynamoDB permits at most 100 items and 4 MB in one transaction, and 400 KB in
one item. Every `commit({ changes, expectations })` envelope is one transaction,
with its index items, relation counters, and cascade deletions; a commit over
the limit is refused before anything is written. A Release with a wide app
version range also writes up to 16 base-candidate rows, so commit Releases a
few at a time.
