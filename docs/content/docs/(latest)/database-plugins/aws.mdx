## Installation

```package-install
npm install @hot-updater/aws --save-dev
```

## Create the table

For AWS installations created by `npx hot-updater init`, DynamoDB is selected
by default and this table is created or validated automatically.

For custom installations, create one on-demand table manually with the
overloaded index used for update checks and patch relations:

```bash
aws dynamodb create-table \
  --table-name hot-updater \
  --billing-mode PAY_PER_REQUEST \
  --deletion-protection-enabled \
  --on-demand-throughput MaxReadRequestUnits=4000,MaxWriteRequestUnits=100 \
  --attribute-definitions \
    AttributeName=pk,AttributeType=S \
    AttributeName=sk,AttributeType=S \
    AttributeName=gsi1pk,AttributeType=S \
    AttributeName=gsi1sk,AttributeType=S \
  --key-schema \
    AttributeName=pk,KeyType=HASH \
    AttributeName=sk,KeyType=RANGE \
  --global-secondary-indexes '[
    {
      "IndexName": "hot-updater-update-index",
      "KeySchema": [
        { "AttributeName": "gsi1pk", "KeyType": "HASH" },
        { "AttributeName": "gsi1sk", "KeyType": "RANGE" }
      ],
      "Projection": { "ProjectionType": "ALL" },
      "OnDemandThroughput": {
        "MaxReadRequestUnits": 4000,
        "MaxWriteRequestUnits": 100
      }
    }
  ]'
```

The same table stores all seven official database domains: Bundles, Bundle
patches, Releases, Release Catalogs, Channels, Insights events, and API keys.
`dynamoDB()` provides all seven models directly; there is no
component registry or feature migration to compose before serving traffic:

```typescript
import { dynamoDB } from "@hot-updater/aws";
import { createHotUpdater } from "@hot-updater/server";

const database = dynamoDB({
  tableName: "hot-updater",
  region: "us-east-1",
});
const hotUpdater = createHotUpdater({
  database,
  clientAccess: { type: "api-key" },
});
```

The built-in Insights event and query routes are always available.
`clientAccess` is required. The `api-key` policy protects update checks and
event ingestion with keys stored through the database's official API key model.

## Configuration

```typescript
interface DynamoDBConfig {
  tableName: string;
  region?: string;
  endpoint?: string;
  apiBasePath?: string;
  cloudfrontDistributionId?: string;
  shouldWaitForInvalidation?: boolean;
  credentials?: {
    accessKeyId: string;
    secretAccessKey: string;
  };
}
```

If `credentials` is omitted, the AWS SDK default credential chain is used. This
lets you rely on local AWS CLI sessions, `AWS_PROFILE`, shared config files, or
other standard AWS credential sources.

When `cloudfrontDistributionId` is set, a successful database commit containing
a Bundle or Bundle-patch change submits an invalidation for
`/release-catalogs/*` by default. Commits that change only Releases, Release
Catalogs, Channels, Insights, or API keys do not trigger this
adapter-level invalidation. Override `apiBasePath` only when a custom deployment
mounts the catalog routes elsewhere. Set `shouldWaitForInvalidation: true` when
a deployment or E2E flow must wait for CloudFront propagation; it defaults to
`false`.

## Usage

```typescript
import { dynamoDB } from "@hot-updater/aws";
import { defineConfig } from "hot-updater";

export default defineConfig({
  database: dynamoDB({
    tableName: "hot-updater",
    region: "us-east-1",
    credentials: {
      accessKeyId: process.env.AWS_ACCESS_KEY_ID,
      secretAccessKey: process.env.AWS_SECRET_ACCESS_KEY,
    },
  }),
});
```

## Complete Example

Combined storage and database:

```typescript
import { dynamoDB, s3Storage } from "@hot-updater/aws";
import { defineConfig } from "hot-updater";

const credentials = {
  accessKeyId: process.env.AWS_ACCESS_KEY_ID,
  secretAccessKey: process.env.AWS_SECRET_ACCESS_KEY,
};

export default defineConfig({
  storage: s3Storage({
    region: "us-east-1",
    credentials,
    bucketName: "my-bundles-bucket",
  }),
  database: dynamoDB({
    tableName: "hot-updater",
    region: "us-east-1",
    credentials,
  }),
});
```

## Custom Server Usage

Use `dynamoDB` with `createHotUpdater` for self-hosted servers:

```typescript
import { dynamoDB } from "@hot-updater/aws";
import { createHotUpdater } from "@hot-updater/server";

const hotUpdater = createHotUpdater({
  database: dynamoDB({
    tableName: process.env.AWS_DYNAMODB_TABLE_NAME!,
    region: process.env.AWS_REGION!,
    credentials: {
      accessKeyId: process.env.AWS_ACCESS_KEY_ID!,
      secretAccessKey: process.env.AWS_SECRET_ACCESS_KEY!,
    },
  }),
  clientAccess: { type: "api-key" },
});
```

The Lambda or server role needs `Query` access to the update index,
`BatchGetItem`/`GetItem` access to Bundle, patch, and API key partitions,
and `PutItem`/`Query` access to the Insights event partition. CLI and Console
writers need the transaction and write permissions required to manage Bundle
metadata and API keys. The AWS adapter does not impose an Insights
retention period.

The provider does not impose a total bundle, patch, or patch-relationship count
limit. Each serialized metadata item is limited to 8 KiB, and counters and
relation counts are updated in the same DynamoDB transaction as each mutation.
Cursor-based bundle pages read only the requested page, exact bundle references
use strongly consistent key reads, and single-owner patch hydration uses index
keys only to discover candidates before strongly reading their base-table rows.
Unfiltered totals use the transactionally maintained metadata counter. Batch
reads retry unprocessed keys with bounded exponential backoff.

DynamoDB permits at most 100 actions in one transaction. Every
`commit({ mutations })` envelope is planned and submitted as one transaction,
including relation counters and cascade deletions; a commit that exceeds the
service limit is rejected before it can be partially applied.
