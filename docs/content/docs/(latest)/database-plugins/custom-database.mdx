## When to write an adapter

Every Hot Updater database runs on one storage engine. Core (Bundles,
Releases, Release Catalogs and Channels) and server plugins such as
`insights()` and `apiKeys()` declare tables and indexes, and the engine turns
their reads and transactions into a few calls on a storage adapter. The adapter
stores rows and reads index ranges with its backend's native features. It knows
nothing about Bundles, Releases or plugins.

Write an adapter when no existing one reaches your backend. Database plugins
cover [Supabase](/docs/database-plugins/supabase),
[Cloudflare D1](/docs/database-plugins/cloudflare),
[Firestore](/docs/database-plugins/firestore) and
[DynamoDB](/docs/database-plugins/aws), and a
[custom server](/docs/custom/overview#database-adapters) can use Kysely,
Drizzle, Prisma or MongoDB. A database that speaks PostgreSQL, MySQL or SQLite
needs only a SQL executor.

## Install

```package-install
npm install @hot-updater/server @hot-updater/plugin-core
npm install @hot-updater/test-utils vitest --save-dev
```

`@hot-updater/server/database` exports the adapter contract and the helpers
that implement it, and `@hot-updater/plugin-core` exports the `EngineDatabase`
type that a provider returns. Keep the three Hot Updater packages on the same
version. The examples run PostgreSQL through `pg`; use your own driver in its
place.

## How the pieces fit

```text
createHotUpdater, CLI, console
  core and plugins     tables, indexes, typed reads and transactions
  storage engine       guards, retries, references, aggregates, schema fence
  storage adapter      get, query, write, fits
  your backend
```

A provider's factory returns an `EngineDatabase`, `{ name, adapter, dispose? }`.
`hot-updater.config.ts`, the console and `createHotUpdater` all take it as
`database`. The engine keeps references, cascades, counters and retries itself
and expresses them as the ops below, so an adapter implements none of them.

## The adapter contract

```ts
interface DatabaseAdapter {
  /** Names the adapter in messages, such as "sql:postgresql". */
  readonly id: string;
  /** Whether the ops commit atomically in one write. */
  fits(ops: readonly WriteOp[]): boolean;
  /** A strongly consistent batch point read, in the order of `keys`. */
  get(
    table: PhysicalTable,
    keys: readonly DatabaseKey[],
  ): Promise<readonly (StoredRow | null)[]>;
  /** One index range, up to `request.limit` rows. */
  query(
    table: PhysicalTable,
    request: QueryRequest,
  ): Promise<readonly StoredRow[]>;
  /** Applies every op or none. */
  write(ops: readonly WriteOp[]): Promise<WriteResult>;
  /** Creates tables; only the migration helpers call it. */
  readonly migrations?: {
    apply(tables: readonly PhysicalTable[]): Promise<void>;
  };
  dispose?(): Promise<void>;
}
```

### Tables and values

Each call names a `PhysicalTable`: its columns, its primary key (a list of
columns) and its indexes. The table name is logical, and an adapter may add
its own prefix.

```ts
interface PhysicalTable {
  readonly name: string;
  readonly columns: readonly PhysicalColumn[];
  readonly key: readonly string[];
  readonly indexes: readonly PhysicalIndex[];
}

interface PhysicalIndex {
  readonly name: string;
  readonly eq: readonly string[];
  readonly sort: readonly string[];
  readonly unique?: true;
}
```

| Column field | Meaning                                                                                                     |
| ------------ | ----------------------------------------------------------------------------------------------------------- |
| `type`       | `string`, `integer` (safe integers), `number` (finite numbers), `boolean`, or `json` (any JSON value)       |
| `nullable`   | Whether the column holds `null`                                                                             |
| `maxLength`  | Strings: the longest value in UTF-16 code units; unbounded text when absent                                 |
| `ascii`      | Strings: ASCII only, so a backend that limits index size (MySQL) can store it in single bytes               |
| `default`    | A whole number the backend stores when a write leaves the column out; the engine's own columns default to 0 |
| `multi`      | An array of 1–16 values of `type`, indexable in `eq` only                                                   |

Every table has `_v`, the row version that guards writes. Key and index values
are strings, numbers or booleans. Rows come back exactly as written: empty,
long and non-ASCII strings, integers up to `Number.MAX_SAFE_INTEGER`, arrays in
their order, and nested JSON. `normalizeStoredRow(table, raw, { jsonText })`
converts what drivers return (int8 as text, `BigInt`, decimals, SQLite 0 and 1,
JSON as text) to stored values.

### Point reads

`get(table, keys)` reads rows by primary key, strongly consistently, in one
batch. It returns one entry per key in the order of `keys`, with `null` for a
key that has no row. An empty `keys` returns no rows.

### Index reads

```ts
interface QueryRequest {
  readonly index: string;
  /** One value for each `eq` column of the index, in order. */
  readonly eq: readonly DatabaseKeyValue[];
  readonly lower?: QueryBound;
  readonly upper?: QueryBound;
  readonly order: "asc" | "desc";
  /** 1–500 rows. */
  readonly limit: number;
}

interface QueryBound {
  /** A prefix of the index's order columns. */
  readonly values: readonly DatabaseKeyValue[];
  readonly inclusive: boolean;
}
```

- An index orders rows by its `sort` columns, then by the key columns that
  neither `eq` nor `sort` names. `indexOrderColumns(table, index)` returns
  them. Bounds compare a prefix of that tuple, and the engine pages by passing
  the last row's tuple as an exclusive bound.
- Strings order by UTF-8 bytes, with no collation: `B` sorts before `a`, and
  `a ` after `a`. Numbers order numerically, and `false` before `true`.
- A row with `null` in an index column is not in that index. A multi-valued
  `eq` column indexes the row under each of its values.
- A unique index holds at most one row for each `eq` tuple.
- Return `limit` rows unless the range ends first. When the backend reads in
  native pages, keep reading them: a result shorter than `limit` means the
  range has ended. The test suites pass `nativePageSize` to your adapter
  factory to cap native pages at two rows and check that every page still
  fills.

### Writes and guards

A write is a list of ops, applied atomically:

| Op          | Applies when                                                                     | Effect                                                                         |
| ----------- | -------------------------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| `insert`    | no row has the key                                                               | writes `row`, `_v` included                                                    |
| `patch`     | the row's `_v` is `guard.v`                                                      | writes the columns in `set`, and sets `_v` to `guard.v + 1`                    |
| `delete`    | the row's `_v` is `guard.v`                                                      | deletes the row                                                                |
| `increment` | the row exists or `init` is given, and its `_v` is `guard.v` when a guard is set | creates a missing row from `init`, then adds `by` to its columns and 1 to `_v` |
| `check`     | the row's `_v` is `guard.v`                                                      | writes nothing, but conflicts with any concurrent write to the row             |

A write has at most one op per row, and every guard is checked against the
rows as they were before the write. An insert or patch fails when it would give
a unique index a second row with the same values. The engine sends deletes
first, so a later op in the same write can take a unique value that a delete
frees. `patch` and `delete` carry `previous`, the row as the engine read it,
for adapters that keep their own index entries.

`write` resolves to one of three results, and throws only when it cannot tell
whether the write committed:

| Result                       | When                                                                                                         | The engine                                                                                                                                                              |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `{ ok: true }`               | every op applied                                                                                             | returns                                                                                                                                                                 |
| `{ ok: false, failedOp }`    | the op at position `failedOp` failed its guard or a unique index, and nothing applied                        | reads that row again: it reports `DatabaseConstraintError` (`exists`, `unique` or `not_found`) when the current state confirms it, and otherwise reruns the transaction |
| `{ ok: false, retry: true }` | a transient failure: a deadlock, serialization failure, lock timeout, busy database, or transaction conflict | sends the write again after a backoff                                                                                                                                   |
| thrown error                 | the outcome is unknown, such as a connection lost during commit                                              | reports `DatabaseAmbiguousCommitError` and never sends the write again                                                                                                  |

A `check` guards a row that the transaction read and does not change, so two
transactions cannot each change what the other read. The SQL core locks the
row with `SELECT … FOR UPDATE`; on SQLite, `BEGIN IMMEDIATE` locks the whole
database. The MongoDB adapter increments a field on the row, so a concurrent
transaction on it conflicts.

### Write limits

`fits(ops)` says whether the ops fit in one atomic write of the backend: its
limits on ops, items or bytes. The engine asks before every write and refuses
a transaction that does not fit with `DatabaseConstraintError` `too_large`,
before anything is sent. Return `true` when the backend has no limit.

### Migrations

`migrations.apply(tables)` creates each table with its indexes. A table that
exists keeps its rows, so running it twice changes nothing. Only the
migration helpers call it; leave it out when other tooling creates the tables.

## Choose how to build it

| Backend                                                   | Implement                               | Built this way                                                                            |
| --------------------------------------------------------- | --------------------------------------- | ----------------------------------------------------------------------------------------- |
| PostgreSQL, MySQL or SQLite                               | a `SqlExecutor` for `createSqlAdapter`  | `postgres`, `d1Database`, `supabaseDatabase`, and the Kysely, Drizzle and Prisma adapters |
| A key-value store with atomic conditional writes          | a `KeyValueStore` for `createKvAdapter` | `dynamoDB`, `firebaseDatabase`                                                            |
| Any other backend with transactions and secondary indexes | `DatabaseAdapter` itself                | the MongoDB adapter                                                                       |

### A SQL executor

`createSqlAdapter({ executor })` compiles every read and write to SQL for
PostgreSQL, MySQL or SQLite, and runs it through an executor for your driver:

```ts
interface SqlExecutor {
  readonly dialect: "postgresql" | "mysql" | "sqlite";
  /** Runs one statement: `{ sql, params }` to `{ rows, changes }`. */
  execute(statement: SqlStatement): Promise<SqlResult>;
  /** Commits when `fn` resolves and rolls back when it throws. */
  transaction<T>(fn: (connection: SqlConnection) => Promise<T>): Promise<T>;
  /** Runs statements as one atomic batch, for drivers without transactions. */
  batch?(statements: readonly SqlStatement[]): Promise<readonly SqlResult[]>;
}
```

A complete provider over `pg`:

```ts title="myDatabase.ts"
import type { EngineDatabase } from "@hot-updater/plugin-core";
import {
  createEngineDatabase,
  createSqlAdapter,
  migrateBuiltInSchema,
  type SqlConnection,
  type SqlExecutor,
} from "@hot-updater/server/database";
import pg, { type PoolClient, type PoolConfig } from "pg";

/** Runs the SQL core's statements on a pool; a transaction holds one client. */
export const myExecutor = (pool: pg.Pool): SqlExecutor => {
  const over = (runner: pg.Pool | PoolClient): SqlConnection => ({
    execute: async ({ sql, params }) => {
      const result = await runner.query(sql, [...params]);
      return { rows: result.rows, changes: result.rowCount ?? 0 };
    },
  });
  return {
    dialect: "postgresql",
    ...over(pool),
    async transaction(fn) {
      const client = await pool.connect();
      try {
        await client.query("BEGIN");
        const result = await fn(over(client));
        await client.query("COMMIT");
        return result;
      } catch (error) {
        await client.query("ROLLBACK").catch(() => undefined);
        throw error;
      } finally {
        client.release();
      }
    },
  };
};

/** Hot Updater's database on PostgreSQL through `pg`. */
export const myDatabase = (config: PoolConfig): EngineDatabase => {
  const pool = new pg.Pool(config);
  return {
    ...createEngineDatabase({
      name: "myDatabase",
      adapter: createSqlAdapter({ executor: myExecutor(pool) }),
    }),
    dispose: () => pool.end(),
  };
};

/** Creates the tables, then writes the settings rows the schema fence checks. */
export const migrateMyDatabase = async (config: PoolConfig) => {
  const pool = new pg.Pool(config);
  try {
    await migrateBuiltInSchema(
      createSqlAdapter({ executor: myExecutor(pool) }),
      "myDatabase",
    );
  } finally {
    await pool.end();
  }
};
```

- `execute` returns the rows of a `SELECT` and, as `changes`, the number of
  rows an `INSERT`, `UPDATE` or `DELETE` changed. The core reads `changes` to
  tell whether a guarded update applied.
- `transaction` runs `fn` on one connection. On SQLite, begin it with
  `BEGIN IMMEDIATE` and run statements one at a time.
- Keep the driver's error codes on what you throw (`code`, `errno`, `sqlState`,
  also on `cause`). The core maps a unique violation to `failedOp`, and a
  serialization failure, deadlock, lock timeout or busy database to `retry`,
  by SQLSTATE, MySQL and SQLite codes.
- Statements use `$1`, `$2`… on PostgreSQL and `?` elsewhere. JSON and
  multi-valued values are bound as JSON text, cast to `jsonb` on PostgreSQL,
  and booleans as 0 or 1 outside PostgreSQL.
- A driver with a Kysely dialect needs no executor of its own:
  `kyselyExecutor(db, dialect)` from `@hot-updater/server/adapters/kysely` is
  one, and the `postgres` provider is `createSqlAdapter` over it.

| `createSqlAdapter` option | Meaning                                                                             |
| ------------------------- | ----------------------------------------------------------------------------------- |
| `executor`                | The executor                                                                        |
| `tablePrefix`             | Prepended to every table name                                                       |
| `maxOps`                  | The most ops one write accepts (default 1,000); `fits` refuses more                 |
| `maxParams`               | The most parameters one statement binds; a batch read splits to fit (D1 allows 100) |

An executor without interactive transactions, such as D1 or a database RPC,
provides `batch` instead. Each write is then one atomic batch that records the
first failed guard in the `_hu_write` table (`WRITE_GUARD_TABLE`) and applies
its changes only when no guard failed. Create that table with the others.

`adapter.migrations.apply` creates tables with `createTableStatements(dialect,
tables, tablePrefix)`: strings with binary collation (`COLLATE "C"` on
PostgreSQL, `utf8mb4_0900_bin` or `ascii_bin` on MySQL), whole numbers as
`bigint`, and a table `<table>__<index>` for each index over a multi-valued
column.

### A key-value store

`createKvAdapter({ store, tablePrefix })` implements the contract over a store
with strongly consistent point reads, sorted partitions and atomic conditional
writes, such as DynamoDB or Firestore:

```ts
interface KeyValueStore {
  readonly id: string;
  /** The most items and bytes one write takes, per item, and per key. */
  readonly limits: {
    readonly items: number;
    readonly bytes: number;
    readonly itemBytes?: number;
    readonly keyBytes?: { readonly pk: number; readonly sk: number };
  };
  /** Strongly consistent point reads, in the order of `keys`. */
  get(keys: readonly KvKey[]): Promise<readonly (StoredRow | null)[]>;
  /** One native page of one partition's sort-key range. */
  query(
    range: KvRange,
  ): Promise<{ readonly items: readonly KvItem[]; readonly more: boolean }>;
  /** Applies every op or none. */
  write(ops: readonly KvOp[]): Promise<WriteResult>;
  /** Prepares the store, such as creating its table. */
  readonly migrations?: { apply(): Promise<void> };
  dispose?(): Promise<void>;
}
```

- An item is addressed by a partition key `pk` and a sort key `sk`, both
  strings. Sort keys compare by UTF-8 bytes.
- `query({ pk, gte, lt, order, limit, after })` returns one page of the
  partition's items from `gte` up to `lt`, past `after`, and `more` when the
  range may go on. An empty page ends the range.
- `write(ops)` applies `put`, `delete`, `check` and `add`, an increment that
  creates a missing item from `init`. Every op's `condition` (the item exists,
  does not exist, or has `_v` equal to `v`) sees the state before the write.
  Return `failedOp` for an op whose condition failed and `retry` for a
  transient conflict, as an adapter does.
- If the store throws when its table is missing, give that error
  `code: "42P01"`, as the DynamoDB store does, so the schema fence reports a
  missing schema.

The helper stores a row as one item at `pk = <table>`, and an index in key
order reads those items. Every other index adds an item per entry in its own
partition, holding a copy of the row, written in the same write. A unique entry
is an item that one row at a time may hold. `fits` counts items and bytes
against `limits`. The
[DynamoDB store](https://github.com/gronxb/hot-updater/blob/next/plugins/aws/src/dynamoDBStore.ts)
and the
[Firestore store](https://github.com/gronxb/hot-updater/blob/next/plugins/firebase/src/firestoreStore.ts)
are complete implementations. Wrap the adapter as in `myDatabase`, with
`createKvAdapter({ store })` in place of `createSqlAdapter`.

### The contract directly

A backend with its own transactions and secondary indexes can implement
`DatabaseAdapter` directly: keep each table's rows by key, create each index
as declared, and read an index range in `indexOrderColumns` order.
`createMemoryAdapter()` implements every rule on this page and is the
reference. The
[MongoDB adapter](https://github.com/gronxb/hot-updater/blob/next/packages/server/src/adapters/mongodbAdapter.ts)
is a production one: a collection per table keyed by `_id`, guards as
conditional updates, and one transaction per write. While you develop, wrap
your adapter in `verifyAdapter(adapter)`. It fails reads that return rows for
other keys, rows outside the range or out of order, or more than `limit` rows,
and writes that touch a row twice or that `fits` refuses.

## Wrap it as a database

`createEngineDatabase({ name, adapter })` returns the `EngineDatabase` a
provider's factory returns, as `myDatabase` does. It puts the adapter behind
the schema fence and forwards the adapter's `dispose`. Add your own `dispose`
when the factory opens a client.

| Option                 | Meaning                                                                                                                                                                                              |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `name`                 | Names the database in messages; `createHotUpdater` reports it as `adapterName`                                                                                                                       |
| `adapter`              | The storage adapter                                                                                                                                                                                  |
| `onCachedRoutesChange` | Called after a committed write that changes what the cacheable client routes answer (a Release Catalog row), so a CDN in front of them can purge its copies. `dynamoDB` invalidates CloudFront here. |

Pass the database to the CLI and the server. Partial configuration:

```ts title="hot-updater.config.ts"
import { defineConfig } from "hot-updater";

import { myDatabase } from "./myDatabase";

export default defineConfig({
  // build: ...,
  // storage: ...,
  database: myDatabase({ connectionString: process.env.DATABASE_URL }),
});
```

```ts title="server.ts"
import { createHotUpdater } from "@hot-updater/server";
import { apiKeys } from "@hot-updater/server/plugins/api-keys";
import { insights } from "@hot-updater/server/plugins/insights";

import { myDatabase } from "./myDatabase";

export const hotUpdater = createHotUpdater({
  database: myDatabase({ connectionString: process.env.DATABASE_URL }),
  // storage: [...],
  plugins: [insights(), apiKeys()],
});
```

## Create the schema

Migrations write settings rows to `private_hot_updater_settings` last, after
every table exists: `schema.engine` (`"1"`) and one row per module,
`schema.core`, `schema.insights` and `schema.apiKeys` (`"1.0.0"`). Before a
process's first read or write, the schema fence reads them in one batch. A
missing or different row throws `HotUpdaterSchemaMigrationRequiredError`,
which names the setting, and the server's handlers answer 503. A read that
fails because the settings table is missing counts as a missing row when the
error says so: PostgreSQL `42P01` or `42703`, MySQL `ER_NO_SUCH_TABLE` or
`ER_BAD_FIELD_ERROR`, or a message such as `no such table`. Any other failure,
such as a refused connection, is thrown as it is.

Export a migration with your factory, as `migrateMyDatabase` does.
`migrateBuiltInSchema(adapter, name)` passes core's and the built-in plugins'
tables to `adapter.migrations.apply`, then writes the settings rows. Running it
again changes nothing. It refuses a database that has `schema.core` but no
`schema.engine`; create a new database instead. Run the migration from a
script, a deploy job or your provider's setup command, as `migrateDynamoDB` and
`migrateFirebaseDatabase` do for their providers. `hot-updater db migrate` runs
the migrators of the Kysely, Drizzle, Prisma and MongoDB adapters and refuses
other databases.

A SQL provider can check in its schema instead.
`generateEngineSql(dialect, builtInSchema, builtInSettings, { tablePrefix })`
from `@hot-updater/server/db` returns the statements: tables and indexes, then
the settings rows. The `postgres` and D1 providers generate their checked-in
SQL this way, and a test fails when a file differs from the generator. Add
`createTableStatements(dialect, [WRITE_GUARD_TABLE])` when the executor has
`batch`. When other tooling creates the tables,
`writeSchemaSettings(adapter, name, builtInSettings)` writes only the settings
rows.

## Test the adapter

`@hot-updater/test-utils` publishes the suites that every official database
runs. Register all three:

| Suite                                  | Runs                                                                                             | Against                                  |
| -------------------------------------- | ------------------------------------------------------------------------------------------------ | ---------------------------------------- |
| `setupDatabaseAdapterConformanceSuite` | the contract on this page, case by case                                                          | your adapter, on two test tables         |
| `setupReadBudgetTestSuite`             | what each read of core and the built-in plugins costs                                            | your adapter, on the built-in tables     |
| `setupDatabaseTestSuite`               | core, Bundles, the Release Catalog contract and Insights, through the admin and client HTTP APIs | your database, behind `createHotUpdater` |

The examples expect `TEST_DATABASE_URL` to name an empty PostgreSQL database.
Each suite creates its own tables, and the specs drop or empty them through
this helper:

```ts title="testTables.ts"
import { isMultiIndex, type PhysicalTable } from "@hot-updater/server/database";

/** The quoted tables the SQL core creates for `tables`, index tables included. */
export const tableNames = (tables: readonly PhysicalTable[], prefix = "") =>
  tables
    .flatMap((table) => [
      table.name,
      ...table.indexes
        .filter((index) => isMultiIndex(table, index))
        .map((index) => `${table.name}__${index.name}`),
    ])
    .map((name) => `"${prefix}${name}"`)
    .join(", ");
```

### Adapter conformance

```ts title="myDatabase.conformance.spec.ts"
import { createSqlAdapter } from "@hot-updater/server/database";
import { setupDatabaseAdapterConformanceSuite } from "@hot-updater/test-utils";
import pg from "pg";
import { afterAll } from "vitest";

import { myExecutor } from "./myDatabase";
import { tableNames } from "./testTables";

const pool = new pg.Pool({ connectionString: process.env.TEST_DATABASE_URL });
afterAll(() => pool.end());

setupDatabaseAdapterConformanceSuite({
  name: "myDatabase",
  createAdapter: async ({ tables }) => {
    const adapter = createSqlAdapter({ executor: myExecutor(pool) });
    await adapter.migrations!.apply(tables);
    return {
      adapter,
      cleanup: async () => {
        await pool.query(`DROP TABLE ${tableNames(tables)}`);
      },
    };
  },
});
```

| Option          | Meaning                                                                                                                                                                                                                                         |
| --------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `name`          | Names the suite                                                                                                                                                                                                                                 |
| `createAdapter` | Returns `{ adapter, cleanup? }` over newly created, empty `tables`, for each case; `cleanup` runs after the case. One case passes `nativePageSize: 2`: fetch at most that many rows per native page. A backend without native pages ignores it. |
| `maxOps`        | The most ops one write accepts. The suite then checks that `fits` refuses one more op and that nothing is written. Omit it when the backend has no limit.                                                                                       |
| `writers`       | Concurrent writers in the contention cases (default 32)                                                                                                                                                                                         |

The cases cover value round-trips, point reads in key order, each op's guard,
all-or-nothing writes with a failure at every position, unique indexes and the
op they name, UTF-8 byte order, cursor paging without gaps or repeats,
multi-valued indexes, full pages under capped native pages, one winner among
concurrent writers, no lost increments, write-skew rejection, and over-limit
writes refused before sending. Every call also passes through `verifyAdapter`.

A key-value store takes `nativePageSize` as its page size. Its `maxOps` is the
number of conformance inserts one write fits: the DynamoDB spec sets 33,
since an insert there is 3 items and a transaction takes 100.

### Read budgets

```ts title="myDatabase.readBudgets.spec.ts"
import { builtInSchema, createSqlAdapter } from "@hot-updater/server/database";
import {
  createMeasuredDatabase,
  targetBaseCandidateKey,
} from "@hot-updater/server/db";
import { apiKeys } from "@hot-updater/server/plugins/api-keys";
import { insights } from "@hot-updater/server/plugins/insights";
import {
  postgresRowsExamined,
  setupReadBudgetTestSuite,
} from "@hot-updater/test-utils";
import pg from "pg";
import { afterAll } from "vitest";

import { myExecutor } from "./myDatabase";
import { tableNames } from "./testTables";

const pool = new pg.Pool({ connectionString: process.env.TEST_DATABASE_URL });
afterAll(() => pool.end());

setupReadBudgetTestSuite({
  name: "myDatabase",
  server: {
    createMeasuredDatabase,
    builtInSchema,
    plugins: [insights(), apiKeys()],
    targetBaseCandidateKey,
  },
  createAdapter: async ({ tables }) => {
    // Each read is explained on one session of the pool.
    const session = await pool.connect();
    const reads = postgresRowsExamined(
      async (sql, params) => (await session.query(sql, [...params])).rows,
    );
    const adapter = createSqlAdapter({
      executor: reads.wrap(myExecutor(pool)),
      tablePrefix: "budget_",
    });
    await adapter.migrations!.apply(tables);
    return {
      adapter,
      examined: reads.examined,
      cleanup: async () => {
        session.release();
        await pool.query(`DROP TABLE ${tableNames(tables, "budget_")}`);
      },
    };
  },
});
```

`createMeasuredDatabase(adapter, plugins, options)` from
`@hot-updater/server/db` assembles core and the plugins as `createHotUpdater`
does, on an engine that checks every adapter call, without the schema fence.
The suite seeds Bundles, Releases, Channels, an API key and Insights events,
caps native pages at two rows, and checks each API's reads exactly, at the
adapter and at the engine. For example, the update check is one point read of
a catalog row, and artifact resolution is one batch read of two Bundles plus
one patch read.

| `createAdapter` result | Meaning                                                                                                                                                                                                       |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `adapter`              | Your adapter over newly created, empty `tables`: core's and the built-in plugins'                                                                                                                             |
| `cleanup`              | Runs after the suite                                                                                                                                                                                          |
| `examined`             | SQL backends: the rows the database examined. `postgresRowsExamined(query)` and `mysqlRowsExamined(query)` explain each read the wrapped executor runs, so a read that scans more rows than it returns fails. |
| `indexCopies`          | `true` when index reads return row copies without `_v`, as `createKvAdapter` does; a transaction then reads the rows it guards again                                                                          |

### The server over HTTP

```ts title="myDatabase.spec.ts"
import { createHotUpdater } from "@hot-updater/server";
import { builtInSchema } from "@hot-updater/server/database";
import { createDatabasePluginApis } from "@hot-updater/server/db";
import {
  createInsightsModel,
  insights,
} from "@hot-updater/server/plugins/insights";
import {
  setupDatabaseTestSuite,
  startHttpTestServer,
} from "@hot-updater/test-utils";
import pg from "pg";

import { migrateMyDatabase, myDatabase } from "./myDatabase";
import { tableNames } from "./testTables";

const config = { connectionString: process.env.TEST_DATABASE_URL };
const pool = new pg.Pool(config);

setupDatabaseTestSuite({
  name: "myDatabase",
  migrate: () => migrateMyDatabase(config),
  createDatabase: () => myDatabase(config),
  // Every table but the settings, which the schema fence checks.
  reset: async () => {
    await pool.query(`TRUNCATE ${tableNames(builtInSchema.tables)}`);
  },
  dispose: async (database) => {
    await database.dispose?.();
    await pool.end();
  },
  createHttpClient: (options) =>
    startHttpTestServer(
      createHotUpdater({
        ...options,
        plugins: [insights()],
        clientAccess: "public",
      }).handlers,
    ),
  createInsightsModel: (database) =>
    createInsightsModel(
      createDatabasePluginApis(database, [insights()]).insights,
    ),
});
```

| Option                | Meaning                                                                                                                                                                                                        |
| --------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `migrate`             | Creates the tables and settings rows, once, before `createDatabase`                                                                                                                                            |
| `createDatabase`      | Your database, as your factory returns it                                                                                                                                                                      |
| `reset`               | Empties every data table before each test and keeps the settings rows                                                                                                                                          |
| `dispose`             | Closes the database after the suite                                                                                                                                                                            |
| `createHttpClient`    | Serves the handlers of `createHotUpdater({ database, storage, plugins: [insights()], clientAccess: "public" })`: `startHttpTestServer` on loopback in Node, or `createHandlerHttpTestClient` in a Workers pool |
| `createInsightsModel` | Optional. Also runs the Insights report contract in process, on the plugin's tables                                                                                                                            |

The suite sends real requests to the admin API and the client routes. It runs
core's operations, the Bundle admin API, the Release Catalog contract and the
Insights routes. The Release Catalog scenarios pass each catalog they receive
to the production client selector and carry a simulated device from its
built-in bundle to OTA A, OTA B, back to A, and back to built-in. Other
scenarios cover deleted Releases, the native minimum, cohort changes and
crashed updates.

Run the specs with Vitest:

```bash
TEST_DATABASE_URL=postgres://localhost:5432/hot_updater_test npx vitest run
```

### Test a running server

`setupReleaseCatalogTestSuite` runs the Release Catalog scenarios against a
server you started, through its framework routing and authentication:

```ts title="server.spec.ts"
import {
  createHttpTestClient,
  setupReleaseCatalogTestSuite,
} from "@hot-updater/test-utils";

setupReleaseCatalogTestSuite({
  getClient: () =>
    createHttpTestClient({
      clientBaseUrl: "http://127.0.0.1:3000/hot-updater",
      adminBaseUrl: "http://127.0.0.1:3000/hot-updater/admin",
      adminHeaders: { Authorization: `Bearer ${process.env.ADMIN_TOKEN}` },
    }),
});
```

Start the server on a disposable database, with
`createReleaseCatalogTestStorage()` from `@hot-updater/test-utils/node` in its
`storage`. That entry does not load Vitest, so a separate server process can
import it. Add `clientHeaders` when the server's client routes need a key.
