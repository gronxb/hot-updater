Use this guide when you are implementing a new persistence backend. If your
backend already works with [Kysely](/docs/custom/database/kysely),
[Drizzle](/docs/custom/database/drizzle), [Prisma](/docs/custom/database/prisma)
or [MongoDB](/docs/custom/database/mongodb), configure that adapter instead.

The current public API is `createDatabasePlugin({ name, models, commit })`.
You supply the complete domain models and atomic commit implementation. There
is no public `createAdapterFactory` or `@hot-updater/plugin-core/adapters` export.
Start with [provider wiring](#create-a-provider), then implement the
[model contract](#domain-interfaces) and run [conformance](#test-the-provider).

## Installation

```package-install
npm install @hot-updater/plugin-core
```

Install the public conformance suite and test server in the provider project:

```package-install
npm install @hot-updater/test-utils @hot-updater/server @hot-updater/core execa vitest@^4 --save-dev
```

Keep the `@hot-updater/*` packages on the same release, including the RC version
when applicable. The test-utils package requires Vitest 4, `execa`, core and
plugin-core as peers. Install your database driver separately. A deployed server
also needs `@hot-updater/server` as a runtime dependency in its server project.

## Contract

`createDatabasePlugin` exposes seven fixed persistence models and one atomic
commit boundary:

```ts
import { createDatabasePlugin } from "@hot-updater/plugin-core";

// Supply the models and native commit described below.
createDatabasePlugin({
  name,
  models: {
    bundles,
    bundlePatches,
    releases,
    releaseCatalogs,
    channels,
    insights,
    apiKeys,
  },
  commit,
  dispose,
});
```

There is no `queries` member or provider-owned update decision. Hot Updater
compiles desired-state policy into Release catalogs when Releases change. A
device catalog GET performs one exact catalog read and never scans Releases or
Bundles.

The fixed domains are:

- `bundles`: immutable artifact metadata.
- `bundle_patches`: patch artifacts owned by Bundles.
- `releases`: mutable rollout and compatibility policy that references an
  artifact Bundle.
- `release_catalogs`: deterministic projections with persistent identity and
  generation history, keyed by scope.
- `channels`: persistent deployment-channel identity.
- `insights`: immutable Bundle reports and latest installation state.
- `api_keys`: hashed API key records.

`private_hot_updater_settings` remains the schema-version marker managed by
the server database tooling.

### What the public constructor provides

| Entry point | Contract |
| --- | --- |
| `@hot-updater/plugin-core` | `DatabasePlugin`, domain model types, and the `createDatabasePlugin` constructor for custom providers |
| `@hot-updater/test-utils` | The shared provider and HTTP conformance suites |

`createDatabasePlugin` accepts complete domain models and a native atomic
`commit`. It validates the entire commit envelope before calling the provider,
including every change and expectation. It also validates Channel insert/delete
inputs and results, and Insights inputs and results. Providers remain responsible
for their other model reads, stored-row validation, references, indexes and
atomicity. The constructor does not generate database queries or transactions.

The bundled `createDatabasePluginAdapter` is an internal implementation detail,
not a supported custom-provider import. Its existence does not make the public
constructor a CRUD adapter factory. Use only public types and exports in your
provider package; the current domain implementation burden remains yours.

### Bounded reads

Apply the requested predicates, ordering and window in the database. Exact IDs
and finite ID sets must use targeted reads. Missing indexes or unsupported
queries must fail explicitly; never retry by listing all Bundles, Releases or
events and filtering them in memory. Do not truncate results at an arbitrary
global row ceiling.

Native continuation pages and ID batches are allowed within the requested
scope. Enumerating patches for supplied owners, compiling all Releases in one
scope, explicit full lists and scalar aggregates retain their documented cost.
These operations do not authorize a full-history fallback for a point lookup
or a bounded page.

## Create a provider

This is a complete **wiring** example, not a database implementation. It accepts
your seven model objects, native `commit`, and optional `dispose` through the
exported `DatabasePlugin` type. It does not require a particular collection of
model-builder helpers.

```ts title="myDatabase.ts"
import {
  createDatabasePlugin,
  type DatabasePlugin,
} from "@hot-updater/plugin-core";

export type MyDatabaseImplementation = Omit<DatabasePlugin, "name">;

export const myDatabase = (
  implementation: MyDatabaseImplementation,
): DatabasePlugin => createDatabasePlugin({
  name: "my-database",
  ...implementation,
});
```

Implement `MyDatabaseImplementation` using your database driver. The models must
return the public row/result shapes, and `commit` must enforce the ordered
conditional transaction described below. Do not fill missing methods with
successful no-ops. Keep SQL values parameterized and canonical row field names
unchanged. Methods receive no HTTP request context; close over your configured
client or runtime binding.

The constructor does not initialize a schema, open or close a connection, or
make your implementation lazy. Create an owned client at the appropriate time
and expose `dispose` to close it. If the caller supplies a shared client, let the
caller own its lifetime or document an explicit ownership transfer. Do not
close that client after each request. The test harness invokes its disposal
hook; application lifecycle shutdown remains the caller's responsibility.

## Domain interfaces

Use the exported interfaces rather than redeclaring them:

```ts
import type {
  InsightsModel,
  BundleModel,
  BundlePatchModel,
  ChannelModel,
  ApiKeyModel,
  DatabaseCommit,
  DatabaseCommitResult,
  ReleaseCatalogModel,
  ReleaseModel,
} from "@hot-updater/plugin-core";
```

### Bundles and patches

```ts
interface BundleModel {
  findById(id: string): Promise<BundleRow | null>;
  findMany(query: BundleModelQuery): Promise<readonly BundleRow[]>;
  count(where?: DatabaseBundleQueryWhere): Promise<number>;
}

interface BundlePatchModel {
  findByBaseBundleIds?(
    baseBundleIds: readonly string[],
  ): Promise<readonly BundlePatchRow[]>;
  findByBundleIds(
    bundleIds: readonly string[],
  ): Promise<readonly BundlePatchRow[]>;
}
```

Apply filters and ordering before offset and limit. An empty `id.in` filter
and an empty patch owner list return no rows without I/O. Bundle rows contain
artifact identity and storage fields only; rollout, channel, compatibility,
force-update, and message fields belong to Releases.

`findByBaseBundleIds` is an optional indexed reverse lookup for patches that
reference the supplied base Bundles. Return all matching patches across native
pages, without enumerating unrelated Bundles. An operation requiring this
capability fails explicitly when it is absent; there is no list-all fallback.

`BundlePatchRow.byte_size` is a required immutable non-negative safe integer.
Reject missing, fractional, negative, or out-of-range values on every read and
write. Bundle manifest storage fields are required. Optional manifest asset
`downloadByteSize` and `downloadFileHash` values live in manifest JSON and are
not additional database columns.

### Releases

```ts
interface ReleaseModel {
  findById(id: string): Promise<ReleaseRow | null>;
  findMany(input: {
    afterReleaseId?: string;
    beforeReleaseId?: string;
    bundleId?: string;
    channelId?: string;
    enabled?: boolean;
    platform?: "ios" | "android";
    targetAppVersion?: string;
    limit: number;
  }): Promise<readonly ReleaseRow[]>;
  findManyByScope(input: {
    scopeKey: string;
    afterReleaseId?: string;
    limit: number;
    consistency: "strong";
  }): Promise<readonly ReleaseRow[]>;
}
```

`findMany` supports management views in newest-first Release-ID order. Do not
combine `afterReleaseId` and `beforeReleaseId`. An `afterReleaseId` query selects
the nearest newer rows before returning them newest-first. All supplied filters,
including the exact `targetAppVersion`, apply before the limit.
`findManyByScope` is the catalog compiler input and has stricter semantics:

- read the canonical primary storage path with strong consistency;
- order by Release ID ascending;
- apply `afterReleaseId` as an exclusive keyset cursor;
- never use an eventually consistent secondary index;
- return at most `limit` rows.

The compiler may page tens of thousands of Releases without holding a write
transaction open. The catalog-generation expectation described below detects
any write that crosses that snapshot.

### Release catalogs

```ts
interface ReleaseCatalogModel {
  findByScopeKey(scopeKey: string): Promise<ReleaseCatalogRow | null>;
  findMany(input: {
    afterScopeKey?: string;
    limit: number;
  }): Promise<readonly ReleaseCatalogRow[]>;
}
```

`findByScopeKey` is an exact point read. `findMany` orders by scope key and is
used by migration and rebuild tooling. Providers do not compile or interpret
the JSON payload. Only an atomic commit may write `releaseCatalogs`.

Never delete the last catalog for a scope. Removing the last eligible Release
writes a tombstone catalog with a higher generation.

Back up Catalog rows together with Releases. Rebuild preserves an existing
Catalog's identity and generation history; it cannot recover that history from
Release rows alone. Restore a missing Catalog row from backup before rebuilding
or deploying to its scope.

### Channels and API keys

Channel names are exact and case-sensitive. Concurrent insert returns the
canonical stored row. Empty Channels persist until explicit deletion, and the
reference check plus deletion must be atomic. API key creation is idempotent
by hash; revocation updates only `revoked_at_ms`.

### Insights

Implement all seven `InsightsModel` methods using the exported input and result
types. Every call takes an object.

```ts
interface InsightsModel {
  recordEvent(input: InsightsRecordEventInput): Promise<void>;
  listEvents(
    input: InsightsListEventsInput,
  ): Promise<readonly BundleEventRow[]>;
  findLatestEvents(
    input: InsightsFindLatestEventsInput,
  ): Promise<readonly BundleEventRow[]>;
  countLatestEvents(input: InsightsCountLatestEventsInput): Promise<number>;
  countEvents(input: InsightsCountEventsInput): Promise<number>;
  getReleaseActivity(
    input: InsightsGetReleaseActivityInput,
  ): Promise<InsightsGetReleaseActivityResult>;
  getAppUsage(
    input: InsightsGetAppUsageInput,
  ): Promise<InsightsGetAppUsageResult>;
}
```

`recordEvent({ event })` receives one validated, immutable `BundleEventRow`. Store
it once by `id`; the first accepted payload wins, even if a retry carries different
fields. There is no required installation table or second input to prepare.

A provider may maintain a private latest index keyed by `install_id`, containing
the canonical access fields or the complete supplied event. Event acceptance and
advancing that index must be one native atomic operation. Replace its fields
only if `(received_at_ms, id)` increases. A duplicate event ID changes nothing,
including private indexes. Older events enter history without restoring an old
user association. A winning `user_id: null` removes the previous association.
Implement these storage rules directly; no lifecycle helper or reducer is required.

`metadata` uses the same JSON value conventions as Bundle metadata. Its required
known keys are `cohort: string`, `username: string | null`,
`update_strategy: "appVersion" | "fingerprint" | null`,
`fingerprint_hash: string | null`, and `sdk_version: string | null`.
Core validates these and the event-type relationship before calling `recordEvent`.
Preserve all supplied JSON keys, including nested objects, arrays, and nulls.
Do not unpack metadata into provider-specific columns or interpret it for queries.

`listEvents({ filter, sinceMs?, beforeReceivedAtMs, after?, limit })` returns
newest-first `(received_at_ms, id)` order in the half-open interval
`[sinceMs ?? 0, beforeReceivedAtMs)`. `after: { receivedAtMs, id }` is an
exclusive key: return strictly smaller tuples. The fixed filter is one of:

```ts
{ kind: "all" }
{ kind: "installationMovement", installId }
{ kind: "bundle", platform, channel, type: "RECOVERED", fromBundleId }
{ kind: "bundle", platform, channel,
  type: "UPDATE_DOWNLOADED" | "UPDATE_APPLIED" | "UNCHANGED", toBundleId }
```

Installation movement means `UPDATE_DOWNLOADED`, `UPDATE_APPLIED`, or `RECOVERED`. Apply filters
before the limit using indexed cursor ranges; do not load global history or
walk preceding pages. Limits are integers from 1 to 101; core uses lookahead
to return at most 100. A short or empty native page with a continuation token
is not exhaustion: continue until the result prefix is full or exhausted.

`findLatestEvents` returns canonical event rows, not installation DTOs:

```ts
type InsightsFindLatestEventsInput =
  | { installId: string }
  | { userId: string; afterInstallId?: string; limit: number };

type InsightsCountLatestEventsInput = {
  platform: "ios" | "android";
  channel: string;
  sinceMs: number;
  bundle?: readonly {
    field: "from_bundle_id" | "to_bundle_id";
    value: string;
    types: readonly BundleEventRow["type"][];
  }[];
};
```

For each installation, select the greatest `(received_at_ms, id)` across all
its events, including `UNCHANGED`, before applying user, scope, receipt-window,
or bundle predicates. Otherwise a historical match can restore a logged-out user.
Exact lookup returns zero or one row. A user page returns matches ordered by
`install_id` in ascending UTF-8 byte order, strictly after `afterInstallId`, with
the same 1 to 101 limit. IDs are case-sensitive without Unicode normalization.
A lagging secondary user index must validate candidates against canonical state
and continue past stale candidates; newly assigned users can be temporarily absent.

`countLatestEvents` counts selected latest events matching `platform`, `channel`,
and `received_at_ms >= sinceMs`. If `bundle` is supplied, it contains one or two predicates joined by OR.
A predicate matches when `event[predicate.field] === predicate.value` and
`event.type` is in `predicate.types`. Count a matching installation once even
when both predicates match. Evaluate the disjunction in one native query or
stable installation traversal; do not sum independently observed counts. These are fixed native predicates;
core supplies the Downloaded/from-bundle or other-type/to-bundle cases.
Do not derive running/pending state inside the plugin. Use a native event query
or a private latest index. A mutable last-seen cursor can double-count rows;
DynamoDB instead traverses stable installation IDs in a compact scope partition. Propagate query failure
rather than returning partial counts.

`countEvents({ filter, sinceMs, beforeReceivedAtMs })` counts a fixed raw bundle
filter in the same receipt interval as `listEvents`. The filter has platform,
channel, type, and `fromBundleId` for `RECOVERED` or `toBundleId` for
`UPDATE_DOWNLOADED`/`UPDATE_APPLIED`/`UNCHANGED`; it has no `kind`. `UNCHANGED` means the running files did not change, including selecting another Release for those same files. Its `from_bundle_id` and `metadata.update_strategy` must be null. Recovery B → A therefore
counts against B while latest state names A. Counts concern reports, not
unique attempts or installations. Count all native pages or propagate failure.

`getReleaseActivity` reads maintained summaries for 1 to 100 supplied Release
references, optionally within a time range, or for one scope within a required
time range. `getAppUsage` reads a Channel's usage for `all`, `ios`, or `android`,
with a required time range and an interval of at least one hour. It returns the
contract's active-installation count, time points, version/platform breakdowns
and Bundle distribution. Time ranges use inclusive `start` and exclusive `end`
UTC milliseconds. Both methods report `coverage` and `measuredAtMs`; do not
scan raw event history to reconstruct these summaries on each read.

Core owns report preparation, validation, windows, cursors, movement semantics
and product labels. Providers own atomic storage, native queries, indexes,
scalar counts and the two fixed summary projections. Keep event acceptance,
latest-state advancement and affected summary updates atomic. Separate live
counts are not a common snapshot and must not imply an exact percentage.
Document query costs and propagate native errors rather than returning
truncated results. Summary coverage may explicitly report incomplete history.

The public constructor validates Insights queries and results, but cannot prove
atomicity or index usage. Run the repository conformance suite plus native rollback,
concurrency, continuation, schema-bootstrap, and query-plan tests for your
backend.

#### Native storage and atomicity

A private latest-head row/document is an implementation choice, not an extra
public model. It must preserve the canonical ordering and query fields, plus
any Release/app-version attribution needed to update the maintained summaries.
The bundled schema includes those attribution fields; an event/head-only insert
is not a complete `recordEvent` implementation.

For every newly accepted event, keep history, relevant counters/HLL summaries,
and any latest-head/current-user/distribution changes in one atomic operation.
A duplicate must change none of them. An older but newly accepted event still
contributes its report metrics without replacing the latest head. Summary reads
merge bounded HLL summaries; do not replace approximate distinct-user metrics
with an unbounded set of installation IDs.

| Native backend | Implementation requirement |
| --- | --- |
| SQL or a transaction-capable ORM | Use real transactions, uniqueness, conditional mutations and native accumulation. Concurrent first reports for an absent head also need protection. |
| Firestore | Read all required event/head/summary state before writing inside the native transaction; retry with the same prepared event. |
| DynamoDB | Include head, summary, uniqueness and relation guards in one conditional transaction; account for physical index writes and native limits. |
| D1 | Compile checks and conditional effects into one atomic batch. A zero-row update alone does not abort a batch. |
| Supabase | Execute the complete operation in one installed RPC transaction; separate REST calls are not atomic. |

Select only the fields needed by each indexed read. An exact count may examine
its matching index range even when it returns one number. Returning a small page
or using a native query is not proof of bounded examined work. Run native
rollback/concurrency and query-cost tests alongside the published conformance
suite; the public constructor cannot supply those guarantees for your driver.

## Atomic commit and optimistic CAS

`commit` receives one declarative envelope. All changes and expectations are
one transaction:

```ts
const result = await database.commit({
  expectations: [
    { model: "releases", id: release.id, revision: release.revision },
    {
      model: "releaseCatalogs",
      scopeKey: catalog.scope_key,
      generation: catalog.generation,
    },
  ],
  changes: [
    {
      model: "releases",
      operation: "update",
      where: { id: release.id },
      update: nextRelease,
    },
    {
      model: "releaseCatalogs",
      operation: "put",
      row: nextCatalog,
    },
  ],
});
```

An expectation version of `null` means the row must not exist. Check every
expectation and apply every change inside one short provider-native
transaction. A mismatch returns the actual version and writes nothing:

```ts
{
  committed: false,
  conflict: {
    changeIndex: -1,
    reason: "version_conflict",
    model: "releaseCatalogs",
    key: scopeKey,
    expectedVersion: 41,
    actualVersion: 42,
  },
}
```

Expected missing targets and referenced-row deletes continue to return their
source `changeIndex`. All other validation, constraint, and provider failures
reject. A provider without an atomic conditional primitive must reject before
its first write; there is no Release-now/catalog-later fallback.

Input validation does not serialize concurrent writers. When a parent deletion
enumerates its relationships, a concurrent child insertion must either be
included or invalidate the transaction. Protect both sides using native
constraints, transactional reads or conditional version writes. Native action
limits must reject an oversized commit without partially applying it.

## Implement the 1.0.0 schema

The initial `1.0.0` schema includes the required Insights storage and indexes,
exact identity collations, and atomic recording. Initialize the complete schema
on empty storage and retain it on repeated initialization. The `1.0.0` marker
alone does not prove that an existing RC
installation has the final schema/indexes. Inspect and reconcile that schema
explicitly; do not replay initialization, add a second pre-GA migration, or
repair it during requests. Unsupported populated storage is rejected without
deleting its data. See [Upgrade to v1](/docs/guides/upgrade-to-v1).

1. Implement the public models and native commit; leave update selection and
   Release-catalog compilation to Hot Updater.
2. Keep Bundle rows as immutable manifest artifacts and validate patch byte
   sizes. Store rollout and compatibility policy on Releases.
3. Add Channel, Release, and Release-catalog storage, indexes, and references.
4. Implement exact catalog reads and strongly consistent, keyset-paged Release
   scope reads.
5. Extend the atomic commit with Release revision and catalog generation
   expectations.
6. Implement atomic Insights recording and the fixed queries above. Record
   `schema.core = 1.0.0` after successful initialization;
   reject unsupported source versions without deleting their data.
7. Run conformance and integration tests against the real backend.

Provider-specific consistency requirements:

- DynamoDB uses a strongly consistent base-table scope partition, not a GSI.
- Firestore uses strong server reads and transaction preconditions.
- PostgreSQL, Supabase, and SQL adapters use ordered primary reads and revision
  and generation predicates in the write transaction.
- MongoDB uses deterministic majority reads and a short write transaction.
- D1 must prove a failed generation predicate aborts the complete batch.

## Catalog transport caching

The database contract is independent of HTTP caching. If a custom deployment
places a shared cache in front of the server, its catalog cache key must include
the host, canonical path, supported content encoding, and the configured API
key header (`x-api-key` by default). When using `clientAccess.headerName`,
partition on that header instead. It must not include installation state.
Invalid-key and error responses remain `private, no-store`.

If custom authentication varies on any other header, map that identity to one
stable, documented catalog cache partition and include it in the cache key.
Do not enable shared caching for arbitrary request headers without an explicit
partition contract.

## Test the provider

Use the same conformance suite as the official database providers. Install the
published `@hot-updater/test-utils` package; no repository checkout is needed.
Keep test-utils, server, and plugin-core on the same Hot Updater version.

Connect your plugin and its test database lifecycle:

```ts title="myDatabase.spec.ts"
import { createHotUpdater } from "@hot-updater/server";
import {
  setupDatabasePluginTestSuite,
  startHttpTestServer,
} from "@hot-updater/test-utils";
import { myDatabase } from "./myDatabase";
import {
  createTestDatabase,
  createTestImplementation,
  destroyTestDatabase,
  migrateDatabase,
  resetDatabase,
} from "./testDatabase";

let db: Awaited<ReturnType<typeof createTestDatabase>>;

setupDatabasePluginTestSuite({
  name: "my database",
  createHttpClient: (options) => startHttpTestServer(
    createHotUpdater({ ...options, clientAccess: { type: "public" } }).handlers,
  ),
  migrate: async () => {
    db = await createTestDatabase();
    await migrateDatabase(db);
  },
  createPlugin: () => myDatabase(createTestImplementation(db)),
  reset: () => resetDatabase(db),
  dispose: async (plugin) => {
    try {
      await plugin.dispose?.();
    } finally {
      await destroyTestDatabase(db);
    }
  },
});
```

The functions imported from `./testDatabase` are your backend-specific test
fixture, not package exports. `createTestImplementation(db)` returns a complete
`MyDatabaseImplementation` over that disposable database. Its `dispose` closes
an owned client; `destroyTestDatabase` removes the test database/resources using
an appropriate administrative connection and must not close that same client
again. Keep every resource isolated from development and production data.

`migrate` creates the isolated database and applies its schema once, before
`createPlugin`. `reset` clears all test data before each scenario while retaining
the schema and schema-version settings. `dispose` closes the plugin and removes
any test resources after the suite. The HTTP adapter above connects the actual
server to the suite. Do not copy scenarios or implement expected responses in the adapter.

```bash
pnpm exec vitest run myDatabase.spec.ts
```

Vitest runs in Node by default. `startHttpTestServer` starts a loopback HTTP
server using your plugin; the suite supplies deterministic storage fixtures and
runs real `fetch` requests through its admin and client handlers. Every registered
provider must pass the complete suite. Passing establishes compatibility with the **DatabasePlugin and Release
Catalog HTTP contracts for that Hot Updater version**:

- Model reads and writes, pagination and ordering, relations, Channel safety,
  atomic rollback, independent Release/Catalog version and absence expectations,
  and competing conditional writes with exactly one winner.
- Insights event identity, deduplication, counts, filtering, and ordering.
- Version and fingerprint projections, rollout metadata, rollback candidates,
  Catalog identity, cache expiry, ETag revalidation, and HTTP errors.
- Artifact identity and archive, manifest, and patch response selection.
- Device selection across built-in → OTA A → OTA B → rollback A → built-in,
  using HTTP catalogs and the production client selector. Each OTA transition
  verifies the selected Bundle's artifact before advancing the simulated device.
- Deleted active Releases, rollback below the native minimum, incompatible
  Releases, cohort changes, and exclusion of crashed Bundles on later checks.

This is the acceptance gate used by the official providers. New contract
scenarios are added centrally and run against every provider without changes to
its setup. Run the complete suite against your actual test backend without skipped
scenarios or mocked model methods. Repository mutation tests also run deliberately
broken providers through this public suite to verify that known contract violations
fail. Passing certifies the exercised versioned contracts; it does not prove every
possible execution or deployment condition.

Provider-specific concurrency stress, migrations, real storage access, and
native installation have their own integration tests; the conformance suite
certifies the database and HTTP behavior above.

For a complete implementation of the lifecycle, see the
[mock provider tests](https://github.com/gronxb/hot-updater/blob/next/plugins/mock/src/test/mockDatabase.spec.ts).

### Test an existing HTTP server

Use the HTTP suite directly to verify framework routing and authentication on a
separately started server. All `examples-server` projects run this same suite
against their spawned server processes.

```ts
import {
  createHttpTestClient,
  setupReleaseCatalogTestSuite,
} from "@hot-updater/test-utils";

// Start your server against an isolated, disposable database in beforeAll.
// Stop the server and dispose of that database in afterAll.
setupReleaseCatalogTestSuite({
  getClient: () => createHttpTestClient({
    clientBaseUrl: "http://127.0.0.1:3000/hot-updater",
    adminBaseUrl: "http://127.0.0.1:3000/hot-updater/admin",
    adminHeaders: { Authorization: `Bearer ${adminToken}` },
    // clientHeaders: { "x-api-key": clientApiKey },
  }),
});
```

Configure the test server's storage with `createReleaseCatalogTestStorage` from
`@hot-updater/test-utils/node`. That entry does not load Vitest and can
be imported by a separate server process. The database provider suite supplies
it automatically to `createHttpClient`.

Data preparation and policy changes use admin HTTP APIs; assertions use client
and admin HTTP responses. Lifecycle scenarios pass the received Catalog to
`selectDesiredRelease` from `@hot-updater/core`, just as the React Native client
does. The simulated device retains its active Bundle, Release receipt, native
minimum, cohort, and crash history between checks. Catalog refreshes honor real
server cache expiry. The suite verifies selection and artifact resolution;
native byte installation, activation, restart, and crash recovery require device
E2Es. It never calls the database or compiler directly.

The suite isolates cache keys by Channel and removes
reusable Bundle/Release fixtures after each scenario. The harness disposes of
the database after the suite to remove Channels and Catalogs, which have no
public Catalog deletion API.

For a Workers Vitest pool, replace `startHttpTestServer` with
`createHandlerHttpTestClient` from the same package. The provider still runs the
same conformance suite at its Web Request/Response boundary; see the
[D1 provider setup](https://github.com/gronxb/hot-updater/blob/next/plugins/cloudflare/worker/src/databasePlugins.integration.spec.ts).

## Configure Hot Updater

Use the same provider in the CLI and self-hosted server:

```ts title="hot-updater.config.ts"
import { defineConfig } from "hot-updater";
import { myDatabase } from "./myDatabase";
import { implementation } from "./implementation";

export default defineConfig({
  database: myDatabase(implementation), // [!code ++]
  // build: ...
  // storage: ...
});
```

```ts title="server.ts (excerpt)"
import { createHotUpdater } from "@hot-updater/server";
import { myDatabase } from "./myDatabase";
import { implementation } from "./implementation";

export const hotUpdater = createHotUpdater({
  database: myDatabase(implementation), // [!code ++]
  clientAccess: { type: "api-key" },
  storage,
});
```

Here `./implementation` exports your completed model/commit implementation;
`storage` is your configured storage plugin list. The CLI and server connect to
the same database, while each process owns its own client lifecycle. Catalog
identity is managed automatically; there is no additional identifier to
configure or synchronize.

## Standalone repositories

A Standalone management repository exposes Bundle, patch, Release, catalog,
and Channel models through the canonical server routes. It is not a complete
database plugin because the server owns Insights, API keys, compilation,
and the actual atomic transaction.

## SQL Server limitation

The Prisma SQL Server adapter retains its other models, but all seven Insights
methods reject before database I/O. SQL Server's padded string equality can
merge IDs that differ by trailing spaces; its default Unicode/UUID ordering
also differs from this contract. There is no silent fallback to weaker identity
or pagination semantics. Use a supported Insights provider for these views.

For `UPDATE_DOWNLOADED`, core maps the latest event to a response with its
`from_bundle_id` running and its `to_bundle_id` / `to_release_id` pending.
Other event types clear the pending response fields. These are server DTO rules,
not fields that custom providers must store.
