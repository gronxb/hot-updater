## Installation

```package-install
npm install @hot-updater/plugin-core
```

Install the public conformance suites in the project that tests your provider:

```package-install
npm install @hot-updater/test-utils vitest --save-dev
```

## Contract

`createDatabasePlugin` exposes seven fixed persistence models and one atomic
commit boundary:

```ts
createDatabasePlugin({
  name,
  models: {
    bundles,
    bundlePatches,
    releases,
    releaseCatalogs,
    channels,
    insights,
    apiKeys,
  },
  commit,
  dispose,
});
```

There is no `queries` member or provider-owned update decision. Hot Updater
compiles desired-state policy into Release catalogs when Releases change. A
device catalog GET performs one exact catalog read and never scans Releases or
Bundles.

The fixed domains are:

- `bundles`: immutable artifact metadata.
- `bundle_patches`: patch artifacts owned by Bundles.
- `releases`: mutable rollout and compatibility policy that references an
  artifact Bundle or the embedded app.
- `release_catalogs`: deterministic, rebuildable projections keyed by scope.
- `channels`: persistent deployment-channel identity.
- `insights`: immutable Bundle reports and latest installation state.
- `api_keys`: hashed API key records.

`private_hot_updater_settings` remains the schema-version marker managed by
the server database tooling.

## Domain interfaces

Use the exported interfaces rather than redeclaring them:

```ts
import type {
  InsightsModel,
  BundleModel,
  BundlePatchModel,
  ChannelModel,
  ApiKeyModel,
  DatabaseCommit,
  DatabaseCommitResult,
  ReleaseCatalogModel,
  ReleaseModel,
} from "@hot-updater/plugin-core";
```

### Bundles and patches

```ts
interface BundleModel {
  findById(id: string): Promise<BundleRow | null>;
  findMany(query: BundleModelQuery): Promise<readonly BundleRow[]>;
  count(where?: DatabaseBundleQueryWhere): Promise<number>;
}

interface BundlePatchModel {
  findByBundleIds(
    bundleIds: readonly string[],
  ): Promise<readonly BundlePatchRow[]>;
}
```

Apply filters and ordering before offset and limit. An empty `id.in` filter
and an empty patch owner list return no rows without I/O. Bundle rows contain
artifact identity and storage fields only; rollout, channel, compatibility,
force-update, and message fields belong to Releases.

`BundleRow.archive_byte_size` and `BundlePatchRow.byte_size` are required
immutable non-negative safe integers. Reject missing, fractional, negative, or
out-of-range values on every read and write. Optional manifest asset
`downloadByteSize` and `downloadFileHash` values live in manifest JSON and are
not additional database columns.

### Releases

```ts
interface ReleaseModel {
  findById(id: string): Promise<ReleaseRow | null>;
  findMany(input: {
    beforeReleaseId?: string;
    bundleId?: string;
    channelId?: string;
    enabled?: boolean;
    platform?: "ios" | "android";
    limit: number;
  }): Promise<readonly ReleaseRow[]>;
  findManyByScope(input: {
    scopeKey: string;
    afterReleaseId?: string;
    limit: number;
    consistency: "strong";
  }): Promise<readonly ReleaseRow[]>;
}
```

`findMany` supports management views in newest-first Release-ID order.
`findManyByScope` is the catalog compiler input and has stricter semantics:

- read the canonical primary storage path with strong consistency;
- order by Release ID ascending;
- apply `afterReleaseId` as an exclusive keyset cursor;
- never use an eventually consistent secondary index;
- return at most `limit` rows.

The compiler may page tens of thousands of Releases without holding a write
transaction open. The catalog-generation expectation described below detects
any write that crosses that snapshot.

### Release catalogs

```ts
interface ReleaseCatalogModel {
  findByScopeKey(scopeKey: string): Promise<ReleaseCatalogRow | null>;
  findMany(input: {
    afterScopeKey?: string;
    limit: number;
  }): Promise<readonly ReleaseCatalogRow[]>;
}
```

`findByScopeKey` is an exact point read. `findMany` orders by scope key and is
used by migration and rebuild tooling. Providers do not compile or interpret
the JSON payload. Only an atomic commit may write `releaseCatalogs`.

Never delete the last catalog for a scope. Removing the last eligible Release
writes a tombstone catalog with a higher generation.

### Channels and API keys

Channel names are exact and case-sensitive. Concurrent insert returns the
canonical stored row. Empty Channels persist until explicit deletion, and the
reference check plus deletion must be atomic. API key creation is idempotent
by hash; revocation updates only `revoked_at_ms`.

### Insights

Implement `InsightsModel` with these five exported input types. Every call takes
an object; custom providers do not implement the bundled internal CRUD adapter.

```ts
interface InsightsModel {
  record(input: InsightsRecordInput): Promise<void>;
  listEvents(
    input: InsightsListEventsInput,
  ): Promise<readonly BundleEventRow[]>;
  findInstallations(
    input: InsightsFindInstallationsInput,
  ): Promise<readonly InsightsInstallationRow[]>;
  countInstallations(input: InsightsCountInstallationsInput): Promise<number>;
  countEvents(input: InsightsCountEventsInput): Promise<number>;
}
```

`record({ event, installation })` receives a prepared immutable report and its
full latest-state candidate. Atomically insert the event and replace the
installation row only if `(received_at_ms, id)` advances. The first event ID
wins: a duplicate must not overwrite the event or update state again. Retrying
an identical prepared input after an ambiguous commit is safe. An older event
still enters history without restoring an old user or bundle. A winning
`user_id: null` clears the old association. Sequential best-effort writes are
insufficient; native transaction prerequisites belong in provider documentation.

`listEvents({ filter, sinceMs?, beforeReceivedAtMs, after?, limit })` returns
newest-first `(received_at_ms, id)` order in the half-open interval
`[sinceMs ?? 0, beforeReceivedAtMs)`. `after: { receivedAtMs, id }` is an
exclusive key: return strictly smaller tuples. The fixed filter is one of:

```ts
{ kind: "all" }
{ kind: "installationMovement", installId }
{ kind: "bundle", platform, channel, type: "RECOVERED", fromBundleId }
{ kind: "bundle", platform, channel,
  type: "UPDATE_APPLIED" | "RELEASE_ADOPTED", toBundleId }
```

Installation movement means `UPDATE_APPLIED` or `RECOVERED`. Apply filters
before the limit using indexed cursor ranges; do not load global history or
walk preceding pages. Limits are integers from 1 to 101; core uses lookahead
to return at most 100. A short or empty native page with a continuation token
is not exhaustion: continue until the result prefix is full or exhausted.

`findInstallations({ installId })` returns an empty or one-row array from
canonical latest state. `findInstallations({ userId, afterInstallId?, limit })`
returns current matches in ascending UTF-8 byte order of installation ID, with
an exclusive cursor and the same 1–101 limit. Mixing the forms is invalid.
IDs are exact and case-sensitive, with no Unicode normalization. If a secondary
user index lags, recheck candidates against canonical state and continue past
stale candidates. New associations may temporarily be absent; historical users
and usernames are not matches.

`countInstallations({ platform, channel, sinceMs, bundleId? })` counts latest
rows in that scope with `received_at_ms >= sinceMs`, optionally requiring
`to_bundle_id = bundleId`. Each installation contributes at most once. Use a
native aggregate or stable installation-ID traversal; paging a mutable
last-seen index can double-count moving rows. Never derive it from event history.

`countEvents({ filter, sinceMs, beforeReceivedAtMs })` counts a fixed raw bundle
filter in the same receipt interval as `listEvents`. The filter has platform,
channel, type, and `fromBundleId` for `RECOVERED` or `toBundleId` for
`UPDATE_APPLIED`/`RELEASE_ADOPTED`; it has no `kind`. Recovery B → A therefore
counts against B while latest state names A. Counts concern reports, not
unique attempts or installations. Count all native pages or propagate failure.

Core owns report preparation, validation, windows, cursors, movement semantics,
and product labels. Providers own atomic storage, native queries, indexes, and
scalar counts. Do not implement summary objects, group-by, top-N distributions,
chart buckets, or independently maintained outcome tables. Separate live counts
are not a common snapshot and must not imply an exact percentage. Document
query costs: a scalar can require traversing many records, and no operation may
silently return a 50,000-row partial result. Empty/zero means a successful empty
query; native errors must propagate.

The public constructor validates queries and returned rows, but cannot prove
atomicity or index usage. Run the public conformance suite plus native rollback,
concurrency, continuation, migration, and query-plan tests for your backend.

## Atomic commit and optimistic CAS

`commit` receives one declarative envelope. All changes and expectations are
one transaction:

```ts
const result = await database.commit({
  expectations: [
    { model: "releases", id: release.id, revision: release.revision },
    {
      model: "releaseCatalogs",
      scopeKey: catalog.scope_key,
      generation: catalog.generation,
    },
  ],
  changes: [
    {
      model: "releases",
      operation: "update",
      where: { id: release.id },
      update: nextRelease,
    },
    {
      model: "releaseCatalogs",
      operation: "put",
      row: nextCatalog,
    },
  ],
});
```

An expectation version of `null` means the row must not exist. Check every
expectation and apply every change inside one short provider-native
transaction. A mismatch returns the actual version and writes nothing:

```ts
{
  committed: false,
  conflict: {
    changeIndex: -1,
    reason: "version_conflict",
    model: "releaseCatalogs",
    key: scopeKey,
    expectedVersion: 41,
    actualVersion: 42,
  },
}
```

Expected missing targets and referenced-row deletes continue to return their
source `changeIndex`. All other validation, constraint, and provider failures
reject. A provider without an atomic conditional primitive must reject before
its first write; there is no Release-now/catalog-later fallback.

## Implement the 1.0.1 schema

Fresh storage uses schema `1.0.1`. Existing complete `1.0.0` storage upgrades
additively: preserve events and latest installation rows, add the bundle-outcome
and latest-scope indexes, and apply exact identity collations. Advance the
schema marker only after the upgrade succeeds. Stop older ingestion writers
while applying the upgrade.

The `1.0.0` → `1.0.1` upgrade assumes the complete `1.0.0` shape, including
required archive and patch byte sizes. Older pre-release schemas missing those
fields and populated v0 databases are separate migration cases; this Insights
upgrade does not infer missing artifact metadata. Keep a backup and reconcile
those schemas explicitly before applying it. Do not reset a complete `1.0.0`
database to upgrade Insights.

1. Remove `queries`, `getUpdateInfo`, provider decision SQL/RPCs, and any
   desired-state cache owned by the provider.
2. Keep Bundle rows as immutable artifacts, including required archive and
   patch byte sizes. Store rollout and compatibility policy on Releases.
3. Add Channel, Release, and Release-catalog storage, indexes, and references.
4. Implement exact catalog reads and strongly consistent, keyset-paged Release
   scope reads.
5. Extend the atomic commit with Release revision and catalog generation
   expectations.
6. Implement atomic Insights recording and the fixed queries above. Record
   `schema.core = 1.0.1` after fresh creation or a successful supported upgrade;
   reject unsupported source versions without deleting their data.
7. Run the public conformance and integration suites against the real backend.

Provider-specific consistency requirements:

- DynamoDB uses a strongly consistent base-table scope partition, not a GSI.
- Firestore uses strong server reads and transaction preconditions.
- PostgreSQL, Supabase, and SQL adapters use ordered primary reads and revision
  and generation predicates in the write transaction.
- MongoDB uses deterministic majority reads and a short write transaction.
- D1 must prove a failed generation predicate aborts the complete batch.

## Create a provider

```ts title="myDatabase.ts"
import {
  createDatabasePlugin,
  type DatabaseCommit,
  type DatabaseCommitResult,
} from "@hot-updater/plugin-core";

export const myDatabase = ({ db }: { db: MyDatabaseClient }) => {
  const commit = (input: DatabaseCommit): Promise<DatabaseCommitResult> =>
    db.transaction((transaction) =>
      applyConditionalChanges(transaction, input),
    );

  return createDatabasePlugin({
    name: "my-database",
    models: {
      bundles: createBundleModel(db),
      bundlePatches: createBundlePatchModel(db),
      releases: createReleaseModel(db),
      releaseCatalogs: createReleaseCatalogModel(db),
      channels: createChannelModel(db),
      insights: createInsightsModel(db),
      apiKeys: createApiKeyModel(db),
    },
    commit,
    dispose: () => db.close(),
  });
};
```

Keep SQL values parameterized and preserve the canonical snake-case row
fields. Database methods do not receive request context; close over the
configured client or runtime binding.

## Catalog transport caching

The database contract is independent of HTTP caching. If a custom deployment
places a shared cache in front of the server, its catalog cache key must include
the host, canonical path, `x-api-key`, and supported content encoding. It must
not include installation state. Invalid-key and error responses remain
`private, no-store`.

If custom authentication varies on any other header, map that identity to one
stable, documented catalog cache partition and include it in the cache key.
Do not enable shared caching for arbitrary request headers without an explicit
partition contract.

## Test the provider

```ts title="myDatabase.spec.ts"
import { createDatabaseClient } from "@hot-updater/plugin-core";
import {
  setupDatabaseClientTestSuite,
  setupDatabasePluginTestSuite,
} from "@hot-updater/test-utils";

const lifecycle = {
  name: "my database",
  createPlugin: () => myDatabase({ db }),
  migrate: () => migrateDatabase(db),
  reset: () => resetDatabase(db),
  dispose: (plugin: ReturnType<typeof myDatabase>) => plugin.dispose?.(),
};

setupDatabasePluginTestSuite(lifecycle);
setupDatabaseClientTestSuite({
  ...lifecycle,
  createClient: createDatabaseClient,
});
```

The suites verify exact model semantics, strong Release paging, catalog point
reads, Release/catalog CAS conflicts, all-model rollback, Channel safety,
Insights duplicate/identity/count/filter semantics, ordering, and the absence
of a public `queries` surface. Supplement these with native rollback, concurrent
transaction, index-continuation, migration, and query-plan evidence.

## Configure Hot Updater

Use the same provider in the CLI and self-hosted server:

```ts title="hot-updater.config.ts"
import { defineConfig } from "hot-updater";

export default defineConfig({
  database: myDatabase({ db }),
  // build: ...
  // storage: ...
});
```

```ts title="server.ts"
export const hotUpdater = createHotUpdater({
  database: myDatabase({ db }),
  clientAccess: { type: "api-key" },
  storage,
});
```

The CLI and server use the same database. Catalog identity is managed
automatically; there is no additional identifier to configure or synchronize.

## Standalone repositories

A Standalone management repository exposes Bundle, patch, Release, catalog,
and Channel models through the canonical server routes. It is not a complete
database plugin because the server owns Insights, API keys, compilation,
and the actual atomic transaction.

## SQL Server limitation

The Prisma SQL Server adapter retains its other models, but its five Insights
methods reject before database I/O. SQL Server's padded string equality can
merge IDs that differ by trailing spaces; its default Unicode/UUID ordering
also differs from this contract. There is no silent fallback to weaker identity
or pagination semantics. Use a supported Insights provider for these views.
