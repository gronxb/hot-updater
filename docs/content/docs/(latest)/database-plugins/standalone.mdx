## Overview

The `standaloneRepository` HTTP repository connects your Hot Updater CLI to a
self-hosted backend server. This is the **client-side configuration** for
connecting to your server.

<Callout type="info">
**Building a Self-Hosted Server?**

See the [Self-Hosting (Custom) Guide](/docs/custom/overview) for complete server implementation instructions using `@hot-updater/server` with database adapters (Drizzle, Prisma, Kysely, MongoDB) and frameworks (Hono, Express, Elysia).

</Callout>

## Installation

```package-install
npm install @hot-updater/standalone --save-dev
```

## Usage

Configure your CLI to connect to your self-hosted server:

```typescript title="hot-updater.config.ts (excerpt)"
import { standaloneRepository } from "@hot-updater/standalone"; // [!code ++]
import { defineConfig } from "hot-updater";

const adminToken = process.env.HOT_UPDATER_ADMIN_TOKEN;
if (!adminToken) {
  throw new Error("HOT_UPDATER_ADMIN_TOKEN is required");
}

export default defineConfig({
  build, // Your existing build plugin
  storage, // Your existing storage plugin
  database: standaloneRepository({ // [!code ++]
    baseUrl: "http://localhost:3000/hot-updater/admin", // [!code ++]
    commonHeaders: { // [!code ++]
      Authorization: `Bearer ${adminToken}`, // [!code ++]
    }, // [!code ++]
  }), // [!code ++]
  updateStrategy: "appVersion",
});
```

## Remote Storage Adapter

For CLI uploads through a separate HTTP storage service, use
[`standaloneStorage`](/docs/storage-plugins/standalone). Its configuration and
service contract belong to Storage Plugins; the repository below manages
database rows through the admin API.

## Configuration

The `standaloneRepository` HTTP repository accepts the following options:

```typescript
interface StandaloneRepositoryConfig {
  baseUrl: string; // Exact root where handlers.admin is mounted
  commonHeaders?: Record<string, string>; // Framework authentication headers
  routes?: Routes; // Optional custom route configuration
}
```

`routes` remaps only the five legacy-compatible Bundle CRUD/list requests.
Release, Release Catalog, database commit, and Channel requests use the fixed
canonical paths documented below:

```typescript
interface RouteConfig {
  path: string;
  headers?: Record<string, string>;
}

interface Routes {
  create?: () => RouteConfig;
  update?: (bundleId: string) => RouteConfig;
  list?: () => RouteConfig;
  retrieve?: (bundleId: string) => RouteConfig;
  delete?: (bundleId: string) => RouteConfig;
}
```

### Secure Example

```typescript title="hot-updater.config.ts"
const adminToken = process.env.HOT_UPDATER_ADMIN_TOKEN;
if (!adminToken) {
  throw new Error("HOT_UPDATER_ADMIN_TOKEN is required");
}

database: standaloneRepository({
  baseUrl: "http://localhost:3000/hot-updater/admin",
  commonHeaders: { // [!code ++]
    Authorization: `Bearer ${adminToken}`, // [!code ++]
  }, // [!code ++]
});
```

The admin handler does not authenticate requests itself. Keep its credential in
server-side CLI or Console configuration and match the framework middleware in
the server setup.

### Alternate Authentication

```typescript title="hot-updater.config.ts"
database: standaloneRepository({
  baseUrl: process.env.HOT_UPDATER_ADMIN_URL!,
  commonHeaders: {
    "X-Internal-Service-Key": process.env.INTERNAL_SERVICE_KEY!, // [!code ++]
  },
});
```

### With Custom Routes

```typescript title="hot-updater.config.ts"
const adminToken = process.env.HOT_UPDATER_ADMIN_TOKEN;
if (!adminToken) {
  throw new Error("HOT_UPDATER_ADMIN_TOKEN is required");
}

database: standaloneRepository({
  baseUrl: "https://api.example.com/hot-updater/admin",
  commonHeaders: {
    Authorization: `Bearer ${adminToken}`,
  },
  routes: { // [!code ++]
    create: () => ({ // [!code ++]
      path: "/v1/bundles", // [!code ++]
      headers: { "X-Custom-Header": "value" }, // [!code ++]
    }), // [!code ++]
    update: (bundleId) => ({ // [!code ++]
      path: `/v1/bundles/${bundleId}`, // [!code ++]
      headers: { "X-Custom-Header": "value" }, // [!code ++]
    }), // [!code ++]
    list: () => ({ // [!code ++]
      path: "/v1/bundles", // [!code ++]
    }), // [!code ++]
    retrieve: (bundleId) => ({ // [!code ++]
      path: `/v1/bundles/${bundleId}`, // [!code ++]
    }), // [!code ++]
    delete: (bundleId) => ({ // [!code ++]
      path: `/v1/bundles/${bundleId}`, // [!code ++]
    }), // [!code ++]
  }, // [!code ++]
});
```

## Server Contract

`standaloneRepository` is an HTTP client. If you are building a custom
backend, your server must implement the admin contract below. All paths in the
table are relative to `baseUrl`.

<Callout type="info">
  If you use `@hot-updater/server`, you do **not** need to implement these
  endpoints manually. `createHotUpdater()` provides this contract through
  `handlers.admin`, including the canonical `GET /channels` route.
</Callout>

### Contract Types

```typescript
interface PaginationInfo {
  total: number;
  hasNextPage: boolean;
  hasPreviousPage: boolean;
  currentPage: number;
  totalPages: number;
  nextCursor?: string | null;
  previousCursor?: string | null;
}

interface DataResponse<TData> {
  data: TData;
}

interface Paginated<TData> extends DataResponse<TData> {
  pagination: PaginationInfo;
}

type PaginatedResult = Paginated<Bundle[]>;
interface ChannelRow {
  id: string;
  name: string;
}
type ChannelsResponse = DataResponse<{ channels: ChannelRow[] }>;
```

### Default Routes

These are the routes used by `standaloneRepository`. The `routes` option can
remap only the five Bundle rows marked **remappable**. All other rows use fixed
paths relative to `baseUrl`.

| Method | Default route                 | Mapping    | Success response                     |
| ------ | ----------------------------- | ---------- | ------------------------------------ |
| POST   | `/bundles`                    | remappable | `{ "success": true }`                |
| PATCH  | `/bundles/:id`                | remappable | `{ "success": true }`                |
| GET    | `/bundles`                    | remappable | `Paginated<Bundle[]>`                |
| GET    | `/bundles/:id`                | remappable | `Bundle`                             |
| DELETE | `/bundles/:id`                | remappable | `{ "success": true }`                |
| GET    | `/releases/:id`               | fixed      | `DataResponse<ReleaseRow>`           |
| GET    | `/releases`                   | fixed      | `DataResponse<ReleaseRow[]>`         |
| GET    | `/release-catalogs/:scopeKey` | fixed      | `DataResponse<ReleaseCatalogRow>`    |
| GET    | `/release-catalogs`           | fixed      | `DataResponse<ReleaseCatalogRow[]>`  |
| POST   | `/database/commit`            | fixed      | `DataResponse<DatabaseCommitResult>` |
| GET    | `/channels`                   | fixed      | `ChannelsResponse`                   |
| POST   | `/channels`                   | fixed      | `DataResponse<ChannelInsertResult>`  |
| DELETE | `/channels/:id`               | fixed      | `204 No Content`                     |

### Bundle Shape

Create requests send full `Bundle` objects. Update requests send
`Partial<Bundle>` and, if an `id` is present in the body, it must match the
`:id` route parameter.

```typescript
interface BundlePatchArtifact {
  baseBundleId: string;
  baseFileHash: string;
  byteSize: number;
  patchFileHash: string;
  patchStorageUri: string;
}

interface Bundle {
  id: string;
  platform: "ios" | "android";
  fileHash: string;
  storageUri: string;
  archiveByteSize: number;
  gitCommitHash: string | null;
  metadata?: {
    app_version?: string;
  };
  manifestStorageUri?: string | null;
  manifestFileHash?: string | null;
  assetBaseStorageUri?: string | null;
  patches?: BundlePatchArtifact[] | null;
}
```

`archiveByteSize` and every patch `byteSize` are required non-negative safe
integers. Bundle objects contain immutable artifact data only; Channel,
rollout, targeting, enablement, force-update, and message policy belong to
Releases.

### List Bundles Contract

`GET /bundles` must accept the pagination and filter query params used by
the console and `standaloneRepository`, and return a paginated JSON body.

Cursor-based pagination is the official contract. `page` is an optional
positive integer for page-aligned requests and cannot be combined with
`after` or `before` in the same request.

Supported query params:

| Query param | Type                 | Notes                                                          |
| ----------- | -------------------- | -------------------------------------------------------------- |
| `platform`  | `"ios" \| "android"` | Exact match                                                    |
| `limit`     | `number`             | Window size                                                    |
| `page`      | `number`             | Optional positive page number for stable page-aligned requests |
| `after`     | `string`             | Fetch the next window after this bundle ID                     |
| `before`    | `string`             | Fetch the previous window before this bundle ID                |

Expected response:

```json
{
  "data": [
    {
      "id": "bundle-id",
      "platform": "ios",
      "fileHash": "bundle-file-hash",
      "storageUri": "s3://bucket/bundles/bundle-id/bundle.zip",
      "archiveByteSize": 1048576,
      "gitCommitHash": null,
      "patches": []
    }
  ],
  "pagination": {
    "total": 1,
    "hasNextPage": false,
    "hasPreviousPage": false,
    "currentPage": 1,
    "totalPages": 1,
    "nextCursor": null,
    "previousCursor": null
  }
}
```

`standaloneRepository` reads pagination metadata from the response body. It
does not derive pagination from headers. `currentPage` and `totalPages` are
kept for backwards compatibility; `nextCursor` and `previousCursor` are the
preferred navigation fields.

If your standalone server is backed by object storage or manifest files, keep
`GET /bundles` on an index-backed path once the index is warm. Cursor
pages should not require rescanning all manifests, and this should be covered
by deterministic read-counter regression tests.

### Retrieve And Channels Contract

- `GET /bundles/:id` should return `200` with a `Bundle` body or `404` if
  the bundle does not exist.
- `GET /channels` must return normalized Channel rows:

```json
{
  "data": {
    "channels": [
      { "id": "channel-production", "name": "production" },
      { "id": "channel-staging", "name": "staging" }
    ]
  }
}
```

- `POST /channels` must accept a concurrency-safe insert:

```json
{
  "row": { "id": "candidate-id", "name": "production" },
  "onConflict": "returnExisting"
}
```

It returns `{ "data": { "row": ChannelRow, "inserted": boolean } }`. When
the name already exists, `row` is the canonical stored row rather than the
caller's losing candidate.

- `DELETE /channels/:id` deletes an empty Channel and returns
  `204 No Content`. It returns `404` with reason `not_found` for a missing ID
  and `409` with reason `not_empty` when a Release still references the Channel.
  The reference check and deletion are atomic.

### Minimal `@hot-updater/server` Example

If you want this contract without implementing it yourself, use
`@hot-updater/server`:

```typescript
import { createHotUpdater } from "@hot-updater/server";

const hotUpdater = createHotUpdater({
  database,
  clientAccess: { type: "api-key" },
  storage: [storage],
});
```

Mount `hotUpdater.handlers.admin` at `/hot-updater/admin` to expose the Bundle,
Release, Release Catalog, database-commit, Channel, and Insights-query routes.
Protect that mount with framework middleware and configure matching
`commonHeaders` in `standaloneRepository`. Mounting the handler is the explicit
opt-in; there is no built-in admin authenticator.

`standaloneRepository` remains an admin HTTP client used only in
`hot-updater.config.ts`. Its Bundle-management boundary includes Bundles,
patches, Releases, Release Catalogs, Channels, and the conditional commit that
keeps those records consistent. It does not expose Insights or client
API key administration. The server-side `database` passed to
`createHotUpdater` owns those additional official domains. Insights is always
available, while the required `clientAccess` policy decides whether client
routes are public or require an API key.

<Callout type="warn">
  The Console cannot read Insights or manage API keys through
  `standaloneRepository`. Local/direct-provider Console access is unaffected. A
  hosted Console must protect its browser session separately and keep the admin
  bearer token in server-side `commonHeaders`. Do not put that token in browser
  or React Native code, and do not pass `standaloneRepository` to
  `createHotUpdater`.
</Callout>
