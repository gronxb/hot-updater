## Overview

The `standaloneRepository` HTTP repository connects your Hot Updater CLI to a
self-hosted backend server. This is the **client-side configuration** for
connecting to your server.

<Callout type="info">
**Building a Self-Hosted Server?**

See the [Self-Hosting (Custom) Guide](../custom/overview) for complete server implementation instructions using `@hot-updater/server` with database adapters (Drizzle, Prisma, Kysely, MongoDB) and frameworks (Hono, Express, Elysia).

</Callout>

## Installation

```package-install
npm install @hot-updater/standalone --save-dev
```

## Usage

Configure your CLI to connect to your self-hosted server:

```typescript title="hot-updater.config.ts (excerpt)"
import { standaloneRepository } from "@hot-updater/standalone";
import { defineConfig } from "hot-updater";

export default defineConfig({
  authorityId: "project-01",
  build: /* your build plugin */,
  storage: /* your storage plugin */,
  database: standaloneRepository({
    baseUrl: "http://localhost:3000/hot-updater",
  }),
  updateStrategy: "appVersion",
});
```

## Remote Storage Adapter

`standaloneStorage` is a CLI-side adapter for sending storage operations to a
remote HTTP service. `baseUrl` selects that HTTP transport, while `protocol`
selects the persisted Storage URI scheme owned by the adapter. They are
independent: an HTTPS service can, for example, own `s3://...` URIs.

```typescript title="hot-updater.config.ts"
import { bare } from "@hot-updater/bare";
import {
  standaloneRepository,
  standaloneStorage,
} from "@hot-updater/standalone";
import { defineConfig } from "hot-updater";

export default defineConfig({
  authorityId: "project-01",
  build: bare({ enableHermes: true }),
  database: standaloneRepository({
    baseUrl: "https://api.example.com/hot-updater",
  }),
  storage: standaloneStorage({
    baseUrl: "https://storage.example.com/hot-updater",
    protocol: "s3",
  }),
  updateStrategy: "appVersion",
});
```

The remote storage service must implement these separate routes:

| Method   | Default route | Request                             | Success response                         |
| -------- | ------------- | ----------------------------------- | ---------------------------------------- |
| `POST`   | `/upload`     | multipart `file` and `key` fields   | JSON `{ "storageUri": "s3://..." }`      |
| `POST`   | `/get`        | JSON `{ "storageUri": "s3://..." }` | Object bytes, or `404` when missing      |
| `POST`   | `/exists`     | JSON `{ "storageUri": "s3://..." }` | JSON `{ "exists": true }`                |
| `DELETE` | `/delete`     | JSON `{ "storageUri": "s3://..." }` | Any `2xx`, or `404` for an absent object |

`standaloneStorage` intentionally has no `getDownloadUrl` capability. It is
for CLI-to-service storage transport, not the runtime storage passed to
`createHotUpdater`. The built-in bundle routes mounted by `createHotUpdater`
do not implement `/upload`, `/get`, `/exists`, or `/delete`; your remote
storage service must provide them separately.

## Configuration

The `standaloneRepository` HTTP repository accepts the following options:

```typescript
interface StandaloneRepositoryConfig {
  baseUrl: string; // Your server URL
  commonHeaders?: Record<string, string>; // Optional headers (e.g., authentication)
  routes?: Routes; // Optional custom route configuration
}
```

`routes` remaps only the five legacy-compatible Bundle CRUD/list requests.
Release, Release Catalog, database commit, and Channel requests use the fixed
canonical paths documented below:

```typescript
interface RouteConfig {
  path: string;
  headers?: Record<string, string>;
}

interface Routes {
  create?: () => RouteConfig;
  update?: (bundleId: string) => RouteConfig;
  list?: () => RouteConfig;
  retrieve?: (bundleId: string) => RouteConfig;
  delete?: (bundleId: string) => RouteConfig;
}
```

### Basic Example

```typescript
database: standaloneRepository({
  baseUrl: "http://localhost:3000/hot-updater",
});
```

### With Authentication

```typescript
const managementToken = process.env.HOT_UPDATER_AUTH_TOKEN;
if (!managementToken) {
  throw new Error("HOT_UPDATER_AUTH_TOKEN is required");
}

database: standaloneRepository({
  baseUrl: process.env.HOT_UPDATER_SERVER_URL!,
  commonHeaders: {
    Authorization: `Bearer ${managementToken}`,
  },
});
```

### With Custom Routes

```typescript
database: standaloneRepository({
  baseUrl: "https://api.example.com",
  routes: {
    create: () => ({
      path: "/v1/hot-updater/api/bundles",
      headers: { "X-Custom-Header": "value" },
    }),
    update: (bundleId) => ({
      path: `/v1/hot-updater/api/bundles/${bundleId}`,
      headers: { "X-Custom-Header": "value" },
    }),
    list: () => ({
      path: "/v1/hot-updater/api/bundles",
    }),
    retrieve: (bundleId) => ({
      path: `/v1/hot-updater/api/bundles/${bundleId}`,
    }),
    delete: (bundleId) => ({
      path: `/v1/hot-updater/api/bundles/${bundleId}`,
    }),
  },
});
```

## Server Contract

`standaloneRepository` is an HTTP client. If you are building a custom
backend, your server must implement the management contract below.

<Callout type="info">
  If you use `@hot-updater/server`, you do **not** need to implement these
  endpoints manually. `createHotUpdater()` provides this contract when bundle
  routes are explicitly enabled, including the canonical `GET /api/channels`
  route.
</Callout>

### Contract Types

```typescript
interface PaginationInfo {
  total: number;
  hasNextPage: boolean;
  hasPreviousPage: boolean;
  currentPage: number;
  totalPages: number;
  nextCursor?: string | null;
  previousCursor?: string | null;
}

interface DataResponse<TData> {
  data: TData;
}

interface Paginated<TData> extends DataResponse<TData> {
  pagination: PaginationInfo;
}

type PaginatedResult = Paginated<Bundle[]>;
interface ChannelRow {
  id: string;
  name: string;
}
type ChannelsResponse = DataResponse<{ channels: ChannelRow[] }>;
type ChannelInsertResponse = DataResponse<{
  row: ChannelRow;
  inserted: boolean;
}>;
type ReleaseResponse = DataResponse<ReleaseRow>;
type ReleaseListResponse = DataResponse<ReleaseRow[]>;
type ReleaseCatalogResponse = DataResponse<ReleaseCatalogRow>;
type ReleaseCatalogListResponse = DataResponse<ReleaseCatalogRow[]>;
type CommitResponse = DataResponse<DatabaseCommitResult>;
```

### Default Routes

These are the routes used by `standaloneRepository`. The `routes` option can
remap only the five Bundle rows marked **remappable**. All other rows use fixed
paths relative to `baseUrl`.

| Method | Default route                     | Mapping    | Success response             |
| ------ | --------------------------------- | ---------- | ---------------------------- |
| POST   | `/api/bundles`                    | remappable | `{ "success": true }`        |
| PATCH  | `/api/bundles/:id`                | remappable | `{ "success": true }`        |
| GET    | `/api/bundles`                    | remappable | `Paginated<Bundle[]>`        |
| GET    | `/api/bundles/:id`                | remappable | `Bundle`                     |
| DELETE | `/api/bundles/:id`                | remappable | `{ "success": true }`        |
| GET    | `/api/releases/:id`               | fixed      | `ReleaseResponse`            |
| GET    | `/api/releases`                   | fixed      | `ReleaseListResponse`        |
| GET    | `/api/release-catalogs/:scopeKey` | fixed      | `ReleaseCatalogResponse`     |
| GET    | `/api/release-catalogs`           | fixed      | `ReleaseCatalogListResponse` |
| POST   | `/api/database/commit`            | fixed      | `CommitResponse`             |
| GET    | `/api/channels`                   | fixed      | `ChannelsResponse`           |
| POST   | `/api/channels`                   | fixed      | `ChannelInsertResponse`      |
| DELETE | `/api/channels/:id`               | fixed      | `204 No Content`             |

### Bundle Shape

Create requests send full `Bundle` objects. Update requests send
`Partial<Bundle>` and, if an `id` is present in the body, it must match the
`:id` route parameter.

```typescript
interface Bundle {
  id: string;
  platform: "ios" | "android";
  shouldForceUpdate: boolean;
  enabled: boolean;
  fileHash: string;
  storageUri: string;
  gitCommitHash: string | null;
  message: string | null;
  channel: string;
  targetAppVersion: string | null;
  fingerprintHash: string | null;
  metadata?: {
    app_version?: string;
  };
  rolloutCohortCount?: number | null;
  targetCohorts?: string[] | null;
}
```

### List Bundles Contract

`GET /api/bundles` must accept the pagination and filter query params used by
the console and `standaloneRepository`, and return a paginated JSON body.

Cursor-based pagination is the official contract. `page` is an optional
positive integer used alongside cursors when the caller needs stable page
numbers.

Supported query params:

| Query param | Type                 | Notes                                                          |
| ----------- | -------------------- | -------------------------------------------------------------- |
| `platform`  | `"ios" \| "android"` | Exact match                                                    |
| `idEq`      | `string`             | Bundle ID equals                                               |
| `idGt`      | `string`             | Bundle ID greater than                                         |
| `idGte`     | `string`             | Bundle ID greater than or equal                                |
| `idLt`      | `string`             | Bundle ID less than                                            |
| `idLte`     | `string`             | Bundle ID less than or equal                                   |
| `idIn`      | repeated `string`    | Append once for each accepted Bundle ID                        |
| `limit`     | `number`             | Window size                                                    |
| `page`      | `number`             | Optional positive page number for stable page-aligned requests |
| `after`     | `string`             | Fetch the next window after this bundle ID                     |
| `before`    | `string`             | Fetch the previous window before this bundle ID                |

Expected response:

```json
{
  "data": [{ "id": "bundle-id", "channel": "production" }],
  "pagination": {
    "total": 1,
    "hasNextPage": false,
    "hasPreviousPage": false,
    "currentPage": 1,
    "totalPages": 1,
    "nextCursor": null,
    "previousCursor": null
  }
}
```

`standaloneRepository` reads pagination metadata from the response body. It
does not derive pagination from headers. `currentPage` and `totalPages` are
kept for backwards compatibility; `nextCursor` and `previousCursor` are the
preferred navigation fields.

If your standalone server is backed by object storage or manifest files, keep
`GET /api/bundles` on an index-backed path once the index is warm. Cursor
pages should not require rescanning all manifests, and this should be covered
by deterministic read-counter regression tests.

### Release, Catalog, and Commit Contract

These routes are mandatory for the v1 repository and are not configurable
through `routes`. Every successful read response uses the `{ "data": ... }`
wrapper.

`GET /api/releases/:id` returns `{ "data": ReleaseRow }`, or `404` when the
Release does not exist. `GET /api/releases` has two query modes:

| Query param        | Type                 | Management list | Scope scan | Notes                                    |
| ------------------ | -------------------- | --------------- | ---------- | ---------------------------------------- |
| `limit`            | `number`             | yes             | yes        | Integer from 1 through 1000              |
| `afterReleaseId`   | `string`             | optional        | optional   | Exclusive forward cursor                 |
| `beforeReleaseId`  | `string`             | optional        | ignored    | Exclusive backward cursor                |
| `bundleId`         | `string`             | optional        | ignored    | Exact Bundle ID                          |
| `channelId`        | `string`             | optional        | ignored    | Exact Channel ID                         |
| `enabled`          | `"true" \| "false"`  | optional        | ignored    | Any other value is rejected              |
| `platform`         | `"ios" \| "android"` | optional        | ignored    | Any other value is rejected              |
| `targetAppVersion` | `string`             | optional        | ignored    | Exact target app-version expression      |
| `scopeKey`         | `string`             | absent          | required   | A nonempty value selects the strong scan |

Without `scopeKey`, the response is the newest-first management result
`{ "data": ReleaseRow[] }`. With `scopeKey`, the server performs the strongly
consistent ascending compiler scan and uses only `scopeKey`, `limit`, and the
optional `afterReleaseId` cursor.

`GET /api/release-catalogs/:scopeKey` returns
`{ "data": ReleaseCatalogRow }`, or `404` when the catalog does not exist. The
client percent-encodes both Release IDs and scope keys when it builds these
item URLs.

`GET /api/release-catalogs` accepts a required positive `limit` up to 1000 and
an optional exclusive `afterScopeKey` cursor. It returns
`{ "data": ReleaseCatalogRow[] }` in ascending scope-key order.

`POST /api/database/commit` receives the exported `DatabaseCommit` envelope as
its JSON body and returns `{ "data": DatabaseCommitResult }`. The commit and
conflict shapes are defined in the
[Release Catalog database contract](./release-catalog-contract#declarative-conditional-commit).

### Retrieve And Channels Contract

- `GET /api/bundles/:id` should return `200` with a `Bundle` body or `404` if
  the bundle does not exist.
- `GET /api/channels` must return normalized Channel rows:

```json
{
  "data": {
    "channels": [
      { "id": "channel-production", "name": "production" },
      { "id": "channel-staging", "name": "staging" }
    ]
  }
}
```

- `POST /api/channels` must accept a concurrency-safe insert:

```json
{
  "row": { "id": "candidate-id", "name": "production" },
  "onConflict": "returnExisting"
}
```

It returns `{ "data": { "row": ChannelRow, "inserted": boolean } }`. When
the name already exists, `row` is the canonical stored row rather than the
caller's losing candidate.

- `DELETE /api/channels/:id` deletes an empty Channel and returns
  `204 No Content`. It returns `404` with reason `not_found` for a missing ID
  and `409` with reason `not_empty` when a Release still references the Channel.
  The reference check and deletion are atomic.

### Minimal `@hot-updater/server` Example

If you want this contract without implementing it yourself, use
`@hot-updater/server`:

```typescript
import { createHotUpdater } from "@hot-updater/server";

const hotUpdater = createHotUpdater({
  authorityId: "project-01",
  database,
  storage: [storage],
  basePath: "/hot-updater",
  features: {
    updateCheck: true,
    bundles: true,
    analytics: true,
    clientAccessKeys: true,
  },
});
```

This mounts the Bundle, Release, Release Catalog, database-commit, and Channel
routes consumed by `standaloneRepository` under `/hot-updater/api/*`.
`features.bundles: true` is the explicit opt-in for this management contract;
protect it at the framework or reverse proxy layer, and configure matching
`commonHeaders` in `standaloneRepository`.

`standaloneRepository` remains a management HTTP client used only in
`hot-updater.config.ts`. Its Bundle-management boundary includes Bundles,
patches, Releases, Release Catalogs, Channels, and the conditional commit that
keeps those records consistent. It does not expose Analytics or client
access-key administration. The server-side `database` passed to
`createHotUpdater` owns those additional official domains, and `features`
decides whether the self-host runtime exposes them.

<Callout type="warn">
  The Console cannot read Analytics or manage client access keys through
  `standaloneRepository`. Run Console or another protected management surface
  with direct access to those server-side database domains. Do not pass
  `standaloneRepository` to `createHotUpdater`.
</Callout>
