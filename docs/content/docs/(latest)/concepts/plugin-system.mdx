## Plugin kinds

Every part of Hot Updater that talks to a bundler, a cloud service, or a
database is a plugin. A plugin is a plain object that a factory function
returns, such as `s3Storage(options)`. Official plugins and the ones you write
use the same contracts, and there is no registry: install the package and pass
the object to the CLI's `hot-updater.config.ts`, the server's
`createHotUpdater`, or the app's `HotUpdater.init`.

| Kind                                   | What it does                                                                        | Runs in                        | Official plugins                                                                    | Write one                                                          |
| -------------------------------------- | ----------------------------------------------------------------------------------- | ------------------------------ | ----------------------------------------------------------------------------------- | ------------------------------------------------------------------ |
| [Build](#build-plugin)                 | Bundles the app's JavaScript for `hot-updater deploy`                               | CLI                            | [Bare](/docs/build-plugins/bare), [Expo](/docs/build-plugins/expo), [Rock](/docs/build-plugins/rock) | `BuildPlugin` from `@hot-updater/plugin-core`                      |
| [Signing](#bundle-signing)             | Signs artifact hashes during deploy                                                 | CLI                            | Local PEM, remote, AWS KMS, Google Cloud KMS                                        | `BundleSigningPlugin` from `@hot-updater/plugin-core`              |
| [Storage](#storage-plugin)             | Stores bundle artifacts and resolves their download URLs                            | CLI, Console, server           | Supabase, Cloudflare R2, AWS S3, Firebase, Standalone                               | [Create a storage plugin](/docs/storage-plugins/custom-storage)    |
| [Database](#database-plugin)           | Stores Bundles, Releases, Release Catalogs, Channels, and server plugins' tables    | CLI, Console, server           | Supabase, Cloudflare D1, DynamoDB, Firestore, Kysely, Drizzle, Prisma, MongoDB | [Create a database plugin](/docs/database-plugins/custom-database) |
| [Integration](#integration-plugins)    | Uploads source maps for the bundles a build plugin makes                            | CLI                            | [Sentry](/docs/integration-plugins/sentry), [Datadog](/docs/integration-plugins/datadog), [BugSnag](/docs/integration-plugins/bugsnag) | A function that wraps a build plugin                               |
| [Server](#server-plugins)              | Adds tables, APIs, routes, CLI commands, and client authentication to the update server | Server; the CLI creates tables | [`insights()`](/docs/guides/insights), [`apiKeys()`](/docs/custom/api-key-authentication) | [Create a server plugin](/docs/custom/server-plugins)              |
| [Client](#client-plugins)              | Observes launches, update checks, downloads, and failures in the app, and calls the server | React Native app               | [Insights](/docs/react-native-api/insights)                                         | [Create a client plugin](/docs/react-native-api/client-plugins)    |

The managed Cloudflare, Supabase, AWS, and Firebase servers are prebuilt with
their provider's storage, database, and server plugins. Other plugins of those
kinds run on a [custom server](/docs/custom/overview). Client plugins run in
any app.

A feature can ship both halves, as Insights does: a server plugin that stores
data and serves routes, and a client plugin that calls those routes with the
app's base URL and headers. The server plugin names its client plugin in
[`cli.clientPlugin`](/docs/custom/server-plugins#name-the-apps-client-plugin),
which managed init and the agent scaffold use to add it to the app's
`HotUpdater.init`.

## Write your own plugin

Pick the contract for the kind of plugin and write a factory that returns it.
Each guide builds one and tests it:

| Kind     | Contract                                                                          | Guide                                                              |
| -------- | --------------------------------------------------------------------------------- | ------------------------------------------------------------------ |
| Storage  | `createStoragePlugin` from `@hot-updater/plugin-core`                             | [Create a storage plugin](/docs/storage-plugins/custom-storage)    |
| Database | `createSqlAdapter`, `createKvAdapter`, or a `DatabaseAdapter`, wrapped by `createEngineDatabase` from `@hot-updater/server/database` | [Create a database plugin](/docs/database-plugins/custom-database) |
| Server   | `definePlugin` from `@hot-updater/server/plugins`                                 | [Create a server plugin](/docs/custom/server-plugins)              |
| Client   | `defineClientPlugin` from `@hot-updater/react-native`                             | [Create a client plugin](/docs/react-native-api/client-plugins)    |
| Signing  | `BundleSigningPlugin` from `@hot-updater/plugin-core`: `getPublicKey` and `sign`  | [Remote Signing](/docs/guides/signing/remote) describes the service protocol |
| Build    | A function from `{ cwd }` to a `BuildPlugin` from `@hot-updater/plugin-core`      | The [official build plugins](https://github.com/gronxb/hot-updater/tree/next/plugins) are the reference |

Then package it for npm with Hot Updater as a peer dependency; see
[Test and publish a plugin](/docs/plugins/publish).

## Community plugins

Community plugins are npm packages that use the contracts above. Search npm
for the `hot-updater-plugin` keyword to find them. Hot Updater does not review
or maintain them: read a plugin's source and its tested Hot Updater versions
before you install it. To list yours here, open a pull request in the
[Hot Updater repository](https://github.com/gronxb/hot-updater).

## Build plugin

Build plugins generate JavaScript bundles when you run `hot-updater deploy`.

### Supported plugins

- `@hot-updater/bare`: Runs the project's configured bundler through the
  React Native CLI `bundle` command.
- `@hot-updater/rock`: Runs the project's configured bundler through the
  [Rock CLI](https://github.com/callstack/rock) `bundle` command.
- `@hot-updater/expo`: Executes the bundle command through Expo.

## Bundle signing

Signing plugins authenticate immutable OTA artifact content during
`hot-updater deploy`. They resolve the provider public key and sign the 32 raw
bytes decoded from each SHA-256 artifact hash. The deploy command verifies
every returned RSA-SHA256 signature before upload and checks that the signer
identity matches the native app trust anchor.

Signing is independent of the storage and database plugins. Omit `signing` or
set local `enabled: false` for unsigned deployments; Hot Updater never falls
back from an enabled signer to an unsigned deployment.

### Supported options

- Built-in local signing: Use `enabled: true` and `privateKeyPath`. Signing
  is never enabled automatically.
- `hot-updater/signing`: Use a compatible signing endpoint with
  `remoteSigning`, or hardened managed-key custody with `awsKmsSigning` and
  `googleCloudKmsSigning`.

Expo projects configure the native trust anchor independently through the
`@hot-updater/expo` app plugin's `publicKeyPath`. This keeps EAS builds outside
the private-key and KMS credential boundary.

The cloud KMS SDKs are optional peer dependencies and load only when their
signer is used for deployment.

See [Bundle Signing](/docs/guides/bundle-signing) for custody differences,
provider setup, native trust-anchor rollout, and rotation guidance.

## Storage plugin

Storage plugins upload generated bundles to your chosen provider during
`hot-updater deploy`, and the server resolves the URLs devices download them
from.

Storage plugins expose one flat, runtime-independent byte contract. CLI and
server consumers validate only the operations they need. Provider packages can
export the same plugin name from runtime-specific subpaths; for example,
`@hot-updater/cloudflare` uses S3-compatible credentials while
`@hot-updater/cloudflare/worker` captures an R2 binding.

### Supported plugins

- `@hot-updater/supabase`: Stores bundles in Supabase with `supabaseStorage`.
- `@hot-updater/cloudflare`: Provides deploy-time `r2Storage` and Worker runtime storage for Cloudflare R2.
- `@hot-updater/aws`: Stores bundles in AWS S3 with `s3Storage`.
- `@hot-updater/firebase`: Stores bundles in Firebase Storage with `firebaseStorage`.
- `@hot-updater/standalone`: Sends storage operations to your own HTTP service
  with `standaloneStorage`.

To write one, see [Create a storage plugin](/docs/storage-plugins/custom-storage).

## Database plugin

Database plugins persist immutable artifact metadata, Release policy, compiled
Catalogs and Channels, and the tables of the server plugins a server runs,
such as Insights and API keys. Deploy and administrative operations commit
changes atomically. The server uses the same provider for Catalog reads,
artifact resolution and its plugins; the device selects an update from the
returned Catalog.

Core and server plugins declare their tables and run their reads and
transactions on one storage engine, so a database plugin supplies only a
storage adapter for its backend.

### Supported plugins

- `@hot-updater/supabase`: Stores metadata in Supabase with `supabaseDatabase`.
- `@hot-updater/aws`: Provides `dynamoDB` for metadata.
- `@hot-updater/cloudflare`: Stores metadata in Cloudflare D1 with `d1Database`.
- `@hot-updater/firebase`: Stores update metadata in Firebase Firestore with `firebaseDatabase`.
- `@hot-updater/standalone`: Reaches a self-hosted server's database through
  its admin API with `standaloneRepository`.
- The [custom-server adapters](/docs/custom/overview#database-adapters) for
  Kysely, Drizzle, Prisma, and MongoDB connect an existing database.

To run on another backend, see
[Create a database plugin](/docs/database-plugins/custom-database).

## Integration plugins

Integration plugins connect bundle builds to error-monitoring services. They
compose with your selected build plugin to upload source maps and associate
them with the deployed update. The app's monitoring SDK must use matching
identifiers for readable stack traces.

- [Sentry](/docs/integration-plugins/sentry): `withSentry`.
- [Datadog](/docs/integration-plugins/datadog): `withDatadog`.
- [BugSnag](/docs/integration-plugins/bugsnag): `withBugsnag`.

Each guide covers service credentials, build configuration and symbolication
verification. These integrations can be used with any hosting, storage and
database choice supported by the selected build workflow.

## Server plugins

Server plugins extend the update server rather than the CLI. They run inside
`createHotUpdater`, own tables and aggregates on the server's database, and add
APIs, routes and client authentication. Core has none of their tables or
routes: a server has Insights only when it runs the `insights()` plugin, which
records Insights reports, and `apiKeys()` protects client routes. Managed
providers run both. To write one for a custom server, see
[Server Plugins](/docs/custom/server-plugins).

## Client plugins

Client plugins run in the React Native app. They observe launches, update
checks, downloads, and update failures, and can send requests to the update
server with the app's base URL and headers. Pass them to `plugins` in
`HotUpdater.init` or `HotUpdater.wrap`. The built-in
[Insights plugin](/docs/react-native-api/insights) reports to the server's
`insights()` plugin. To write one, see
[Client Plugins](/docs/react-native-api/client-plugins).
