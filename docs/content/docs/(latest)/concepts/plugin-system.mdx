## Build Plugin

Build plugins handle the bundling process when you run the `hot-updater deploy` command. They generate the JavaScript bundles for your updates.

### Supported Plugins

- **`@hot-updater/bare`**: Runs the project's configured bundler through the
  React Native CLI `bundle` command.
- **`@hot-updater/rock`**: Runs the project's configured bundler through the
  [Rock CLI](https://github.com/callstack/rock) `bundle` command.
- **`@hot-updater/expo`**: Executes the bundle command through Expo.

## Bundle Signing

Signing plugins authenticate immutable OTA artifact content during
`hot-updater deploy`. They resolve the provider public key and sign the 32 raw
bytes decoded from each SHA-256 artifact hash. The deploy command verifies
every returned RSA-SHA256 signature before upload and checks that the signer
identity matches the native app trust anchor.

Signing is independent of the storage and database plugins. Omit `signing` or
set local `enabled: false` for unsigned deployments; Hot Updater never falls
back from an enabled signer to an unsigned deployment.

### Supported Options

- **Built-in local signing**: Use `enabled: true` and `privateKeyPath`. Signing
  is never enabled automatically.
- **`hot-updater/signing`**: Use a compatible signing endpoint with
  `remoteSigning`, or hardened managed-key custody with `awsKmsSigning` and
  `googleCloudKmsSigning`.

Expo projects configure the native trust anchor independently through the
`@hot-updater/expo` app plugin's `publicKeyPath`. This keeps EAS builds outside
the private-key and KMS credential boundary.

The cloud KMS SDKs are optional peer dependencies and load only when their
signer is used for deployment.

See [Bundle Signing](/docs/guides/bundle-signing) for custody differences,
provider setup, native trust-anchor rollout, and rotation guidance.

## Storage Plugin

Storage plugins upload your generated bundles during the `hot-updater deploy` command and store them in your chosen storage provider.

Storage plugins expose one flat, runtime-independent byte contract. CLI and
server consumers validate only the operations they need. Provider packages can
export the same plugin name from runtime-specific subpaths; for example,
`@hot-updater/cloudflare` uses S3-compatible credentials while
`@hot-updater/cloudflare/worker` captures an R2 binding.

### Supported Plugins

- **`@hot-updater/supabase`**: Provides `supabaseStorage` functionality, leveraging Supabase for storage.
- **`@hot-updater/cloudflare`**: Provides deploy-time `r2Storage` and Worker runtime storage for Cloudflare R2.
- **`@hot-updater/aws`**: Provides `s3Storage` functionality, enabling the use of AWS S3 for storage.
- **`@hot-updater/firebase`**: Provides `firebaseStorage` functionality, utilizing Firebase Storage for storing update bundles.

## Database Plugin

Database plugins store bundle metadata that your app uses to check for updates. They run during the `hot-updater deploy` command.

### Supported Plugins

- **`@hot-updater/supabase`**: Provides `supabaseDatabase` functionality, using Supabase as a database solution.
- **`@hot-updater/aws`**: Provides `dynamoDB` for metadata.
- **`@hot-updater/cloudflare`**: Provides `d1Database` functionality, leveraging Cloudflare D1 for database storage.
- **`@hot-updater/firebase`**: Provides `firebaseDatabase` functionality, using Firebase Firestore for storing update metadata.
