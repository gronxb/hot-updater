## Adapters and plugins

Hot Updater talks to bundlers, cloud services, and databases through two kinds
of objects:

- An **adapter** fills one slot of a configuration: the `database` and
  `storage` of the server's `createHotUpdater`, or the `build` and `signing` of
  `hot-updater.config.ts`. A configuration has one adapter per slot; `storage`
  takes a list so the server can read Bundles that different adapters stored.
- A **plugin** is one entry of a list: the `plugins` of `createHotUpdater` or of
  the app's `HotUpdater.init`, or an integration that wraps a build adapter. A
  configuration can have any number.

Both are plain objects that a factory function returns, such as
`s3Storage(options)` or `insights()`. Official adapters and plugins use the
same contracts as the ones you write, and there is no registry: install the
package and pass the object in.

Plugins are configured in exactly two places:

- The **server definition**, a module that exports
  `hotUpdater = createHotUpdater({ database, storage, plugins })`, for server
  plugins, beside the server's database and storage adapters. The server, the
  CLI, the Console, and managed init all read it.
- The app's **`HotUpdater.init({ plugins })`**, for client plugins.

`hot-updater.config.ts` holds the deploy settings, with the build and signing
adapters, and points at the server definition with
[`server`](/docs/custom/cli-configuration). A CLI or Console that reaches a
self-hosted server through `standaloneRepository` reads the server's plugins
from its admin API, and lists the server's storage adapters again for its own
uploads and reads.

Some setups need a second definition: a Console deployed apart from the server,
or a Cloudflare Worker server, whose CLI loads a Node definition. Keep the
second one a copy: import the same plugins from one shared module, or copy the
server's definition unchanged. Change plugins only in the server's own
definition, and update the copy with it.

A managed Cloudflare, Supabase, AWS, or Firebase server runs on its provider's
storage and database adapters, and runs the server plugins its definition
lists: Insights and API keys by default, or the ones you
[choose](/docs/managed/server-plugins). Other storage and database adapters run
on a [custom server](/docs/custom/overview). Client plugins run in any app.

A feature can ship both halves, as Insights does: a server plugin that stores
data and serves routes, and a client plugin that calls those routes with the
app's base URL and headers. The server plugin names its client plugin in
[`cli.clientPlugin`](/docs/custom/server-plugins#name-the-apps-client-plugin),
which managed init and the agent scaffold use to add it to the app's
`HotUpdater.init`.

## Write your own

Pick the contract for the slot or the list, and write a factory that returns
it. Each guide builds one and tests it:

| Kind             | Contract                                                                          | Guide                                                               |
| ---------------- | --------------------------------------------------------------------------------- | ------------------------------------------------------------------- |
| Storage adapter  | `createStorageAdapter` from `@hot-updater/plugin-core`                            | [Create a storage adapter](/docs/storage-adapters/custom-storage)   |
| Database adapter | `createSqlAdapter`, `createKvAdapter`, or a `DatabaseAdapter`, wrapped by `createEngineDatabase` from `@hot-updater/plugin-core` | [Create a database adapter](/docs/database-adapters/custom-database) |
| Server plugin    | `definePlugin` from `@hot-updater/plugin-core`                                    | [Create a server plugin](/docs/custom/server-plugins)               |
| Client plugin    | `defineClientPlugin` from `@hot-updater/protocol`                                 | [Create a client plugin](/docs/react-native-api/client-plugins)     |
| Signing adapter  | `BundleSigningAdapter` from `@hot-updater/plugin-core`: `getPublicKey` and `sign` | [Remote Signing](/docs/guides/signing/remote) describes the service protocol |
| Build adapter    | A function from `{ cwd }` to a `BuildAdapter` from `@hot-updater/plugin-core`     | The [official build adapters](https://github.com/gronxb/hot-updater/tree/next/plugins) are the reference |

Hot Updater's packages divide by where their code runs:

| Package                     | What it holds                                                                                                                                                                                                                                     | Imported by                                              |
| --------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------- |
| `@hot-updater/protocol`     | The device-safe, zero-dependency package for what crosses a boundary: the data formats and pure computations the app and the server share, and the contracts between a host and its extensions on the device, such as the client plugin contract. | The app, the server, the CLI, and client plugins         |
| `@hot-updater/plugin-core`  | The kit that extends the server: the adapter and server plugin contracts and their helpers, and the storage engine they run on. It runs wherever the server runs, and depends on `@hot-updater/protocol`.                                       | Adapters and server plugins, including Hot Updater's own |
| `@hot-updater/server`       | The runtime host: `createHotUpdater` and its handlers, with the built-in adapters and plugins it re-exports.                                                                                                                                      | The server definition                                    |
| `@hot-updater/react-native` | The app's SDK. It imports `@hot-updater/protocol` and the built-in Insights client, never `@hot-updater/plugin-core` or the server.                                                                                                               | The app                                                  |

An adapter or a server plugin you write imports `@hot-updater/plugin-core`, and
a client plugin imports `@hot-updater/protocol`, as Hot Updater's own plugin
packages do. A database adapter builds on the engine kit there too.
`@hot-updater/react-native` re-exports the client plugin names for app code.

Each package's API is its root. A subpath only sets apart a part some projects
leave out: `@hot-updater/server/adapters/*` holds the Kysely, Drizzle, Prisma
and MongoDB adapters, `@hot-updater/server/plugins/*` the built-in plugins, and
an official plugin package has one entry per side. No package has an internal
entry, and a package uses another only through that package's API. Test
helpers live in `@hot-updater/test-utils` alone.

Then package it for npm with Hot Updater as a peer dependency; see
[Test and publish](/docs/plugins/publish).

## Community adapters and plugins

Community adapters and plugins are npm packages that use the contracts above.
Search npm for the `hot-updater-adapter` and `hot-updater-plugin` keywords to
find them. Hot Updater does not review or maintain them: read a package's
source and its tested Hot Updater versions before you install it. To list
yours here, open a pull request in the
[Hot Updater repository](https://github.com/gronxb/hot-updater).

## Build adapter

Build adapters generate JavaScript bundles when you run `hot-updater deploy`.

- `@hot-updater/bare`: Runs the project's configured bundler through the
  React Native CLI `bundle` command.
- `@hot-updater/rock`: Runs the project's configured bundler through the
  [Rock CLI](https://github.com/callstack/rock) `bundle` command.
- `@hot-updater/expo`: Executes the bundle command through Expo.

## Storage adapter

Storage adapters upload generated bundles to your chosen provider during
`hot-updater deploy`, and the server resolves the URLs devices download them
from.

Storage adapters expose one flat, runtime-independent byte contract. CLI and
server consumers validate only the operations they need. Provider packages can
export the same adapter name from runtime-specific subpaths; for example,
`@hot-updater/cloudflare` uses S3-compatible credentials while
`@hot-updater/cloudflare/worker` captures an R2 binding.

- `@hot-updater/supabase`: Stores bundles in Supabase with `supabaseStorage`.
- `@hot-updater/cloudflare`: Provides deploy-time `r2Storage` and Worker runtime storage for Cloudflare R2.
- `@hot-updater/aws`: Stores bundles in AWS S3 with `s3Storage`.
- `@hot-updater/firebase`: Stores bundles in Firebase Storage with `firebaseStorage`.
- `@hot-updater/standalone`: Sends storage operations to your own HTTP service
  with `standaloneStorage`.

To write one, see [Create a storage adapter](/docs/storage-adapters/custom-storage).

## Database adapter

Database adapters persist immutable artifact metadata, Release policy,
compiled Catalogs and Channels, and the tables of the server plugins a server
runs, such as Insights and API keys. Deploy and administrative operations
commit changes atomically. The server uses the same database for Catalog
reads, artifact resolution and its plugins; the device selects an update from
the returned Catalog.

Core and server plugins declare their tables and run their reads and
transactions on one storage engine, so a database adapter only stores rows and
reads index ranges on its backend.

- `@hot-updater/supabase`: Stores metadata in Supabase with `supabaseDatabase`.
- `@hot-updater/aws`: Provides `dynamoDB` for metadata.
- `@hot-updater/cloudflare`: Stores metadata in Cloudflare D1 with `d1Database`.
- `@hot-updater/firebase`: Stores update metadata in Firebase Firestore with `firebaseDatabase`.
- `@hot-updater/standalone`: `standaloneRepository` reaches a self-hosted
  server's database through its admin API, as the `server` of
  `hot-updater.config.ts` or of the Console's configuration.
- [Kysely](/docs/custom/database/kysely), [Drizzle](/docs/custom/database/drizzle),
  [Prisma](/docs/custom/database/prisma), and
  [MongoDB](/docs/custom/database/mongodb) connect an existing database to a
  custom server.

To run on another backend, see
[Create a database adapter](/docs/database-adapters/custom-database).

## Signing adapter

Signing adapters authenticate immutable OTA artifact content during
`hot-updater deploy`. They resolve the provider public key and sign the 32 raw
bytes decoded from each SHA-256 artifact hash. The deploy command verifies
every returned RSA-SHA256 signature before upload and checks that the signer
identity matches the native app trust anchor.

Signing is independent of the storage and database adapters. Omit `signing` or
set local `enabled: false` for unsigned deployments; Hot Updater never falls
back from an enabled signer to an unsigned deployment.

- Built-in local signing: Use `enabled: true` and `privateKeyPath`. Signing
  is never enabled automatically.
- `hot-updater/signing`: Use a compatible signing endpoint with
  `remoteSigning`, or hardened managed-key custody with `awsKmsSigning` and
  `googleCloudKmsSigning`.

Expo projects configure the native trust anchor independently through the
`@hot-updater/expo` app plugin's `publicKeyPath`. This keeps EAS builds outside
the private-key and KMS credential boundary.

The cloud KMS SDKs are optional peer dependencies and load only when their
signer is used for deployment.

See [Bundle Signing](/docs/guides/bundle-signing) for custody differences,
provider setup, native trust-anchor rollout, and rotation guidance.

## Integration plugins

Integration plugins connect bundle builds to error-monitoring services. They
wrap your selected build adapter to upload source maps and associate them with
the deployed update. The app's monitoring SDK must use matching identifiers
for readable stack traces.

- [Sentry](/docs/integration-plugins/sentry): `withSentry`.
- [Datadog](/docs/integration-plugins/datadog): `withDatadog`.
- [BugSnag](/docs/integration-plugins/bugsnag): `withBugsnag`.

Each guide covers service credentials, build configuration and symbolication
verification. These integrations can be used with any hosting, storage and
database choice supported by the selected build workflow.

## Server plugins

Server plugins extend the update server rather than the CLI. They run inside
`createHotUpdater`, own tables and aggregates on the server's database, and add
APIs, routes and client authentication. Core has none of their tables or routes:
a server has Insights only when it runs the `insights()` plugin, which records
Insights reports, and `apiKeys()` protects client routes. Managed providers run
both unless the project
[drops them](/docs/managed/server-plugins#drop-insights-or-api-keys). To write
one, see [Create a server plugin](/docs/custom/server-plugins).

Hot Updater's own plugins are packages built the same way:
`@hot-updater/plugin-insights` and `@hot-updater/plugin-api-keys`.
`@hot-updater/server/plugins/insights` and `@hot-updater/server/plugins/api-keys`
re-export them, so a server installs nothing more. Each package has an entry
per side, the layout a plugin you publish follows; see
[Ship both sides from one package](/docs/plugins/publish#ship-both-sides-from-one-package).

The Console has built-in screens for these official features, and shows each
one only when the server runs its plugin. It has no UI extension API: a plugin
extends the server, the CLI, and the app, and its data reaches people through
its API, its routes, and its commands.

## Client plugins

Client plugins run in the React Native app. They observe launches, update
checks, downloads, and update failures, and can send requests to the update
server with the app's base URL and headers. Pass them to `plugins` in
`HotUpdater.init` or `HotUpdater.wrap`. The
[Insights plugin](/docs/react-native-api/insights) reports to the server's
`insights()` plugin; it is `@hot-updater/plugin-insights/client`, which
`@hot-updater/react-native` exports from its root. To write one, see
[Create a client plugin](/docs/react-native-api/client-plugins).
