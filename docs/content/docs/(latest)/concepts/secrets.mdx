## This machine or the team

The config's `secrets` adapter decides who shares the credentials:

|                  | `localSecrets()`, the default                                           | A team store                                                                                                                                                                                                                                                                                              |
| ---------------- | ----------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Adapters         | [`localSecrets()`](/docs/guides/secrets-adapters/local-secrets)         | [1Password](/docs/guides/secrets-adapters/1password), [Infisical](/docs/guides/secrets-adapters/infisical), AWS [`secretsManager()`](/docs/guides/secrets-adapters/aws-secrets-manager), Google Cloud [`secretManager()`](/docs/guides/secrets-adapters/google-secret-manager), or an adapter of your own |
| Who has the keys | This machine only                                                       | Everyone with the config and access to the store, and CI                                                                                                                                                                                                                                                  |
| A teammate       | Signs in and issues their own keys, or imports yours with `secrets put` | Runs `apple login` or `google-play login`, finds the keys already stored, and builds, uploads, and deploys with them                                                                                                                                                                                      |

A team store shares every credential the CLI reads by `secret:` name: the
App Store Connect API key, the Play service account, the Android upload
keystore, and, with
[local PEM signing](#sign-bundles-with-a-key-from-secrets), the bundle
signing key. It also shares the deploy credentials the config reads with
[`secretEnv`](#deploy-credentials-with-secretenv), such as a Cloudflare API
token or R2 keys, and the app's API key, which managed `init` stores there.
`native-build`, the store uploads, `deploy`, and CI read the same names, so
nobody issues a second key. With a team store, nothing is kept on your
machine: `hot-updater doctor` shows each `secret:` and `secretEnv` name and
whether the store, the environment, or nothing holds it.

## Where the CLI reads secrets

Your CI, your secrets store, and your own machine keep the CLI's
credentials, and the CLI reads each one when a command needs it:

| Credential                                        | Where the CLI reads it                                                                                                                                                                                                                                                                   |
| ------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Provider credentials for `storage` and `database` | The environment, through [`secretEnv`](#deploy-credentials-with-secretenv) or the config itself, then the config's `secrets` adapter                                                                                                                                                      |
| Native build signing and store upload keys        | The environment, then the config's `secrets` adapter, [`localSecrets()`](#the-localsecrets-store) by default, through [`secret:<name>`](#sign-native-builds-with-secrets)                                                                                                             |
| Bundle signing key                                | The `signing` adapter: a key that stays in [AWS KMS](/docs/guides/signing/aws-kms), [Google Cloud KMS](/docs/guides/signing/google-cloud-kms), or a [remote signer](/docs/guides/signing/remote), or a [local PEM](/docs/guides/signing/local) from a secret or from a file             |

With `localSecrets()`, the adapter `init` writes and a config without
`secrets` behaves as, a build credential comes from the first of:

1. its per-field environment variables, such as `HOT_UPDATER_ASC_KEY_ID`,
   which the [native build guide](/docs/guides/native-build#provide-signing-credentials)
   lists;
2. its whole value in one environment variable, such as
   `HOT_UPDATER_ASC_API_KEY` for `asc-api-key`, as a CI job maps a GitHub
   Actions secret;
3. a file in your home directory, where `apple login`, `google-play login`,
   and `secrets put` keep it.

```ts title="hot-updater.config.ts (partial)"
import { defineConfig, localSecrets } from "hot-updater";

export default defineConfig({
  secrets: localSecrets(),
  // build, storage, database and plugins stay as they are
});
```

"The environment" is the process environment and the project's
`.env.hotupdater`, the deploy settings file managed `init` writes and the
config loads. Hot Updater never writes a key to an `.env` file. Keep these
values out of version control and out of the app.
[Security](/docs/policy/security) lists which values belong where.

## The localSecrets() store

With [`localSecrets()`](/docs/guides/secrets-adapters/local-secrets), a key
Hot Updater issues after a sign-in, and a credential `secrets put` imports,
goes to a file in your home directory:

```txt
~/.hot-updater/secrets/<project-key>/<name>.json
```

- The file holds the value as it is, such as an App Store Connect key's JSON,
  so `gh secret set HOT_UPDATER_ASC_API_KEY < <file>` copies it to GitHub.
- The directories are `0700` and the files `0600`: only your user reads them.
  On Windows the store is under your user profile, whose permissions apply
  instead.
- It is outside the repository, and `rm -rf node_modules` keeps it.
- `<project-key>` is the project directory's name and a hash of its real
  path, such as `my-app-3f2a9c1d04be`, so each checkout has its own keys: a
  second clone signs in again, or imports the key with `secrets put`.
- `HOT_UPDATER_HOME` moves `~/.hot-updater`, such as to a CI cache or a test
  directory.

`localSecrets({ path })` keeps the files in another directory, such as one
every clone of the app shares:

```ts title="hot-updater.config.ts (partial)"
secrets: localSecrets({ path: "~/.hot-updater/secrets/my-app" }),
```

`~` is your home directory, on Windows too, and a relative path is the
project's. A directory inside a git repository must be one git ignores, such
as a `.secrets/` you add to `.gitignore`: the first use refuses any other,
so a secret can't be committed, and refuses a path that is a file.

The next build on the machine reads the key from there, with no step in
between. With another `secrets` adapter, this store is not used: the adapter
is the only place the CLI reads and stores credentials.

## Share a key across machines

With `localSecrets()`, each machine keeps its own keys. On a machine without
one, `apple login` or `google-play login` says so before it signs in, and
signing in issues a new key: App Store Connect and Google Cloud then list one
key per machine. Revoke
the ones nothing uses anymore on App Store Connect's Integrations page (Team
Keys), or under the service account's keys in Google Cloud.

To use one key everywhere instead, either:

- import it on the other machine with `secrets put`, from the files you have:

  ```package-install
  npx hot-updater secrets put asc-api-key --kind asc-api-key --p8 ./AuthKey_ABC123.p8 --key-id ABC123 --issuer-id 00000000-0000-0000-0000-000000000000
  ```

- or keep it in a [team store](#this-machine-or-the-team) every machine and
  CI reads, with a [secrets adapter](#choose-an-adapter):
  [dotenvx](/docs/guides/secrets-adapters/dotenvx) commits it encrypted to
  your repository for free.

## Read secrets in CI

CI needs no adapter: map each GitHub Actions secret to the job's environment
under the variable of its name, and `localSecrets()`, which reads the environment
before its files, reads it there.

| Secret                                | Workflow `env`                                                                      |
| ------------------------------------- | ----------------------------------------------------------------------------------- |
| `secret:asc-api-key`                  | `HOT_UPDATER_ASC_API_KEY: ${{ secrets.HOT_UPDATER_ASC_API_KEY }}`                   |
| `secret:release-keystore`             | `HOT_UPDATER_RELEASE_KEYSTORE: ${{ secrets.HOT_UPDATER_RELEASE_KEYSTORE }}`         |
| `secret:play-service-account`         | `HOT_UPDATER_PLAY_SERVICE_ACCOUNT: ${{ secrets.HOT_UPDATER_PLAY_SERVICE_ACCOUNT }}` |
| `secretEnv(["CLOUDFLARE_API_TOKEN"])` | `CLOUDFLARE_API_TOKEN: ${{ secrets.CLOUDFLARE_API_TOKEN }}`                         |

After a sign-in issues a key into `localSecrets()`, the CLI offers once to store it
as that GitHub Actions secret too, when it runs at a terminal, the project's
`origin` is on GitHub, and you have a user token (`gh auth token`, or
`GH_TOKEN`). Otherwise, copy the file yourself:

```bash
gh secret set HOT_UPDATER_ASC_API_KEY < ~/.hot-updater/secrets/<project-key>/asc-api-key.json
```

[Build and upload from CI](/docs/guides/ci-native-build) has the complete
workflow.

## Choose an adapter

Pick the store by who builds:

| Adapter                                                                       | For                                         | Reads from                                         | CI signs in with                 |
| ----------------------------------------------------------------------------- | ------------------------------------------- | -------------------------------------------------- | -------------------------------- |
| [`localSecrets()`](/docs/guides/secrets-adapters/local-secrets)               | One developer on one machine                | The environment, then a file in your home directory | The job's environment            |
| [dotenvx](/docs/guides/secrets-adapters/dotenvx)                              | Any machine and CI, for free                | An encrypted file committed to the repository      | `DOTENV_PRIVATE_KEY`             |
| [Bitwarden Secrets Manager](/docs/guides/secrets-adapters/bitwarden)          | A small team, hosted, for free              | A Bitwarden project                                | A machine account token          |
| [AWS Secrets Manager](/docs/guides/secrets-adapters/aws-secrets-manager)      | Teams on AWS                                | AWS Secrets Manager                                | GitHub Actions OIDC, or AWS keys |
| [Google Secret Manager](/docs/guides/secrets-adapters/google-secret-manager)  | Teams on Google Cloud                       | Google Cloud Secret Manager                        | Workload Identity Federation     |
| [1Password](/docs/guides/secrets-adapters/1password)                          | Teams on 1Password                          | A 1Password vault                                  | A service account token          |
| [Infisical](/docs/guides/secrets-adapters/infisical)                          | Teams on Infisical                          | An Infisical project                               | Universal Auth                   |

`localSecrets()` ships with `hot-updater`. The AWS and Google Cloud adapters
ship with their provider packages, `secretsManager()` from `@hot-updater/aws`
and `secretManager()` from `@hot-updater/firebase`. The others are short files
you paste into your project, built on the store's official SDK:

```ts title="hot-updater.config.ts (partial)"
import { defineConfig } from "hot-updater";

import { dotenvx } from "./secrets/dotenvx";

export default defineConfig({
  secrets: dotenvx(),
  // build, storage, database and plugins stay as they are
});
```

## Name a secret

A config names a secret, and the store maps the name. In the environment, a
name that is a variable name, such as `CLOUDFLARE_API_TOKEN`, is that
variable. Any other name, such as `asc-api-key`, is `HOT_UPDATER_` and the
name upper-cased, with `_` for every character but letters and digits:
`secret:asc-api-key` reads `HOT_UPDATER_ASC_API_KEY`, and
`secret:release-keystore` reads `HOT_UPDATER_RELEASE_KEYSTORE`.
dotenvx stores a name under the same variable name,
`localSecrets()` as `<name>.json`, `secretsManager()` and `secretManager()`
as `<prefix><name>`, such as `hot-updater/asc-api-key` and
`hot-updater-asc-api-key`, and the pasted adapters as the secret's own name.

A build credential has a default name for its kind, which a `secret:`
reference replaces: `asc-api-key`, `android-keystore`, and
`play-service-account`.

## Sign native builds with secrets

A [native build](/docs/guides/native-build) names its signing credentials as
`secret:<name>`:

```ts title="hot-updater.config.ts (partial)"
nativeBuild: {
  android: {
    release: {
      packageName: "com.example.app",
      signing: { keystore: "secret:release-keystore" },
    },
  },
  ios: {
    release: {
      bundleIdentifier: "com.example.app",
      scheme: "ExampleApp",
      signing: { ascApiKey: "secret:asc-api-key" },
    },
  },
},
```

Each credential is one JSON value per name, binary in base64:

| Kind                   | Value                                                                                         |
| ---------------------- | --------------------------------------------------------------------------------------------- |
| `asc-api-key`          | `{"keyId": "…", "issuerId": "…", "p8": "-----BEGIN PRIVATE KEY-----…"}`, the `.p8` file's PEM |
| `android-keystore`     | `{"keystore": "<base64>", "storePassword": "…", "keyAlias": "…", "keyPassword": "…"}`         |
| `play-service-account` | The service account's JSON key file as it is                                                  |

The build reads the secrets it signs and uploads with in one call to the
adapter, before the build adapter's prebuild, so a missing one fails before
anything is built. A credential's own environment variables, such as
`HOT_UPDATER_ASC_KEY_PATH`, override every store for that credential.

## Sign bundles with a key from secrets

`secrets` and `signing` are separate slots. A `secrets` adapter returns
values to the CLI; a `signing` adapter signs a digest, and the KMS and remote
signers do it with a key that never leaves the signer. Only
[local PEM signing](/docs/guides/signing/local) reads its RSA private key as
a secret, `secret:<name>`, such as `HOT_UPDATER_BUNDLE_SIGNING_KEY` in the
environment:

```ts title="hot-updater.config.ts (partial)"
signing: { enabled: true, privateKey: "secret:bundle-signing-key" },
```

`npx hot-updater keys generate --secret` stores a new key there, through the
config's `secrets` adapter.
[Signing and Secrets](/docs/guides/bundle-signing#signing-and-secrets)
explains when a key belongs in a KMS instead.

## Deploy credentials with secretEnv

`secretEnv` from `hot-updater` returns a function an adapter calls for its
credentials, so loading the config reads no secret:

```ts title="hot-updater.config.ts"
import { s3Storage } from "@hot-updater/aws";
import { defineConfig, secretEnv } from "hot-updater";

const deploy = secretEnv(["S3_ACCESS_KEY_ID", "S3_SECRET_ACCESS_KEY"]);

export default defineConfig({
  storage: s3Storage({
    bucketName: "bundles",
    region: "us-east-1",
    credentials: async () => {
      const values = await deploy();
      return {
        accessKeyId: values.S3_ACCESS_KEY_ID,
        secretAccessKey: values.S3_SECRET_ACCESS_KEY,
      };
    },
  }),
  // ...
});
```

- A name set in the environment or `.env.hotupdater` wins. With a `secrets`
  adapter other than `localSecrets()`, the other names are read from it in one
  call. `localSecrets()`'s files hold only the keys Hot Updater stores, so
  with it every name must be set in the environment.
- The values go only to the adapter that called: the CLI never sets them in its
  own `process.env`.
- Names that change how a process loads code are refused: `NODE_*` but
  `NODE_ENV`, `PATH`, `LD_*`, `DYLD_*`, `BASH_ENV`, `ENV`, `GIT_*`,
  `npm_config_*`, `JAVA_TOOL_OPTIONS`, `_JAVA_OPTIONS`, `JDK_JAVA_OPTIONS`,
  `GRADLE_OPTS`, `RUBYOPT`, `RUBYLIB`, `PYTHONPATH`, `PYTHONSTARTUP`,
  `PERL5OPT`, and the variables Hot Updater reads its own credentials from,
  such as the credential overrides and `HOT_UPDATER_HOME`.

### Managed projects

The config managed `init` writes names its resources and reads the
provider's credentials with `secretEnv`. `init` saves them in
`.env.hotupdater`; with a team store in `secrets`, it also stores them there,
with `HOT_UPDATER_API_KEY`, and reads each back. A teammate's `init` reads
from the store what their `.env.hotupdater` lacks.

To move a project's credentials from `.env.hotupdater` to a team store you
add later, set `secrets`, then run:

```package-install
npx hot-updater secrets import
```

It stores each name the config's `secretEnv` reads, and
`HOT_UPDATER_API_KEY`, then reads them back. It deletes nothing: delete
those lines from `.env.hotupdater`, or keep them to override the store on
your machine.

## Store a secret

`secrets put` stores a build credential you have as its JSON value, through
the config's adapter.

```package-install
npx hot-updater secrets put asc-api-key --kind asc-api-key --p8 ./AuthKey_ABC123.p8 --key-id ABC123 --issuer-id 00000000-0000-0000-0000-000000000000
```

| Kind                   | Options                                                                                                                                                                |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `asc-api-key`          | `--p8 <file>`, `--key-id <id>`, `--issuer-id <id>`                                                                                                                     |
| `android-keystore`     | `--keystore <file>`, `--key-alias <alias>`. The passwords come from `HOT_UPDATER_ANDROID_KEYSTORE_PASSWORD` and `HOT_UPDATER_ANDROID_KEY_PASSWORD`, or a hidden prompt |
| `play-service-account` | `--service-account <file>`, the JSON key file                                                                                                                          |

### Issue a key with a sign-in

Without a key file, sign in and Hot Updater issues the key and stores it, as
a build does when its key is missing:

```package-install
npx hot-updater apple login
npx hot-updater google-play login
```

`apple login` and `google-play login` are shortcuts for `secrets issue`, the
command's full form, for the name builds resolve by default. They take no
options or arguments:

| Shortcut            | Full form                                                                                  |
| ------------------- | ------------------------------------------------------------------------------------------ |
| `apple login`       | `secrets issue asc-api-key`                                                                |
| `google-play login` | `secrets issue play-service-account`, then [the upload key](#create-an-android-upload-key) |

- `apple login` [signs in with your Apple Account](/docs/guides/native-build#sign-in-with-your-apple-account).
- `google-play login` signs in to Google with the
  [gcloud CLI](https://cloud.google.com/sdk/docs/install), which it needs,
  creates the service account and its key, and opens Play Console's invite
  page for the service account. Invite it there with the app permission
  **Release apps to testing tracks**, one click, while the CLI waits
  ([Upload to Google Play](/docs/guides/native-build#upload-to-google-play)).
  Then it sets up the [upload key](#create-an-android-upload-key) that signs
  the builds Google Play takes.

The full form's argument stores the key under another name, such as
`secrets issue asc-api-key widget-asc` for
`signing.ascApiKey: "secret:widget-asc"`.

Hot Updater keeps no Apple or Google session, so there is no logout (gcloud
keeps its own sign-in): the command ends with the stored key's ID and where it
is. The key goes through the config's adapter, which must read it back as
stored; otherwise the key is revoked.

A key the environment or the adapter already holds is kept: the command
prints its key ID or service account and the one place it read it from, and
signs in to nothing. To issue a new key, run `secrets issue <kind> --replace`, such as
`secrets issue asc-api-key --replace`. The CLI stores the new key, then names the old one and where to revoke it: App Store
Connect's Integrations page for an App Store Connect key, the service
account's keys in Google Cloud for a Play service account. It never revokes
the old key itself, since CI or another machine may still use it.
`--replace` refuses a key the environment sets, since builds read it before
any store: unset it first.

It signs in only at a terminal. In CI or without a terminal, a key already
held is reported as above, and a missing one is an error; store a key you
have with `secrets put` there.

### Create an Android upload key

Google Play takes only builds signed with the app's upload key. Hot Updater
creates one with `keytool`, from the JDK that Android builds already use, so
you need neither EAS nor Android Studio for it:

```package-install
npx hot-updater secrets issue android-keystore
```

It creates an RSA 4096 key, alias `upload`, valid for 10,000 days, in a
PKCS12 keystore with a random password, and stores it as the
`android-keystore` JSON value in the config's adapter, such as a team's AWS
or Google Cloud store, and only there: it reads the value back and fails
when the store doesn't return it as written, keeping no copy on your
machine. With no adapter configured, it goes to the `localSecrets()` store.
A scheme signs with it through
`signing: { keystore: "secret:android-keystore" }`; a second argument stores
it under another name. The command prints the key's alias, its certificate's
SHA-256 and SHA-1 fingerprints, and where it is. Neither password is printed.

- **Back it up.** It is your Play upload key: the adapter, or with
  `localSecrets()` the file in your home directory, holds its only copy.
- **A stored keystore is kept.** Once Google Play has a key, it rejects
  builds signed with another. `--replace` overwrites the stored keystore and
  prints the old key's fingerprint.
- **Play already has another upload key**, such as one from an earlier EAS
  or Android Studio build: store that keystore with `secrets put` instead, or
  ask for an upload key reset in Play Console with the new key's certificate.
  `--pem <file>` writes it, for the key it creates or the one already stored.

Without `keytool` it stops and names the JDK to install. It creates a key only
at a terminal: a key created on a CI runner would be lost with it.

`google-play login` does the same after the service account, for each secret
a release scheme's `signing.keystore` names, `android-keystore` when none
does. It reports a keystore the adapter already holds, in CI too; a file on
your machine doesn't count when the config sets an adapter. Otherwise it asks
whether to create a new upload key or use the keystore you have: the keystore
file, its alias, and its passwords, which it checks open the key before it
stores them, as `secrets put` would. When Play already releases the app, it
suggests your keystore, since Play has its key.

## Write a secrets adapter

A store of your own implements `SecretsAdapter`, a type `hot-updater`
exports, as the [pasted adapters](/docs/guides/secrets-adapters/dotenvx)
do:

```ts
import type { SecretsAdapter } from "hot-updater";

export const mySecrets = (): SecretsAdapter => ({
  name: "mySecrets",
  // One call for every name; undefined for a name the store does not hold.
  get: async (names, { cwd }) => readFromMyStore(names, cwd),
  // Stores a value, such as a key Hot Updater issues.
  set: async (name, value, { cwd }) => writeToMyStore(name, value, cwd),
  // Optional: where the user finds a name, for messages.
  describe: (name) => `my-store://${name}`,
});
```

`get` throws on any failure but a missing name, such as a missing permission
or an unreachable store, and the CLI reports it with the environment
variables that provide the credential instead. Values are strings: a
credential with several fields is one JSON value, and binary is base64.

## How the CLI handles values

Every adapter, the built-in ones and yours, runs under the same rules:

- Nothing is cached. Nothing is written to disk but the `localSecrets()`
  store's files and temporary files only your user can read, deleted when
  the command ends or is interrupted.
- Resolved values go only to what asked for them: a credential's temporary
  file, the adapter that called `secretEnv`, or the environment of the one
  child process that needs them, such as Gradle's keystore passwords. They
  never enter the CLI's own `process.env`, and no value goes on a command
  line.
- Every value the CLI resolves or stores, and every secret field of a JSON
  credential, is masked in its output and in build logs. Its IDs, key alias,
  and service account email stay readable. A value shorter than six
  characters, such as `1`, is masked only where it stands as a whole word, as
  in `PASSWORD=1`, so it never masks the digits of a URL or a version. The
  [`native-build`](/docs/guides/ci-native-build#inputs) action also masks the
  job's `HOT_UPDATER_*` credentials in the GitHub Actions log.
- In CI (`CI` is set) or without a terminal, the CLI never starts an Apple or
  Google sign-in. CI identities only read; only the developer who stores a
  secret or signs in needs write access, as each adapter's page lists.
