## Where the CLI reads secrets

Hot Updater stores no secrets. Your secrets store, CI, and signing service
keep them, and the CLI reads each one through the `secrets` slot of
`hot-updater.config.ts` when a command needs it:

| Credential                                        | Where the CLI reads it                                                                                                                                                                                                                                                                   |
| ------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Provider credentials for `storage` and `database` | The `secrets` adapter through [`secretEnv`](#deploy-credentials-with-secretenv), or the environment the config reads                                                                                                                                                                     |
| Native build signing and store upload keys        | The `secrets` adapter through [`secret:<name>`](#sign-native-builds-with-secrets), or the environment variables in [Provide signing credentials](/docs/guides/native-build#provide-signing-credentials)                                                                                  |
| Bundle signing key                                | The `signing` adapter: a key that stays in [AWS KMS](/docs/guides/signing/aws-kms), [Google Cloud KMS](/docs/guides/signing/google-cloud-kms), or a [remote signer](/docs/guides/signing/remote), or a [local PEM](/docs/guides/signing/local) from the `secrets` adapter or from a file |

The default adapter, [`env()`](/docs/guides/secrets-adapters/env) from
`hot-updater/secrets`, reads each name from an environment variable, in the
environment or the project's `.env.hotupdater`. Keep these values out of
version control and out of the app. [Security](/docs/policy/security) lists
which values belong where.

```ts title="hot-updater.config.ts (partial)"
import { defineConfig } from "hot-updater";
import { env } from "hot-updater/secrets";

export default defineConfig({
  secrets: env(),
  // build, storage, database and plugins stay as they are
});
```

## Choose an adapter

| Adapter                                                                        | Reads from                            | Stores issued keys | CI signs in with                       |
| ------------------------------------------------------------------------------ | ------------------------------------- | ------------------ | -------------------------------------- |
| [`env()`](/docs/guides/secrets-adapters/env)                                   | The environment and `.env.hotupdater` | No                 | The job's environment                  |
| [`githubActions()`](/docs/guides/secrets-adapters/github-actions)              | Only a workflow run, through its env  | Yes                | The workflow's secrets                 |
| [`awsSecretsManager()`](/docs/guides/secrets-adapters/aws-secrets-manager)     | AWS Secrets Manager                   | Yes                | GitHub Actions OIDC, or AWS keys       |
| [`googleSecretManager()`](/docs/guides/secrets-adapters/google-secret-manager) | Google Cloud Secret Manager           | Yes                | Workload Identity Federation           |
| [`infisical()`](/docs/guides/secrets-adapters/infisical)                       | An Infisical project                  | Yes                | GitHub Actions OIDC, or Universal Auth |

[Build and upload from CI](/docs/guides/ci-native-build) has a complete
workflow for each.

## Name a secret

A config names a secret, and the adapter maps the name to its store.
`env()` reads a name that is an environment variable name, such as
`CLOUDFLARE_API_TOKEN`, as that variable. Any other name, such as
`asc-api-key`, is `HOT_UPDATER_` and the name upper-cased, with `_` for every
character but letters and digits: `secret:asc-api-key` reads
`HOT_UPDATER_ASC_API_KEY`, and `secret:release-keystore` reads
`HOT_UPDATER_RELEASE_KEYSTORE`. `githubActions()` stores a name under the
same variable name. The store adapters keep a name as the secret's own name,
with the adapter's `prefix` or folder.

A build credential has a default name for its kind, which a `secret:`
reference replaces: `asc-api-key`, `android-keystore`, and
`play-service-account`.

## Sign native builds with secrets

A [native build](/docs/guides/native-build) names its signing credentials as
`secret:<name>`:

```ts title="hot-updater.config.ts (partial)"
nativeBuild: {
  android: {
    release: {
      packageName: "com.example.app",
      signing: { keystore: "secret:release-keystore" },
    },
  },
  ios: {
    release: {
      bundleIdentifier: "com.example.app",
      scheme: "ExampleApp",
      signing: { ascApiKey: "secret:asc-api-key" },
    },
  },
},
```

Each credential is one JSON value per name, binary in base64:

| Kind                   | Value                                                                                         |
| ---------------------- | --------------------------------------------------------------------------------------------- |
| `asc-api-key`          | `{"keyId": "…", "issuerId": "…", "p8": "-----BEGIN PRIVATE KEY-----…"}`, the `.p8` file's PEM |
| `android-keystore`     | `{"keystore": "<base64>", "storePassword": "…", "keyAlias": "…", "keyPassword": "…"}`         |
| `play-service-account` | The service account's JSON key file as it is                                                  |

The build reads the secrets it signs and uploads with in one call to the
adapter, before the build adapter's prebuild, so a missing one fails before
anything is built. A credential's own environment variables, such as
`HOT_UPDATER_ASC_KEY_PATH`, override the adapter for that credential: the
[native build guide](/docs/guides/native-build#provide-signing-credentials)
lists them.

## Sign bundles with a key from secrets

`secrets` and `signing` are separate slots. A `secrets` adapter returns
values to the CLI; a `signing` adapter signs a digest, and the KMS and remote
signers do it with a key that never leaves the signer. Only
[local PEM signing](/docs/guides/signing/local) reads its RSA private key
from `secrets`, as `secret:<name>`, such as `HOT_UPDATER_BUNDLE_SIGNING_KEY`
with `env()`:

```ts title="hot-updater.config.ts (partial)"
signing: { enabled: true, privateKey: "secret:bundle-signing-key" },
```

`npx hot-updater keys generate --secret` stores a new key there.
[Signing and Secrets](/docs/guides/bundle-signing#signing-and-secrets)
explains when a key belongs in a KMS instead.

## Deploy credentials with secretEnv

`secretEnv` from `hot-updater` returns a function an adapter calls for its
credentials, so loading the config reads no secret:

```ts title="hot-updater.config.ts"
import { s3Storage } from "@hot-updater/aws";
import { defineConfig, secretEnv } from "hot-updater";

const deploy = secretEnv(["S3_ACCESS_KEY_ID", "S3_SECRET_ACCESS_KEY"]);

export default defineConfig({
  storage: s3Storage({
    bucketName: "bundles",
    region: "us-east-1",
    credentials: async () => {
      const values = await deploy();
      return {
        accessKeyId: values.S3_ACCESS_KEY_ID,
        secretAccessKey: values.S3_SECRET_ACCESS_KEY,
      };
    },
  }),
  // ...
});
```

- A name set in the environment or `.env.hotupdater` wins. The other names are
  read from the `secrets` adapter in one call.
- The values go only to the adapter that called: the CLI never sets them in its
  own `process.env`.
- Names that change how a process loads code are refused: `NODE_*` but
  `NODE_ENV`, `PATH`, `LD_*`, `DYLD_*`, `BASH_ENV`, `ENV`, `GIT_*`,
  `npm_config_*`, `JAVA_TOOL_OPTIONS`, `_JAVA_OPTIONS`, `JDK_JAVA_OPTIONS`,
  `GRADLE_OPTS`, `RUBYOPT`, `RUBYLIB`, `PYTHONPATH`, `PYTHONSTARTUP`,
  `PERL5OPT`, and the variables Hot Updater reads its own credentials from,
  such as the credential overrides and the `INFISICAL_*` variables
  `infisical()` signs in with.

## Store a secret

`secrets put` stores a build credential you have as its JSON value through
the adapter's `set`:

```package-install
npx hot-updater secrets put asc-api-key --kind asc-api-key --p8 ./AuthKey_ABC123.p8 --key-id ABC123 --issuer-id 00000000-0000-0000-0000-000000000000
```

| Kind                   | Options                                                                                                                                                                |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `asc-api-key`          | `--p8 <file>`, `--key-id <id>`, `--issuer-id <id>`                                                                                                                     |
| `android-keystore`     | `--keystore <file>`, `--key-alias <alias>`. The passwords come from `HOT_UPDATER_ANDROID_KEYSTORE_PASSWORD` and `HOT_UPDATER_ANDROID_KEY_PASSWORD`, or a hidden prompt |
| `play-service-account` | `--service-account <file>`, the JSON key file                                                                                                                          |

With a read-only adapter such as `env()`, `secrets put` stores nothing and
names the variable to set instead.

### Issue a key with a sign-in

Without a key file, `secrets issue` signs you in and stores the key Hot
Updater issues, as a build does when its key is missing:

```package-install
npx hot-updater secrets issue asc-api-key
npx hot-updater secrets issue play-service-account
```

- `asc-api-key` [signs in with your Apple Account](/docs/guides/native-build#sign-in-with-your-apple-account).
- `play-service-account` signs in with Google and creates the service
  account and its key ([Upload to Google Play](/docs/guides/native-build#upload-to-google-play)).
  Until Hot Updater ships its own OAuth client, it needs a "Desktop app"
  OAuth client of yours in `HOT_UPDATER_GOOGLE_OAUTH_CLIENT_ID` and
  `HOT_UPDATER_GOOGLE_OAUTH_CLIENT_SECRET`.

A second argument stores the key under another name, such as
`secrets issue asc-api-key widget-asc` for `signing.ascApiKey:
"secret:widget-asc"`.

The key goes through the adapter's `set` when the adapter stores values.
With a read-only adapter such as `env()`, the CLI writes it to a file only
your user can read, prints the variables to store it in, and offers to store
it as a GitHub Actions secret
([where an issued key goes](/docs/guides/native-build#where-an-issued-key-goes)).

A key the adapter already holds, or the credential's environment variables
such as `HOT_UPDATER_ASC_KEY_ID` set, is kept: `secrets issue` prints where
it is and its key ID or service account, and signs in to nothing. To issue a
new key, run it with `--replace`. The CLI stores the new key, then names the
old one and where to revoke it: App Store Connect's Integrations page for an
App Store Connect key, the service account's keys in Google Cloud for a Play
service account. It never revokes the old key itself, since CI or a GitHub
Actions secret may still use it. With a read-only adapter, the variable that
holds the old key keeps it until you change it. `--replace` refuses a key
the credential's environment variables set, since builds read them before
any adapter: unset them first.

`secrets issue` signs in only at a terminal. In CI or without a terminal it
exits with an error before anything else; store a key you have with
`secrets put` there.

## Write a secrets adapter

A store of your own implements `SecretsAdapter` from `@hot-updater/plugin-core`:

```ts
import type { SecretsAdapter } from "@hot-updater/plugin-core";

export const mySecrets = (): SecretsAdapter => ({
  name: "mySecrets",
  // One call for every name; undefined for a name the store does not hold.
  get: async (names, { cwd }) => readFromMyStore(names, cwd),
  // Optional: stores a value, such as a key Hot Updater issues.
  set: async (name, value, { cwd }) => writeToMyStore(name, value, cwd),
  // Optional: where the user finds a name, for messages.
  describe: (name) => `my-store://${name}`,
});
```

`get` throws on any failure but a missing name, such as a missing permission
or an unreachable store, and the CLI reports it with the environment
variables that provide the credential instead. Values are strings: a
credential with several fields is one JSON value, and binary is base64.

## How the CLI handles values

Every adapter, the official ones and yours, runs under the same rules:

- Nothing is cached. Nothing is written to disk but temporary files only
  your user can read, deleted when the command ends or is interrupted, and
  the file a key issued for a read-only adapter is written to, which you
  delete once you stored the key.
- Resolved values go only to what asked for them: a credential's temporary
  file, the adapter that called `secretEnv`, or the environment of the one
  child process that needs them, such as Gradle's keystore passwords. They
  never enter the CLI's own `process.env`, and no value goes on a command
  line.
- Every value the CLI resolves or stores, and every secret field of a JSON
  credential, is masked in its output and in build logs. Its IDs, key alias,
  and service account email stay readable. A value shorter than six
  characters, such as `1`, is masked only where it stands as a whole word, as
  in `PASSWORD=1`, so it never masks the digits of a URL or a version. The
  [`native-build`](/docs/guides/ci-native-build#inputs) action also masks the
  job's `HOT_UPDATER_*` credentials in the GitHub Actions log.
- The official adapters talk to their store over HTTPS, or HTTP only to a
  self-hosted Infisical on `localhost`, and never follow a redirect.
- In CI (`CI` is set) or without a terminal, the CLI never starts an Apple or
  Google sign-in. CI identities only read, and sign in without a stored key
  where the store allows it: GitHub Actions OIDC for AWS and Infisical,
  Workload Identity Federation for Google Cloud. Only the developer who
  stores a secret or signs in needs write access, as each adapter's page
  lists.
