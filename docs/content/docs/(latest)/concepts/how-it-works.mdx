## Core Infrastructure

Hot Updater separates immutable update bytes from mutable delivery policy:

- **Storage** holds immutable Bundle archives, manifests, assets, and patch
  objects.
- **Database** holds Bundle metadata, canonical Releases, Channels, and Release
  Catalog rows.
- **Release Catalog** is a deterministic, derived projection of Release policy
  for one channel, platform, and compatibility scope.
- **Server** serves the exact Catalog for an app's scope and resolves the
  selected Bundle artifact.

Storage and Database are configured using plugins in `hot-updater.config.ts`.
The Server is initialized and deployed with `hot-updater init`.

The deployment output, console, and `HotUpdater.getBundleId()` use the same
update ID. File identifiers are reserved for Advanced diagnostics and artifact
operations.

## Bundle, Release, and Catalog

### Bundle

A Bundle identifies installable bytes. Its ID, hashes, Storage URIs, manifest,
assets, patches, signing identity, and crash identity are artifact concerns.
Bundle records do not own channel, enabled, rollout, compatibility, cohort,
force-update, or message policy.

### Release

A Release references a Bundle and owns delivery policy: Channel, platform,
compatibility target, enabled state, rollout, target cohorts, force update, and
message. Its ID also controls delivery chronology and the stable numeric
rollout seed.

Multiple Releases can reuse the same Bundle. For example, `release promote`
creates a new target-channel Release without copying Storage bytes. The new
Release has its own chronology and rollout seed even though its Bundle is
unchanged.

### Release Catalog

The Catalog is compiled from canonical Releases whenever policy changes. It is
not edited independently. Release and Catalog changes commit atomically so
clients never observe policy without its matching projection.

## Deployment and Selection

1. `hot-updater deploy` builds and uploads an immutable Bundle.
2. Deploy creates a Release for that Bundle and compiles the affected Catalog.
3. The app requests the Catalog for its channel, platform, and
   app-version or fingerprint scope.
4. The client evaluates compatibility, Release chronology, rollout, and target
   cohorts, then resolves the selected Bundle artifact.
5. When no compatible enabled Release remains, the complete Catalog can direct
   the app to its local built-in Bundle (`BUILTIN`).

Changing rollout, enabled, force update, cohorts, or message mutates the
Release and increments its revision and Catalog generation. It never rewrites
the Bundle bytes.

## Two Different Rollback Mechanisms

Operational rollback disables a Release with
`hot-updater release disable <id>`. Affected installations then select
a previous compatible enabled Release or `BUILTIN`; the result can differ by
app version, fingerprint, and cohort.

Automatic crash rollback is a separate native safety mechanism. It rejects a
Bundle that failed startup and restores the last safe local Bundle. Crash
history therefore records file IDs. See
[Automatic Rollback](/docs/concepts/automatic-rollback) for that lifecycle.
