## The Bundle model

Hot Updater keeps the v0 public model: a deployment creates a Bundle with one
ID. The deployment result, Console, `HotUpdater.getBundleId()`, and every
`hot-updater bundle` command use that same ID.

A Bundle's delivery settings include its channel, platform, compatibility
target, enabled state, rollout, target cohorts, force-update value, and message.
Changing those settings keeps the same ID. Promoting a Bundle creates a new ID
in the target channel without uploading the same bytes again.

```text
deploy → ID → bundle show/update/enable/disable/delete/promote
```

## Infrastructure

- **Storage** holds immutable archives, manifests, assets, and patch objects.
- **Database** holds Bundle delivery settings and internal catalog rows.
- **Server** selects the compatible Bundle for an app's channel, platform, and
  app-version or fingerprint scope.

Storage and Database are configured using plugins in `hot-updater.config.ts`.
The Server is initialized and deployed with `hot-updater init`.

Internally, v1 can reuse one immutable artifact across multiple public Bundle
IDs. This avoids copying uploaded bytes during promotion and lets policy changes
recompile the delivery catalog without rebuilding the archive. The internal
artifact identity is shown only as **Artifact ID** in Advanced diagnostics and
artifact commands.

## Deployment and selection

1. `hot-updater deploy` builds and uploads an immutable artifact.
2. The database creates the public Bundle ID and compiles its delivery catalog.
3. The app requests the catalog for its channel, platform, and app-version or
   fingerprint scope.
4. The client evaluates compatibility, chronology, rollout, and target cohorts,
   then resolves the selected artifact.
5. When no compatible enabled Bundle remains, the app uses its built-in Bundle
   (`BUILTIN`).

Changing rollout, enabled, force update, cohorts, or message never rewrites the
uploaded bytes.

## Two rollback mechanisms

Operational rollback disables a Bundle with `hot-updater bundle disable <id>`.
Affected installations select a previous compatible enabled Bundle or
`BUILTIN`; the result can differ by app version, fingerprint, and cohort.

Automatic crash rollback is a separate native safety mechanism. It rejects an
artifact that failed startup and restores the last safe local Bundle. Crash
history therefore records Artifact IDs. See
[Automatic Rollback](/docs/concepts/automatic-rollback) for that lifecycle.
