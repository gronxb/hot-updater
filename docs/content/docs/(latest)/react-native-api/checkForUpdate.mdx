## Usage

Use `checkForUpdate` to check whether an update bundle is available. The function
reuses the update source configured in [`HotUpdater.init`](/docs/react-native-api/init).
Call it when your app is ready to check, then use the returned helper to
download and stage the selected update.

```tsx
import { HotUpdater } from "@hot-updater/react-native";

// Configure the client once at module scope
HotUpdater.init({
  baseURL: "<your-update-server-url>",
  requestHeaders: {
    "x-api-key": "<client-api-key>",
  },
  onError: (error) => console.error("Hot Updater:", error),
});

async function checkForAppUpdate() {
  try {
    const updateInfo = await HotUpdater.checkForUpdate({
      updateStrategy: "appVersion",
    });

    if (!updateInfo) {
      return;
    }

    // The helper resolves the artifact and preserves the selected transition.
    const didUpdate = await updateInfo.updateBundle();

    if (!didUpdate) {
      throw new Error("Could not prepare the update");
    }

    if (updateInfo.shouldForceUpdate) {
      await HotUpdater.reload();
    }
  } catch (error) {
    console.error("Could not prepare update:", error);
  }
}
```

## Initialize before checking

Configure `HotUpdater.init()` once at module scope before calling
`checkForUpdate`. This connects lifecycle reporting and update requests to your
server without starting a check. See
[custom update flows](/docs/guides/custom-update) for a complete integration.

The optional [`HotUpdater.wrap`](/docs/react-native-api/wrap) flow also
configures the client and performs its own automatic startup check. Choose
one configuration API. Calling `checkForUpdate` before either API throws an
error with configuration instructions.

## Parameters

`checkForUpdate` accepts these parameters:

| Parameter        | Type                              | Required | Description                                                 |
| ---------------- | --------------------------------- | -------- | ----------------------------------------------------------- |
| `updateStrategy` | `"appVersion"` \| `"fingerprint"` | ✅       | Update detection strategy for this check.                   |
| `channel`        | `string`                          | ❌       | Channel to check. Defaults to the currently active channel. |
| `requestHeaders` | `Record<string, string>`          | ❌       | Optional headers to include in the update request.          |
| `requestTimeout` | `number`                          | ❌       | Request timeout in milliseconds (default: 5000).            |
| `onError`        | `(error: Error) => void`          | ❌       | Called when a check fails, including failures that return `null`. |

The update source is always from `HotUpdater.init()` or `HotUpdater.wrap()`; it
cannot be overridden in `checkForUpdate`.

A requested channel switch is persisted only after the returned update applies
successfully. If a different runtime channel is already active, call
`resetChannel()` first; that conflict rejects instead of returning `null`.

## How it works

The client fetches a shared Release Catalog and evaluates it on the device.
When installation is needed, the returned `updateBundle()` helper resolves the
selected artifact when called:

- App version catalog: `GET {baseURL}/release-catalogs/app-version/:platform/:channelKey/:appVersion`
- Fingerprint catalog: `GET {baseURL}/release-catalogs/fingerprint/:platform/:channelKey/:fingerprintHash`
- Artifact resolution: `GET {baseURL}/artifacts/:targetBundleId/from/:currentBundleId`

`:channelKey` is the base64url-encoded channel name.

## Return value

The function returns `null` when no transition is selected, when checks are
skipped in development, or after a check fails and calls `onError`. Do not
interpret `null` alone as a successful up-to-date check. Use the shared
`init.onError` reporter for check failures and `try/catch` for rejected
operations. A per-check `onError` is an optional override; it is not needed in
the normal flow.

When a transition is selected, the result includes its ID from the console, status,
message, and an `updateBundle()` helper. The `fileUrl` and `fileHash` fields are
`null` in this result: the helper resolves the artifact lazily when needed.
Call the helper instead of copying these fields into `HotUpdater.updateBundle`.

| Result field | Type | Meaning |
| --- | --- | --- |
| `id` | `string` | Selected update ID shown in the Console. |
| `status` | `"UPDATE" \| "ROLLBACK"` | Selected transition direction. |
| `shouldForceUpdate` | `boolean` | Whether the caller should apply the transition immediately; the helper does not reload. |
| `message` | `string \| null` | Release message. |
| `rolloutCohortCount` | `number` | Numeric cohort count selected by the Release policy. |
| `targetCohorts` | `string[]` | Explicit cohort targets in that policy. |
| `releaseId` | `string \| null \| undefined` | Release identifier when present. |
| `transitionKind` | `"INSTALL" \| "ADOPT_RELEASE" \| "USE_EMBEDDED" \| "USE_BUILTIN" \| undefined` | How the selected transition will be applied. |
| `updateBundle` | `() => Promise<boolean>` | Stage or commit this selection; resolves with whether it succeeded. |

A different Release can reference the same artifact. `ADOPT_RELEASE` commits
that policy selection without downloading the artifact or forcing a reload.
The built-in and embedded transitions also do not require an artifact download.
