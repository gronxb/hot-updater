## Usage

Call `HotUpdater.init` at the top level of your app entry module, outside React
components and effects. It configures the update server and handles native
startup verification internally. Call `HotUpdater.checkForUpdate()` separately
when your app should check for updates.

Do not use `HotUpdater.init` and `HotUpdater.wrap` in the same app. Hot Updater
reports mixed usage with `console.error`. Use `init + checkForUpdate` for a
custom or manual update flow.

Use the client handler URL and client API key produced by your infrastructure
setup. For a custom server, follow
[API key authentication](/docs/custom/api-key-authentication) to configure the
client access policy and create a key.

```tsx
import { HotUpdater } from "@hot-updater/react-native";

HotUpdater.init({
  baseURL: "<your-update-server-url>",
  requestHeaders: {
    "x-api-key": "<your-api-key>",
  },
  onError: (error) => {
    console.error("Hot Updater failed", error);
  },
});
```

Point `baseURL` at the client handler root, for example
`https://example.com/hot-updater`. Never embed the admin bearer token in a
React Native app. If `clientAccess` uses the `api-key` policy, send only the
API key using `x-api-key` as shown above.

Automatic app-ready transition and Bundle adoption Insights are enabled by
default. Set `insights: false` to send no Insights events. The server routes
remain available either way. See [Insights](/docs/guides/insights) for report
contents, optional user identity, and verification.

`baseURL` can also be resolved at runtime. The function may return a string or
a promise, and Hot Updater calls it before each update check.

```tsx
HotUpdater.init({
  baseURL: "<your-update-server-url>", // [!code --]
  baseURL: () => getUpdateServerURL(), // [!code ++]
});
```

After initialization, call `HotUpdater.checkForUpdate()` wherever your runtime
or app state says it is safe to check.

```tsx
async function prepareUpdate() {
  try {
    const update = await HotUpdater.checkForUpdate({
      updateStrategy: "appVersion",
    });

    if (!update) {
      return;
    }

    const downloaded = await update.updateBundle();

    if (!downloaded) {
      throw new Error("Could not prepare the update");
    }

    if (update.shouldForceUpdate) {
      await HotUpdater.reload();
    }
  } catch (error) {
    console.error("Could not prepare update:", error);
  }
}
```

## Configuration Reference

| Option             | Type                                        | Required | Description                                                      |
| ------------------ | ------------------------------------------- | -------- | ---------------------------------------------------------------- |
| `baseURL`          | `string \| (() => string \| Promise<string>)` | Yes      | Your client handler URL or runtime URL function                  |
| `insights`         | `boolean`                                   | No       | Send app-ready and Bundle adoption events (default: true)        |
| `requestHeaders`   | `Record<string, string>`                    | No       | Shared headers used by update checks and app-ready notifications |
| `requestTimeout`   | `number`                                    | No       | Request timeout in milliseconds (default: 5000)                  |
| `onNotifyAppReady` | `(result: NotifyAppReadyResult) => void`    | No       | Callback invoked after native launch verification finishes       |
| `onError`          | `(error) => void`                           | No       | Default error handler for initialization and update checks       |

`baseURL` is the only React Native transport configuration. A GraphQL, RPC,
or other custom backend must expose the Hot Updater HTTP protocol through an
adapter or proxy and use that endpoint as `baseURL`.

See [`NotifyAppReadyResult`](/docs/react-native-api/notifyAppReady#return-value)
for the `UNCHANGED`, `UPDATE_APPLIED`, and `RECOVERED` result shapes and a
callback example. A callback result describes local native state; it does not
confirm Insights delivery to the server.

`HotUpdater.checkForUpdate({ onError })` overrides the `onError` handler from
`HotUpdater.init` for that specific update check.

If the server intentionally uses the unauthenticated
`clientAccess: { type: "public" }` alternative, omit `x-api-key` from
`requestHeaders`.

## Recommended Flow

Initialize once at module scope, then call `HotUpdater.checkForUpdate` from the
point where your app should check. Initialization returns `void`; no effect,
readiness state or `onNotifyAppReady` callback is required. Use that callback
only when your app needs to observe the native startup result.
