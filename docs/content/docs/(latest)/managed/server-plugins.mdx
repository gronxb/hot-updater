## Overview

A managed server runs the server definition that `hot-updater init` writes,
`hotUpdater.ts`. Its `plugins` start as the provider package's `plugins`:
[`insights()`](/docs/guides/insights) and
[`apiKeys()`](/docs/custom/api-key-authentication). Edit that list to add a
[server plugin](/docs/concepts/plugin-system#server-plugins), such as a
package's or [one you write](/docs/custom/server-plugins), or to drop Insights
or API keys to save cost, then [redeploy](#redeploy) with init.

While `hotUpdater.ts` is the definition init writes, init deploys the
provider's prebuilt server. Once it differs, ignoring formatting, init bundles
it into the managed Worker, Edge Function, Lambda@Edge function, or Cloud
Function. The bundle is minified, keeps function and class names, and carries
no path from your machine.

## Add a plugin

Install the plugin's package in the project that holds `hotUpdater.ts`, and add
the plugin to `plugins`:

```ts title="hotUpdater.ts (excerpt)"
import { d1Database, plugins, r2Storage } from "@hot-updater/cloudflare";
import { createHotUpdater } from "@hot-updater/server";

import { feedback } from "./src/feedback"; // [!code ++]

export const hotUpdater = createHotUpdater({
  // ... database and storage, as init wrote them
  plugins: [...plugins, feedback()], // [!code ++]
});
```

Init bundles the plugin and the npm packages it imports. Only what the runtime
provides stays outside the bundle:

- on Workers, `cloudflare:*` modules;
- on Supabase, the Hot Updater packages and `supabase-js`, which the function's
  import map vendors;
- on Lambda@Edge, the AWS SDK packages Hot Updater's function uses, such as
  `@aws-sdk/client-s3`, `@aws-sdk/lib-dynamodb`, and
  `@aws-sdk/credential-providers`. Another AWS client that a plugin imports is
  bundled, and counts toward the zip's 50 MB;
- on Cloud Functions, `firebase-admin` and `firebase-functions`.

A managed server serves client routes only, whatever the definition lists. A
plugin's client endpoints, such as `POST /feedback`, run there; its admin
endpoints don't. Reach the plugin through the definition instead: through its
CLI commands, and through code that imports the definition, such as a script
that calls `hotUpdater.api.feedback`. The Console shows only Insights and API
keys, which it reads over the database, so it needs no admin routes.

When a plugin names a client plugin, the `App.tsx` code that init prints adds
it to `HotUpdater.init({ plugins })`, and
[`hot-updater doctor`](/docs/guides/doctor#check-client-plugins) warns when the
app doesn't.

## Drop Insights or API keys

Nothing requires `insights()` or `apiKeys()`. List the plugins you keep instead
of the provider's `plugins`:

```ts title="hotUpdater.ts (excerpt)"
import { createHotUpdater } from "@hot-updater/server";
import { insights } from "@hot-updater/server/plugins/insights"; // [!code ++]

export const hotUpdater = createHotUpdater({
  // ... database and storage, as init wrote them
  plugins: [insights()], // [!code ++]
  clientAccess: "public", // [!code ++]
});
```

- Without `apiKeys()`, or another plugin that authenticates clients, set
  `clientAccess: "public"`, which `createHotUpdater` requires. Client routes are
  then public, init provisions no API key, and the app sends none.
- Without `insights()`, the server has no Insights routes, and the Console
  hides Insights. Remove the
  [Insights client plugin](/docs/react-native-api/insights) from the app too,
  since an app whose reports the server doesn't take
  [stops reporting](/docs/react-native-api/insights#when-the-server-has-insights-off)
  for 24 hours at a time.

A plugin you drop keeps its tables and rows: init deletes nothing, and a
definition that adds the plugin back finds its data.

## Redeploy

Rerun init in the project. Init saved the build adapter, the provider, and the
inputs you let it save in `.env.hotupdater`, so this redeploys without prompts:

```bash
npx hot-updater init --from-env-file .env.hotupdater
```

`--from-env-file` reports missing values instead of asking for them: a missing
build adapter or provider before init installs packages, and every missing
provider input once it has installed the provider package, before it creates
or changes any resource. Pass `--provider` and `--build` to choose them
explicitly, or leave out `--from-env-file` to answer prompts. A project that the
[agent infrastructure](#agent-infrastructure) scaffold set up has neither saved,
so pass both:

```bash
npx hot-updater init --provider <cloudflare|supabase|aws|firebase> --build <bare|rock|expo> --from-env-file .env.hotupdater
```

Init follows `server` in `hot-updater.config.ts` to the definition. Before it
creates or changes any resource, it loads the definition with `.env.hotupdater`
applied and checks it:

- The database must be the provider's `d1Database`, `supabaseDatabase`,
  `dynamoDB`, or `firebaseDatabase`, and the storage the provider's `r2Storage`,
  `supabaseStorage`, `s3Storage`, or `firebaseStorage`. Another database or
  storage needs a [custom server](/docs/custom/overview).
- They must reach the resources init set up: the same account, D1 database,
  bucket, table, region, Supabase URL, or Firebase project that
  `.env.hotupdater` holds. Init refuses another value and names the adapter,
  the setting, and both values.
- A definition that imports another managed provider's package is refused; see
  [switching providers](/docs/get-started/basic-usage#switch-providers).
- A package the definition imports must be installed in the project, and the
  bundle can hold only one copy of `@hot-updater/server`: install the version
  your provider package uses.

On Firebase, when init creates a new project, it creates the project first and
stops; the next init checks the definition before it changes the project.

In the managed server, the provider's database and storage are the ones init
set up. The settings the definition passes them are the CLI's, such as its
credentials, and the managed server doesn't read them.

Init creates the tables and settings rows of the plugins the definition lists:

| Provider   | The plugins' tables                                                                                              |
| ---------- | ---------------------------------------------------------------------------------------------------------------- |
| Cloudflare | Init writes a D1 migration of them, which Wrangler applies after the package's migration of core's tables.       |
| Supabase   | Init writes a migration of them, which `supabase db push` applies after the package's migration of core's tables. |
| AWS        | Key prefixes in the one DynamoDB table. Init writes their settings rows.                                         |
| Firebase   | Key prefixes in the one Firestore collection. Init writes their settings rows.                                   |

## A plugin's settings and secrets

Init reads the definition on your machine, with `.env.hotupdater` applied. The
managed server evaluates it again where it runs, and `.env.hotupdater` isn't
there. A value written in `hotUpdater.ts` is bundled with the server, so keep
secrets out of it. A plugin option read from `process.env` is read from the
runtime's environment:

| Provider   | `process.env` in the managed server                                                                                              | A plugin's secret                                                                                   |
| ---------- | -------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| Cloudflare | The Worker's variables and secrets, at module scope too. Init sets `BUCKET_NAME` and `STORAGE_DOWNLOAD_URL_SIGNING_KEY`.          | `npx wrangler secret put <NAME> --name <worker>`. A redeploy keeps secrets and replaces variables. |
| Supabase   | The function's environment: Supabase's `SUPABASE_*` values and the project's secrets.                                            | `npx supabase secrets set <NAME>=<value>`                                                           |
| AWS        | Only Lambda's reserved variables, such as `AWS_REGION`: Lambda@Edge takes no variables of your own.                              | None. Host a plugin that needs one on a [custom server](/docs/custom/overview).                     |
| Firebase   | What Cloud Functions sets, such as `GCLOUD_PROJECT` and `FIREBASE_CONFIG`. Init deploys no `.env` file with the function.         | None through init. Host a plugin that needs one on a [custom server](/docs/custom/overview).        |

A value missing where the server runs reaches the plugin as whatever the
runtime has, often `undefined`.

## AWS

- **Routes:** CloudFront sends each plugin client endpoint to the function
  uncached, with the request's headers, cookies, and query string. The behavior
  covers the endpoint's path up to its first parameter, then `*`: `/notes/:id`
  becomes `/notes/*`. Init refuses an endpoint under `/bundles` or `/assets`,
  or one that starts with a parameter such as `/:id`, since CloudFront serves
  bundles from S3 there. A plugin you drop loses its behaviors.
- **Permissions:** the function's role reads core's tables and the listed
  plugins' tables, and writes only the plugins' tables and the aggregate log
  and lease; core's tables and the settings rows change only through the CLI.
  While CloudFront still runs the previous version, the role keeps that
  version's access, and the first init after the distribution reports the new
  version as Deployed removes it.
- **Policy size:** IAM limits a role's inline policies to 10,240 characters.
  Init checks this when it sets up the role, after the bucket, the table, and
  the API key. It refuses a definition whose plugins' tables go past the limit,
  and names the plugins. When only the kept access of the previous version goes
  past it, init asks for two inits: first a definition without the plugins it
  drops, then, once the distribution reports that deploy as Deployed, one with
  the plugins it adds.
- **Zip size:** the function's zip must stay under Lambda@Edge's 50 MB limit.
  Init checks it before it creates a resource.

## Agent infrastructure

The [agent infrastructure](/docs/guides/agent-infrastructure) scaffold deploys
the prebuilt servers: keep its `app/hotUpdater.ts` as it is. Its D1 and
Supabase migrations are core's tables, then the prebuilt server's plugins'
tables. To run other plugins, edit the definition and deploy it with init,
passing `--provider` and `--build`, as [Redeploy](#redeploy) shows: the scaffold
doesn't save the build and provider that `--from-env-file` reads.
