## Overview

Use this preset to provision an OTA server on Firebase. For a new app,
start with [Choose infrastructure](/docs/get-started/choose-provider). Provision
the provider resources here, then connect your app with the verified URL and key.

## Prerequisites

Your deployment needs the resources and access below. When using an AI agent,
it can prepare missing resources through its available provider tools.

- **Node.js**: The CLI requires 20.19+. Agent setup uses a client-key helper that
  requires Node 22.18+ or Node 24+; prepare it before provisioning resources.
- **Firebase account and project access**: Sign in to the account that will own the deployment. An agent can discover an existing project or create a missing one.
- **Google Cloud CLI (terminal setup)**: Install `gcloud` and authenticate the account that owns the Firebase project.
- **Service readiness**: Agent setup can enable Storage and prepare Firestore. Terminal init needs Storage enabled so it can find the project's canonical default `.firebasestorage.app` or `.appspot.com` bucket. Complete any required billing activation in your account when prompted.

## Step 1: Install Required Packages

Complete [Install v1 packages](/docs/get-started/installation) in the React
Native project before running init or an agent scaffold. Install the CLI, React
Native SDK, and the build plugin that matches your app, then install this provider:

```package-install
npm install @hot-updater/firebase --save-dev
```

An agent can perform these steps after inspecting the app's package manager
and build configuration.

After setup, review the local configuration. Interactive init writes the settings
below to `.env.hotupdater`; an agent merges the needed settings into your project.
The project, region, and canonical bucket are persisted for deterministic reruns.
The service-account path is included only when configured and approved for
persistence.

```
HOT_UPDATER_FIREBASE_PROJECT_ID=your-project-id
HOT_UPDATER_FIREBASE_REGION=your-functions-region
HOT_UPDATER_FIREBASE_STORAGE_BUCKET=your-bucket-name
HOT_UPDATER_API_KEY=your-api-key
# Optional: only if using a private credential file instead of existing ADC
# GOOGLE_APPLICATION_CREDENTIALS=/private/path/your-credentials.json
```

Managed init reuses `HOT_UPDATER_API_KEY` when supplied or creates an API key,
registers it in Firestore, and persists the plaintext value locally. Send this
API key in the app's `x-api-key` request header. Do not run
`hot-updater api-key create` for a managed installation.

<Callout type="warn">

Provider credentials from `.env.hotupdater` are not included in your app bundle
unless you explicitly configure that behavior. The API key is the exception:
add `HOT_UPDATER_API_KEY` to your React Native build-time configuration as
shown in [Set up your app](/docs/get-started/app-setup), but never add the Firebase service-account credential.

For more details, see:
[Security](/docs/policy/security#plugin-token-protection)

</Callout>

## Optional: Bundle Signing

Managed Firebase init does not create or enable a signing key. The
[built-in local config](/docs/guides/bundle-signing#local-private-key) works
without a signing plugin. For non-exportable key custody, use the
[Google Cloud KMS signer](/docs/guides/bundle-signing#hardened-google-cloud-kms)
from `hot-updater/signing`; signing is independent of storage and database
choice. Embed the chosen public key in a native release before deploying
signed bundles. Signing credentials belong in the deploy environment, never
in the React Native app.

## Step 3: Add HotUpdater to Your Project

After provisioning, record these outputs for [Set up your app](/docs/get-started/app-setup):

| Output | Value |
| --- | --- |
| Client base URL | `<verified Firebase Function URL>` |
| Client request header | `x-api-key` |
| Client API key | The saved `HOT_UPDATER_API_KEY` in your ignored `.env.hotupdater` |
| Deploy configuration | `hot-updater.config.ts` and the selected provider resources |

Use the actual URL returned by deployment. Configure the SDK and native bundle
loader through [Set up your app](/docs/get-started/app-setup), using the selected
build plugin and the same update strategy as `hot-updater.config.ts`. Only the
client API key belongs in the mobile app's build-time configuration; provider
credentials stay in the deploy environment.

<Callout type="info">
  The managed Firebase runtime exposes `/version` publicly. OTA update checks
  and Insights ingestion require `x-api-key: $HOT_UPDATER_API_KEY`. Internally,
  it enables Insights and mounts only `handlers.client`. Admin routes,
  including Insights queries, are not mounted on the public Function URL.
</Callout>

## Generated Configuration and Operations

During the initialization process, the following file is automatically generated:

- `hot-updater.config.ts`: This file contains the configuration settings for integrating Firebase with your project.
- `.env.hotupdater`: Provider settings and optional credential-file path. Reuse
  working application-default credentials first. Set `GOOGLE_APPLICATION_CREDENTIALS`
  only when a private local credential file is needed; downloading a new key is
  not required when ADC already works. A Firebase CLI login alone does not
  necessarily authenticate the local Admin SDK. See
  [Firebase Admin setup](https://firebase.google.com/docs/admin/setup#initialize_the_sdk_in_non-google_environments).

```bash title=".env.hotupdater"
HOT_UPDATER_FIREBASE_PROJECT_ID=your-project-id
HOT_UPDATER_FIREBASE_REGION=your-functions-region
HOT_UPDATER_FIREBASE_STORAGE_BUCKET=your-bucket-name
HOT_UPDATER_API_KEY=your-api-key
# Optional: only if using a private credential file instead of existing ADC
# GOOGLE_APPLICATION_CREDENTIALS=/private/path/your-credentials.json
```

```ts title="hot-updater.config.ts"
import { bare } from "@hot-updater/bare";
import { firebaseStorage, firebaseDatabase } from "@hot-updater/firebase";
import { applicationDefault } from "firebase-admin/app";
import { defineConfig } from "hot-updater";
import { config } from "dotenv";

config({ path: ".env.hotupdater" });

// https://firebase.google.com/docs/admin/setup?hl=en#initialize_the_sdk_in_non-google_environments
// Reuse working application-default credentials (ADC).
// Only when a credential file is needed, set its private local path in .env.hotupdater:
// GOOGLE_APPLICATION_CREDENTIALS=./firebase-adminsdk-credentials.json
const credential = applicationDefault();

export default defineConfig({
  build: bare({
    enableHermes: true,
  }),
  updateStrategy: "appVersion",
  storage: firebaseStorage({
    projectId: process.env.HOT_UPDATER_FIREBASE_PROJECT_ID!,
    storageBucket: process.env.HOT_UPDATER_FIREBASE_STORAGE_BUCKET!,
    credential,
  }),
  database: firebaseDatabase({
    projectId: process.env.HOT_UPDATER_FIREBASE_PROJECT_ID!,
    credential,
  }),
});
```

### Resource names

Managed Firestore collections use the fixed `hot_updater_v1_*` namespace,
and the managed Function is named `hot-updater-v1`. Bundles use the project's
canonical Storage bucket with independent object keys.

### Release catalog cache

Firebase uses the direct `hot-updater-v1` Function URL in `origin-only` mode.
Init prints the deployed URL and does not deploy Firebase Hosting, because the
default Hosting site may already belong to the app or another service.
Catalog checks still use the precompiled Release Catalog and the runtime's
short in-process cache, but every device request invokes the Function.

## Upgrade infrastructure

With the [Hot Updater skill](/docs/guides/ai-agents) attached, ask your agent:

```text
$hot-updater Upgrade this project's existing Firebase server infrastructure.
```

The agent discovers the existing deployment, uses `hot-updater agent infra upgrade`,
and reads the applicable version files before changing resources. It applies pending
changes and verifies the server with doctor. See
[Upgrade an existing server](/docs/guides/agent-infrastructure#upgrade-an-existing-server)
for the workflow or [Doctor](/docs/guides/doctor#update-outdated-infrastructure)
for terminal instructions.

For server templates to apply with your own deployment tooling, use
`hot-updater infra scaffold --provider firebase`. See
[Infrastructure Templates](/docs/guides/infrastructure-templates).

## Verifying the Setup

1. Confirm the selected Firebase resources and the deployed client base URL.
2. From the React Native project, check the server and native integration:

   ```bash
   npx hot-updater doctor --server-base-url <client-base-url> --json
   ```

   Doctor checks the public `/version` endpoint. It does not prove an
   authenticated update download or application.
3. Complete [Test an OTA update](/docs/guides/simulator-test) on a release build.
   Verify that the app downloads and runs the changed code, then survives a restart.

An agent should report the selected resources, verified URL, configuration file
paths and verification result. Report a missing access, billing or native-build
prerequisite explicitly instead of marking an untested installation complete.

## Host the Console

Host the console on **Vercel, Netlify, or Docker/Node** with Firebase Admin SDK
credentials. Cloud Run is another option when you want to use the existing
Google Cloud project and service identity. See the
[console hosting matrix](/docs/guides/console-deployment#choose-a-host).
