## Overview

Use this preset to provision an OTA server on Azure: bundles in Azure Blob
Storage, metadata in Azure Cosmos DB for NoSQL, and the server in an Azure
Functions app. For a new app, start with
[Choose infrastructure](/docs/get-started/choose-provider). Provision the
provider resources here, then connect your app with the verified URL and key.

## Prerequisites

You need the following resources and access. An AI agent can prepare missing
resources through its available provider tools.

- **Node.js**: The CLI and the agent setup's client-key helper require
  Node.js 22.23.4+, 24.22.1+, or 26.12.1+. The Function runs on Node.js 22.
- **Azure subscription**: Sign in with an account that can create resource
  groups, storage accounts, Cosmos DB accounts, and Function Apps in the
  subscription.
- **Azure CLI 2.60.0+ (terminal setup)**: Install
  [`az`](https://learn.microsoft.com/cli/azure/install-azure-cli); Flex
  Consumption needs 2.60.0 or later. Init runs
  `az login` when the CLI is not signed in yet.

## Step 1: Install required packages

Complete [Install packages](/docs/get-started/installation) in the React
Native project before running init or an agent scaffold. Install the CLI, React
Native SDK, and the build adapter that matches your app, then install this provider:

```package-install
npm install @hot-updater/azure --save-dev
```

An agent can perform these steps after inspecting the app's package manager
and build configuration.

After setup, review the local configuration. Interactive init writes the
settings below to `.env.hotupdater`; an agent merges the needed settings into
your project. The resource names are persisted for deterministic reruns, and
init saves the two connection strings, which `hot-updater.config.ts` reads to
reach the storage account and Cosmos DB, again on every run.

```
HOT_UPDATER_AZURE_SUBSCRIPTION_ID=your-subscription-id
HOT_UPDATER_AZURE_RESOURCE_GROUP=hot-updater
HOT_UPDATER_AZURE_LOCATION=eastus
HOT_UPDATER_AZURE_STORAGE_ACCOUNT=your-storage-account
HOT_UPDATER_AZURE_COSMOS_ACCOUNT=your-cosmos-account
HOT_UPDATER_AZURE_FUNCTION_APP=your-function-app
HOT_UPDATER_AZURE_STORAGE_CONNECTION_STRING=DefaultEndpointsProtocol=https;AccountName=...
HOT_UPDATER_AZURE_COSMOS_CONNECTION_STRING=AccountEndpoint=https://...;AccountKey=...
HOT_UPDATER_API_KEY=your-api-key
```

Managed init reuses `HOT_UPDATER_API_KEY` when supplied or creates an API key,
registers it in Cosmos DB, and persists the plaintext value locally. Send this
API key in the app's `x-api-key` request header. To list, add, or revoke
keys later, run `hot-updater api-key` from the app directory.

<Callout type="warn">

Provider credentials from `.env.hotupdater` are not included in your app bundle
unless you explicitly configure that behavior. The API key is the exception:
add `HOT_UPDATER_API_KEY` to your React Native build-time configuration as
shown in [Set up your app](/docs/get-started/app-setup), but never add the
Azure connection strings.

See [Security](/docs/policy/security#plugin-token-protection).

</Callout>

## Optional: Bundle signing

Managed Azure init does not create or enable a signing key. The
[built-in local config](/docs/guides/bundle-signing#local-private-key) works
without a signing adapter. Signing is independent of storage and database
choice; embed the chosen public key in a native release before deploying
signed bundles. Signing credentials belong in the deploy environment, never
in the React Native app.

## Step 3: Add HotUpdater to your project

After provisioning, record these outputs for [Set up your app](/docs/get-started/app-setup):

| Output                | Value                                                                                 |
| --------------------- | ------------------------------------------------------------------------------------- |
| Client base URL       | `https://<Function App default host name>`                                            |
| Client request header | `x-api-key`                                                                           |
| Client API key        | The saved `HOT_UPDATER_API_KEY` in your ignored `.env.hotupdater`, or your team store |
| Deploy configuration  | `hot-updater.config.ts` and the selected provider resources                           |

Use the actual URL init prints. Configure the SDK and native bundle loader
through [Set up your app](/docs/get-started/app-setup), using the selected
build adapter and the same update strategy as `hot-updater.config.ts`. Only the
client API key belongs in the mobile app's build-time configuration; provider
credentials stay in the deploy environment.

<Callout type="info">
  The managed Azure runtime exposes `/version` publicly. OTA update checks,
  Insights ingestion, and Remote Config fetches require `x-api-key:
  $HOT_UPDATER_API_KEY`. Internally, the Function runs the `insights()`,
  `apiKeys()`, and `remoteConfig()` plugins and mounts only `handlers.client`.
  Admin routes, including Insights queries and Remote Config publishing, are not
  mounted on the public Function URL.
</Callout>

## Generated configuration and operations

Init generates `hot-updater.config.ts` with your Azure storage and database,
and `plugins`: the server plugins the managed Function runs, `apiKeys()`,
`insights()`, and `remoteConfig()`, imported from `hot-updater/plugins`.
The CLI and the Console reach Blob Storage and Cosmos DB through these settings
and run the same plugins as the Function. The managed Function runs these
official plugins only; to run other server plugins, use a
[custom server](/docs/custom/overview).

The config names the Cosmos DB account init chose and reads both connection
strings with
[`secret()`](/docs/concepts/secrets#adapter-credentials):
the environment and `.env.hotupdater` first, then the config's `secrets`
adapter. With a
[team store](/docs/concepts/secrets#this-machine-or-the-team) there, such as
[`keyVault()`](/docs/guides/secrets-adapters/azure-key-vault) from
`@hot-updater/azure`, init also stores them and `HOT_UPDATER_API_KEY` in it, so a teammate's commands
read them there.

On a rerun, init updates `storage`, `database`, and `plugins` in the existing
file and keeps your other settings, including a wrapped build such as
`withSentry(bare())`. When it cannot edit `hot-updater.config.ts`, such as a
config that a function returns, it leaves the file unchanged and prints the
`storage`, `database`, and `plugins` lines to add.

```ts title="hot-updater.config.ts"
import { azureBlobStorage, cosmosDatabase } from "@hot-updater/azure";
import { bare } from "@hot-updater/bare";
import { defineConfig, localSecrets, secret } from "hot-updater";
import { apiKeys, insights, remoteConfig } from "hot-updater/plugins";
import { existsSync } from "node:fs";

if (existsSync(".env.hotupdater")) {
  process.loadEnvFile(".env.hotupdater");
}

export default defineConfig({
  build: bare({ enableHermes: true }),
  storage: azureBlobStorage({
    connectionString: secret("HOT_UPDATER_AZURE_STORAGE_CONNECTION_STRING"),
    containerName: "hot-updater",
  }),
  database: cosmosDatabase({
    endpoint: "https://your-cosmos-account.documents.azure.com:443/",
    connectionString: secret("HOT_UPDATER_AZURE_COSMOS_CONNECTION_STRING"),
  }),
  plugins: [apiKeys(), insights(), remoteConfig()],
  secrets: localSecrets(), // keys from apple login and secrets put
  updateStrategy: "appVersion", // or "fingerprint"
});
```

### Resource names

Bundles live in the storage account's `hot-updater` container. Cosmos DB
keeps every item in the `hot_updater_v1` container of the `hot-updater`
database. The Function App serves every route from its default host name: its
`host.json` drops the `/api` route prefix. The Function reads its storage and
Cosmos DB connection strings from the app settings
`HOT_UPDATER_AZURE_STORAGE_CONNECTION_STRING`,
`HOT_UPDATER_AZURE_BLOB_CONTAINER`, and
`HOT_UPDATER_AZURE_COSMOS_CONNECTION_STRING`.

### Release catalog cache

Azure uses the Function App URL in `origin-only` mode. Catalog checks use the
precompiled Release Catalog and the runtime's short in-process cache, but every
device request invokes the Function. Devices download bundles through
read-only SAS URLs that expire after an hour.

## Upgrade infrastructure

Rerun init with the inputs it saved in `.env.hotupdater`, the command
[`hot-updater doctor`](/docs/guides/doctor#update-outdated-infrastructure)
names for an outdated server:

```package-install
npx hot-updater init --provider azure --from-env-file .env.hotupdater
```

It applies the release's database migrations, then redeploys the Function App
from the installed `@hot-updater/azure`, back to back: after a release whose schema changed, the server answers
503 only while it deploys. With the
[Hot Updater skill](/docs/guides/ai-agents) attached, you can also ask your
agent:

```text
$hot-updater Upgrade this project's existing Azure server infrastructure.
```

The agent discovers the existing deployment, uses `hot-updater agent infra upgrade`,
and reads the applicable version files before changing resources. It applies pending
changes and verifies the server with doctor. See
[Upgrade an existing server](/docs/guides/agent-infrastructure#upgrade-an-existing-server)
for the workflow or [Doctor](/docs/guides/doctor#update-outdated-infrastructure)
for terminal instructions.

For server templates to apply with your own deployment tooling, use
`hot-updater infra scaffold --provider azure`. See
[Infrastructure Templates](/docs/guides/infrastructure-templates).

## Verifying the setup

1. Confirm the selected Azure resources and the deployed client base URL.
2. From the React Native project, check the server and native integration:

   ```bash
   npx hot-updater doctor --server-base-url <client-base-url> --json
   ```

   Doctor checks the public `/version` endpoint. It does not prove an
   authenticated update download or application.

3. Complete [Test an OTA update](/docs/get-started/test-ota) on a release build.
   Verify that the app downloads and runs the changed code, then survives a restart.

An agent should report the selected resources, verified URL, configuration file
paths and verification result. Report a missing access, quota or native-build
prerequisite explicitly instead of marking an untested installation complete.

## Host the Console

Host the console on **Vercel, Netlify, or Docker/Node** with the same two
connection strings. Azure App Service or Azure Container Apps are other options
when you want to keep the Console in the same subscription. See the
[console hosting matrix](/docs/guides/console-deployment#choose-a-host).
