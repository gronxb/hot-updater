## Overview

Use this preset to provision an OTA server on Vercel: bundles in a Vercel Blob
store, metadata in a PostgreSQL database, and the server in a Vercel Function.
For a new app, start with [Choose infrastructure](/docs/get-started/choose-provider).
Provision the provider resources here, then connect your app with the verified
URL and key.

## Prerequisites

You need the following resources and access. An AI agent can prepare missing
resources through its available provider tools.

- **Node.js**: The CLI and the agent setup's client-key helper require
  Node.js 22.23.4+, 24.22.1+, or 26.12.1+.
- **Vercel account**: Sign up at [Vercel](https://vercel.com) if you don't have one.
  Init signs in with the Vercel CLI, or uses `VERCEL_TOKEN` when it is set.
- **PostgreSQL database**: A database from the
  [Vercel Marketplace](https://vercel.com/marketplace/category/database), such as
  Neon, connected to the project, or any PostgreSQL connection URL. Init can
  create a Neon database for you; the Vercel CLI asks you to accept Neon's terms
  the first time.

## Step 1: Install required packages

Complete [Install packages](/docs/get-started/installation) in the React
Native project before running init or an agent scaffold. Install the CLI, React
Native SDK, and the build adapter that matches your app, then install this provider:

```package-install
npm install @hot-updater/vercel --save-dev
```

An agent can perform these steps after inspecting the app's package manager
and build configuration.

After setup, review the local configuration. Interactive init writes the settings
below to `.env.hotupdater`; an agent merges the needed settings into your project.
Resource names and IDs are persisted for deterministic reruns. The Blob token, the database URL and `VERCEL_TOKEN` are persisted only
when you consent.

```
HOT_UPDATER_VERCEL_TEAM_ID=your-team-id
HOT_UPDATER_VERCEL_PROJECT_NAME=your-project-name
HOT_UPDATER_VERCEL_PROJECT_ID=your-project-id
HOT_UPDATER_VERCEL_BLOB_STORE_NAME=your-blob-store-name
HOT_UPDATER_VERCEL_BLOB_STORE_ID=your-blob-store-id
HOT_UPDATER_API_KEY=your-api-key
# Included only when credential persistence is approved:
HOT_UPDATER_VERCEL_BLOB_READ_WRITE_TOKEN=your-blob-read-write-token
HOT_UPDATER_VERCEL_DATABASE_URL=your-postgres-url
```

Init connects the Blob store to the project's production environment, which adds
`HOT_UPDATER_VERCEL_BLOB_READ_WRITE_TOKEN` to the project, and sets
`HOT_UPDATER_VERCEL_DATABASE_URL` there. The Function reads these production
environment variables.

The Blob store is always private: devices download bundles only through signed
URLs that expire, which the server issues to requests with a valid API key. Init
does not use a public store.

Managed init reuses `HOT_UPDATER_API_KEY` when supplied or creates an API key,
registers it in the database, and persists the plaintext value locally. Send this
API key in the app's `x-api-key` request header. To list, add, or revoke
keys later, run `hot-updater api-key` from the app directory.

<Callout type="warn">

Provider credentials from `.env.hotupdater` are not included in your app bundle
unless you explicitly configure that behavior. The API key is the exception:
add `HOT_UPDATER_API_KEY` to your React Native build-time configuration as
shown in [Set up your app](/docs/get-started/app-setup), but never add the Blob
token, the database URL or a Vercel token.

See [Security](/docs/policy/security#plugin-token-protection).

</Callout>

## Optional: Bundle signing

Managed Vercel init does not create or enable a signing key. Run
`npx hot-updater secrets issue bundle-signing-key`, which sets
`signing: secret("bundle-signing-key")`, then embed the public key in a
native release before deploying signed bundles: see
[Bundle Signing](/docs/guides/bundle-signing). Until then, `deploy` warns
that bundles are unsigned. The signing key belongs in the deploy environment,
never in the React Native app.

## Step 3: Add HotUpdater to your project

After provisioning, record these outputs for [Set up your app](/docs/get-started/app-setup):

| Output                | Value                                                                                 |
| --------------------- | ------------------------------------------------------------------------------------- |
| Client base URL       | The project's production domain, such as `https://<your-project>.vercel.app`          |
| Client request header | `x-api-key`                                                                           |
| Client API key        | The saved `HOT_UPDATER_API_KEY` in your ignored `.env.hotupdater`, or your team store |
| Deploy configuration  | `hot-updater.config.ts` and the selected provider resources                           |

Use the URL init prints. Configure the SDK and native bundle loader through
[Set up your app](/docs/get-started/app-setup), using the selected build adapter
and the same update strategy as `hot-updater.config.ts`. Only the client API key
belongs in the mobile app's build-time configuration; provider credentials stay
in the deploy environment.

<Callout type="info">
  The managed Vercel Function exposes `/version` publicly. OTA update checks,
  Insights ingestion, and Remote Config fetches require `x-api-key:
  $HOT_UPDATER_API_KEY`. Internally, the Function runs the `insights()`,
  `apiKeys()`, and `remoteConfig()` plugins and mounts only `handlers.client`.
  Admin routes, including Insights queries and Remote Config publishing, are not
  mounted on the production URL.
</Callout>

## Generated configuration and operations

Init generates `hot-updater.config.ts` with your Vercel Blob storage and
PostgreSQL database, and `plugins`: the server plugins the managed Function
runs, `apiKeys()`, `insights()`, and `remoteConfig()`, imported from
`hot-updater/plugins`. The CLI and the Console reach the Blob store and the
database through these settings and run the same plugins as the Function. The
managed Function runs these official plugins only; to run other server plugins,
use a [custom server](/docs/custom/overview).

The config reads the Blob token and the database URL with
[`secret()`](/docs/concepts/secrets#adapter-credentials):
the environment and `.env.hotupdater` first, then the config's `secrets`
adapter. With a
[team store](/docs/concepts/secrets#this-machine-or-the-team) there, init
also stores them and `HOT_UPDATER_API_KEY` in it, so a teammate's commands
read them there.

On a rerun, init updates `storage`, `database`, and `plugins` in the existing
file and keeps your other settings, including a wrapped build such as
`withSentry(bare())`. When it cannot edit `hot-updater.config.ts`, such as a
config that a function returns, it leaves the file unchanged and prints the
`storage`, `database`, and `plugins` lines to add.

```ts title="hot-updater.config.ts"
import { bare } from "@hot-updater/bare";
import { postgres, vercelBlobStorage } from "@hot-updater/vercel";
import { defineConfig, localSecrets, secret } from "hot-updater";
import { apiKeys, insights, remoteConfig } from "hot-updater/plugins";
import { existsSync } from "node:fs";

if (existsSync(".env.hotupdater")) {
  process.loadEnvFile(".env.hotupdater");
}

export default defineConfig({
  build: bare({ enableHermes: true }),
  storage: vercelBlobStorage({
    token: secret("HOT_UPDATER_VERCEL_BLOB_READ_WRITE_TOKEN"),
  }),
  database: postgres({
    connectionString: secret("HOT_UPDATER_VERCEL_DATABASE_URL"),
  }),
  plugins: [apiKeys(), insights(), remoteConfig()],
  secrets: localSecrets(), // keys from apple login and secrets put
  updateStrategy: "appVersion", // or "fingerprint"
});
```

## Upgrade infrastructure

Rerun init with the inputs it saved in `.env.hotupdater`, the command
[`hot-updater doctor`](/docs/guides/doctor#update-outdated-infrastructure)
names for an outdated server:

```package-install
npx hot-updater init --provider vercel --from-env-file .env.hotupdater
```

It applies the release's database migrations, then redeploys the Function
from the installed `@hot-updater/vercel`, back to back: after a release whose schema changed, the server answers
503 only while it deploys. With the
[Hot Updater skill](/docs/guides/ai-agents) attached, you can also ask your
agent:

```text
$hot-updater Upgrade this project's existing Vercel server infrastructure.
```

The agent discovers the existing deployment, uses `hot-updater agent infra upgrade`,
and reads the applicable version files before changing resources. It applies pending
changes and verifies the server with doctor. See
[Upgrade an existing server](/docs/guides/agent-infrastructure#upgrade-an-existing-server)
for the workflow or [Doctor](/docs/guides/doctor#update-outdated-infrastructure)
for terminal instructions.

For server templates to apply with your own deployment tooling, use
`hot-updater infra scaffold --provider vercel`. See
[Infrastructure Templates](/docs/guides/infrastructure-templates).

## Verifying the setup

1. Confirm the selected Vercel resources and the deployed client base URL.
2. From the React Native project, check the server and native integration:

   ```bash
   npx hot-updater doctor --server-base-url <client-base-url> --json
   ```

   Doctor checks the public `/version` endpoint. It does not prove an
   authenticated update download or application.

3. Complete [Test an OTA update](/docs/get-started/test-ota) on a release build.
   Verify that the app downloads and runs the changed code, then survives a restart.

An agent should report the selected resources, verified URL, configuration file
paths and verification result. Report a missing access, billing or native-build
prerequisite explicitly instead of marking an untested installation complete.

with the same Blob store and database settings. See the
