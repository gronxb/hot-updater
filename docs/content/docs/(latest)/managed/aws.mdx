## Prerequisites

Before you begin, make sure the following are ready:

- **Node.js**: Version 20.19 or later is required; Node 22 is recommended.
- **AWS Account**: Sign up at [AWS](https://aws.amazon.com) if you don't have one.
- **AWS CLI**: Install the AWS CLI and sign in or configure a profile.

## Required AWS Permissions

Hot Updater requires specific AWS IAM permissions for setup and ongoing usage:

### 1. Initialization (One-Time Setup)

Used for `hot-updater init`:

- `AmazonS3FullAccess`: Create and read S3 buckets.
- `AmazonDynamoDBFullAccess_v2`: Create and configure the metadata table.
- `AWSLambda_FullAccess`: Create and update Lambda functions.
- `CloudFrontFullAccess`: Manage CloudFront distributions.
- `IAMFullAccess`: Create IAM roles for Lambda@Edge.
- `AmazonSSMFullAccess`: Access SSM Parameters used for CloudFront key pairs.

### 2. Ongoing Usage

Used for `hot-updater deploy` and `hot-updater console`:

- `AmazonS3FullAccess`: Manage bundle artifacts in the S3 bucket.
- DynamoDB table access for metadata queries and writes.
- `cloudfront:CreateInvalidation`: Invalidate CloudFront cache after deployments.

For ongoing usage, create a separate access token with limited permissions. Here's a minimal policy example for CloudFront invalidation:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": ["cloudfront:CreateInvalidation"],
      "Resource": "arn:aws:cloudfront::<ACCOUNT_ID>:distribution/<DISTRIBUTION_ID>"
    }
  ]
}
```

If this permission is missing, you may encounter the following error:

```
AccessDenied: User: arn:aws:sts::***:assumed-role/***/*** is not authorized to perform: cloudfront:CreateInvalidation on resource: arn:aws:cloudfront::***:distribution/*** because no identity-based policy allows the cloudfront:CreateInvalidation action
```


Once setup is complete, `.env.hotupdater` may include the following values.
Resource selections and the authentication mode are persisted for deterministic
reruns. AWS credentials are included only for account/access-key mode and only
when you consent to storing them.

```
HOT_UPDATER_DYNAMODB_TABLE_NAME=hot-updater
HOT_UPDATER_AWS_AUTH_MODE=local-session
HOT_UPDATER_AWS_LAMBDA_NAME=hot-updater-edge
HOT_UPDATER_S3_BUCKET_NAME=your-s3-bucket-name
HOT_UPDATER_S3_REGION=your-region
HOT_UPDATER_CLOUDFRONT_DISTRIBUTION_ID=your-distribution-id
HOT_UPDATER_API_KEY=your-api-key
```

Init reuses `HOT_UPDATER_API_KEY` when supplied or creates an API key,
registers it in DynamoDB, and persists the plaintext value locally. Send this
API key in the app's `x-api-key` request header. It does not authorize
management or Analytics-query routes.

If you choose a shared AWS profile or SSO, the generated env file also includes:

```bash
HOT_UPDATER_AWS_PROFILE=your-profile-name
```

If you choose the current AWS CLI/default session mode, no extra credential env
variables are written. The generated config uses the AWS SDK default provider
chain directly.

If you choose account/access-key mode and consent to persistence, the generated
env file also includes:

```bash
# The generated key may be over-privileged or temporary depending on how you authenticated during init.
HOT_UPDATER_S3_ACCESS_KEY_ID=your-access-key-id
HOT_UPDATER_S3_SECRET_ACCESS_KEY=your-secret-access-key
```

## Cost and capacity

Managed AWS init uses DynamoDB on-demand capacity, so an idle installation has
no provisioned read/write capacity charge. Release-catalog requests use a
dedicated CloudFront behavior whose cache key contains the canonical path,
`x-api-key`, and supported content encoding. It excludes SDK version,
Authorization, cookies, query strings, and installation state. A cold origin
fill performs one exact DynamoDB catalog read; a warm CloudFront hit skips both
Lambda@Edge and DynamoDB. Each authenticated Analytics event invokes
Lambda@Edge and appends one event row; server-side Analytics queries read event
pages from DynamoDB.
Review the [DynamoDB pricing model](https://aws.amazon.com/dynamodb/pricing/) and
[Lambda@Edge pricing](https://aws.amazon.com/lambda/pricing/).

Each API key authorizes OTA selectors and event ingestion, but not
Analytics query or management routes. Managed tables cap on-demand throughput
at 4,000 reads and 100 writes per second for both the table and update index.
The cap is a cost guardrail and can throttle bursts; protect production
distributions with AWS WAF rate-based rules and configure AWS Budgets for a
monthly spending threshold. The AWS adapter does not impose an Analytics
retention period. The bounded Analytics provider still rejects `all` reports
above 50,000 events, while 24-hour, 7-day, and 30-day queries apply their query
window independently of storage retention.

Bundle metadata has no fixed bundle, patch, or patch-relationship count limit.
Each serialized metadata item is limited to 8 KiB. The database maintains counters
and relation counts in the same transactions as metadata writes. Cursor pages
and exact/single-owner hydration use targeted key/index reads; owner-index keys
are hydrated from strongly consistent base-table rows and unprocessed batch keys
use bounded exponential backoff. Unfiltered totals use the transactionally
maintained metadata counter. Broad filtered scans paginate through all matching
metadata and may be throttled by the managed table's throughput cost guardrail.
DynamoDB's 100-action transaction service limit applies to the complete
`commit({ mutations })` envelope, including cascade deletions.

New tables enable deletion protection. Init validates the billing mode,
throughput caps, string key types, and index layout before reusing an existing
table, then enables point-in-time recovery on both new and compatible reused
tables. Point-in-time recovery is a billed DynamoDB feature. Init does not
change deletion protection on an operator-owned reused table.

New distributions use `PriceClass_All` to preserve worldwide OTA latency. The
Release-catalog behavior honors the server's five-second shared TTL. Catalog
authentication failures, missing rows, and server errors are private and are
not cached. Cache identity uses only the API key and content encoding;
the removed v0 SDK-version header is not forwarded.

If regional reach matters less than transfer price, change the distribution price
class in AWS after init; later init runs preserve that setting. Init invalidates
only `/version`, `/events`, `/release-catalogs/*`, and `/artifacts/*`, leaving
immutable bundle caches warm.
CloudFront provides the first 1,000 invalidation paths per account each month
at no extra charge; see [invalidation pricing](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/PayingForInvalidation.html).

Rerunning init preserves unrelated CloudFront origins/cache behaviors and S3
bucket-policy statements. Lambda roles are isolated by Lambda name and grant
access only to the selected bucket, SSM parameter, DynamoDB table, and update
index. Init provisions these resources through AWS APIs rather than a
CloudFormation stack, so deletion and rollback remain operator-managed.

Init does not upgrade a v0 CloudFront endpoint in place. It checks the selected
distribution's `/version` response before writing env files or changing AWS
resources. If the generation-1 marker is missing, use new S3, DynamoDB, Lambda,
and CloudFront resources and ship the new endpoint in a new native build. Keep
the v0 distribution available for installed v0 binaries that still need OTA
service.

## Step 3: Generated Configurations

During the initialization process, the following file is automatically generated:

- `hot-updater.config.ts`: This file contains the configuration settings for integrating AWS with your project.

If you choose **current AWS CLI/default session**, the generated config uses the
AWS SDK default provider chain instead of embedding access keys:

```ts title="hot-updater.config.ts"
import { bare } from "@hot-updater/bare";
import { fromNodeProviderChain } from "@aws-sdk/credential-providers";
import { dynamoDB, s3Storage } from "@hot-updater/aws";
import { defineConfig } from "hot-updater";
import { config } from "dotenv";

config({ path: ".env.hotupdater" });

const awsOptions = {
  region: process.env.HOT_UPDATER_S3_REGION!,
  credentials: fromNodeProviderChain(),
};

const storageOptions = {
  ...awsOptions,
  bucketName: process.env.HOT_UPDATER_S3_BUCKET_NAME!,
};

export default defineConfig({
  authorityId: "aws.<generated-authority-id>",
  build: bare({ enableHermes: true }),
  updateStrategy: "appVersion",
  storage: s3Storage(storageOptions),
  database: dynamoDB({
    ...awsOptions,
    tableName: process.env.HOT_UPDATER_DYNAMODB_TABLE_NAME!,
    // prettier-ignore
    cloudfrontDistributionId: process.env.HOT_UPDATER_CLOUDFRONT_DISTRIBUTION_ID!,
  }),
});
```

If you choose **shared AWS profile**, `fromNodeProviderChain()` is replaced with
`fromIni({ profile: process.env.HOT_UPDATER_AWS_PROFILE! })`. SSO uses
`fromSSO({ profile: process.env.HOT_UPDATER_AWS_PROFILE! })`; only
account/access-key mode emits a literal access-key credential block. Keep the
generated `authorityId`: it is derived from the selected DynamoDB table.

## Step 4: Replace Account Access Keys (Optional)

By this point, `.env.hotupdater` already contains the settings selected during
`hot-updater init`.

This step applies only if you selected **account/access-key mode** during
`init`. Current AWS CLI/default session, shared-profile, and SSO modes use their
generated credential providers and do not read these two variables.

The account-mode credentials entered during infrastructure setup may have
broader permissions than ongoing deployment requires.

To avoid issues, replace it with a permanent least-privilege identity that can
write bundle artifacts to S3, read and write the selected DynamoDB table, and
invalidate the CloudFront distribution.

```bash title=".env.hotupdater"
HOT_UPDATER_S3_ACCESS_KEY_ID=your-access-key-id
HOT_UPDATER_S3_SECRET_ACCESS_KEY=your-secret-access-key
```

## Step 5: Add HotUpdater to Your Project

The HotUpdater component wraps your application, enabling seamless delivery of updates and fallback UI during updates. Follow these steps to integrate it into your App.tsx:

```tsx title="App.tsx"
import { HotUpdater } from "@hot-updater/react-native";
import { Text, View } from "react-native";

function App() {
  return (
    <View>
      <Text>Hello World</Text>
    </View>
  );
}

export default HotUpdater.wrap({
  baseURL: "https://<your-cloudfront-distribution-url>", // [!code ++]
  updateStrategy: "appVersion", // or "fingerprint" // [!code ++]
  requestHeaders: {
    "x-api-key": "<HOT_UPDATER_API_KEY from .env.hotupdater>", // [!code ++]
  },
  fallbackComponent: ({ progress, status }) => (
    <View
      style={{
        flex: 1,
        padding: 20,
        borderRadius: 10,
        justifyContent: "center",
        alignItems: "center",
        backgroundColor: "rgba(0, 0, 0, 0.5)",
      }}
    >
      {/* You can put a splash image here. */}

      <Text style={{ color: "white", fontSize: 20, fontWeight: "bold" }}>
        {status === "UPDATING" ? "Updating..." : "Checking for Update..."}
      </Text>
      {progress > 0 ? (
        <Text style={{ color: "white", fontSize: 20, fontWeight: "bold" }}>
          {Math.round(progress * 100)}%
        </Text>
      ) : null}
    </View>
  ),
})(App);
```

<Callout type="info">
  The managed AWS runtime exposes `/version` publicly. OTA update checks and
  Analytics ingestion require `x-api-key: $HOT_UPDATER_API_KEY`, using a key
  registered or created during init. Internally, Analytics is always available
  and `clientAccess` uses the `api-key` policy; only `handlers.client` is
  mounted. API keys do not authorize Analytics query routes, and bundle
  management endpoints are not mounted on the public function URL.
</Callout>
