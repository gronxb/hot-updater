## Overview

Use this preset to provision an OTA server on AWS. For a new app,
start with [Choose infrastructure](/docs/get-started/choose-provider). Provision
the provider resources here, then connect your app with the verified URL and key.

## Prerequisites

You need the following resources and access. An AI agent can prepare missing
resources through its available provider tools.

- **Node.js**: The CLI and the agent setup's client-key helper require
  Node.js 22.23.4+, 24.22.1+, or 26.12.1+.
- **AWS Account**: Sign up at [AWS](https://aws.amazon.com) if you don't have one.
- **AWS CLI (terminal setup)**: Install the AWS CLI and sign in or configure a profile.

## Required AWS permissions

Hot Updater requires specific AWS IAM permissions for setup and ongoing usage:

### 1. Initialization (one-time setup)

Used for `hot-updater init`:

- `AmazonS3FullAccess`: Create and read S3 buckets.
- `AmazonDynamoDBFullAccess_v2`: Create and configure the metadata table.
- `AWSLambda_FullAccess`: Create and update Lambda functions.
- `CloudFrontFullAccess`: Manage CloudFront distributions.
- `IAMFullAccess`: Create IAM roles for Lambda@Edge.
- `AmazonSSMFullAccess`: Access SSM Parameters used for CloudFront key pairs.

### 2. Ongoing usage

Used for `hot-updater deploy` and `hot-updater console`:

- `AmazonS3FullAccess`: Manage bundle artifacts in the S3 bucket.
- DynamoDB table access for metadata queries and writes.
- `cloudfront:CreateInvalidation`: Invalidate CloudFront cache after deployments.

For ongoing usage, create a separate access token with limited permissions. Here's a minimal policy example for CloudFront invalidation:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": ["cloudfront:CreateInvalidation"],
      "Resource": "arn:aws:cloudfront::<ACCOUNT_ID>:distribution/<DISTRIBUTION_ID>"
    }
  ]
}
```

If this permission is missing, you may encounter the following error:

```
AccessDenied: User: arn:aws:sts::***:assumed-role/***/*** is not authorized to perform: cloudfront:CreateInvalidation on resource: arn:aws:cloudfront::***:distribution/*** because no identity-based policy allows the cloudfront:CreateInvalidation action
```

and build configuration.

After setup, review the local configuration. Interactive init writes the settings
below to `.env.hotupdater`; an agent merges the needed settings into your project.
Resource selections and the authentication mode are persisted for deterministic
reruns. AWS credentials are included only for account/access-key mode and only
when you consent to storing them.

```
HOT_UPDATER_DYNAMODB_TABLE_NAME=hot-updater-v1
HOT_UPDATER_AWS_AUTH_MODE=local-session
HOT_UPDATER_AWS_LAMBDA_NAME=hot-updater-v1-edge
HOT_UPDATER_S3_BUCKET_NAME=your-s3-bucket-name
HOT_UPDATER_S3_REGION=your-region
HOT_UPDATER_CLOUDFRONT_DISTRIBUTION_ID=your-distribution-id
HOT_UPDATER_API_KEY=your-api-key
```

Managed init reuses `HOT_UPDATER_API_KEY` when supplied or creates an API key,
registers it in DynamoDB, and persists the plaintext value locally. Send this
API key in the app's `x-api-key` request header. It does not authorize
management or Insights-query routes. To list, add, or revoke keys later, run
`hot-updater api-key` from the app directory.

If you choose a shared AWS profile or SSO, the generated env file also includes:

```bash
HOT_UPDATER_AWS_PROFILE=your-profile-name
```

If you choose the current AWS CLI/default session mode, no extra credential env
variables are written. The generated config uses the AWS SDK default provider
chain directly.

If you choose account/access-key mode and consent to persistence, the generated
env file also includes:

```bash
# The generated key may be over-privileged or temporary depending on how you authenticated during init.
HOT_UPDATER_S3_ACCESS_KEY_ID=your-access-key-id
HOT_UPDATER_S3_SECRET_ACCESS_KEY=your-secret-access-key
```

<Callout type="warn">

Keep provider credentials from `.env.hotupdater` in the CLI, CI, or server environment.
Configure the update server URL and client API key explicitly in the app as shown
below. Treat both as extractable from the app bundle; never include provider credentials.

See [Security](/docs/policy/security#plugin-token-protection).

</Callout>

## Optional: Bundle signing

Managed AWS init does not create or enable a signing key. Run
`npx hot-updater secrets issue bundle-signing-key`, which sets
`signing: secret("bundle-signing-key")`, then embed the public key in a
native release before deploying signed bundles: see
[Bundle Signing](/docs/guides/bundle-signing). Until then, `deploy` warns
that bundles are unsigned. The signing key belongs in the deploy environment,
never in the React Native app.

## Step 3: Add HotUpdater to your project

After provisioning, record these outputs for [Set up your app](/docs/get-started/app-setup):

| Output                | Value                                                                                 |
| --------------------- | ------------------------------------------------------------------------------------- |
| Client base URL       | `https://<your-cloudfront-distribution-url>`                                          |
| Client request header | `x-api-key`                                                                           |
| Client API key        | The saved `HOT_UPDATER_API_KEY` in your ignored `.env.hotupdater`, or your team store |
| Deploy configuration  | `hot-updater.config.ts` and the selected provider resources                           |

Use the actual URL returned by deployment. Configure the SDK and native bundle
loader through [Set up your app](/docs/get-started/app-setup), using the selected
build adapter and the same update strategy as `hot-updater.config.ts`. Only the
client API key belongs in the mobile app's build-time configuration; provider
credentials stay in the deploy environment.

<Callout type="info">
  The managed AWS runtime exposes `/version` publicly. OTA update checks,
  Insights ingestion, and Remote Config fetches require `x-api-key:
  $HOT_UPDATER_API_KEY`, using a key registered or created during init.
  Internally, the server runs the `insights()`, `apiKeys()`, and
  `remoteConfig()` plugins; only `handlers.client` is mounted. API keys do not
  authorize Insights query routes, and bundle management endpoints are not
  mounted on the public function URL.
</Callout>

## Generated configuration and operations

Init generates `hot-updater.config.ts` with your AWS storage and database, and
`plugins`: the server plugins the managed Lambda@Edge function runs,
`apiKeys()`, `insights()`, and `remoteConfig()`, imported from `hot-updater/plugins`.
The CLI and the Console reach S3 and DynamoDB through these settings and run the same plugins
as the function. The managed function runs these official plugins only; to run
other server plugins, use a [custom server](/docs/custom/overview).

The config names the resources init chose and reads an account's access keys
with
[`secret()`](/docs/concepts/secrets#adapter-credentials):
the environment and `.env.hotupdater` first, then the config's `secrets`
adapter. With a
[team store](/docs/concepts/secrets#this-machine-or-the-team) there, such as
[`secretsManager()`](/docs/guides/secrets-adapters/aws-secrets-manager) from
`@hot-updater/aws`, init also stores them and `HOT_UPDATER_API_KEY` in it, so a teammate's commands
read them there.

On a rerun, init updates `storage`, `database`, and `plugins` in the existing
file and keeps your other settings, including a wrapped build such as
`withSentry(bare())`. When it cannot edit `hot-updater.config.ts`, such as a
config that a function returns, it leaves the file unchanged and prints the
`storage`, `database`, and `plugins` lines to add.

If you choose **current AWS CLI/default session**, the generated config uses the
AWS SDK default provider chain instead of embedding access keys:

```ts title="hot-updater.config.ts"
import { dynamoDB, s3Storage } from "@hot-updater/aws";
import { bare } from "@hot-updater/bare";
import { fromNodeProviderChain } from "@aws-sdk/credential-providers";
import { defineConfig, localSecrets } from "hot-updater";
import { apiKeys, insights, remoteConfig } from "hot-updater/plugins";
import { existsSync } from "node:fs";

if (existsSync(".env.hotupdater")) {
  process.loadEnvFile(".env.hotupdater");
}

const awsOptions = {
  region: "us-east-1",
  credentials: fromNodeProviderChain(),
};

export default defineConfig({
  build: bare({ enableHermes: true }),
  storage: s3Storage({
    ...awsOptions,
    bucketName: "your-bucket-name",
  }),
  database: dynamoDB({
    ...awsOptions,
    tableName: "hot-updater",
    cloudfrontDistributionId: "your-distribution-id",
  }),
  plugins: [apiKeys(), insights(), remoteConfig()],
  secrets: localSecrets(), // keys from apple login and secrets put
  updateStrategy: "appVersion", // or "fingerprint"
});
```

If you choose **shared AWS profile**, `fromNodeProviderChain()` is replaced with
`fromIni({ profile: process.env.HOT_UPDATER_AWS_PROFILE! })` from the same
package. SSO uses `fromSSO({ profile: process.env.HOT_UPDATER_AWS_PROFILE! })`
from `@aws-sdk/credential-provider-sso`. Init installs the package the config
imports as a dev dependency: `@aws-sdk/credential-providers` for the default
session and shared profile, `@aws-sdk/credential-provider-sso` for SSO. Only
account/access-key mode emits a literal access-key credential block.

### Replace account access keys (optional)

By this point, `.env.hotupdater` already contains the settings selected during
`hot-updater init`.

This step applies only if you selected **account/access-key mode** during
`init`. Current AWS CLI/default session, shared-profile, and SSO modes use their
generated credential providers and do not read these two variables.

The account-mode credentials entered during infrastructure setup may have
broader permissions than ongoing deployment requires.

Replace those credentials with a permanent least-privilege identity that can
write bundle artifacts to S3, read and write the selected DynamoDB table, and
invalidate the CloudFront distribution.

```bash title=".env.hotupdater"
HOT_UPDATER_S3_ACCESS_KEY_ID=your-access-key-id
HOT_UPDATER_S3_SECRET_ACCESS_KEY=your-secret-access-key
```

## Upgrade infrastructure

Rerun init with the inputs it saved in `.env.hotupdater`, the command
[`hot-updater doctor`](/docs/guides/doctor#update-outdated-infrastructure)
names for an outdated server:

```package-install
npx hot-updater init --provider aws --from-env-file .env.hotupdater
```

It applies the release's database migrations, then redeploys the Lambda@Edge function with its IAM role policy
from the installed `@hot-updater/aws`, back to back: after a release whose schema changed, the server answers
503 only while it deploys. With the
[Hot Updater skill](/docs/guides/ai-agents) attached, you can also ask your
agent:

```text
$hot-updater Upgrade this project's existing AWS server infrastructure.
```

The agent discovers the existing deployment, uses `hot-updater agent infra upgrade`,
and reads the applicable version files before changing resources. It applies pending
changes and verifies the server with doctor. See
[Upgrade an existing server](/docs/guides/agent-infrastructure#upgrade-an-existing-server)
for the workflow or [Doctor](/docs/guides/doctor#update-outdated-infrastructure)
for terminal instructions.

For server templates to apply with your own deployment tooling, use
`hot-updater infra scaffold --provider aws`. See
[Infrastructure Templates](/docs/guides/infrastructure-templates).

## Verifying the setup

1. Confirm the selected AWS resources and the deployed client base URL.
2. From the React Native project, check the server and native integration:

   ```bash
   npx hot-updater doctor --server-base-url <client-base-url> --json
   ```

   Doctor checks the public `/version` endpoint. It does not prove an
   authenticated update download or application.

3. Complete [Test an OTA update](/docs/get-started/test-ota) on a release build.
   Verify that the app downloads and runs the changed code, then survives a restart.

An agent should report the selected resources, verified URL, configuration file
paths and verification result. Report a missing access, billing or native-build
prerequisite explicitly instead of marking an untested installation complete.

## Host the Console

Host the console on **Vercel, Netlify, or Docker/Node** with AWS SDK credentials
for the existing DynamoDB and S3 resources. ECS/Fargate is another option when
you want an AWS task role. See the
