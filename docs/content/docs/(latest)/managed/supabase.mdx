## Overview

Use this preset to provision an OTA server on Supabase. For a new app,
start with [Choose infrastructure](/docs/get-started/choose-provider). Provision
the provider resources here, then connect your app with the verified URL and key.

## Prerequisites

Your deployment needs the resources and access below. When using an AI agent,
it can prepare missing resources through its available provider tools.

- **Node.js**: The CLI requires 20.19+. Agent setup uses a client-key helper that
  requires Node 22.18+ or Node 24+; prepare it before provisioning resources.
- **Supabase CLI (terminal setup)**: Install it via `npx supabase`.
- **Supabase Account**: Sign up at [Supabase](https://supabase.com) if you don't have one.

Docker or OrbStack is needed only when you choose to run Supabase locally; the
managed remote init flow does not require a local container runtime.

## Step 1: Install Required Packages

Complete [Install v1 packages](/docs/get-started/installation) in the React
Native project before running init or an agent scaffold. Install the CLI, React
Native SDK, and the build plugin that matches your app, then install this provider:

```package-install
npm install @hot-updater/supabase@rc --save-dev
```

Each package has its own `rc` version. Use its `@rc` tag; do not copy the CLI's
exact version onto every package. An agent can perform these steps after
inspecting the app's package manager and build configuration.

After setup, review the local configuration. Interactive init writes the settings
below to `.env.hotupdater`; an agent merges the needed settings into your project.
Project and function selections are persisted for deterministic reruns.
Personal access tokens and database passwords are included only when needed and
when you consent to persistence; project-creation inputs appear only when a
project is created.

```
HOT_UPDATER_SUPABASE_PROJECT_ID=your-project-id
HOT_UPDATER_SUPABASE_FUNCTION_NAME=hot-updater-v1
HOT_UPDATER_SUPABASE_SERVICE_ROLE_KEY=your-service-role-or-secret-key
HOT_UPDATER_SUPABASE_BUCKET_NAME=your-bucket-name
HOT_UPDATER_SUPABASE_URL=https://your-project-id.supabase.co
HOT_UPDATER_API_KEY=your-api-key
# Conditional credentials/create-only values may include:
SUPABASE_ACCESS_TOKEN=your-personal-access-token
HOT_UPDATER_SUPABASE_DB_PASSWORD=your-database-password
HOT_UPDATER_SUPABASE_PROJECT_NAME=your-new-project-name
HOT_UPDATER_SUPABASE_ORGANIZATION_SLUG=your-organization-slug
HOT_UPDATER_SUPABASE_REGION=your-region
```

Managed init reuses `HOT_UPDATER_API_KEY` when supplied or creates an API key,
registers it in Postgres, and persists the plaintext value locally. Send this
API key in the app's `x-api-key` request header. Do not run
`hot-updater api-key create` for a managed installation.

<Callout type="warn">

Provider credentials from `.env.hotupdater` are not included in your app bundle
unless you explicitly configure that behavior. The API key is the exception:
add `HOT_UPDATER_API_KEY` to your React Native build-time configuration as
shown in [Set up your app](/docs/get-started/app-setup), but never add the Supabase service-role key or access token.

For more details, see:
[Security](/docs/policy/security#plugin-token-protection)

</Callout>

## Optional: Bundle Signing

Managed Supabase init does not create or enable a signing key. After
provisioning the OTA infrastructure, configure
[local PEM, AWS KMS, or Google Cloud KMS signing](/docs/guides/bundle-signing),
embed its public key in a native release, and only then deploy signed bundles.
Storage and database selection does not constrain the signer. KMS signing runs
directly in the protected deploy job; no Edge Function proxy is required. A
compatible signing service can also be used through `remoteSigning`.

## Step 3: Add HotUpdater to Your Project

After provisioning, record these outputs for [Set up your app](/docs/get-started/app-setup):

| Output | Value |
| --- | --- |
| Client base URL | `https://<project-ref>.supabase.co/functions/v1/<function-name>` |
| Client request header | `x-api-key` |
| Client API key | The saved `HOT_UPDATER_API_KEY` in your ignored `.env.hotupdater` |
| Deploy configuration | `hot-updater.config.ts` and the selected provider resources |

Use the actual URL returned by deployment. Configure the SDK and native bundle
loader through [Set up your app](/docs/get-started/app-setup), using the selected
build plugin and the same update strategy as `hot-updater.config.ts`. Only the
client API key belongs in the mobile app's build-time configuration; provider
credentials stay in the deploy environment.

<Callout type="info">
  The managed Supabase runtime exposes `/version` publicly. OTA update checks
  and Insights ingestion require `x-api-key: $HOT_UPDATER_API_KEY`. Internally,
  it enables Insights and mounts only `handlers.client`. Admin routes,
  including Insights queries, are not mounted on the public Edge Function URL.
</Callout>

## Generated Configuration and Operations

During the initialization process, the following file is automatically generated:

- `hot-updater.config.ts`: This file contains the configuration settings for integrating Supabase with your project.

```ts title="hot-updater.config.ts"
import { bare } from "@hot-updater/bare";
import { supabaseDatabase, supabaseStorage } from "@hot-updater/supabase";
import { defineConfig } from "hot-updater";
import { config } from "dotenv";

config({ path: ".env.hotupdater" });

export default defineConfig({
  build: bare({ enableHermes: true }),
  updateStrategy: "appVersion",
  storage: supabaseStorage({
    supabaseUrl: process.env.HOT_UPDATER_SUPABASE_URL!,
    supabaseServiceRoleKey: process.env.HOT_UPDATER_SUPABASE_SERVICE_ROLE_KEY!,
    bucketName: process.env.HOT_UPDATER_SUPABASE_BUCKET_NAME!,
  }),
  database: supabaseDatabase({
    supabaseUrl: process.env.HOT_UPDATER_SUPABASE_URL!,
    supabaseServiceRoleKey: process.env.HOT_UPDATER_SUPABASE_SERVICE_ROLE_KEY!,
  }),
});
```

The generated Supabase migrations enable Row Level Security on Hot Updater
tables and keep direct table/function access limited to the service role used by
the CLI and deployed Edge Function.

### Resource names and storage

Managed tables, indexes, settings, and RPC functions use the fixed
`hot_updater_v1_*` namespace, and the managed Edge Function defaults to
`hot-updater-v1`.

The same Storage bucket can be reused because each bundle has its own object
key. Init does not change an existing bucket between public and private; doing
so could break an already installed app. A reused public bucket therefore
remains public, while a newly created bucket is private.

### Release catalog cache

Supabase officially uses the direct Edge Function URL in `origin-only` mode.
`hot-updater init` generates that URL in the React Native configuration, and
`hot-updater doctor --server-base-url <direct-edge-url>` reports the mode as a
healthy informational status.

The request still benefits from the Release Catalog architecture: the Edge
Function serves an already compiled catalog, coalesces concurrent cold reads,
and performs one exact catalog-row read on an in-process cache miss instead of
running per-install rollout decisions. However, Supabase does not document a
reusable response cache in front of Function execution, so every device check
still invokes the Edge Function. Supabase origin-only measurements must report
Edge Function invocations and Postgres reads separately and must not be
presented as shared-CDN hit metrics.

## Upgrade infrastructure

With the [Hot Updater skill](/docs/guides/ai-agents) attached, ask your agent:

```text
$hot-updater Upgrade this project's existing Supabase server infrastructure.
```

The agent discovers the existing deployment, uses `hot-updater agent infra upgrade`,
and reads the applicable version files before changing resources. It applies pending
changes and verifies the server with doctor. See
[Upgrade an existing server](/docs/guides/agent-infrastructure#upgrade-an-existing-server)
for the workflow or [Doctor](/docs/guides/doctor#update-outdated-infrastructure)
for terminal instructions.

For server templates to apply with your own deployment tooling, use
`hot-updater infra scaffold --provider supabase`. See
[Infrastructure Templates](/docs/guides/infrastructure-templates).

## Verifying the Setup

1. Confirm the selected Supabase resources and the deployed client base URL.
2. From the React Native project, check the server and native integration:

   ```bash
   npx hot-updater doctor --server-base-url <client-base-url> --json
   ```

   Doctor checks the public `/version` endpoint. It does not prove an
   authenticated update download or application.
3. Complete [Test an OTA update](/docs/guides/simulator-test) on a release build.
   Verify that the app downloads and runs the changed code, then survives a restart.

An agent should report the selected resources, verified URL, configuration file
paths and verification result. Report a missing access, billing or native-build
prerequisite explicitly instead of marking an untested installation complete.
