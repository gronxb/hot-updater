## Installation

```package-install
npm install @hot-updater/aws --save-dev
```

## Create the table

For managed AWS installations, `npx hot-updater init` selects DynamoDB by
default and creates or validates this table automatically.

For custom installations, create one on-demand table manually with the
overloaded index used for update checks and patch relations:

```bash
aws dynamodb create-table \
  --table-name hot-updater \
  --billing-mode PAY_PER_REQUEST \
  --deletion-protection-enabled \
  --on-demand-throughput MaxReadRequestUnits=4000,MaxWriteRequestUnits=100 \
  --attribute-definitions \
    AttributeName=pk,AttributeType=S \
    AttributeName=sk,AttributeType=S \
    AttributeName=gsi1pk,AttributeType=S \
    AttributeName=gsi1sk,AttributeType=S \
  --key-schema \
    AttributeName=pk,KeyType=HASH \
    AttributeName=sk,KeyType=RANGE \
  --global-secondary-indexes '[
    {
      "IndexName": "hot-updater-update-index",
      "KeySchema": [
        { "AttributeName": "gsi1pk", "KeyType": "HASH" },
        { "AttributeName": "gsi1sk", "KeyType": "RANGE" }
      ],
      "Projection": { "ProjectionType": "ALL" },
      "OnDemandThroughput": {
        "MaxReadRequestUnits": 4000,
        "MaxWriteRequestUnits": 100
      }
    }
  ]'
```

Analytics uses the same table for append-only events. Before enabling the
`analytics()` server plugin, write its schema marker:

```bash
aws dynamodb put-item \
  --table-name hot-updater \
  --item '{"pk":{"S":"_hot-updater"},"sk":{"S":"schema.analytics"},"value":{"S":"3"}}' \
  --condition-expression 'attribute_not_exists(pk)'

aws dynamodb update-time-to-live \
  --table-name hot-updater \
  --time-to-live-specification Enabled=true,AttributeName=expires_at_s

aws dynamodb update-continuous-backups \
  --table-name hot-updater \
  --point-in-time-recovery-specification PointInTimeRecoveryEnabled=true
```

Managed AWS init creates or validates this marker automatically.
The successful readiness check is cached for the lifetime of the provider, so
event writes and paginated Analytics reads do not add one schema `GetItem` per
operation.

## Configuration

```typescript
interface DynamoDBConfig {
  tableName: string;
  region?: string;
  endpoint?: string;
  apiBasePath?: string;
  cloudfrontDistributionId?: string;
  shouldWaitForInvalidation?: boolean;
  credentials?: {
    accessKeyId: string;
    secretAccessKey: string;
  };
}
```

If `credentials` is omitted, the AWS SDK default credential chain is used. This
lets you rely on local AWS CLI sessions, `AWS_PROFILE`, shared config files, or
other standard AWS credential sources.

When `cloudfrontDistributionId` is set, metadata mutations submit an
invalidation for the update-check route. Set `shouldWaitForInvalidation: true`
when a deployment or E2E flow must wait for CloudFront propagation; it defaults
to `false`.

## Usage

```typescript
import { dynamoDB } from "@hot-updater/aws";
import { defineConfig } from "hot-updater";

export default defineConfig({
  database: dynamoDB({
    tableName: "hot-updater",
    region: "us-east-1",
    credentials: {
      accessKeyId: process.env.AWS_ACCESS_KEY_ID,
      secretAccessKey: process.env.AWS_SECRET_ACCESS_KEY,
    },
  }),
});
```

## Complete Example

Combined storage and database:

```typescript
import { dynamoDB, s3Storage } from "@hot-updater/aws";
import { defineConfig } from "hot-updater";

const credentials = {
  accessKeyId: process.env.AWS_ACCESS_KEY_ID,
  secretAccessKey: process.env.AWS_SECRET_ACCESS_KEY,
};

export default defineConfig({
  storage: s3Storage({
    region: "us-east-1",
    credentials,
    bucketName: "my-bundles-bucket",
  }),
  database: dynamoDB({
    tableName: "hot-updater",
    region: "us-east-1",
    credentials,
  }),
});
```

## Custom Server Usage

Use `dynamoDB` with `createHotUpdater` for self-hosted servers:

```typescript
import { dynamoDB } from "@hot-updater/aws";
import { createHotUpdater } from "@hot-updater/server";

const hotUpdater = createHotUpdater({
  database: dynamoDB({
    tableName: process.env.AWS_DYNAMODB_TABLE_NAME!,
    region: process.env.AWS_REGION!,
    credentials: {
      accessKeyId: process.env.AWS_ACCESS_KEY_ID!,
      secretAccessKey: process.env.AWS_SECRET_ACCESS_KEY!,
    },
  }),
});
```

The Lambda or server role needs read access for update checks. Analytics also
needs `GetItem` for the schema marker and `Query`/`PutItem` for the
`analytics#bundle_events#*` time-bucket shards. Events expire after 90 days.
CLI and Console writers need permission to put, update, and delete metadata
items.

The provider does not impose a total bundle, patch, or patch-relationship count
limit. Each serialized metadata item is limited to 8 KiB, and counters and
relation counts are updated in the same DynamoDB transaction as each mutation.
Cursor-based bundle pages read only the requested page, exact bundle references
use strongly consistent key reads, and single-owner patch hydration uses index
keys only to discover candidates before strongly reading their base-table rows.
Unfiltered totals use the transactionally maintained metadata counter. Batch
reads retry unprocessed keys with bounded exponential backoff.

DynamoDB itself permits at most 100 actions in one transaction, so a single
atomic aggregate mutation or cascade deletion must fit that service limit.
Multi-bundle deletes commit one cascade-safe bundle group at a time and can be
retried after an interruption.
