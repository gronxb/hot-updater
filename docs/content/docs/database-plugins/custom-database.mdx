## Installation

```package-install
npm install @hot-updater/plugin-core --save-dev
```

Install the public conformance suites in the project that tests your provider:

```package-install
npm install @hot-updater/test-utils vitest --save-dev
```

## Contract

`createDatabasePlugin` accepts one flat object. The four persistence domains
and `commit` are required; optimized reads and cleanup are optional.

```ts
createDatabasePlugin({
  name,

  bundles,
  bundlePatches,
  analytics,
  clientAccessKeys,

  commit,

  getChannels,
  getUpdateInfo,

  dispose,
});
```

There is no nested `plugin()` factory, public generic CRUD surface,
`commitBatch`, component-data registry, or server feature capability. A
database provider owns the physical storage for all official domains.

The fixed models are:

- `bundles`: one row per OTA bundle.
- `bundle_patches`: patch artifacts owned by bundles.
- `bundle_events`: Analytics events in stable cursor order.
- `client_access_keys`: hashed client access-key records.
- `private_hot_updater_settings`: the schema-version marker managed by the
  server database tooling.

Hot Updater owns bundle aggregation, Analytics calculations, access-key
authentication, validation, and HTTP routes. Providers implement only the
physical persistence contract.

## Domain interfaces

Use the exported interfaces instead of redeclaring them:

```ts
import type {
  AnalyticsTable,
  BundlePatchTable,
  BundleTable,
  ClientAccessKeyTable,
  DatabaseCommit,
  DatabaseCommitResult,
} from "@hot-updater/plugin-core";
```

### Bundles

```ts
interface BundleTable {
  findById(id: string): Promise<BundleRow | null>;
  findMany(query: BundleTableQuery): Promise<readonly BundleRow[]>;
  count(where?: DatabaseBundleQueryWhere): Promise<number>;
}
```

Apply filtering and ordering before offset and limit. `findMany` receives an
explicit order, limit, and offset. An empty `id.in` filter returns no rows.

### Bundle patches

```ts
interface BundlePatchTable {
  findByBundleIds(
    bundleIds: readonly string[],
  ): Promise<readonly BundlePatchRow[]>;
}
```

Return every patch whose `bundle_id` is in the requested set. Return an empty
array without I/O when the input set is empty.

### Analytics

```ts
interface AnalyticsTable {
  append(row: BundleEventRow): Promise<void>;
  scan(input: AnalyticsScanInput): Promise<readonly BundleEventRow[]>;
}
```

`scan` returns rows in ascending `(received_at_ms, id)` order. It excludes rows
at or after `beforeReceivedAtMs`, starts strictly after the optional cursor,
and never returns more than `limit` rows.

### Client access keys

```ts
interface ClientAccessKeyTable {
  create(row: ClientAccessKeyRow): Promise<"created" | "existing">;
  findByHash(hash: string): Promise<ClientAccessKeyRow | null>;
  list(): Promise<readonly ClientAccessKeyRow[]>;
  revoke(input: {
    id: string;
    revokedAtMs: number;
  }): Promise<ClientAccessKeyRow | null>;
}
```

`create` is idempotent by hash. `list` orders newest `created_at_ms` first and
then `id` ascending. `revoke` updates only `revoked_at_ms` and returns `null`
when the ID does not exist.

## Atomic commit

`commit` receives one envelope containing every bundle mutation in the deploy
operation:

```ts
const commit = async (
  input: DatabaseCommit,
): Promise<DatabaseCommitResult> => {
  return db.transaction(async (tx) => {
    return applyBundleMutations(tx, input.mutations);
  });
};
```

The complete envelope must be atomic across `bundles` and `bundle_patches`.
This is what makes a multi-platform deploy safe. If any mutation fails, none
of the changes may remain visible.

For an update whose bundle ID does not exist, return:

```ts
{
  applied: false,
  missingBundleId: bundleId,
}
```

Do not add a separate batch method. `DatabaseCommit.mutations` is already the
batch and transaction boundary.

## Create a provider

Accept provider configuration in your own function, build each official port,
and pass the ports directly to `createDatabasePlugin`:

```ts title="myDatabase.ts"
import {
  createDatabasePlugin,
  type AnalyticsTable,
  type BundlePatchTable,
  type BundleTable,
  type ClientAccessKeyTable,
  type DatabaseCommit,
  type DatabaseCommitResult,
} from "@hot-updater/plugin-core";

interface MyDatabaseConfig {
  readonly db: MyDatabaseClient;
}

export const myDatabase = ({ db }: MyDatabaseConfig) => {
  const bundles: BundleTable = createBundleTable(db);
  const bundlePatches: BundlePatchTable = createBundlePatchTable(db);
  const analytics: AnalyticsTable = createAnalyticsTable(db);
  const clientAccessKeys: ClientAccessKeyTable =
    createClientAccessKeyTable(db);

  const commit = (
    input: DatabaseCommit,
  ): Promise<DatabaseCommitResult> =>
    db.transaction((transaction) =>
      applyBundleMutations(transaction, input.mutations),
    );

  return createDatabasePlugin({
    name: "my-database",
    bundles,
    bundlePatches,
    analytics,
    clientAccessKeys,
    commit,
    getChannels: () => db.findDistinctBundleChannels(),
    getUpdateInfo: (input) => db.findUpdateInfo(input),
    dispose: () => db.close(),
  });
};
```

The helper names in this example represent your database mapping. Keep SQL
values parameterized and preserve the canonical snake-case row fields.

## Optional methods

### `getChannels`

Use `getChannels` when the backend can return sorted, distinct bundle channels
more efficiently. If omitted, Hot Updater derives channels from bundle pages.

### `getUpdateInfo`

Use `getUpdateInfo` only when the backend can answer update checks more
efficiently than the shared bundle-query path. Its result must match the
generic behavior for channel defaults, rollouts, rollback constraints,
patches, and manifest fields.

### `dispose`

Use `dispose` to close resources owned by the configured provider. It replaces
the old `onUnmount` lifecycle name. Cache invalidation belongs inside the
provider's atomic write path; there is no `onDatabaseUpdated` callback.

Database methods do not receive request context. Close over the configured
client or binding. Request context remains available to server handlers and
storage providers.

## Test the provider

Run both public suites against the real database used by the provider:

```ts title="myDatabase.spec.ts"
import { createDatabaseClient } from "@hot-updater/plugin-core";
import {
  setupDatabaseClientTestSuite,
  setupDatabasePluginTestSuite,
} from "@hot-updater/test-utils";

const lifecycle = {
  name: "my database",
  createPlugin: () => myDatabase({ db }),
  migrate: () => migrateDatabase(db),
  reset: () => resetDatabase(db),
  dispose: (plugin: ReturnType<typeof myDatabase>) => plugin.dispose?.(),
};

setupDatabasePluginTestSuite(lifecycle);

setupDatabaseClientTestSuite({
  ...lifecycle,
  createClient: createDatabaseClient,
});
```

The plugin suite verifies bundle reads, patch hydration, official Analytics
and access-key domains, stable cursor ordering, atomic multi-mutation rollback,
and optional optimized reads. The client suite verifies aggregate bundle
insert, update, delete, pagination, channels, and patch replacement behavior.

## Configure Hot Updater

Use the same configured provider in the CLI and self-hosted server:

```ts title="hot-updater.config.ts"
import { defineConfig } from "hot-updater";
import { myDatabase } from "./myDatabase";

export default defineConfig({
  database: myDatabase({ db }),
  // build: ...
  // storage: ...
});
```

```ts title="server.ts"
import { createHotUpdater } from "@hot-updater/server";
import { myDatabase } from "./myDatabase";

export const hotUpdater = createHotUpdater({
  database: myDatabase({ db }),
  storage,
});
```

Keep all five physical models in sync with the installed Hot Updater schema
version.

## Standalone repositories

A standalone bundle repository may implement `BundleRepository` without the
Analytics or client access-key domains. It is not a database plugin and must
not be passed to `createHotUpdater` as one.
