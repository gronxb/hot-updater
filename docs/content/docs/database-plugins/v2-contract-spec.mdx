## Status

This is the normative database-provider contract for Hot Updater schema
`1.0.0`. It replaces the #1141 contract that stored rollout policy on Bundle
rows and exposed an optional provider decision query.

The change is intentionally breaking. Removed members are not retained as
aliases.

## Responsibility boundary

```text
Bundle          immutable artifact identity and storage metadata
Release         rollout, compatibility, Channel, operation, and message policy
ReleaseCatalog  deterministic desired-state projection for one canonical scope
Database        canonical rows, strong reads, and atomic conditional commits
Server          catalog compiler, v2 routes, and legacy response bridge
Device          catalog acceptance and local desired-state selection
```

A database provider persists official domains. It does not decide which
Release an installation should run.

## Public interface

```ts
interface DatabasePlugin {
  readonly name: string;
  readonly models: DatabaseModels;
  commit(input: DatabaseCommit): Promise<DatabaseCommitResult>;
  readonly dispose?: () => Promise<void>;
}

interface DatabaseModels {
  readonly bundles: BundleModel;
  readonly bundlePatches: BundlePatchModel;
  readonly releases: ReleaseModel;
  readonly releaseCatalogs: ReleaseCatalogModel;
  readonly channels: ChannelModel;
  readonly analytics: AnalyticsModel;
  readonly clientAccessKeys: ClientAccessKeyModel;
}
```

The following are absent:

- `DatabasePlugin.queries` and `DatabaseQueries`;
- provider `getUpdateInfo` methods, SQL functions, or RPCs;
- provider callback transactions and generic public CRUD;
- Bundle policy fields and Bundle-to-Channel ownership;
- asynchronous Release writes followed by projection repair.

`createDatabasePlugin` may adapt a provider's internal CRUD and transaction
implementation, but those details are not public.

## Artifact models

`BundleModel.findMany` applies filtering and ordering before offset and limit.
Bundle rows contain only artifact fields: ID, platform, hashes, storage URIs,
manifest/asset information, Git commit, and artifact metadata.

`BundlePatchModel.findByBundleIds` returns all patch rows owned by the requested
Bundle IDs. It returns immediately for an empty owner list.

A Bundle referenced by any Release cannot be deleted. Release policy changes
never mutate a Bundle.

## Release model

```ts
interface ReleaseModel {
  findById(id: string): Promise<ReleaseRow | null>;
  findMany(input: {
    beforeReleaseId?: string;
    bundleId?: string;
    channelId?: string;
    enabled?: boolean;
    platform?: "ios" | "android";
    limit: number;
  }): Promise<readonly ReleaseRow[]>;
  findManyByScope(input: {
    scopeKey: string;
    afterReleaseId?: string;
    limit: number;
    consistency: "strong";
  }): Promise<readonly ReleaseRow[]>;
}
```

`findMany` is a newest-first management query. `findManyByScope` is an
ascending, exclusive-keyset compiler scan over canonical primary storage. It
must be strongly consistent. A provider may not satisfy it with an eventual
secondary index or an unordered scan.

A Release has a monotonically increasing `revision`, one canonical
`scope_key`, one Channel, platform, `BUNDLE` or `EMBEDDED` kind, compatibility
strategy, rollout/target policy, operation lineage, and timestamps. A Bundle
Release references a same-platform Bundle. An embedded Release has no Bundle.

## Catalog model

```ts
interface ReleaseCatalogModel {
  findByScopeKey(scopeKey: string): Promise<ReleaseCatalogRow | null>;
  findMany(input: {
    afterScopeKey?: string;
    limit: number;
  }): Promise<readonly ReleaseCatalogRow[]>;
}
```

The runtime read is an exact point lookup by scope key. The ordered list exists
for preflight, migration, and deterministic rebuild. Providers treat `payload`
as canonical opaque JSON and do not evaluate it.

Catalog rows include authority, strategy, Channel identity, platform,
optional fingerprint, generation, canonical hash, byte size, tombstone state,
and update time. A logical Release mutation increments every affected catalog
generation. An empty scope remains as a newer tombstone row; generation never
resets by deleting a catalog.

## Channels, Analytics, and access keys

Channels use opaque IDs and exact case-sensitive names. Concurrent
`insert({ onConflict: "returnExisting" })` returns the canonical stored row.
An empty Channel remains visible. Its reference check and explicit deletion
are atomic against Releases.

Analytics append and stable cursor scan remain provider-owned persistence.
Transition rows carry directional Release identity alongside Bundle identity.
Old nullable Release IDs remain valid and are never inferred from Bundle ID.

Client access-key create is idempotent by hash. Lookup, stable list ordering,
and revoke semantics are unchanged.

## Declarative conditional commit

```ts
interface DatabaseCommit {
  readonly changes: readonly DatabaseChange[];
  readonly expectations?: readonly DatabaseCommitExpectation[];
}

type DatabaseCommitExpectation =
  | { model: "releases"; id: string; revision: number | null }
  | {
      model: "releaseCatalogs";
      scopeKey: string;
      generation: number | null;
    };
```

Release changes support insert, update, and delete. Catalog changes use
`{ model: "releaseCatalogs", operation: "put", row }`. Bundle, patch,
Channel, Analytics, and access-key changes retain their declared operations.

The provider performs these steps inside one short native transaction:

1. Check all expectations against canonical rows. `null` means absent.
2. Validate references and ordered changes.
3. Apply every change.
4. Commit all results together.

An expectation mismatch returns no writes:

```ts
{
  committed: false,
  conflict: {
    changeIndex: -1,
    reason: "version_conflict",
    model: "releases" | "releaseCatalogs",
    key: string,
    expectedVersion: number | null,
    actualVersion: number | null,
  },
}
```

An expected missing update or referenced delete reports its original
`changeIndex`. Constraint, validation, connection, and provider failures reject
the Promise. A provider without an atomic conditional primitive rejects before
its first write.

## Compiler snapshot protocol

Compilation deliberately occurs outside the write transaction:

```text
strongly read current Release revisions and catalog generations
  -> strongly keyset-page every affected Release scope
  -> apply requested mutation in memory
  -> compile, canonicalize, hash, and size-check catalogs
  -> conditionally commit Release changes and all catalog rows
  -> retry a bounded VERSION_CONFLICT
```

The generation expectation invalidates a paged read series crossed by a
concurrent mutation. Providers must not hold a transaction open while parsing
or compiling a large history.

Required provider mappings:

| Provider | Strong compiler read | Conditional write |
| --- | --- | --- |
| DynamoDB | base-table scope partition with `ConsistentRead=true` | `TransactWrite` condition checks |
| Firestore | strong server document/query reads | transaction preconditions |
| PostgreSQL/Supabase | ordered primary reads | revision/generation predicates in one transaction |
| D1 | ordered primary reads | batch whose failed predicate aborts every statement |
| MongoDB | deterministic majority reads | short write transaction with predicates |
| Drizzle/Kysely/Prisma | adapter's ordered canonical query | adapter's real transaction and affected-row checks |

## Schema 1.0.0 migration

Migration from `0.38.0` performs preflight before recording the new version:

1. Validate Channels, compatibility ranges, scopes, cohort limits, and
   provider conditional-commit support.
2. Create Release/catalog storage, references, and canonical strong-read
   indexes.
3. Backfill one Release per legacy Bundle using the Bundle ID as Release ID,
   revision `1`, operation `DEPLOY`, and the Bundle's former policy.
4. Compile every scope and compare optimized selection with the reference
   selector.
5. Reject an invalid or oversized scope without advancing the schema version.
6. Remove policy columns from final Bundle mappings.
7. Record `schema.core = 1.0.0` only after the complete cutover succeeds.

Managed migration scripts materialize authority-specific scope keys before
execution. Re-running an interrupted migration must either resume from a
validated boundary or fail on incompatible drift; it must not invent a second
identity.

## Runtime route boundary

The shared device endpoints are:

```text
GET /v2/release-catalogs/app-version/:authorityId/:platform/:channelKey/:canonicalAppVersion
GET /v2/release-catalogs/fingerprint/:authorityId/:platform/:channelKey/:fingerprintHash
GET /v2/artifacts/:targetBundleId/from/:currentBundleId
```

Catalog URLs contain no installation state. Successful catalog responses are
short-lived shared-cacheable and vary by content encoding and `x-api-key`.
Authentication errors, missing/incomplete catalogs, and server errors are
`private, no-store`. Artifact resolution remains Bundle-keyed and private.

A custom `HotUpdaterResolver` opts into shared catalog transport only by
declaring a stable `catalogCachePartition` and using that same partition in
its cache key. Omit the declaration when arbitrary headers or request context
make the response private; those responses must remain `private, no-store`.

Legacy update-check routes evaluate the same catalog with the reference
selector. They never call a removed provider decision query.

## Standalone boundary

Standalone is a remote management repository, not a complete
`DatabasePlugin`. Its models expose Bundles, patches, Releases, catalogs, and
Channels through canonical server routes. The server owns Analytics, client
keys, strong compiler reads, and the real conditional transaction.

## Acceptance criteria

The contract is complete only when:

- the public database surface has `name`, `models`, `commit`, and optional
  `dispose`, with no `queries` property;
- every provider implements all seven models;
- Release scope paging is strong, ordered, and keyset-based;
- Release revision and catalog generation conflicts roll back the whole
  envelope;
- catalog GETs perform one exact read and no Release/Bundle scan;
- empty-scope generations persist as tombstones;
- schema migration backfills deterministic Release identity and blocks partial
  cutover;
- public conformance, provider integration, legacy bridge, managed runtime,
  and standalone verification suites pass.
