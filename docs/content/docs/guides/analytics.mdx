## Overview

Analytics records one app-ready observation when a JavaScript runtime starts.
The Console uses these observations to show active installations, reported
bundle outcomes, and installation history.

Analytics is opt-in. Database support, client event ingestion, and Console
query routes are separate capabilities. A deployment needs all three before it
can collect and display reports.

## Enable analytics

Install the Analytics client next to the React Native SDK:

```package-install
npm install @hot-updater/analytics @hot-updater/react-native
```

Create one client and compose `recordAppReady` into the updater's existing
`onNotifyAppReady` callback:

```tsx
import { createReactNativeAnalytics } from "@hot-updater/analytics/react-native";
import { HotUpdater } from "@hot-updater/react-native";

const baseURL = "<your-update-server-url>";
const analytics = createReactNativeAnalytics({ baseURL });

export default HotUpdater.wrap({
  baseURL,
  updateStrategy: "appVersion",
  onNotifyAppReady: (result) => {
    analytics.recordAppReady(result);
    observeAppReady(result);
  },
})(App);
```

For a manual update flow, use the same composition with `HotUpdater.init`:

```tsx
HotUpdater.init({
  baseURL,
  onNotifyAppReady: (result) => {
    analytics.recordAppReady(result);
  },
});
```

The Analytics client owns event transport and installation identity.
`HotUpdater.wrap` and `HotUpdater.init` continue to own update checks and
produce the generic app-ready result. Do not pass `analytics: true` to either
React Native API; that option no longer exists. Analytics is enabled only by
creating the feature-owned client and composing `recordAppReady`.

When an app uses a custom updater resolver, give Analytics its own transport
instead of adding an Analytics method to `HotUpdaterResolver`:

```tsx
const analytics = createReactNativeAnalytics({
  transport: {
    async send(event) {
      await sendAnalyticsEvent(event);
    },
  },
  onError: (error) => {
    reportAnalyticsDeliveryError(error);
  },
});
```

The default transport accepts `baseURL`, `requestHeaders`, and
`requestTimeout`. It sends `POST <baseURL>/events`, requires HTTP 204, makes one
best-effort attempt per JavaScript runtime, and never retries. When the server
requires an API key, pass the same immutable headers to the updater and the
Analytics client.

## Associate reports with a user

Analytics always counts installations by `installId`. You can attach a
`userId` and `username` as searchable aliases:

```tsx
analytics.setUser({
  userId: currentUser.id,
  username: currentUser.username,
});
```

Call `setUser` before the app-ready callback when the identity is already
available. If the user signs in later, call `setUser` then; the identity
appears on future app-ready reports. Clear the persisted aliases on sign-out:

```tsx
analytics.setUser(null);
```

Changing or clearing an alias does not rewrite historical reports. Multiple
installations with the same `userId` remain separate installations.

Use `analytics.getInstallId()` when you need to correlate app diagnostics with
the stable installation identifier used by Analytics:

```tsx
const installId = analytics.getInstallId();
```

## Configure a custom server

Managed Cloudflare, Firebase, and Supabase presets install the Analytics
feature by default, so the client works without additional server
configuration. This includes event ingestion and Analytics query routes. Treat
all reported identifiers as untrusted telemetry and configure provider-level
access controls, rate limits, quotas, logging, and retention.

Managed server presets and the local Console are configured independently.
The Console has no Analytics feature unless `console.plugins` installs an
Analytics manifest in its local runtime. Console runtime plugins are not
forwarded to managed presets, deployment handlers, or separate
`createHotUpdater` calls.

For a custom server, install Analytics next to any database that implements the
complete generic `DatabasePlugin` contract:

```ts
import { analytics } from "@hot-updater/analytics";
import { createHotUpdater } from "@hot-updater/server";

export const hotUpdater = createHotUpdater({
  database,
  storages,
  routes: {
    updateCheck: true,
    bundles: { access: { kind: "public" } },
  },
  plugins: [analytics({ queryAccess: "public" })],
});
```

`analytics()` creates its database-backed provider from the guarded generic
database runtime and mounts `POST /events` together with the Analytics and
installation query routes. `queryAccess` controls only these six query and
history routes:

- `GET /api/bundles/:id/events/summary`
- `GET /api/bundles/:id/events/analytics`
- `GET /api/installations`
- `GET /api/installations/overview`
- `GET /api/installations/active`
- `GET /api/installations/:installId/events`

It does not change `POST /events`, which remains public unless a protect-all
authentication plugin protects the complete handler. The example selects
public query access because it delegates management and query authentication to
the surrounding framework. Omit `queryAccess: "public"` and install a
protect-all authentication plugin when the kernel should protect every route,
including event ingestion. Add rate limits and quotas at any public ingestion
boundary because event payloads are untrusted telemetry.

Standalone proxies also check the upstream `/version` capability before
forwarding ingestion or query requests. An upstream route reported as
unavailable remains unavailable locally, and the two route capabilities are
preserved independently.

Analytics is omitted by default and is independent from bundle management.
Protect `/events`, `/api/bundles/*/events*`, and `/api/installations*` with the
appropriate kernel authentication plugin, framework authentication, or public
telemetry controls for your deployment.

`GET /version` reports these states independently:

| Capability                      | Meaning                                                                         |
| ------------------------------- | ------------------------------------------------------------------------------- |
| `capabilities.analytics`        | The installed Analytics provider is available.                                  |
| `capabilities.eventIngestion`   | Event ingestion is available from the provider.                                 |
| `capabilities.analyticsQueries` | All six Analytics query and history operations are available from the provider. |

When `capabilities.analytics === true`, `mode` and the optional
`maxMatchingRows` describe the structural query implementation and its scan
bound. Capability values describe availability, not route access. They never
indicate that a route is public or that a request is authenticated.

Standalone and Console require `capabilities.analyticsQueries === true` before
calling query routes. A legacy `/version` response without the route-specific
fields is treated as unavailable, even when it reports
`capabilities.analytics === true`. Upgrade the remote server and
Standalone/Console packages together.

### Migrate legacy server configuration

The supported `@hot-updater/server` entrypoint does not accept
`routes.analytics`. New code must install `analytics()` through the `plugins`
array. During the compatibility window, only the dedicated legacy subpath
recognizes the old route flag:

```ts
import { createLegacyHotUpdater } from "@hot-updater/analytics/legacy-server";

export const hotUpdater = createLegacyHotUpdater({
  database,
  routes: {
    analytics: true,
    bundles: false,
    updateCheck: true,
  },
});
```

This bridge preserves the old public Analytics routes. It does not add a
`routes.eventIngestion` option, and it should not be used for new server
configurations.

## Understand the Console data

| Console value          | Meaning                                                                                                  |
| ---------------------- | -------------------------------------------------------------------------------------------------------- |
| Active installations   | Distinct `installId` values that reported app ready during the selected 24-hour, 7-day, or 30-day window |
| Latest reported bundle | The bundle from the latest report received for each installation in the window                           |
| Applied on             | Distinct installations that reported an `UPDATE_APPLIED` transition to a bundle                          |
| Recovered from         | Distinct installations that reported a `RECOVERED` transition away from a bundle                         |
| Configured rollout     | The rollout availability stored on the bundle, independent from received reports                         |

An active installation is not realtime presence or a complete fleet count. A
device appears only after the app starts and its report reaches the server.

Hot Updater records three app-ready outcomes:

- `UPDATE_APPLIED` records the previous and current bundle after an update.
- `RECOVERED` records the failed bundle and the bundle restored after recovery.
- `UNCHANGED` records the currently active bundle without an update outcome.

`UNCHANGED` contributes to active-installation windows and latest-bundle
distribution. It is excluded from Applied on, Recovered from, and transition
history.

Each JavaScript runtime makes at most one best-effort reporting attempt.
Timeouts, unsupported servers, and non-success responses produce a warning.
They do not block app readiness, call the app's `onError`, or retry in the
background.

## Database support

| Database plugin                              | Analytics                      | Notes                                                                                                                        |
| -------------------------------------------- | ------------------------------ | ---------------------------------------------------------------------------------------------------------------------------- |
| Supabase Database                            | Supported                      | Uses append-only row storage.                                                                                                |
| Cloudflare D1 Database                       | Supported                      | Uses append-only row storage.                                                                                                |
| Firestore Database                           | Supported                      | Uses append-only document storage.                                                                                           |
| PostgreSQL Database                          | Supported                      | Uses append-only row storage.                                                                                                |
| Drizzle, Kysely, Prisma, and MongoDB plugins | Supported                      | The plugin must include the `bundle_events` model.                                                                           |
| Standalone Database                          | Conditional                    | Requires an explicit `standaloneAnalytics(...)` companion and an upstream server that advertises the Analytics query routes. |
| AWS S3 Database (`s3Database`)               | Supported with explicit opt-in | Uses versioned ETag compare-and-swap plus row-ID merge. The managed AWS preset remains core-only.                            |

The Console installs Analytics only when `console.plugins` includes an
Analytics manifest. It then checks actual query-route availability and hides
Analytics when the installed provider reports those routes unavailable.

### Upgrade an existing PostgreSQL plugin installation

Databases initialized with `@hot-updater/postgres` before 0.38.0 do not have
the `bundle_events` table. After upgrading the package, apply the dedicated
forward-only migration once:

```bash
psql "$DATABASE_URL" \
  -f node_modules/@hot-updater/postgres/sql/migrations/0.38.0-bundle-events.sql
```

Use `sql/bundles.sql` only for a new database. It recreates the complete
PostgreSQL schema and is not an existing-install migration.

There is no `supportsAnalytics` database option to set. For a generic database
that satisfies the complete `bundle_events` contract, install
`analytics({ queryAccess: "public" })` through `console.plugins`. Use
`standaloneAnalytics(config, { queryAccess: "public" })` in the same array
beside `database: standaloneRepository(config)` when Console Analytics must
proxy to a standalone upstream. These are local Console runtime plugins only;
they do not configure a deployment handler. The remote server must also
advertise `capabilities.analyticsQueries === true`.

## Support Analytics in a custom database plugin

Use `createDatabasePlugin` for a row- or document-oriented database plugin.
No Analytics import or wrapper belongs in the database factory:

```ts
import {
  createDatabasePlugin,
  type DatabasePluginImplementation,
} from "@hot-updater/plugin-core";

export const myDatabase = (implementation: DatabasePluginImplementation) =>
  createDatabasePlugin({
    name: "my-database",
    plugin: () => implementation,
  });
```

The implementation must provide `create`, `update`, `delete`, `count`,
`findOne`, and `findMany` for the fixed `bundles`, `bundle_patches`, and
`bundle_events` models. For Analytics, `bundle_events` must:

- allow concurrency-safe, append-only creates;
- support filtering, ordering, selection, pagination, and distinct queries;
  and
- remain independent from bundle deletion because events may reference old or
  unknown bundle IDs.

The shared Analytics implementation scans at most 50,000 matching event rows.
If a query exceeds that limit, the server returns HTTP 503 with code
`ANALYTICS_SCAN_LIMIT_EXCEEDED`. Narrow the query or provide a dedicated bundle
event service for larger datasets.

`createBlobDatabasePlugin` commits immutable revisions through a
compare-and-swap active pointer and merges disjoint row-ID changes after a lost
race. This makes concurrent append-only events safe for `s3Database`. It also
means each event writes a new snapshot and revision objects, and a hot key can
exhaust the bounded 16-attempt commit retry. Keep the managed AWS preset
core-only unless that write amplification and contention profile is acceptable,
then opt a custom server into `analytics()` explicitly.

See [Custom Database Plugin](/docs/database-plugins/custom-database) for the
complete fixed-model contract and conformance tests.

## Deploy safely

Use a native-first rollout. Deploy the database schema and server before
enabling Analytics in JavaScript:

1. Back up the database, then add the `bundle_events` table or collection.
2. Deploy the server and verify the `/version` route-capability fields.
3. Release a store build containing the matching React Native native module.
4. Configure Console Analytics explicitly and confirm the intended query route.
5. Create the React Native Analytics client and compose `recordAppReady` only
   after the native build is in service.

Old clients continue to work with the new server. A new client connected to an
old or unsupported server logs a warning and continues, but that report is not
stored.

New JavaScript also preserves a recovery reported by an older native binary as
`RECOVERED`. For the legacy `{ status: "RECOVERED", crashedBundleId }` result,
Hot Updater uses the current active bundle as the recovered-to bundle when it
can. Legacy native payloads do not contain all directional and strategy
metadata required by Analytics, so Hot Updater skips that telemetry event
without discarding the readiness result.

Custom resolvers continue to use their generic `notifyAppReady` callback.
Analytics no longer adds a resolver-specific callback. Compose
`analytics.recordAppReady(result)` in `onNotifyAppReady` alongside any existing
readiness observer. Analytics transport failures remain best effort and do not
call the updater's `onError` or block app readiness.

## Retention and downgrade policy

Hot Updater does not add foreground heartbeats, sessions, durable retries, or
an event-retention policy. Bundle deletion does not delete historical
`bundle_events`. Configure a provider-native scheduled job or TTL policy to
remove events according to your privacy, storage, and query-performance
requirements. Monitor row growth before queries reach the 50,000 matching-row
scan limit.

Official schema migrations are forward-only and do not include a down
migration. Before upgrading, back up the database and verify the provider's
clean-install and upgrade path. Roll back application or server code against
the newer schema only when that complete Hot Updater package set is documented
as compatible. Otherwise, stop writers and restore the pre-migration database
backup as a coordinated recovery. Do not partially reverse the
`bundle_events` schema.
