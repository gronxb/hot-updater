# Live Cloudflare update-check measurement — 2026-09-08

**p95 update-check response time decreased by 75.3%, from 283.2 ms to
70.0 ms**, in this 1,000-check-per-deployment observation. The percentage
uses the unrounded request timings: `(1 - v1_p95 / v0_p95) * 100`.
The deployments had different datasets and edge routing, so this is an
observed latency reduction rather than a protocol-only or server-load
reduction claim.

In a bounded test of two existing deployments, **969 of 1,000 v1 Catalog
requests (96.9%) were served as Cloudflare Workers Cache HITs**. Those HITs
did not execute the Worker. This measures cache offload for the tested
update-check workload, not a 96.9% reduction in total infrastructure load
or cost. [Cloudflare documents the cache HIT behavior and billing separately](https://developers.cloudflare.com/workers/cache/#pricing).

## Results

Measured on September 8, 2026, from **14:47:26.995 to 14:49:07.127 UTC**.
Each deployment received 1,000 measured checks at a target rate of 10
requests/second, after 10 warmup requests. All measured responses passed
status and payload validation.

## Workload and method

The scenario is an installation that already has its latest eligible
Bundle and checks again. The v0 endpoint returned `null`. The v1 endpoint
returned a nonempty Catalog whose selected Bundle was already installed;
no artifact resolution or download was needed.

- One Node.js `v24.15.0` process on the same Mac sent both request streams
  concurrently, with HTTP connection reuse. Dispatch order alternated on
  successive ticks.
- Each stream scheduled one request every 100 ms. There was a safety cap
  of five in-flight requests per deployment and a five-second request
  timeout. The runner would stop scheduling on three failures or a full
  concurrency cap. Neither stop condition occurred.
- v0 used
  `/api/check-update/app-version/ios/1.4.0/production/{minimumBundleId}/{currentBundleId}/{cohort}`.
  The minimum ID was the nil UUID, the current Bundle was the latest
  eligible installed Bundle, and numeric cohorts ran from 1 through 1,000.
- v1 used
  `/release-catalogs/app-version/ios/cHJvZHVjdGlvbg/1.5.0` with the same
  existing client API key for every check. The installed Bundle was the
  Catalog's latest eligible Bundle. The Catalog had full rollout and no
  custom cohort restriction.
- The v1 response used `Cache-Control: public, max-age=0, s-maxage=5` and
  `Vary: Accept-Encoding, x-api-key`. Requests did not add cache-busting
  parameters or client `If-None-Match` headers. The existing cache was
  warmed, not purged.
- Duration runs from just before `fetch` until the complete response body
  has been read, before JSON validation. It includes network time. p50,
  p95, and p99 use the nearest-rank method over all measured requests.
- No Insights events, release mutations, artifact requests, or downloads
  were generated by the measured workload.

## Interpretation limits

This is a live deployment observation, not a controlled same-data
benchmark, a maximum-throughput test, or a measurement of 1,000 real
users. In particular, v1 mostly reached Osaka while v0 mostly reached
Hong Kong and Tokyo. Latency percentages must not be presented as a
protocol-only speedup.

The directly observed result is that the shared Catalog URL allowed
**96.9% of these checks to be served without running the Worker**. Cache
hit rates depend on request density per scope, edge location, cache TTL,
API-key and encoding variants, and deployment activity. Artifact delivery,
Catalog compilation, and Insights reporting have their own workloads.

Cloudflare still charges its standard request rate for Workers Cache
HITs; a HIT avoids Worker CPU execution, not the request charge. This
test therefore does not establish an equal percentage of cost savings.

Cloudflare GraphQL analytics were also collected for the surrounding
second-aligned interval. Those adaptive aggregates cover all traffic to
each Worker or database, can include background traffic, and are subject
to sampling and ingestion delay. They are retained as supporting evidence,
not used to claim an exact CPU, database, or total-load reduction for the
1,000 measured requests. See [Cloudflare's metrics definitions](https://developers.cloudflare.com/workers/observability/metrics-and-analytics/).
